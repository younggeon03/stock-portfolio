# 결정기록

되돌리기 어려운 판단을 하나씩 남깁니다.

코드를 읽으면 **무엇을** 했는지는 보입니다. 하지만 **왜 그렇게 했는지**, 그리고 **무엇을 안 했는지**는 안 보입니다. 나중에 "이거 왜 이렇게 했지" 싶을 때 여기를 보세요.

한 번 쓴 기록은 고치지 않습니다. 판단이 바뀌면 새 기록을 아래에 덧붙이고 옛 기록의 상태를 "대체됨"으로 바꿉니다. 틀린 판단도 기록으로 남아야 같은 고민을 두 번 안 합니다.

## 001. 주문 API를 만들지 않는다

- **상태:** 확정
- **시점:** 1단계 (프로젝트 시작)

### 맥락

토스증권과 나무증권 Open API에는 주문 기능이 있습니다. 매수·매도 주문을 프로그램으로 낼 수 있습니다.

이 앱의 목적은 분석입니다. 주문은 필요 없습니다. 그런데 "필요 없으니 안 쓴다"는 것만으로는 부족합니다. 버그 하나, 오타 하나로 실제 돈이 움직입니다. 되돌릴 수 없습니다.

특히 이 앱은 LLM이 붙어 있습니다. 나중에 누군가 "분석 결과대로 자동 매매하게 해볼까"라고 생각하기 쉬운 구조입니다.

### 결정

**`BrokerageClient` 인터페이스에 주문 메서드를 정의하지 않습니다.**

안 쓰기로 한 게 아니라, 부를 대상 자체를 만들지 않습니다.

```java
public interface BrokerageClient {
    String brokerName();
    List<Holding> loadHoldings();
    // 주문 메서드 없음. 의도적이다.
}
```

### 결과

주문을 내려면 인터페이스를 고치고, 구현을 쓰고, 컨트롤러를 만들어야 합니다. 실수로는 못 합니다. **작정해야 합니다.**

대신 이 앱으로는 절대 거래를 할 수 없습니다. 그게 목적입니다.

부수 효과로 코드 리뷰가 쉬워졌습니다. "주문이 나갈 수 있나요"라는 질문에 인터페이스 한 장을 보여주면 끝납니다. 호출부를 전부 뒤질 필요가 없습니다.

### 되돌리려면

되돌리지 마세요.

정말 필요하다면 별도의 저장소에서, 모의투자 계좌로, 사람이 매번 확인하는 구조로 시작하세요. 이 앱에 얹지 마세요.

## 002. 시세는 토스에서만 가져온다

- **상태:** 확정
- **시점:** 5단계 (나무증권을 붙일 때)

### 맥락

나무증권을 추가하면서 "각 증권사 종목은 그 증권사 시세로 조회한다"는 구조를 생각했습니다. 자연스러워 보였습니다.

그런데 주가는 어느 증권사를 통해 보든 같은 값입니다. 양쪽에서 받으면 얻는 게 없습니다.

잃는 건 있습니다.

- 호출 한도를 두 배로 씁니다. 둘 다 한도가 빡빡합니다
- 응답 시점이 달라서 숫자가 미묘하게 어긋납니다. 같은 종목인데 증권사마다 값이 다르면 합산 비중이 이상해집니다
- 필드명과 숫자 형식이 달라서 변환 코드가 두 벌 생깁니다

### 결정

**시세·일봉·종목정보·환율은 토스에서만 받습니다. 나무 API는 보유 내역 조회에만 씁니다.**

나무에서 산 국내 종목도 토스 시세로 정상 조회되는지 직접 확인했습니다. 됩니다.

### 결과

시세 코드가 한 벌입니다. 증권사가 늘어도 이 부분은 안 늘어납니다.

**예상 못 한 이득이 하나 있었습니다.** 토스의 시세 계열 API는 계좌 헤더가 필요 없습니다. `X-Tossinvest-Account`를 안 붙여도 응답이 옵니다. 계좌와 무관하다는 뜻입니다.

그래서 **앱의 토스 키 하나로 누구의 종목이든 가격을 붙일 수 있습니다.** 이게 스크린샷 등록 기능이 성립하는 근거가 됐습니다. 남의 계좌는 못 봐도, 남이 알려준 종목의 가격은 우리가 채워줄 수 있습니다. 자세히는 [004](#004-증권사-로그인을-포기하고-스크린샷으로-우회한다)를 보세요.

### 대가

**토스가 막히면 모든 가격이 안 붙습니다.** 나무 종목도 마찬가지입니다. 단일 장애점입니다.

허용 IP가 바뀌면 이게 바로 터집니다. 실제로 자주 겪었습니다.

그래서 403 메시지가 지금 이 컴퓨터의 공인 IP를 직접 알려주도록 만들었습니다. 고칠 수 없는 구조적 약점이라면, 고치는 데 걸리는 시간이라도 줄이는 쪽을 택했습니다.

### 되돌리려면

나무 시세 API를 붙여 대체 경로를 만들 수 있습니다. 다만 "둘 다 쓴다"가 아니라 "토스가 죽으면 나무로 넘어간다"여야 합니다. 같은 종목에 두 값이 동시에 존재하면 합산이 어긋납니다.

## 003. 숫자는 앱이 계산하고 조사만 LLM에게 맡긴다

- **상태:** 확정
- **시점:** 6단계 (기업분석을 만들 때)

### 맥락

증권사 어느 쪽도 재무 데이터를 주지 않습니다. 직접 확인했습니다.

| 확인 대상 | 결과 |
|---|---|
| 토스 `/api/v1/stocks` | 종목명·시장·거래정지 여부만. 재무 없음 |
| 나무 API 카탈로그 | "재무", "기업", "컨센서스" 검색 결과 0건 |

그래서 외부 LLM으로 조사하기로 했습니다. 여기까지는 선택의 여지가 없었습니다.

문제는 **어디까지 맡기느냐**입니다.

보유수량과 평단가를 프롬프트에 넣고 "수익률을 계산해서 분석해줘"라고 하면 편합니다. 그런데 LLM은 산수를 틀립니다. 그것도 그럴듯하게 틀립니다.

더 나쁜 건 검증이 안 된다는 점입니다. 분석 글 한복판에 "현재 12.4% 손실 중"이라고 적혀 있으면, 그게 맞는지 확인하려면 사람이 직접 계산해봐야 합니다. 그럴 거면 분석을 왜 맡깁니까.

### 결정

**앱이 계산할 수 있는 건 전부 앱이 계산해서 "사실"로 주입합니다. LLM은 웹에서 찾아야만 아는 것만 조사합니다.**

```
앱이 확정 (LLM이 건드리지 못함)
  보유수량 · 평단가 · 현재가 · 손익 · 수익률
  전체 자산 대비 비중        ← 항상 합산 기준
  연환산 변동성 · 60일 수익률
  ETF 여부 · 레버리지 배수    ← 토스 securityType, leverageFactor
  위험 신호 (집중도·레버리지·정리매매·거래정지)
        |
        |  "이건 사실이다. 다시 계산하지 마라"
        v
LLM이 조사 (웹검색 + 출처 필수)
  재무상태 · PER/ROE · 가이던스/컨센서스 · 매출구조 · 사업분석
```

**나눗셈을 모델에게 시키지 않는 게 환각을 막는 가장 값싼 방법입니다.**

ETF 판별도 마찬가지입니다. "SOXL은 ETF인가요"라고 묻지 않습니다. 토스가 `securityType`과 `leverageFactor`를 주므로 확정 데이터로 가릅니다. ETF면 재무제표·PER·매출구조 섹션이 자동으로 "해당 없음"이 됩니다. 안 그러면 **ETF에 PER을 지어냅니다.**

위험 신호도 앱이 판단합니다. 집중도 30% 초과, 레버리지 1배 초과, 정리매매, 거래정지, 상장폐지는 전부 코드가 켭니다. 모델의 판단에 맡길 항목이 아닙니다.

### 결과

분석 글에 나오는 내 계좌 관련 숫자는 **전부 검증된 값**입니다. 틀릴 수가 없습니다.

테스트로 고정했습니다. `CompanyAnalysisPromptBuilderTest` 열 개가 평단가와 비중이 프롬프트에 실제로 들어가는지 확인합니다. 빠지면 모델이 지어내기 시작합니다. `TossStockInfoTest` 아홉 개가 ETF·레버리지 판별을 지킵니다.

비중을 항상 합산 기준으로 계산하는 것도 이 결정의 일부입니다. 화면에서 "토스만" 탭을 보고 있어도 분석은 합산으로 합니다. SOXL은 토스만 보면 2.98%지만 합치면 81%입니다. **위험 경고가 완전히 뒤집힙니다.**

### 대가

프롬프트가 길어집니다. 매번 계산 결과를 실어 보내니 입력 토큰이 늘고 비용이 조금 올라갑니다.

그만한 값어치가 있습니다. 숫자 하나 틀린 분석은 분석이 아닙니다.

### 되돌리려면

되돌릴 이유가 없습니다. 오히려 확장할 여지가 있습니다. 지금 모델이 웹에서 찾아오는 값 중에서도 API로 확정할 수 있는 게 생기면 그때그때 앱 쪽으로 옮기세요.

## 004. 증권사 로그인을 포기하고 스크린샷으로 우회한다

- **상태:** 확정
- **시점:** 8~9단계

### 맥락

"토스로 로그인"을 붙여서 다른 사람도 자기 계좌를 보게 하고 싶었습니다. 카카오 로그인처럼요.

**안 됩니다.** 세 가지 방법으로 확인했습니다.

**첫째, 스펙 파일을 직접 받아서 봤습니다.**

```json
"securitySchemes": {
  "oauth2ClientCredentials": {
    "flows": { "clientCredentials": { "tokenUrl": "/oauth2/token" } }
  }
}
```

`clientCredentials` 하나뿐입니다. `authorizationCode` 흐름이 없습니다.

**둘째, 경로 목록을 전부 훑었습니다.** OAuth 관련 경로는 `/oauth2/token` 하나입니다. 사용자 동의 화면으로 보낼 주소가 없습니다.

**셋째, 나무증권도 같았습니다.** OAuth 관련 API가 셋뿐입니다.

| API | 경로 |
|---|---|
| 접근토큰발급 | `/oauth2/token` |
| 접근토큰폐기 | `/oauth2/revoke` |
| 웹소켓 세션해제 | `/websocket/close/session` |

#### 왜 그런가

`client_credentials`는 **앱을 인증하는 방식**이지 사람을 인증하는 방식이 아닙니다.

토큰이 가리키는 계좌는 언제나 **키를 발급받은 사람 본인의 계좌**입니다. `X-Tossinvest-Account` 헤더도 남의 계좌를 고르는 게 아니라 내 계좌 여러 개 중 하나를 고르는 용도입니다.

"본인인증만 하면 되는 거 아닌가" 싶지만, 본인인증과 데이터 접근은 별개입니다. 그 사람이 본인임을 확인해도 증권사가 우리에게 그 사람의 계좌를 열어줄 의무는 없습니다. 남의 금융 데이터를 대신 조회하려면 마이데이터 사업자 라이선스가 필요합니다. 개인 프로젝트가 받을 수 있는 게 아닙니다.

### 결정

**계좌 조회를 포기하고, 보유종목을 사용자가 직접 알려주는 경로를 만듭니다. 타이핑 대신 스크린샷으로 받습니다.**

근거는 [002](#002-시세는-토스에서만-가져온다)에서 나온 사실입니다. 시세 계열 API는 계좌 헤더가 필요 없습니다. **앱의 토스 키 하나로 누구의 종목이든 가격을 붙일 수 있습니다.**

그러니 남에게 필요한 건 종목·수량·평단가 세 개뿐입니다. 나머지는 우리가 채웁니다.

```
증권사 앱 화면을 캡처해서 올린다
    ↓
클로드가 이미지를 읽어 종목명·수량·평단가·통화를 뽑는다
    ↓
읽은 이름을 실제 종목코드로 바꾸고 숫자를 다듬는다
    ↓  ("현대차" → 005380, "412,000원" → 412000)
검수 모달에서 사람이 확인·수정한다
    ↓
저장 → 포트폴리오에 즉시 반영. 가격은 실시간
```

직접 입력한 종목도 `ManualBrokerageClient`가 `BrokerageClient`를 구현하므로 진짜 증권사 종목과 똑같이 취급됩니다. 비중·변동성·차트·기업분석 코드는 그게 어디서 왔는지 모릅니다.

### 결과

**포기가 아니라 다른 길이었습니다.** 오히려 증권사에 안 묶입니다. 미래에셋을 쓰든 키움을 쓰든 캡처만 하면 됩니다.

사람 구분은 로그인 없이 합니다. 브라우저가 처음 들어올 때 임의의 값을 만들어 저장하고 요청마다 `X-Owner-Key` 헤더로 보냅니다. 회원가입 없이 각자 자기 포트폴리오를 갖습니다.

### 대가

**이름 매칭이 완벽하지 않습니다.** "삼송전자"가 "삼영전자"로 갑니다. 고칠 수 없습니다. 그래서 확신이 낮으면 노랗게 표시하고 사람이 확인하게 합니다. 검수 모달이 존재하는 이유입니다.

**브라우저를 바꾸면 다른 사람이 됩니다.** 나중에 로그인을 붙이면 계정에 연결하면 됩니다.

**이미지 한 장에 수십 원**이 듭니다.

### 되돌리려면

각자 자기 증권사 키를 등록받는 구조는 가능합니다. 토큰 저장소가 이미 키별로 나뉘어 있습니다. 다만 벽이 셋입니다.

1. 사용자마다 자기 토스 설정에 **우리 서버 IP**를 등록해야 합니다
2. 남의 시크릿을 보관하는 책임이 생깁니다. 암호화가 최소 조건이고 유출되면 책임 문제입니다
3. 누가 누구인지 구분할 로그인이 따로 필요합니다

"토스로 로그인" 자체는 증권사가 흐름을 열어주지 않는 한 영원히 불가능합니다.

## 005. 환율을 못 구하면 예외를 던진다

- **상태:** 확정
- **시점:** 9단계

### 맥락

해외 주식을 원화로 환산해야 합니다. 토스에 환율 API가 있습니다.

처음에는 조회에 실패하면 `BigDecimal.ONE`을 돌려주게 해놨습니다. "환율을 못 가져와도 앱이 죽지는 않게" 하려는 의도였습니다.

그러다 이걸 봤습니다.

| | 표시된 값 | 실제 |
|---|---|---|
| 직접 입력한 미국 주식 | 68원 | 154,599원 |

1,380배 틀렸습니다. 그런데 **아무 에러도 안 났습니다.** 화면은 멀쩡했고 숫자만 조용히 거짓말을 하고 있었습니다.

더 나쁜 건 이게 비중 계산까지 오염시킨다는 점입니다. 이 앱의 존재 이유가 비중인데, 해외 종목이 1/1380로 쪼그라들면 국내 종목 비중이 전부 부풀어 오릅니다. **틀린 결론을 자신 있게 보여줍니다.**

### 결정

**환율을 못 가져오면 계산을 포기하고 `AppException`을 던집니다.** 화면에 이유가 뜹니다.

`1`은 "환율을 모른다"는 뜻으로 쓸 수 있는 값이 아닙니다. 그 자리에 들어가면 "1달러는 1원"이라는 주장이 됩니다. 모른다는 것과 1이라는 것은 다릅니다.

### 결과

숫자가 보이면 그 숫자는 맞습니다. 안 보이면 왜 안 보이는지 화면에 적혀 있습니다.

원화 종목만 가진 사람은 애초에 환율을 안 부르므로 영향이 없습니다.

### 대가

미국 주식이 하나라도 있으면 환율 조회 실패가 화면 전체를 막습니다. 예전 같으면 "일부가 이상하지만 나머지는 보이는" 상태였습니다.

**의도한 대가입니다.** 1,380배 틀린 숫자를 조용히 보여주는 것보다 안 보여주는 게 낫습니다.

### 일반화

이 판단은 환율에만 해당하는 게 아닙니다.

**모르는 값을 그럴듯한 기본값으로 때우지 않습니다.** 0, 1, 빈 문자열은 전부 "모른다"를 숨기는 거짓말이 될 수 있습니다.

같은 원칙이 다른 곳에도 적용돼 있습니다. 이동평균선은 기간이 안 찬 앞부분에 **0 대신 값을 안 넣습니다.** 0으로 채우면 선이 바닥에서 솟구치는 그림이 됩니다. 그래프가 거짓말을 하는 겁니다.

### 되돌리려면

되돌리지 마세요. 정 필요하면 환율 출처를 하나 더 붙여 실패 확률을 낮추세요. 실패했을 때 가짜 값을 넣는 쪽으로는 가지 마세요.

## 006. 분석은 버튼을 눌러야 실행된다

- **상태:** 확정
- **시점:** 6단계

### 맥락

기업분석 한 건에 2~5분이 걸리고 $0.5~2가 듭니다.

종목을 클릭하면 자동으로 분석이 돌게 만들면 쓰기 편합니다. 하지만 표를 훑기만 해도 돈이 나갑니다. 여덟 종목을 한 번씩 눌러보면 $4~16입니다. 실수로 새로고침을 몇 번 하면 순식간에 불어납니다.

**비용이 사용자 눈에 안 보이는 곳에서 발생하는 구조**는 위험합니다.

### 결정

**분석은 버튼을 눌러야만 실행됩니다.** 종목을 클릭하면 저장된 분석만 보여줍니다.

- 표의 "기업분석" 칸은 DB만 읽습니다. 비용 0입니다
- 종목을 눌러 드로어를 열어도 비용 0입니다
- "기업분석 실행" 버튼을 눌러야 클로드가 돕니다
- 한 번 분석하면 MySQL에 저장돼서 다시 볼 때는 0원입니다

분석 스레드는 **하나뿐**입니다. 동시에 여러 건이 돌면 비용이 배로 나갑니다.

### 대비 — 뉴스는 자동입니다

같은 드로어 안에 있지만 뉴스는 종목을 누르면 바로 불러옵니다.

구글 뉴스 RSS는 **키가 필요 없고 비용이 0원**이기 때문입니다. 기준은 편의가 아니라 비용입니다.

### 결과

돈이 나가는 지점이 화면에서 한 곳입니다. 버튼 하나입니다.

분석을 다시 돌리려면 "다시 분석"을 눌러야 합니다. 이미 있는 분석을 실수로 덮어쓰지 않습니다.

### 대가

처음 쓰는 사람은 종목을 눌렀는데 분석이 없어서 당황합니다. 그래서 빈 화면에 "버튼을 누르면 클로드가 웹 검색으로 조사합니다. 2~5분 걸리고 비용이 들기 때문에 자동으로 실행하지 않습니다"라고 적어 뒀습니다.

**왜 자동이 아닌지를 화면에서 설명합니다.** 불편함에 이유가 있으면 불편함이 아닙니다.

### 되돌리려면

되돌리지 마세요. 정 편하게 하고 싶으면 "전체 분석" 버튼을 하나 만들고 **예상 비용을 먼저 보여주고 확인받으세요.**

## 007. 토큰을 DB에 저장한다

- **상태:** 확정
- **시점:** 8단계

### 맥락

토큰을 메모리에만 들고 있었습니다. 앱을 재시작할 때마다 새로 발급받았습니다.

개발 중에는 하루에 열 번도 재시작합니다. 열 번 다 새로 받았습니다.

이게 왜 나쁜지 알아보니 생각보다 심각했습니다.

- 토큰 수명이 24시간인데 매번 버리고 새로 받습니다
- 토스도 나무도 **"client 당 유효한 토큰은 1개"** 입니다. 재발급하면 이전 토큰이 즉시 죽습니다
- 나무는 토큰 발급 자체가 **초당 1회** 제한입니다

앱을 두 개 띄우면 서로의 토큰을 죽입니다.

### 결정

**토큰을 MySQL에 저장하고 2단 캐시로 꺼냅니다.**

```
메모리 (1차)  ─ 있으면 바로 반환. DB 를 매번 읽지 않는다
    ↓ 없으면
MySQL  (2차)  ─ 재시작 직후가 이 경우. 살아있으면 그대로 재사용
    ↓ 없으면
증권사에 발급 요청 → 메모리와 DB 양쪽에 저장
```

401을 받아 토큰을 무효화할 때는 **DB에서도 지웁니다.** 안 지우면 재시작 후 죽은 토큰을 다시 꺼내 씁니다. 이게 가장 놓치기 쉬운 부분이라 테스트로 고정했습니다.

### 키별로 나눠 저장합니다

토큰은 `(provider, owner_key)`로 저장됩니다. `owner_key`는 **API 키를 해시한 값**입니다.

지금은 키가 하나라 줄이 하나뿐입니다. 하지만 사람마다 자기 키를 등록하는 구조가 되면 키가 다르니 자동으로 나뉩니다. **그때 이 코드를 고칠 필요가 없습니다.**

client_id를 그대로 저장하지 않는 이유는, DB를 봐도 어떤 키를 쓰는지 바로 알 수 없게 하기 위해서입니다.

### 결과

재시작해도 같은 토큰을 씁니다. 확인했습니다.

```
1차 기동: 나무증권 access token 발급 완료. 만료 예정 = 2026-09-15T04:04:59
2차 기동: 저장해둔 나무증권 토큰을 재사용합니다. 만료 예정 = 2026-09-15T04:04:59
```

`TossAuthServiceTest` 일곱 개가 발급·재사용·재시작 후 재사용·키별 분리를 지킵니다.

### 대가 — 배포하면 위험합니다

**토큰은 비밀번호에 준하는 값입니다.** 그 값만 있으면 24시간 동안 계좌를 조회할 수 있습니다.

지금은 내 PC의 내 MySQL에만 있어서 `.env`와 위험 수준이 비슷합니다. 하지만 서버에 올려 여러 사람이 쓰게 되면 **반드시 암호화해서 저장해야 합니다.**

지금은 평문입니다. 배포 전에 반드시 고쳐야 할 항목이고 [TODO](로드맵.md)에 적어 뒀습니다.

### 되돌리려면

되돌릴 이유가 없습니다. 암호화를 얹는 방향으로만 가세요.

## 008. 색은 빨강과 파랑뿐이고 등락만 뜻한다

- **상태:** 확정
- **시점:** 10단계 (화면을 다시 만들 때)

### 맥락

화면이 별로였습니다. 정보가 한 화면에 다 들어가서 스크롤이 길고, 색이 여기저기 흩어져 있었습니다.

고치려고 보니 진짜 문제가 색이었습니다. 파란 버튼, 초록 배지, 주황 경고, 빨간 수익률, 파란 손실률이 한 화면에 같이 있었습니다.

**수익률이 빨간 건 올랐다는 뜻인데, 옆의 빨간 배지는 아무 뜻도 없었습니다.** 색이 의미를 잃습니다.

### 결정

**빨강과 파랑만 쓰고, 그 둘은 항상 등락만 뜻합니다.**

| 색 | 뜻 |
|---|---|
| `#e03131` 빨강 | 올랐다 (양봉·수익) |
| `#1b64da` 파랑 | 내렸다 (음봉·손실) |

나머지는 전부 검정·회색 계열입니다.

- 강조 버튼은 **검정으로 채웁니다.** 파란 버튼을 쓰면 "내렸다"와 색이 겹칩니다
- 비중 막대는 **색이 아니라 명도**로 구분합니다. 비중이 큰 것부터 짙고, 뒤로 갈수록 옅어집니다
- 경고·성공 배너만 예외로 노랑·빨강을 씁니다. 화면에 하나씩만 뜨고, 뜨면 읽어야 하는 것들입니다

캔들은 **오른 날 빨강, 내린 날 파랑**입니다. 국내 증권사 관습입니다. 미국과 반대지만 이 앱은 한국에서 쓰는 앱입니다.

### 함께 정한 것

**비중 막대를 화면 위쪽 전체 폭으로 올립니다.**

이 앱을 만든 계기가 "SOXL이 자산의 81%였다"를 발견한 것이었는데, 정작 그 숫자가 표 안의 작은 칸에 들어 있었습니다. **발견하라고 만든 숫자가 가장 안 보이는 자리에 있었습니다.**

**상세는 드로어로 뺍니다.** 예전에는 종목을 누르면 표 아래로 차트·뉴스·기업분석이 차례로 펼쳐졌습니다. 기업분석만 7개 섹션이라 셋이 동시에 열리면 스크롤이 감당이 안 됐습니다. 탭으로 나눠 한 번에 하나만 보여줍니다.

**좁은 화면에서는 표가 카드로 바뀝니다. CSS로만 합니다.** 화면 폭에 따라 JS가 DOM을 다시 그리면 열려 있던 드로어나 입력 중이던 값이 날아갑니다.

### 결과

숫자에 색이 있으면 그건 등락입니다. 예외가 없습니다. 화면을 배우지 않아도 읽힙니다.

색을 못 쓰니 위계를 크기·굵기·여백으로 만들게 됐습니다. 총자산은 40px이고 나머지는 13px입니다. 결과적으로 더 깔끔해졌습니다.

### 대가

버튼이 밋밋합니다. 검정 버튼 하나와 흰 버튼 여럿뿐이라 화려하지 않습니다.

**데이터 화면에서는 이게 맞습니다.** 버튼이 눈에 띄어야 할 이유가 없습니다. 봐야 할 건 숫자입니다.

### 되돌리려면

색을 추가하고 싶으면 먼저 물어보세요. **그 색이 무슨 뜻인가?** 답이 "예뻐서"라면 추가하지 마세요.

## 009. 판정을 내린다. 단 내 계좌를 전제로

- **상태:** 확정
- **시점:** 14단계
- **대체하는 것:** [006](#006-분석은-버튼을-눌러야-실행된다) 의 "매수·매도를 단정하지 않는다" 원칙 (실행 조건은 그대로 유효)

### 맥락

분석은 잘 나오는데 **이걸 꼭 써야 할 이유가 없었습니다.**

기존 MTS 의 문제는 한눈에 안 들어오고, 못생기고, 너무 집약적이라는 것입니다. 이 앱은 그중 앞의 둘을 고쳤지만 "매일 열 이유" 를 주지 못했습니다.

지금까지의 후킹은 "두 증권사를 합치면 진짜 비중이 보인다" 였습니다. 약합니다.

- 계좌가 둘 이상이어야 의미가 있는데 대부분은 한 곳만 씁니다
- 한 번 보면 끝입니다. 84.9% 를 발견한 다음 날 다시 열 이유가 없습니다
- 진단이지 행동이 아닙니다. "81% 네" 다음에 뭘 해야 하는지 안 알려줍니다

원래는 [006](#006-분석은-버튼을-눌러야-실행된다) 에서 정한 대로 "매수·매도를 단정하지 않는다" 를 지켰습니다. LLM 이 "매수" 라고 적은 걸 보고 실제로 돈을 넣게 되기 때문입니다.

하지만 단정을 피하니 **결론이 없는 분석**이 됐습니다. 7개 섹션을 다 읽어야 뭘 해야 할지 짐작할 수 있었습니다. 그걸 읽을 사람은 이미 스스로 판단할 수 있는 사람입니다.

### 결정

**분석 맨 위에 판정을 띄웁니다. 단, 종목에 대한 판정이 아니라 이 사람의 보유 상태에 대한 판정입니다.**

| stance | 뜻 |
|---|---|
| `ADD` | 더 담아도 되는 상태 |
| `HOLD` | 그대로 두는 상태 |
| `TRIM` | 비중을 줄일 상태 |
| `EXIT` | 정리를 검토할 상태 |
| `UNCLEAR` | 근거가 모자라 판단 보류 |

**같은 종목이라도 다른 답이 나와야 합니다.**

| SOXL 을 두고 | 판정 |
|---|---|
| 자산의 85% 를 이미 넣은 사람 | 더 담지 마세요 |
| 안 들고 있는 사람 | 볼 만합니다 |
| 평단가가 두 배 위인 사람 | 물타기 전에 이것부터 보세요 |

### 왜 이게 컨센서스와 다른가

증권가 컨센서스는 **누가 얼마나 들고 있는지 모릅니다.** 그래서 모두에게 같은 답을 줍니다. 네이버 증권에 이미 떠 있고 공짜입니다. 거기에 하나 더 얹는 건 의미가 없습니다.

이 앱은 압니다. 평단가, 비중, 손익, 레버리지 배수를 전부 앱이 계산해서 갖고 있습니다. [003](#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다) 에서 정한 구조가 여기서 값을 합니다.

**공개 사이트가 구조적으로 못 하는 일이고, 그게 이 앱을 쓸 이유입니다.**

### 지키는 것

**판정은 `verdict` 한 곳에서만 나옵니다.** 나머지 섹션은 여전히 사실과 관점만 적습니다. 본문 아무 데서나 "지금이 기회다" 가 튀어나오면 안 됩니다.

**근거 없는 판정은 안 띄웁니다.** 판정과 300자 이유는 항상 붙어 나오고, 이유에는 반드시 이 사람의 비중과 평단가가 들어갑니다. "반도체 업황이 좋습니다" 로 끝나면 컨센서스와 같아집니다.

**비중이 판정을 뒤집습니다.** 종목 전망이 좋아도 한 종목이 자산의 30% 를 넘으면 `ADD` 를 쓰지 않습니다. 3배 레버리지가 절반을 넘으면 전망과 무관하게 `TRIM` 입니다.

**모르면 보류합니다.** 근거가 약하면 `UNCLEAR` 를 씁니다. 서버가 한 번 더 거릅니다. stance 가 비었거나 정의에 없는 값이면 화면에 나가기 전에 "판단 보류" 로 떨어집니다. 방향을 지어내는 것보다 모른다고 하는 게 낫습니다.

**목표주가와 수량은 말하지 않습니다.** "12만원까지 간다", "3주 파세요" 는 금지입니다. 판정은 방향까지입니다.

### 대가

**틀린 판정을 보고 돈을 넣을 수 있습니다.** 이게 진짜 위험이고 없앨 수 없습니다.

줄이는 방법만 있습니다. 판정에 근거를 붙이고, 앱이 계산한 숫자를 쓰게 하고, 언제 판정한 건지 항상 보이게 하고, 오래된 분석은 오래됐다고 표시합니다.

여전히 **조회와 분석만 합니다.** 판정을 띄우는 것과 주문을 내는 것은 다릅니다. [001](#001-주문-api를-만들지-않는다) 은 그대로입니다.

### 되돌리려면

`verdict` 를 스키마에서 빼고 화면의 블록을 지우면 됩니다. 나머지 7개 섹션은 영향받지 않습니다. 판정을 한 곳에 몰아둔 이유가 이것이기도 합니다.

## 010. 재무는 공시에서 가져온다

- 상태: 확정
- 날짜: 2026-09-23 ~ 09-27
- 관련: [003 숫자는 앱이, 조사는 LLM이](#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다) 를 재무까지 넓힌 것

### 무엇이 문제였나

[003](#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다) 을 정할 때 증권사 두 곳 모두 재무 데이터를 주지 않았습니다. 그래서 매출·영업이익·부채비율·PER 은 클로드가 웹에서 찾았습니다.

그런데 이 숫자들은 **공시된 확정값**입니다. 웹에서 찾을 이유가 없는 숫자를 웹에서 찾고 있었습니다.

실제로 사고가 날 뻔했습니다. 2026-09-21 삼성중공업 조사에서 목표주가가 15,000원부터 90,000원까지 여섯 배 엇갈렸고, 어떤 자료는 주가를 48,050원이라고 했는데 실제로는 20,500원이었습니다. 눈치채서 뺐지만 못 봤으면 그대로 분석에 들어갔습니다.

### 정한 것

**과거 재무는 공시 원본에서, 비율은 앱이 계산합니다. 클로드는 전망과 의견만 찾습니다.**

| 무엇 | 어디서 | 왜 |
|---|---|---|
| 확정된 과거 (매출·이익·자산·부채·주식수) | 한국 DART, 미국 SEC EDGAR | 공시 원본이라 틀릴 수 없다 |
| 과거 결산일 주가 | 토스 일봉 | 이미 시세를 받는 곳 ([002](#002-시세는-토스에서만-가져온다)) |
| 부채비율·ROE·EPS·BPS·PER·PBR·과거 배수 | 앱 계산 | 두 쪽을 나누면 끝나는 값 |
| 컨센서스·가이던스·산업 동향·뉴스 | 웹 검색 | 공시가 아니라 의견이다 |

둘 다 무료입니다. DART 는 키 하나, EDGAR 는 키 없이 연락처만 밝히면 됩니다.

### 계산 기준을 이렇게 정했다

같은 "PER" 이라도 기준에 따라 두 배씩 달라집니다. 웹에서 찾은 숫자가 믿기 어려웠던 진짜 이유가 이것이었습니다. 그래서 기준을 하나로 정하고 프롬프트에 같이 적습니다.

**이익은 최근 4분기.** 작년 연간 + 올해 누적 − 작년 같은 기간 누적. 삼성전자는 2025년 연간 순이익이 45조인데 최근 4분기는 150조입니다. 연간으로 재면 PER 이 세 배 틀립니다.

**주당 지표는 지배주주 몫으로.** 주가는 지배기업 주식의 값입니다. 자회사 소수주주 몫까지 넣으면 EPS 가 부풉니다. 순이익 표시와 부채비율은 관례대로 연결 그대로 둡니다.

**주식수는 보통주 + 우선주, 자기주식 제외.** 순이익에는 우선주 몫이 들어 있습니다. 보통주로만 나누면 우선주 몫이 보통주에 얹힙니다. 현대차는 이 둘 때문에 PER 이 7.89 → 11.47 로 바뀌었습니다. 삼성중공업은 반대로 내려갔습니다. 방향이 종목마다 달라서 "대충 비슷하다" 가 성립하지 않습니다.

**과거 배수는 결산일 종가로.** 적정가는 "그 회사가 받아온 PER 범위" 에 기대는데, 이 범위야말로 출처마다 기준이 제일 달랐습니다. 결산일은 12월로 가정하지 않고 공시에서 읽습니다.

### 검토했지만 안 한 것

**유료 금융 데이터 API.** 한 번에 깔끔하게 받을 수 있지만 개인 프로젝트에 월 요금은 맞지 않습니다. 그리고 계산 기준이 그 회사 것이라 위의 기준을 우리가 못 고릅니다.

**클로드에게 DART 페이지를 읽히기.** 웹검색 도구로 공시 원문을 찾게 할 수도 있었습니다. 하지만 그러면 숫자를 옮기는 게 여전히 모델이고, 검색 횟수와 비용만 늘어납니다.

**증권사 앱의 PER 을 그대로 쓰기.** 토스·나무 API 에는 PER 이 없습니다 (003 에서 확인).

### 대가

- 호출이 늘었습니다. 국내 종목 하나에 DART 4~8번, 토스 일봉 최대 6번. 전부 0원이고 분석을 누를 때만 돕니다
- 과거 EPS 도 지금 주식수로 나눕니다. 그 사이 소각·증자가 크면 과거 배수가 조금 어긋납니다
- EDGAR 는 태그 이름이 회사·연도마다 바뀝니다. 후보 태그 목록을 계속 관리해야 하고, 은행·보험처럼 매출 태그가 다른 회사는 아직 비어 나옵니다

### 되돌리려면

`FilingService` 가 빈 값을 돌려주면 예전 동작(웹 조사)으로 돌아갑니다. 키를 비우거나 `SEC_USER_AGENT` 를 지우면 됩니다. 프롬프트도 [공시 재무] 블록이 없을 때의 문장이 그대로 남아 있습니다.

## 011. 공개 화면은 "브리핑" 으로 읽히게 한다

- 상태: 확정
- 날짜: 2026-10-02
- 관련: [008 색은 빨강과 파랑뿐이고 등락만 뜻한다](#008-색은-빨강과-파랑뿐이고-등락만-뜻한다) 는 그대로 지킨다

### 무엇이 문제였나

공개 화면(기관 포트폴리오)은 사람을 모으려고 만든 곳인데, 첫 화면이 표 세 개였습니다. 처음 온 사람은 무엇을 봐야 하는지 몰랐고, 공유했을 때 한눈에 읽히는 문장이 없었습니다.

### 정한 것

같은 화면을 세 방향(지금을 다듬은 장부형, 어두운 터미널형, 신문 1면 같은 브리핑형)으로 시안을 만들어 비교했고 브리핑형을 골랐습니다.

- **첫 화면은 한 줄 요약부터.** "버크셔는 GOOGL 주식을 45% 늘렸고, 4곳이 같이 LLY 주식을 늘렸다" 같은 문장을 **자료로 만듭니다.** HTML 에 숫자를 쓰면 분기가 바뀌는 날 틀립니다.
- **그림은 두 가지만.** 비중 트리맵(칸 크기=비중, 명도=순위)과 증감 막대(빨강=늘림, 파랑=줄임). 둘 다 색 규칙 안에 있습니다.
- **종이색 바탕, 큰 제목만 명조(Noto Serif KR).** 본문·표·숫자는 고딕 그대로입니다. 명조는 작게 쓰면 가는 획이 흐려집니다.
- **표를 훑는 화면(나의 포트폴리오)은 밀도를 그대로 둡니다.** 토큰(바탕색·글꼴)만 같이 바뀌고 제목만 명조입니다.

### 대가

- 바탕이 순백이 아니어서 빨강·파랑을 한 단계 어둡게 했습니다(#e03131 → #c92a2a). 그대로 두면 4.5:1 대비를 못 넘깁니다.
- 글꼴을 하나 더 받습니다. jsdelivr 의 글자 범위별 분할 파일이라 화면에 쓴 글자 묶음만 내려받고, CSP 를 바꿀 필요가 없었습니다.
- 다양하게 나눠 담는 기관(국민연금·노르웨이)은 트리맵 대부분이 "그 외" 한 칸입니다. 실제 모양이 그렇기 때문에 그대로 둡니다.

### 덧붙임 (2026-10-02): 어두운 화면을 없앴다

같은 날 사용자가 "밝은/어두운을 나누지 말고 한 가지로" 를 정했습니다. 밝은 종이색만 남겼습니다. 화면 두 벌의 대비를 매번 따로 재야 했고, 차트처럼 CSS 변수를 스스로 못 따라가는 곳은 모드 전환 처리를 따로 둬야 했던 짐이 같이 사라졌습니다.

### 되돌리려면

색과 글꼴은 `static/public/tokens.css` 한 곳입니다. 첫 화면 구성은 `index.html`·`home.js`, 트리맵은 `site.js` 의 `drawTreemap` 입니다.

## 012. 공개 기업분석은 규칙으로 만든 사실만 보인다

- 상태: 확정
- 날짜: 2026-10-02
- 관련: [003 숫자는 앱이, 조사는 LLM이](#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다), [011 브리핑](#011-공개-화면은-브리핑-으로-읽히게-한다)

### 무엇이 문제였나

사용자가 공개 화면의 종목을 누르면 "나의 포트폴리오의 기업분석처럼" 창이 뜨기를 원했습니다. 처음에는 이미 만들어 둔 AI 기업분석을 공개하기로 했는데, 확인해 보니 **저장된 분석 본문 곳곳에 내 평단가·비중·손익이 섞여** 있었습니다. 프롬프트가 내 보유를 사실로 넣기 때문입니다. 판정과 "내 자리" 칸만이 아니라 밸류에이션·사업 칸 문장에도 들어 있어, 칸 단위로 걸러서는 막을 수 없었습니다.

### 정한 것

- 공개 창은 **0원 사실**로 채웁니다: SEC 10-K 재무, 기관 10곳의 이 종목 비중·변화.
- 그 위의 "읽을 점" 문장은 `StockNotes` 가 **정해진 규칙으로** 만듭니다. 같은 숫자면 같은 문장이고, 테스트로 고정합니다. 예: 순이익/영업이익 비율이 5%p 넘게 움직이면 "영업외손익과 법인세를 확인하세요".
- 판정(사라/팔아라)·적정가는 쓰지 않습니다. 테스트가 그런 낱말이 나오지 않는 것까지 확인합니다.
- 내 보유를 넣지 않고 돌리는 **공개용 AI 분석**은 나중에 붙입니다(운영자만 실행, 종목당 1회 비용). 지금 있는 AI 분석은 그대로 비공개입니다.

### 대가

- AI 분석이 하던 웹 조사(컨센서스, 사업 구조)는 공개 창에 없습니다.
- 토스 현재가로 PER·PBR 과 주가 변화(%)를 계산해 보입니다. 시세 재배포 약관은 서버 공개 전에 확인해야 합니다([로드맵](로드맵.md)).

### 덧붙임 (2026-10-03): AI 기업분석을 연결했다

다음 날 사용자가 방향을 분명히 했습니다. "나의 포트폴리오의 기업분석을 가져다 쓴다. 내 포트폴리오에 없는 종목이면 평단가 없이 현재가만 분석한다."

- 기업분석 화면 맨 위에 **나의 포트폴리오와 같은 AI 기업분석**을 붙였습니다. 그리는 코드(`public/analysis-view.js`)와 스타일(`analysis.css`)을 두 화면이 같이 씁니다.
- 분석 엔진은 **안 가진 종목도** 분석합니다. 그때는 보유 값을 전부 비우고 현재가만 넣으며, 판정의 뜻을 "새로 담을 만한가" 로 바꿉니다(`company-analysis-system.md` "보유하지 않은 종목").
- 저장할 때 **평단가가 들어갔는지(`includes_position`)** 를 같이 남깁니다. 공개 주소(`/api/public/analysis/{종목}`)는 들어가지 않은 것만 돌려주고, 들어간 분석이 있어도 "없음" 으로 답합니다. "비공개 분석이 있음" 자체가 내가 그 종목을 가졌다는 정보이기 때문입니다.
- 실행(돈이 드는 POST)은 여전히 로그인한 나만 합니다.
- 공개 화면에 판정(더 담아도/그대로/줄이는 쪽)이 나가게 됐습니다. 사용자가 이 위험을 알고 정했습니다. 화면에 "보유하지 않은 종목 · 현재가 기준" 과 투자 권유가 아니라는 안내가 붙습니다.

## 014. 관측은 서버 안에서만 보고 SSH 터널로 연다

- 상태: 확정
- 날짜: 2026-10-03
- 관련: PR #28 (`deploy/compose.yml`, `deploy/monitoring/`), [운영 7장 지표 보기](운영.md#지표-보기), [로드맵 3단계](로드맵.md#3단계-관측과-알림)

### 무엇이 문제였나

서버 배포 스택에 Prometheus 와 Grafana 를 붙이면서 "어디서 보나" 를 정해야 했습니다. Grafana 를 Caddy 뒤에 붙여 도메인으로 열면 편하지만, 로그인 화면 하나가 인터넷에 더 생기고 그 비밀번호가 새면 서버의 지표(요청 주소·오류 수·메모리)가 통째로 보입니다. 혼자 보는 대시보드라 그만한 편의가 필요 없었습니다.

조사하다 함정을 하나 확인했습니다. **도커가 publish 한 포트는 호스트 방화벽을 우회합니다.** 도커는 iptables 의 nat 표 PREROUTING 에 DOCKER 체인을 걸어 들어오는 패킷의 목적지를 컨테이너로 바꿉니다. 바뀐 패킷은 INPUT 이 아니라 FORWARD 로 가서, ufw 나 INPUT 규칙으로 9090·3000 을 막아 둬도 `0.0.0.0:3000` 으로 열면 인터넷에서 그대로 보입니다.

또 하나는 1GB 서버였습니다. 관측 두 컨테이너는 합쳐 최대 512MB 를 더 씁니다. 관측을 끈 서버에서도 앱 배포는 그대로 돼야 했습니다.

### 정한 것

- **두 포트를 `127.0.0.1` 에만 묶습니다.** 바깥에 열린 포트는 Caddy 의 80·443 뿐입니다. 볼 때는 `ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090` 으로 터널을 엽니다. 이미 배포용으로 SSH 를 쓰고 있어 새로 여는 문이 없습니다.
- **Prometheus 의 `--web.enable-lifecycle` 을 켜지 않습니다.** 켜면 HTTP POST 한 번으로 종료·설정 리로드가 됩니다. 127.0.0.1 이라도 서버 안의 아무 프로세스나 부를 수 있는 문입니다. 설정 리로드는 `deploy.sh` 가 SIGHUP 으로 하고, 방금 새로 만든 컨테이너에는 보내지 않습니다(신호 처리기를 달기 전에 받으면 죽기 때문).
- **관측은 compose profile `monitoring` 으로 켜고 끕니다.** `.env` 의 `COMPOSE_PROFILES` 한 줄입니다.
- **Grafana 비밀번호 검사는 compose 의 `${VAR:?}` 가 아니라 `deploy.sh` preflight 와 Grafana entrypoint 로 했습니다.** compose 는 꺼진 profile 서비스의 변수까지 해석해서, `:?` 를 쓰면 관측을 끈 서버(비밀번호를 안 넣은 서버)에서 `config` 가 실패하고 앱 배포까지 막혔습니다(직접 확인). 그래서 preflight 는 compose 가 prometheus 를 서비스로 볼 때만 비밀번호를 필수로 보고, entrypoint 는 비밀번호가 비었거나 `# ` 로 시작하면 기본값 admin/admin 으로 뜨지 않고 종료합니다.
- **대시보드·데이터소스는 파일이 원본입니다.** 화면 저장을 막고(`allowUiUpdates: false`, `editable: false`) 저장소의 JSON 을 고쳐 PR 로 바꿉니다. 서버를 새로 깔아도 같은 화면이 뜹니다.
- **알림은 미뤘습니다.** 알림의 신호가 될 외부 API 호출 지표(`http_client_requests_seconds`)가 아직 없습니다. `RestClient` 들을 정적 builder 로 만들어 Micrometer 가 붙지 않기 때문입니다. 신호 없이 알림부터 만들면 JVM 메모리 같은 것만 울려서, 3단계의 기준("토스 403 을 내가 먼저 안다")을 못 채웁니다.

### 대가

- 대시보드를 보려면 매번 터널을 열어야 합니다. 휴대폰으로는 못 봅니다.
- "외부 API 실패" 칸은 error/warn 로그 수로 대신합니다. 무엇이 실패했는지는 로그를 봐야 압니다.
- Grafana 비밀번호는 `grafana-data` 볼륨을 처음 만들 때만 들어가서, `.env` 를 바꿔도 반영되지 않습니다. 바꿀 때는 `grafana cli admin reset-admin-password` 를 따로 불러야 합니다.
- 검사가 compose 한 곳이 아니라 `deploy.sh` 와 entrypoint 두 곳에 나뉘었습니다. 한쪽만 고치면 어긋납니다.

### 되돌리려면

밖에서 열고 싶으면 Grafana 를 Caddy 에 경로나 하위 도메인으로 붙이고(그때도 포트는 127.0.0.1 그대로), Grafana 로그인 위에 Caddy 인증을 한 겹 더 둡니다. 관측을 통째로 빼려면 `.env` 에서 `COMPOSE_PROFILES` 를 지우면 되고, 볼륨 `prometheus-data`·`grafana-data` 는 `docker volume rm` 으로 지웁니다.

### 덧붙임 (2026-10-03): 외부 호출 지표가 생겼다

014 에서 미룬 외부 API 호출 지표를 붙였습니다. 모든 `RestClient` 를 주입받은 Builder 로 만들고, uri 태그는 쿼리·호스트를 버리고 키처럼 보이는 경로 조각이 있으면 `none` 으로 바꾸는 규칙(`SafeClientRequestObservationConvention`)을 뒀습니다. 지금은 모든 호출이 템플릿이라 값이 안 실리지만, 나중에 누가 키를 이어 붙여도 지표로 새지 않게 하려는 방어선입니다. 붙이자마자 로컬에서 `openapi.tossinvest.com 403` 이 잡혔습니다. 알림의 신호가 생겼으므로 알림은 다음 차례입니다.

## 015. 바깥 API 재시도는 GET 과 5xx·네트워크 오류에만, 서킷 브레이커는 호스트별로

- 상태: 확정
- 날짜: 2026-10-03
- 관련: [014 관측](#014-관측은-서버-안에서만-보고-ssh-터널로-연다)

### 무엇이 문제였나

로드맵 4단계의 "타임아웃·재시도·서킷 브레이커" 를 시작하며 보니 더 급한 게 있었습니다. **스프링 부트 3.3 의 기본 RestClient 는 타임아웃이 없습니다.** 상대가 연결만 받고 답을 안 주면 그 요청과 스레드가 끝없이 기다리고, 에러 없이 화면만 멈춥니다.

### 정한 것

- 모든 클라이언트에 연결 5초·응답 30초. 클라이언트 코드가 아니라 `RestClientCustomizer` 한 곳에서
- 재시도는 **GET 만, 네트워크 오류와 5xx 만**, 최대 3번(0.5초→1초에 흔들기). 4xx 는 다시 보내도 같고(토스 403 = 허용 IP), 429 는 바로 다시 두드리면 한도가 더 길게 막히고, POST 는 두 번 실행될 수 있습니다
- 서킷 브레이커는 **호스트별**. 최근 20번(최소 10번) 중 절반이 실패면 30초 동안 부르지 않고 바로 실패시킵니다. 실패로 세는 건 네트워크 오류·5xx 뿐입니다. 4xx 로 열면 "허용 IP 를 등록하세요" 안내가 "회로 열림" 으로 가려집니다
- 재시도·서킷을 애노테이션(AOP) 대신 **RestClient 인터셉터 하나**로 걸었습니다. 클라이언트마다 호출하는 곳이 여러 군데라(DART 만 6곳) 애노테이션은 빠뜨리기 쉽고, 같은 클래스 안 호출에는 프록시가 안 걸립니다

### 대가

- 실패한 GET 은 최대 약 2초 더 늦게 실패합니다(대기 0.5+1초)
- 서킷이 열린 30초 동안은 상대가 살아났어도 실패로 보입니다. 반열림 상태에서 3번 시험해 보고 다시 엽니다
- 앤트로픽 SDK 는 RestClient 가 아니라 여기 안 걸립니다(SDK 자체 재시도·타임아웃을 씁니다)

### 되돌리려면

`HttpClientResilienceConfig` 의 `RestClientCustomizer` 빈을 지우면 예전(타임아웃·재시도 없음)으로 돌아갑니다.

### 덧붙임 (2026-10-06): 010 의 공시 재무를 DB 에 저장한다

처음에는 공시 재무를 그때그때 받고 공개 화면에서만 메모리에 6시간 들고 있었습니다. 재시작하면 다시 받았고, 서버가 여러 대면 서버마다 받습니다. 공시 재무는 분기에 한 번 바뀌므로 `stored_financials` 에 저장하고 하루가 지나면 다시 받습니다. 다시 받기가 실패하면 저장본을 씁니다(며칠 묵어도 틀리지 않음).

**주가로 바뀌는 값은 저장하지 않습니다.** PER·PBR 은 읽을 때 지금 주가로 잽니다(`CompanyFinancials.withPrice`). 결산일 종가로 잰 과거 PER·PBR 은 과거 값이라 같이 저장합니다. 토스가 막혀 과거 배수를 못 붙였으면 한 시간에 한 번만 다시 시도합니다.

### 대가

- 뉴스는 제목만이라 기사 속 숫자는 모릅니다. 제목에 없는 큰 사건이 의심될 때만 검색하게 했습니다
- 실제로 몇 % 줄었는지는 크레딧 충전 후 첫 분석 로그(`claude_tokens_total`, 웹검색 횟수)로 확인해야 합니다. 지금 숫자는 추정입니다

## 017. 재무 표는 앱이 붙이고 모델은 해석만 쓴다

- 상태: 확정
- 날짜: 2026-10-06
- 관련: [003 숫자는 앱이, 조사는 LLM이](#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다), [016 앱이 가진 자료를 먼저](#016-ai-기업분석은-앱이-가진-자료를-먼저-넣고-검색을-줄인다)

### 무엇이 문제였나

[공시 재무] 표를 프롬프트로 넣으면 모델이 그 숫자를 재무상태·수치 지표 섹션의 `metrics` JSON 으로 다시 옮겨 적었습니다. 앱이 이미 가진 숫자를 출력 토큰(입력의 5배 단가)으로 되사는 셈이고, 옮기다 틀릴 여지도 있었습니다. 공시 원문 주소도 프롬프트로 받아 `sources` 에 그대로 옮겼습니다.

### 정한 것

- 모델에게 공시 숫자 표와 공시 출처를 쓰지 말라고 합니다. 본문에서 해석하고, 웹에서만 아는 값(적정가·컨센서스 배수·현금흐름)만 `metrics` 에 씁니다
- 결과를 받은 뒤 `FinancialMetrics` 가 같은 `Metric`·`Point` 모양으로 표를 만들어 두 섹션 앞에 끼우고 저장합니다. **화면 코드는 바꾸지 않습니다.** 연간은 "연도" 탭, 올해 누적·최근 4분기는 "분기" 탭, 현재가 배수는 시점값
- 저장할 때 끼웁니다. 분석을 만든 시점의 숫자가 같이 남고, 공개 화면에 따로 할 일이 없습니다
- 모델이 지시를 어기고 같은 이름의 지표를 또 쓰면 공시 값을 남깁니다
- 공시 재무가 없는 종목(키 없음, ETF)은 예전처럼 모델이 씁니다
- 같은 날 지시문에 "모든 섹션 두괄식, 앞에서 한 말 되풀이 금지" 를 넣었습니다. 길이 상한은 두지 않았습니다(사용자 결정: 내용은 줄이지 않는다)

### 대가

- 분기별(1·2·3분기 따로) 실적 표는 사라집니다. 공시 재무는 연간·올해 누적·최근 4분기만 갖고 있습니다
- 모델이 본문에서 인용하는 숫자와 표의 반올림이 조금 다를 수 있습니다(표는 소수 한 자리)
- 하지 않은 것: 노력 `medium`(판단 품질), Batch API(최대 하루 지연). 둘 다 사용자가 대가를 보고 빼기로 했습니다

## 018. 조사와 판단을 나눠 판단만 새로 쓸 수 있게 한다

- 상태: 확정
- 날짜: 2026-10-06
- 관련: [017 재무 표는 앱이](#017-재무-표는-앱이-붙이고-모델은-해석만-쓴다)

### 무엇이 문제였나

"다시 분석" 은 늘 웹 검색부터 일곱 섹션까지 전부 다시 했습니다. 그런데 며칠 사이에 바뀌는 건 현재가와 내 보유 상태뿐이고, 재무·사업·컨센서스 조사는 그대로입니다. 값의 대부분(검색 결과 입력, 섹션 출력)을 같은 내용에 다시 내고 있었습니다.

### 정한 것

- 버튼을 둘로 나눕니다. **판단만 새로**: 저장된 조사 섹션을 사실로 넣고 판정·한 줄 요약·POSITION_REVIEW·위험만 다시 씀. 웹검색 도구를 선언하지 않아 한 번 부르고 끝남. **전체 다시 분석**: 예전 그대로
- 조사가 보관 일수(`anthropic.cache-days`, 7일)를 넘겼으면 판단만 새로는 받지 않습니다(400, 버튼도 숨김). 낡은 컨센서스 위에 새 판정을 얹으면 날짜만 새것인 판단이 됩니다
- `company_analysis.researched_at`(V9) 을 따로 둡니다. 판단만 새로는 `analyzed_at` 만 바꾸고, 화면은 둘이 다르면 "판단 갱신 · 조사" 날짜를 둘 다 보입니다. 오래됨 표시도 조사 기준입니다
- 판정 규칙은 파일 두 곳에 복사하지 않습니다. 짧은 머리말(`company-reassess-system.md`) + 전체 지시문에서 "문장·판정·위험·보유하지 않은 종목" 절만 코드로 뽑아 붙입니다
- 한 번 평단가가 들어간 분석(`includes_position`)은 판단만 새로를 해도 계속 비공개입니다. 조사 섹션 본문에도 "평단가는 몇 배" 같은 문장이 남아 있을 수 있습니다
- 모델이 칸을 비우면 옛 값을 남깁니다

### 대가

- 판단만 새로는 조사 이후 나온 실적·컨센서스 변화를 모릅니다. 뉴스 제목으로만 짐작합니다. 실적 발표가 끼었으면 전체 다시 분석을 눌러야 합니다
- 값(약 100~300원)은 추정입니다. 크레딧 충전 뒤 로그(`claude_requests{kind="reassess"}`)로 확인해야 합니다

## 019. 서버 로그는 JSON 한 줄, 요청마다 번호를 붙인다

- 상태: 확정
- 날짜: 2026-10-07
- 관련: [014 관측은 서버 안에서만](#014-관측은-서버-안에서만-보고-ssh-터널로-연다)

### 무엇이 문제였나

지표(Prometheus)는 "몇 번 실패했나" 는 알려 주지만 "어느 요청이 왜" 는 로그를 봐야 합니다. 그런데 로그가 줄글이라 grep 으로만 찾을 수 있었고, 동시에 들어온 요청의 줄이 섞이면 오류 한 줄이 어느 요청 것인지 알 수 없었습니다. AI 분석처럼 백그라운드로 넘어간 일은 몇 분 뒤 남긴 "분석 실패" 를 시작 요청과 이을 방법이 없었습니다.

### 정한 것

- 요청마다 번호(`requestId`): Caddy 가 UUID 를 붙여 넘기고, 앱(`RequestIdFilter`)이 MDC 에 넣어 모든 줄에 붙이고 응답 헤더 `X-Request-Id` 로 돌려줍니다. 바깥이 보낸 번호는 모양이 맞을 때만 받습니다
- 백그라운드로 넘기는 일은 번호를 복사해 가고(`LogContext.carry`), 배치는 `batch-13f-…` 번호를 새로 답니다(`LogContext.job`)
- 서버는 `LOG_FORMAT=json` 으로 한 줄에 JSON 하나(logstash 인코더). 내 PC 는 줄글 그대로, 줄마다 `[번호]`
- `/api/**` 는 요청마다 `access` 한 줄(메서드·경로·상태·ms). 쿼리스트링은 남기지 않습니다
- 로그 수집 서버(Loki·ELK)는 아직 두지 않습니다. 무료 서버 메모리가 빠듯하고, 혼자 보는 앱이라 서버에서 jq 로 충분합니다

### 대가

- 서버가 통째로 죽으면 로그도 같이 사라집니다(컨테이너 로그, 20MB × 5). 서버 밖으로 모으는 건 로드맵에 남겼습니다
- 스프링 부트 3.4 의 내장 구조화 로그를 못 써서 라이브러리 하나(logstash-logback-encoder)가 늘었습니다. 3.4 로 올리면 지울 수 있습니다
