# 기술노트 — 이 프로젝트로 배우는 실무 기술

이 문서는 주니어 개발자가 이 저장소를 교재 삼아 백엔드, 데이터베이스, 프론트엔드, 배포, 운영을 공부할 수 있도록 정리한 노트다. 주식이나 공시 같은 도메인 이야기는 꼭 필요한 만큼만 하고, 대신 "어떤 기술을 왜 골랐는지", "그 기술이 실무에서는 무엇에 해당하는지", "다음에 무엇을 공부하면 되는지"에 집중한다.

이 저장소는 혼자 만든 작은 서비스지만, 실무 서비스가 갖춰야 하는 것을 대부분 갖고 있다. 로그인 영역과 공개 영역의 분리, 바깥 API가 죽어도 버티는 장치, 매일 도는 배치와 숫자 맞춰 보기(대사), 자동 테스트와 자동 배포, 지표와 알림까지 있다. 그래서 코드 한 줄 한 줄보다 "왜 이렇게 짰는가"를 따라가면 실무의 기본 뼈대를 한 바퀴 돌아볼 수 있다.

지금 구조의 정답은 [아키텍처](아키텍처.md)에, 그렇게 정한 이유는 [결정기록](결정기록.md)에 있다. 이 노트는 그 두 문서를 공부하기 좋은 순서로 다시 엮은 것이다. 파일 경로는 모두 저장소 루트를 기준으로 적었다. 코드 주석에도 "왜"가 적혀 있으니, 노트를 읽으면서 해당 파일을 같이 열어 보면 훨씬 빨리 익힐 수 있다.

### 이 문서를 읽는 법

이 노트는 자바 문법과 예외, 컬렉션 정도는 이미 아는 사람을 위해 썼다. 반대로 스프링, 데이터베이스, 네트워크, 운영에서 쓰는 실무 용어(프록시, 멱등, 서킷 브레이커 같은 말)는 처음 본다고 가정했다. 그런 용어는 0장에 모아 두었고, 본문에서 처음 나올 때도 한 번 더 풀어 쓴다.

각 장은 같은 모양으로 시작하고 끝난다. 아래 표시를 알아 두면 읽기가 편하다.

| 표시 | 뜻 |
|---|---|
| **이 장에서 배울 것** | 장 첫머리의 요약이다. 시간이 없을 때는 이것만 읽고 넘어가도 큰 그림은 잡힌다. |
| **먼저 알아둘 말** | 그 장에 나오는 실무 용어다. 누르면 [0장 용어집](#0-먼저-알아둘-말--용어집)의 해당 갈래로 간다. |
| **함정**, **겪은 함정** | 이 프로젝트를 만들면서 실제로 저지른 실수다. 같은 실수를 반복하지 않으려고 남겼다. |
| **직접 해보기** | 손으로 해 볼 과제다. 읽기만 하는 것보다 하나라도 직접 해 보는 편이 훨씬 오래 남는다. |
| **지도에서 보면** | 장 첫머리의 안내다. HTML 판에서는 서비스 전체 지도 위에 그 장에서 다루는 부분만 진하게 칠해 보여 주고, 앞 장과 어떻게 이어지는지 먼저 설명한다. |
| 선으로 그린 상자 그림 | 흐름도다. 위에서 아래로 읽는다. HTML 판에서는 같은 내용을 그림으로 보여 주고, 글자 그림은 "글로 그린 그림 보기"로 접어 둔다. 편집기에서 선이 어긋나 보이면 고정폭 글꼴(D2Coding, 나눔고딕코딩)로 바꿔 보자. |
| `이런 글자` | 저장소 안의 파일, 클래스, 명령이다. IntelliJ에서 `Shift`를 두 번 누르고 이름을 치면 바로 열 수 있다. |

각 절은 대체로 **무엇인가 → 이 프로젝트에서는 → 실무에서는 → 공부할 것** 순서로 쓴다. 처음 보는 개념이면 그 앞에 **기초부터**를 두어, 그 기술이 없으면 무엇이 불편한지부터 보여 준다.

## 0. 먼저 알아둘 말 — 용어집

> **이 장에서 배울 것** — 뒤에서 계속 나오는 실무 용어를 갈래별로 모았다. 처음부터 다 외울 필요는 없다. 본문을 읽다가 모르는 말이 나오면 이곳으로 돌아와 찾으면 된다. 각 용어 옆에는 그 개념이 이 저장소의 어디에 있는지 적어 두었으니, 코드를 같이 열어 보면 뜻이 훨씬 빨리 잡힌다.

표는 세 칸이다. 첫 칸은 용어, 둘째 칸은 뜻과 짧은 비유, 셋째 칸은 이 저장소에서 그 개념을 볼 수 있는 곳이다.

### 0.1 웹과 네트워크

브라우저와 서버, 서버와 서버가 주고받는 방식에 관한 말이다. 1장과 10장을 읽기 전에 훑어 두면 좋다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **HTTP 메서드** | 요청의 종류다. `GET`은 읽기만 하겠다는 약속이어서 여러 번 보내도 결과가 같아야 한다. `POST`, `PUT`, `DELETE`는 서버의 무언가를 바꾼다. | 공개 화면은 GET만 부른다. 무언가를 바꾸는 요청에는 CSRF 토큰을 붙인다(5.2). |
| **상태 코드** | 응답 맨 앞에 붙는 세 자리 숫자다. 2xx는 성공, 4xx는 요청한 쪽의 문제, 5xx는 서버 쪽의 문제를 뜻한다. 자주 보는 것으로는 401(누군지 모름, 로그인 필요), 403(누군지는 알지만 허락하지 않음), 404(없음), 429(너무 자주 부름), 502(내 서버가 뒤의 서버에게서 잘못된 답을 받음)가 있다. | 토스가 403을 주면 대부분 허용 IP 문제다. 공개 API를 너무 자주 부르면 429를, 바깥 API가 실패하면 502를 돌려준다(`GlobalExceptionHandler`). |
| **헤더** | 요청과 응답에 붙는 `이름: 값` 형태의 꼬리표다. 택배 상자에 붙은 송장을 떠올리면 된다. | `X-Request-Id`(요청 번호), `X-XSRF-TOKEN`(CSRF 토큰), `Retry-After`(429일 때 몇 초 뒤에 다시 오라는 안내)를 쓴다. |
| **포트** | 한 컴퓨터 안에서 프로그램을 구분하는 번호다. IP가 건물 주소라면 포트는 호수다. | 앱은 8080, 관리 주소는 8081, MySQL은 3306, HTTPS는 443을 쓴다. |
| **루프백 (127.0.0.1, localhost)** | 자기 자신만 부를 수 있는 주소다. 이 주소에만 열어 둔 포트는 바깥에서 들어올 수 없다. 집 안에서만 통하는 인터폰과 같다. | 관리 포트, Prometheus, Grafana를 이 주소에만 연다. |
| **공인 IP, 허용 IP** | 공인 IP는 인터넷에서 보이는 내 주소다. 허용 IP는 상대 서비스가 "이 주소에서 온 요청만 받겠다"고 등록해 둔 목록이다. | 토스는 허용 IP를 하나만 받는다. 학교 망은 IP가 자주 바뀌어서 고정 IP 서버가 필요하다. |
| **프록시 (proxy)** | 누군가를 대신해 요청을 주고받는 중간자다. 누구를 대신하느냐에 따라 아래 두 가지로 나뉜다. | 아래 두 줄과, 스프링 안의 프록시(0.2)를 보자. |
| **포워드 프록시** | 클라이언트 쪽의 대리인이다. 회사 망에서 바깥으로 나갈 때 거치는 관문이 대표적이며, 바깥 서버에는 프록시의 주소만 보인다. | 지금은 쓰지 않는다. 로드맵에 있는 "토스 요청만 SSH 터널(SOCKS)로 보내기"가 이 방식이다. |
| **리버스 프록시** | 서버 쪽의 대리인이다. 바깥에서 온 요청을 먼저 받아 안쪽 서버로 넘긴다. 그 과정에서 HTTPS를 풀고, 위험한 주소를 막고, 서버가 재시작하는 동안 요청을 붙잡아 둔다. 건물 1층의 안내 데스크와 비슷하다. | Caddy가 이 역할을 한다(10.2). |
| **로드밸런서** | 여러 대의 서버에 요청을 나눠 주는 리버스 프록시다. 은행 창구에 손님을 배정하는 번호표 기계를 떠올리면 된다. | 앱이 한 대뿐이라 아직 없다. |
| **TLS, HTTPS, TLS 종료** | TLS는 통신을 암호화하는 규약이고, HTTPS는 TLS 위에서 주고받는 HTTP다. TLS 종료는 앞단 프록시가 암호를 풀고 안쪽 서버에는 평문 HTTP로 넘기는 방식을 말한다. | Caddy가 443 포트에서 암호를 풀고 앱의 8080 포트로 넘긴다. |
| **인증서, Let's Encrypt, ACME** | 인증서는 이 도메인이 진짜라는 증명서다. Let's Encrypt는 인증서를 무료로 발급하는 기관이고, ACME는 발급과 갱신을 자동으로 처리하는 규약이다. | Caddy가 인증서를 알아서 받고 갱신한다. |
| **X-Forwarded-For** | 프록시를 거치면 앱에는 프록시의 IP만 보인다. 그래서 프록시가 원래 사용자의 IP를 이 헤더에 적어서 넘긴다. | 공개 API의 호출 한도를 진짜 사용자 IP 기준으로 셀 수 있는 이유다(`forward-headers-strategy` 설정). |
| **쿠키, 세션** | 쿠키는 브라우저가 저장해 두었다가 요청마다 자동으로 보내는 값이다. 세션은 서버가 기억하는 로그인 상태이고, 쿠키에는 그 세션을 찾는 번호표만 들어 있다. 놀이공원 손목밴드와 비슷하다. | 로그인 쿠키에 `HttpOnly`와 `SameSite=Strict`를 걸었다(5.1). |
| **정적 파일** | 서버가 계산 없이 그대로 내보내는 파일이다. HTML, CSS, JS, 이미지가 여기에 속한다. | `src/main/resources/static/`에 있다. jar 안에 들어가므로 CSS만 고쳐도 다시 빌드해야 한다. |
| **JSON, 직렬화** | JSON은 `{"이름": 값}` 모양의 글자 형식이다. 직렬화는 자바 객체를 JSON 글자로, 또는 그 반대로 바꾸는 일이다. | 스프링이 Jackson 라이브러리로 record를 JSON으로 바꿔 응답한다. |

### 0.2 스프링과 서버 안쪽

스프링이 객체를 만들고 이어 주는 방식, 그리고 서버 안에서 일이 도는 방식에 관한 말이다. 2장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **빈 (Bean)** | 스프링이 만들어서 들고 있는 객체다. 보통 앱 전체에서 하나만 만들어 함께 쓴다. | `@Service`, `@Component`, `@RestController`가 붙은 클래스가 빈이 된다. |
| **IoC, DI (의존성 주입)** | 필요한 객체를 내가 `new`로 만들지 않고 생성자로 받기만 하는 방식이다. 무엇을 꽂아 줄지는 스프링이 정한다. 객체를 만드는 주도권이 내 코드에서 스프링으로 넘어갔다고 해서 "제어의 역전(IoC)"이라고 부른다. | 모든 서비스가 생성자로 의존성을 받는다(2.1). |
| **계층 (레이어)** | 역할별로 나눈 코드의 층이다. 컨트롤러가 주소를 받고, 서비스가 규칙을 처리하고, 리포지토리가 DB를, 클라이언트가 바깥 API를 맡는다. | 패키지가 곧 층이다. `web` → `service` → `domain`, `external` 순서로 내려간다. |
| **DTO, 엔티티, record** | DTO는 주고받는 데이터의 모양을 정한 객체다. 엔티티는 테이블의 한 줄과 1:1로 대응하는 객체다. record는 값만 담는 짧은 자바 클래스 문법이다. | `external/toss/dto/`에 DTO가, `domain/`에 엔티티가 있고, 응답 대부분이 record다. |
| **필터 (Filter)** | 모든 요청이 컨트롤러에 닿기 전과 후에 끼어드는 코드다. 건물 입구의 검색대처럼 누구든 거쳐 간다. | `RequestIdFilter`, `PublicRateLimitFilter`, 그리고 Spring Security의 필터 묶음이 있다. |
| **인터셉터** | 정해진 흐름에 끼어드는 코드다. 이 저장소에서는 바깥으로 나가는 HTTP 요청에 끼어드는 것을 말한다. | `ResilientHttpInterceptor`가 타임아웃, 재시도, 서킷 브레이커를 맡는다. |
| **스프링 프록시, AOP** | `@Transactional` 같은 애노테이션이 붙으면 스프링은 원래 객체를 감싸는 대리 객체를 만들고, 메서드 앞뒤에 필요한 일을 끼워 넣는다. 같은 클래스 안에서 `this.메서드()`로 부르면 대리 객체를 거치지 않으므로 애노테이션이 동작하지 않는다. | 그래서 저장만 맡는 빈을 따로 두었다. `CompanyAnalysisStore`, `PortfolioSnapshotStore`가 그 예다(2.7). |
| **트랜잭션** | 여러 DB 작업을 "전부 성공하거나 전부 취소되는" 하나의 묶음으로 처리하는 것이다. 계좌 이체에서 출금과 입금이 같이 되거나 같이 안 되어야 하는 것과 같다. | 장 마감 스냅샷을 저장할 때 한 트랜잭션으로 묶는다(`PortfolioSnapshotStore`). |
| **스레드, 스레드 풀** | 스레드는 동시에 도는 실행 흐름이다. 스레드 풀은 스레드를 미리 만들어 두고 돌려 쓰는 묶음이다. | 톰캣이 요청마다 스레드를 하나씩 내준다. AI 분석, 13F 받기, 캐시 예열은 각자 스레드 하나짜리 `ExecutorService`에서 돈다. |
| **비동기, 폴링** | 비동기는 오래 걸리는 일을 다른 곳에 맡겨 두고 바로 답하는 방식이다. 폴링은 일이 끝났는지 주기적으로 다시 물어보는 방식이다. | AI 분석은 바로 `RUNNING`으로 답하고, 화면이 3초마다 상태를 다시 묻는다(2.3). |
| **이벤트, 느슨한 결합** | "이 일이 일어났다"고 알리기만 하고, 그 소식을 누가 듣는지는 모르게 짜는 방식이다. 한쪽이 고장 나도 다른 쪽은 계속 돌아간다. | 새 13F가 들어오면 `NewFilingEvent`를 내고, 텔레그램 알림은 그 이벤트를 듣고 따로 보낸다. |
| **스케줄러, cron 표현식** | 스케줄러는 정해진 시각에 코드를 실행하는 장치이고, cron 표현식은 그 시각을 적는 형식이다. 스프링은 `초 분 시 일 월 요일` 순서로 쓴다. | `0 0 6 * * *`는 매일 06:00, `0 10 16,18,20 * * MON-FRI`는 평일 16시·18시·20시 10분이다. |
| **설정, 환경변수, `.env`** | 코드 밖에서 넣어 주는 값이다. API 키 같은 비밀값은 코드에 쓰지 않고 실행 환경이 넣어 준다. | `application.yml`의 `${TOSS_CLIENT_ID:}` 같은 자리로 들어온다(2.2). |

### 0.3 데이터베이스

테이블과 키, 그리고 자바에서 DB를 다루는 도구에 관한 말이다. 3장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **스키마, 테이블, 행, 열** | 스키마는 DB 안의 이름공간이고, 테이블은 표, 행은 표의 한 줄, 열은 표의 한 칸이다. | 스키마 이름은 `portfolio`이고 테이블은 16개다(3장). |
| **PK (기본 키)** | 한 줄을 하나로 집어낼 수 있게 해 주는 값이다. 중복되거나 비어 있을 수 없다. | `filing_13f.accession_no`, `stored_financials.symbol`이 PK다. |
| **유니크 키** | 중복을 DB가 직접 막아 주는 열 또는 열의 묶음이다. 코드가 실수해도 DB가 막아 주는 마지막 방어선이다. | `(owner_key, symbol)`, `(snapshot_date, symbol)`에 걸려 있다. |
| **인덱스** | 빨리 찾으려고 따로 만들어 두는 정렬된 목록이다. 책 뒤의 찾아보기와 같다. | `idx_holding_13f_cusip`이 종목별 13F 조회를 받쳐 준다. |
| **FK (외래 키)** | "자식 줄은 반드시 존재하는 부모를 가리켜야 한다"는 규칙을 DB가 강제하는 제약이다. | 이 저장소에는 일부러 하나도 걸지 않았다(3.4). |
| **자연 키, 대리 키** | 자연 키는 업무에 원래 있던 값(종목코드, 공시 번호)이고, 대리 키는 DB가 붙여 주는 일련번호(`id`)다. | 3.3에서 어떤 테이블에 무엇을 골랐는지 설명한다. |
| **ORM, JPA, Hibernate** | ORM은 자바 객체와 테이블을 이어 주는 기술이다. JPA는 그 자바 표준이고, Hibernate는 그 표준을 구현한 라이브러리다. | 엔티티와 `JpaRepository`로 DB를 다룬다(3.7). |
| **쿼리 메서드** | 메서드 이름만 규칙에 맞게 지으면 SQL을 만들어 주는 JPA 기능이다. | `findBySymbolIn(...)`이 `WHERE symbol IN (...)`이 된다. |
| **N+1 문제** | 목록을 한 번 읽은 뒤 줄마다 한 번씩 더 조회하느라 쿼리가 N+1번 나가는 성능 문제다. | 연관관계 매핑을 쓰지 않아서 이 문제가 생길 자리가 없다(3.7). |
| **마이그레이션, Flyway, 체크섬** | 마이그레이션은 스키마 변경을 순서가 있는 SQL 파일로 남기는 방식이고, Flyway는 그 파일을 실행해 주는 도구다. 체크섬은 파일 내용이 바뀌었는지 확인하는 지문이다. | `V1__init.sql`부터 차례로 있다. 이미 적용한 파일을 고치면 체크섬이 달라져 앱이 뜨지 않는다(3.8). |
| **upsert** | 같은 키의 줄이 있으면 고치고(update), 없으면 새로 넣는(insert) 동작이다. | 스냅샷 합계 줄과 `stored_financials`가 이렇게 저장된다. |
| **덤프, 백업** | DB 내용을 SQL 파일로 떠 두는 것이다. | `deploy/backup.sh`가 매일 04:00에 뜬다(11.4). |

### 0.4 바깥 연동과 안정성

다른 회사의 API를 부를 때 쓰는 말, 그리고 상대가 느리거나 죽었을 때 버티는 장치에 관한 말이다. 4장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **API, API 키** | API는 프로그램끼리 서로 부르는 창구다. API 키는 누가 부르는지 증명하는 비밀값이다. | 토스, 나무, DART, SEC, Claude를 API로 부른다. |
| **OAuth 토큰 (액세스 토큰)** | 키로 한 번 로그인해서 받는, 유효기간이 있는 출입증이다. 그 뒤의 요청은 키 대신 이 출입증으로 한다. | 토큰을 메모리와 DB(암호화) 두 곳에 들고 있다(4장). |
| **타임아웃** | "이만큼 기다려도 답이 없으면 포기한다"는 시간이다. 연결 타임아웃은 상대와 연결될 때까지, 응답 타임아웃은 연결된 뒤 답이 올 때까지를 잰다. | 연결 5초, 응답 30초다. 이 값이 없으면 스레드가 영원히 묶일 수 있다(4장). |
| **재시도, 지수 백오프, 지터** | 재시도는 실패한 요청을 다시 보내는 것이다. 지수 백오프는 다시 보내기 전 기다리는 시간을 점점 늘리는 방식이고, 지터는 그 시간에 무작위 값을 섞어 모두가 같은 순간에 몰리지 않게 하는 것이다. | GET 요청이 네트워크 오류나 5xx로 실패했을 때만 최대 3번까지 다시 보낸다(4장). |
| **서킷 브레이커** | 실패가 몰리면 한동안 아예 부르지 않고 바로 실패로 처리하는 장치다. 집의 누전 차단기와 같다. 정상인 **닫힘**, 차단 중인 **열림**, 시험 삼아 몇 번만 보내 보는 **반열림**의 세 상태가 있다. | 상대 호스트마다 하나씩 두며, 최근 20번 중 절반이 실패하면 30초 동안 차단한다(4장). |
| **fail-soft (부분 실패 격리)** | 한 부분이 실패해도 전체는 계속 동작하도록 짜는 방식이다. | 토스가 막혀도 재무와 기관 칸은 그대로 보인다(4장). |
| **호출 한도 (rate limit)** | 정해진 시간 동안 부를 수 있는 횟수의 제한이다. 넘으면 보통 429를 받는다. | SEC는 초당 10건으로 제한한다. 우리도 공개 API에 IP당 분당 120번의 한도를 걸었다. |
| **캐시, TTL, 무효화** | 캐시는 계산이나 조회 결과를 잠시 들고 있는 것이다. TTL은 들고 있을 시간이고, 무효화는 낡은 결과를 버리는 것이다. | 공개 기업분석은 6시간 들고 있고, 13F 집계는 배치가 끝나면 통째로 버린다(1.7). |
| **캐시 예열 (warm-up)** | 사용자가 오기 전에 캐시를 미리 채워 두는 것이다. | `InstitutionCacheWarmer`와 공시 재무 야간 배치가 이 일을 한다. |
| **LRU** | 캐시가 꽉 차면 가장 오래 쓰지 않은 것부터 버리는 규칙이다. | `QueryCache`가 64개까지 들고 이 규칙으로 버린다. |

### 0.5 배치와 숫자 맞추기

사람이 누르지 않아도 정해진 때에 도는 일, 그리고 숫자가 맞는지 확인하는 일에 관한 말이다. 2.4와 15장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **배치 (batch)** | 사람이 누르지 않아도 정해진 때에 한꺼번에 처리하는 일이다. | 매일 06:00 공시 재무, 매일 07:00 13F, 평일 16:10 스냅샷이 돈다(2.4). |
| **멱등 (idempotent)** | 몇 번을 해도 한 번 한 것과 결과가 같은 성질이다. 엘리베이터 버튼은 열 번을 눌러도 엘리베이터가 한 번만 온다. 멱등하게 짜 두면 실패 후 다시 돌리거나 실수로 두 번 돌려도 안전하다. | 이미 받은 공시 번호는 건너뛰고, 스냅샷은 날짜를 키로 저장한다. |
| **원장 (ledger)** | 돈이나 수량의 공식 기록이다. | 이 앱에서는 증권사의 응답이 원장이고, 앱은 그 숫자를 더할 뿐이다. |
| **스냅샷** | 어느 순간의 모습을 그대로 찍어 둔 기록이다. | `portfolio_snapshot`에 하루 한 벌씩 남긴다. |
| **대사 (reconciliation)** | 서로 다른 두 시스템의 숫자가 맞는지 맞춰 보는 일이다. 가계부와 통장 잔고를 맞춰 보는 것과 같다. | 앱이 더한 합계와 증권사가 알려 준 합계를 매일 비교한다(15.4). |
| **재처리** | 실패한 배치를 다시 돌리는 것이다. 배치가 멱등해야 안전하게 재처리할 수 있다. | 18:10과 20:10에 다시 시도하고, `POST /api/portfolio/snapshots`로 손으로도 돌릴 수 있다. |

### 0.6 보안

누가 무엇을 할 수 있는지 정하고, 브라우저를 노리는 공격을 막는 일에 관한 말이다. 5장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **인증, 인가** | 인증은 "당신이 누구인가"를 확인하는 일(로그인)이고, 인가는 "당신이 이것을 해도 되는가"를 판단하는 일(권한)이다. | 폼 로그인으로 인증하고, `SecurityConfig`의 주소별 규칙으로 인가한다. |
| **CSRF** | 다른 사이트가 내 브라우저에 남아 있는 로그인 쿠키를 이용해 몰래 요청을 보내는 공격이다. | `XSRF-TOKEN` 쿠키와 헤더로 막는다(5.2). |
| **XSS, 이스케이프** | XSS는 남이 넣은 글자에 숨어 있던 스크립트가 내 화면에서 실행되는 공격이다. 이스케이프는 `<` 같은 문자를 `&lt;`로 바꿔서 글자로만 보이게 하는 처리다. | 바깥에서 온 글자는 모두 `esc()`를 거쳐 화면에 넣는다. |
| **CSP** | "스크립트는 이 출처에서 온 것만 실행하라"고 브라우저에 지시하는 응답 헤더다. | 인라인 스크립트를 아예 금지했다(5.3). |
| **대칭키 암호, AES-GCM, IV** | 대칭키 암호는 같은 키로 잠그고 여는 암호다. AES-GCM은 암호문이 위조되었는지까지 잡아내는 방식이고, IV는 매번 바꿔 넣는 무작위 시작값이다. | 증권사 토큰을 DB에 넣을 때 암호화한다(`TokenCipher`). |
| **시크릿** | 비밀번호나 키 같은 비밀값이다. 저장소, 로그, 화면 어디에도 남기면 안 된다. | 서버의 `.env`와 GitHub Secrets에만 둔다. |
| **최소 권한 원칙** | 꼭 필요한 권한만 주는 원칙이다. | CI는 기본으로 읽기 권한만 갖고, 이미지를 올리는 단계에만 쓰기 권한을 준다. |

### 0.7 빌드·배포·인프라

코드를 실행 파일로 만들고, 서버에 올리고, 서버를 운영하는 일에 관한 말이다. 8장부터 10장까지 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **jar (fat jar)** | jar는 자바 프로그램을 묶은 파일이다. fat jar는 필요한 라이브러리까지 모두 넣어서 `java -jar` 한 줄로 실행되게 만든 jar다. | `target/portfolio-0.0.1-SNAPSHOT.jar`가 만들어진다. |
| **Maven, 래퍼** | Maven은 의존성 받기, 컴파일, 테스트, 패키징을 맡는 도구다. 래퍼는 누구나 같은 버전의 Maven을 쓰게 해 주는 스크립트다. | `pom.xml`에 설정이 있고, `./mvnw`로 실행한다. |
| **이미지, 컨테이너** | 이미지는 실행에 필요한 모든 것을 통째로 굳혀 둔 꾸러미이고, 컨테이너는 그 이미지를 실제로 띄운 것이다. 붕어빵 틀과 붕어빵의 관계와 같다. | `Dockerfile`이 이미지를 만든다(8장). |
| **레지스트리, 태그** | 레지스트리는 이미지를 보관하는 저장소이고, 태그는 이미지에 붙이는 버전 이름표다. | `ghcr.io/.../stock-portfolio:sha-xxxxxxx` 형태로 올라간다. |
| **볼륨** | 컨테이너를 지워도 사라지지 않는 저장 공간이다. | MySQL 데이터가 `mysql-data` 볼륨에 있다. |
| **Docker Compose, profile** | Compose는 여러 컨테이너를 파일 하나로 함께 띄우는 도구다. profile은 그중 골라서 켜는 묶음이다. | `deploy/compose.yml`이 있고, 모니터링은 `monitoring` profile로 켠다. |
| **CI, CD** | CI(지속적 통합)는 코드를 합치기 전에 자동으로 테스트하고 빌드하는 것이다. CD(지속적 배포)는 합친 뒤 자동으로 서버에 반영하는 것이다. | `.github/workflows/ci.yml`과 `deploy.yml`에 있다(9장). |
| **워크플로, 잡, 러너** | 워크플로는 GitHub Actions에서 자동화를 묶은 단위이고, 잡은 그 안의 작업 하나, 러너는 작업을 실제로 실행하는 컴퓨터다. | "테스트와 패키징" 같은 잡이 있다. |
| **PR, 브랜치 보호, 스쿼시 병합** | PR은 내 브랜치를 합쳐 달라는 요청이고, 브랜치 보호는 `main`에 아무나 바로 밀어 넣지 못하게 막는 규칙이다. 스쿼시 병합은 PR의 여러 커밋을 하나로 눌러 합치는 방식이다. | 9.1에서 설명한다. |
| **헬스체크, liveness, readiness** | 헬스체크는 서버가 괜찮은지 물어보는 주소다. liveness는 프로세스가 살아 있는지를, readiness는 요청을 받을 준비(DB 연결 포함)가 되었는지를 본다. | `:8081/actuator/health/...`에 있다(11.1). |
| **롤백** | 문제가 생겼을 때 앞 버전으로 되돌리는 것이다. | 헬스체크가 실패하면 `deploy.sh`가 자동으로 되돌린다. |
| **무중단 배포, 블루그린, 롤링** | 무중단 배포는 배포하는 동안에도 요청을 놓치지 않는 것이다. 블루그린은 새 버전을 옆에 띄운 뒤 한 번에 전환하는 방식이고, 롤링은 여러 대를 하나씩 바꾸는 방식이다. | 지금은 Caddy가 재시작 동안 요청을 붙잡아 주는 방식을 쓴다(10.3). |
| **SSH, SSH 터널** | SSH는 서버에 암호화된 통로로 접속하는 방법이다. SSH 터널은 내 PC의 포트를 서버 안의 포트에 이어 주는 통로다. | Grafana를 `ssh -L 3000:...`으로 연다. |
| **방화벽, iptables** | 방화벽은 들어오고 나가는 연결을 거르는 규칙이고, iptables는 리눅스에서 그 규칙을 다루는 도구다. | 서버는 80번과 443번 포트만 연다(10.1). |
| **스왑, OOM** | 스왑은 메모리가 모자랄 때 디스크를 메모리처럼 쓰는 공간이다. OOM(Out Of Memory)은 메모리가 바닥나 프로세스가 강제로 죽는 상황이다. | 서버에 스왑 2GB를 잡아 둔다. |

### 0.8 관측과 운영

서비스가 지금 괜찮은지, 무슨 일이 있었는지 알아보는 일에 관한 말이다. 11장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **관측 (observability)** | 밖에서 시스템의 속사정을 알아보는 능력이다. 보통 로그, 지표, 추적의 세 가지로 나눈다. | 11장 전체가 이 이야기다. |
| **로그 레벨** | 로그의 중요도다. `DEBUG`, `INFO`, `WARN`, `ERROR` 순서로 중요해진다. | 실패했지만 계속 진행할 수 있는 일은 WARN으로 남긴다. |
| **구조화 로그** | 줄글 대신 JSON처럼 필드가 나뉜 로그다. 도구로 거르고 모으기 쉽다. | 서버에서는 `LOG_FORMAT=json`으로 이 형식을 쓴다. |
| **MDC** | 스레드마다 따로 붙는 로그 꼬리표 저장소다. 여기 넣은 값은 그 스레드가 찍는 모든 로그 줄에 자동으로 붙는다. | 요청 번호를 넣어 모든 줄에 찍는다(11.3). |
| **요청 ID, trace ID** | 요청 ID는 요청 하나에 붙인 번호다. trace ID는 그 번호를 여러 서버에 걸쳐 이어 붙인 것이다. | `X-Request-Id` 헤더로 주고받는다. |
| **지표, 카운터, 게이지, 태그** | 지표(metric)는 시간에 따라 재는 숫자다. 카운터는 늘어나기만 하는 수, 게이지는 오르내리는 현재 값이고, 태그는 같은 지표를 갈라 보는 이름표다. | `filing_prefetch_runs_total{outcome="failure"}`에서 `outcome`이 태그다. |
| **Actuator, Micrometer** | Actuator는 스프링이 제공하는 운영용 주소 모음이고, Micrometer는 지표를 재는 라이브러리다. | `/actuator/prometheus`에서 지표를 내보낸다. |
| **Prometheus, pull, PromQL** | Prometheus는 지표를 모아 시간순으로 쌓는 DB다. 앱이 지표를 보내는 것이 아니라 Prometheus가 주기적으로 긁어 간다(pull)는 점이 중요하다. PromQL은 그 데이터를 조회하는 언어다. | 15초마다 앱에서 긁어 간다(11.2). |
| **Grafana, 대시보드** | 지표를 그래프로 보여 주는 화면이다. | 대시보드 하나를 파일로 관리한다. |
| **알림, Alertmanager, 알림 피로** | 알림은 규칙에 맞는 상황이 생기면 사람에게 알리는 것이고, Alertmanager는 알림을 묶어서 보내는 도구다. 알림 피로는 알림이 너무 잦아서 결국 아무도 보지 않게 되는 현상이다. | 텔레그램으로 보내며, 규칙은 11개다. |
| **런북 (runbook)** | "이 증상이 보이면 이렇게 한다"를 적어 둔 대응 매뉴얼이다. | [운영 - 장애 대응](운영.md#장애-대응)이 런북이다. |
| **부하 테스트** | 가짜 사용자를 많이 보내서 서버가 버티는지 재는 테스트다. | k6로 하며 스크립트는 `loadtest/`에 있다. |
| **p95** | 응답 시간을 빠른 순으로 줄 세웠을 때 95% 지점의 값이다. 평균보다 "느린 편의 사용자가 실제로 겪는 시간"을 잘 보여 준다. | 첫 화면의 p95를 8.8초에서 0.1초로 줄였다. |

### 0.9 테스트

코드가 맞게 동작하는지 자동으로 확인하는 일에 관한 말이다. 7장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **단위, 통합, E2E 테스트** | 단위 테스트는 클래스 하나만, 통합 테스트는 DB를 포함한 여러 부품을 함께, E2E 테스트는 사용자처럼 화면부터 끝까지 검사한다. | 대부분 단위 테스트이고, 화면은 puppeteer로 확인한다. |
| **목 (mock), 스텁** | 목과 스텁은 진짜 대신 꽂아 쓰는 가짜 객체다. 스텁은 정해 둔 답만 돌려주고, 목은 거기에 더해 "실제로 불렸는지"까지 검사할 수 있다. | Mockito의 `mock()`, `when(...).thenReturn(...)`, `verify(...)`를 쓴다. |
| **픽스처** | 테스트에 쓰려고 저장해 둔 입력 데이터다. | `src/test/resources/dart/`에 실제 응답을 파일로 저장해 두었다. |
| **커버리지, 품질 게이트** | 커버리지는 테스트가 코드의 몇 퍼센트를 실행했는지를 나타낸다. 품질 게이트는 기준에 못 미치면 합치지 못하게 막는 관문이다. | JaCoCo로 재고 `jacoco:check`로 막는다(15.3). |

## 1. 전체 그림

<!-- diagram: map | 서비스 전체 지도. 위쪽은 요청이 처리되는 서버, 아래쪽은 코드가 서버까지 가는 길이다. -->

**지도에서 보면.** 이 노트는 이 지도 한 장을 여러 번 확대하며 읽는다. 1장은 지도 전체를 한 번 훑는다. 2장부터는 장마다 맨 위에 같은 지도를 두고, 그 장에서 다루는 부분만 진하게 칠한다. 지금 어디를 보고 있는지, 그 부분이 앞뒤의 무엇과 이어지는지 먼저 확인하고 들어가면 길을 잃지 않는다.

> **이 장에서 배울 것** — 서버 한 대에 무엇이 떠 있고, 요청 하나가 어디를 거쳐 가는지를 그림으로 본다. 뒤의 장들은 여기 나오는 부품을 하나씩 확대해서 다룬다.
>
> **먼저 알아둘 말** — [포트](#01-웹과-네트워크) · [루프백](#01-웹과-네트워크) · [리버스 프록시](#01-웹과-네트워크) · [컨테이너](#07-빌드배포인프라) · [배치](#05-배치와-숫자-맞추기) · [캐시](#04-바깥-연동과-안정성)

이 장은 지금 이 프로젝트가 실제로 어떤 모양인지를 위에서 아래로 훑는다. 처음에는 세부를 다 이해하지 않아도 괜찮다. "이런 부품들이 있고, 요청이 이런 순서로 지나간다"는 지도만 머리에 넣어 두면, 뒤의 장을 읽을 때 지금 어디를 보고 있는지 길을 잃지 않는다.

그림은 모두 글자로 그렸다. 그래서 GitHub뿐 아니라 IntelliJ나 VS Code에서 열어도 그대로 보인다.

### 1.1 한눈에

아래는 서버 한 대에서 `docker compose`로 띄운 전체 모습이다. 맨 위의 브라우저에서 출발해 아래로 내려가며 읽으면 된다.

<!-- diagram: overview | 바깥에서 들어오는 문은 Caddy의 443 하나다. 앱은 DB와 바깥 API를 부르고, 관측 도구는 서버 안(127.0.0.1)에만 열어 SSH 터널로 본다. -->

```text
[서버 한 대 · docker compose]

브라우저 (HTML/CSS/JS)
  │  HTTPS 443        ← 바깥에 열린 포트는 80·443 뿐
  ▼
Caddy                 HTTPS 종료 · 인증서 자동 갱신 · 재시작 중 요청 붙잡기
  │  HTTP 8080        (서버 안 네트워크)
  ▼
Spring Boot 앱        jar 하나 = 프로세스 하나 (화면도 같이 내보냄)
  ├─ JDBC 3306 ──▶ MySQL 8.4 (도커 볼륨, 바깥 포트 없음)
  └─ HTTPS ──────▶ 바깥 API (토스 · 나무 · DART · SEC · OpenFIGI · Claude · 뉴스)

Prometheus ── 15초마다 긁음 ──▶ 앱 관리 포트 8081 (/actuator/prometheus)
  │  규칙이 맞으면
  ▼
Alertmanager ──▶ 텔레그램

Grafana ── Prometheus 를 읽음 ◀── SSH 터널 ── 운영자 PC

※ 8081 · 9090(Prometheus) · 3000(Grafana) · 9093(Alertmanager) 은 서버 자신(127.0.0.1)에만 열린다
```

브라우저가 보낸 요청은 먼저 Caddy에 닿는다. Caddy는 [리버스 프록시](#01-웹과-네트워크)로서 HTTPS 암호를 풀고, 요청을 서버 안쪽 네트워크를 통해 스프링부트 앱으로 넘긴다. 앱은 필요하면 MySQL을 읽고 쓰거나 바깥 API를 부른 뒤 JSON으로 답한다. 화면 파일(HTML, CSS, JS)도 같은 앱이 내보낸다.

그림의 아래쪽 절반은 운영을 위한 부품이다. Prometheus가 15초마다 앱의 관리 포트에서 지표를 긁어 가고, 규칙에 맞는 상황이 생기면 Alertmanager가 텔레그램으로 알린다. Grafana는 그 지표를 그래프로 보여 주는 화면이다.

이 그림에서 꼭 기억할 점은 두 가지다.

첫째, **바깥에 열린 포트는 80번과 443번뿐이다.** 앱(8080)과 DB(3306)는 컨테이너끼리만 통하는 네트워크에 있고, 관리 포트(8081), Prometheus(9090), Grafana(3000)는 서버 자신을 뜻하는 127.0.0.1에만 열려 있다. 바깥에서 들어올 수 있는 문을 하나로 줄여 두면 그 문 하나만 잘 지키면 된다.

둘째, **앱은 프로세스 하나다.** 화면을 내보내는 서버와 API 서버를 나누지 않았고, 기능별로 여러 서비스로 쪼개는 마이크로서비스 구조도 쓰지 않았다. 혼자 운영하는 규모에서는 나눌 때 드는 비용(서비스 사이의 통신, 배포 순서, 장애 추적)이 얻는 이익보다 크기 때문이다.

### 1.2 실행 단위 — 무엇이 어디서 도나

1.1의 그림에서 상자 하나하나가 컨테이너다. 표로 정리하면 다음과 같다.

| 이름 | 이미지 / 실행 | 포트 | 바깥 공개 | 메모리 | 하는 일 |
|---|---|---|---|---|---|
| caddy | `caddy:2.8` | 80·443 | **예** | - | HTTPS를 풀고 인증서를 자동으로 갱신한다. 앱이 재시작하는 동안 요청을 붙잡아 두고, `/actuator`를 막고, 요청마다 `X-Request-Id`를 붙인다. |
| app | `ghcr.io/.../stock-portfolio:sha-xxxxxxx` (JRE 21) | 8080, 관리 8081 | 아니오 (8081은 127.0.0.1) | 한도 900MB, 힙 512MB | 화면, API, 배치(공시 재무 06:00, 13F 07:00, 스냅샷 평일 16:10), 바깥 API 연동을 모두 맡는다. 로그는 JSON으로 남긴다(`LOG_FORMAT=json`). |
| mysql | `mysql:8.4` | 3306 | 아니오 | - | 데이터를 저장한다. 데이터는 `mysql-data` 볼륨에 있다. |
| prometheus | `prom/prometheus:v3.5.5` (선택) | 9090 | 아니오 (127.0.0.1) | 한도 256MB | 지표를 모아 15일 동안 보관한다. |
| grafana | `grafana/grafana:12.1.10` (선택) | 3000 | 아니오 (127.0.0.1) | 한도 256MB | 지표를 대시보드로 보여 준다. |
| alertmanager | `prom/alertmanager:v0.30.0` (선택) | 9093 | 아니오 (127.0.0.1) | 한도 64MB | 경보를 묶어서 텔레그램으로 보낸다. |

"(선택)"이라고 적힌 세 개는 compose의 `monitoring` profile에 속한다. profile은 골라서 켤 수 있는 묶음이어서, 메모리가 1GB밖에 없는 작은 서버라면 이 셋을 끄고 앱과 DB만 돌릴 수 있다.

내 PC에서 개발할 때는 이 중 app만 `java -jar`로 띄우고, MySQL은 PC에 설치된 것을 쓴다. 서버와 똑같은 구성을 PC에서 확인하고 싶다면 `deploy/` 폴더로 리허설을 하면 된다([운영 7장](운영.md#7-배포)).

### 1.3 앱 안쪽 — 패키지 지도

이번에는 1.1 그림의 "Spring Boot 앱" 상자 안으로 들어가 본다. 앱의 코드는 역할에 따라 패키지로 나뉘어 있다.

<!-- diagram: packages | 의존은 위에서 아래로만 간다. web은 external을 직접 부르지 않고, config는 모든 층에 가로로 걸친다. -->

```text
web          컨트롤러 · 예외 처리 (주소를 받아 JSON 으로 답함)
  │
  ▼
service      업무 규칙 (합산 · 비교 · 문장 규칙)
  ├──▶ brokerage   증권사 보유 (토스 · 나무 · 직접 입력) ──▶ external 를 씀
  ├──▶ external    바깥 API 클라이언트 ──▶ domain 을 씀
  └──▶ domain      JPA 엔티티 · 리포지토리 (아무것도 모름)

config       보안 · 호출 한도 · 관측 · 스케줄 (모든 층에 가로로 걸침)

※ 의존은 위에서 아래로만. web 은 external 을 직접 부르지 않는다
```

요청은 위에서 아래로 흐른다. `web`이 주소를 받아 `service`에 넘기면, `service`가 업무 규칙을 처리하면서 필요한 데이터를 `brokerage`, `external`, `domain`에서 가져온다. `config`는 이 흐름 전체에 가로로 걸쳐 있는 설정이다. 보안 규칙이나 호출 한도처럼 어느 한 층에 속하지 않는 것들이 여기에 있다.

| 패키지 | 하는 일 | 대표 클래스 |
|---|---|---|
| `web` | 주소를 받아 JSON으로 답한다. 업무 규칙은 두지 않는다. | `StockBriefController`, `InstitutionController`, `CompanyAnalysisController`, `GlobalExceptionHandler` |
| `service` | 합산, 비교, 문장 규칙 같은 업무 규칙을 처리한다. | `UnifiedPortfolioService`(증권사 합산), `InstitutionPortfolioService`(13F 비교), `StockNotes`(공개 기업분석 문장), `CompanyAnalysisService`(AI 분석 흐름) |
| `brokerage` | 증권사마다 다른 보유 조회 방식을 하나의 모양으로 맞춘다. **주문 메서드는 없다.** | `BrokerageClient`(인터페이스), `TossBrokerageClient`, `NamuhBrokerageClient`, `ManualBrokerageClient` |
| `external` | 바깥 시스템마다 하위 패키지를 하나씩 둔다. | `toss/`, `namuh/`, `dart/`, `edgar/`, `thirteenf/`, `anthropic/`, `news/`, `telegram/`, `auth/`(토큰 암호화) |
| `domain` | 테이블과 1:1로 대응하는 엔티티와 조회 메서드를 둔다. | `Filing13F`, `Holding13F`, `CompanyAnalysis`, `OAuthToken` 등 |
| `config` | 여러 층에 가로로 걸치는 설정을 둔다. | `SecurityConfig`, `PublicRateLimitFilter`, `SafeClientRequestObservationConvention`, `SchedulingConfig` |

여기서 지키는 규칙은 하나다. **의존은 위에서 아래로만 간다.** `domain`은 다른 패키지를 전혀 모르고, `web`은 `external`을 직접 부르지 않는다. 이렇게 해 두면 바깥 API의 사정이 화면 코드까지 새어 나오지 않는다. 예를 들어 토스의 응답 모양이 바뀌어도 `external/toss` 안에서만 고치면 되고, 컨트롤러는 손댈 필요가 없다.

### 1.4 화면 지도

화면은 `src/main/resources/static/`에 빌드 과정 없이 들어 있다. 모든 화면의 왼쪽에는 같은 사이드바(`public/nav.js`)가 붙는다. 화면마다 누가 볼 수 있는지, 주로 어떤 API를 부르는지를 정리하면 다음과 같다.

| 화면 | 파일 | 누가 보나 | 주로 부르는 API |
|---|---|---|---|
| 기관 포트폴리오(첫 화면) | `index.html` + `public/home.js` | 누구나 | `/api/institutions`, `/consensus` |
| 기관 상세 | `public/institution.html` + `.js` | 누구나 | `/api/institutions/{cik}/holdings`, `/changes` |
| 내 포트폴리오와 비교 | `public/overlap.html` + `.js` | 누구나 | `/api/institutions/overlap` |
| 배당 캘린더 | `public/dividends.html` + `.js` | 누구나 | `/api/public/dividends` |
| 기업분석 (페이지와 창) | `public/company.html`, `public/stock.js` | 누구나 (AI 실행은 운영자만) | `/api/public/stocks/{티커}`, `/chart`, `/analysis` |
| 나의 포트폴리오 | `portfolio.html` + `.js` + `.css` | **로그인한 운영자** | `/api/portfolio/unified`, `/api/portfolio/snapshots`(평가금액 추이와 대사), `/api/analysis`(+`/reassess`), `/api/toss/chart`, `/api/news` |
| 로그인, 404 | `public/login.html`, `public/404.html` | 누구나 | `/login` |

여러 화면이 함께 쓰는 파일도 있다. `tokens.css`에는 색, 간격, 글꼴 같은 디자인 값이 모여 있고, `site.css`와 `site.js`는 공개 화면의 공통 코드다. `analysis-view.js`와 `analysis.css`는 AI 분석 결과를 그리는 코드이고, `chart-view.js`는 캔들차트를 그린다. 마지막 두 묶음은 나의 포트폴리오와 공개 기업분석이 **같은 파일**을 쓴다. 같은 화면 조각을 두 곳에 복사해 두면 한쪽만 고치고 다른 쪽을 잊기 쉬워서, 처음부터 한 파일로 모았다.

### 1.5 데이터 — 테이블 16개

DB에는 테이블이 16개 있다. 그중 관계가 가장 분명한 것은 기관 13F 묶음이다. 기관 하나가 분기마다 13F를 내고, 13F 한 건에는 보유 종목이 여러 줄 들어 있다.

<!-- diagram: chain13f | 기관 → 13F 제출 → 보유 줄은 부모와 자식이고, 티커 표는 CUSIP으로 찾아볼 뿐이다(점선). -->

```text
institution        기관
  │  1 : N         분기마다 13F 를 낸다
  ▼
filing_13f         13F 제출 한 건 (분기 · 제출일 · 합계)
  │  1 : N         보유 줄
  ▼
holding_13f        종목 하나 (CUSIP · 주식 수 · 금액)
  │  N : 1         CUSIP 으로 찾음
  ▼
cusip_ticker       CUSIP → 티커 (못 찾은 것도 남김)
```

전체 테이블과, 각 테이블을 누가 채우는지는 다음과 같다.

| 테이블 | 담는 것 | 누가 채우나 |
|---|---|---|
| `institution` | 따라가는 기관 10곳(꺼 둔 곳 포함) | 마이그레이션(V2, V6) |
| `filing_13f` | 기관이 분기마다 낸 13F 한 건 | 매일 07:00 배치(SEC) |
| `holding_13f` | 그 제출의 보유 줄(종목, 주식 수, 금액) | 같은 배치 |
| `cusip_ticker` | CUSIP을 티커로 바꾼 결과(못 찾은 것도 남김) | 같은 배치(OpenFIGI) |
| `company_analysis` | AI 기업분석 결과(JSON), 평단가가 들어갔는지 여부, 조사와 판정 시각 | "실행"이나 "판단만 새로"를 눌렀을 때 |
| `dividend_event` / `dividend_fetch` | 배당결정 공시 / 종목별 마지막 조회일(하루 한 번 제한용) | 배당 화면을 조회할 때(DART) |
| `oauth_token` | 증권사 토큰(**AES-256-GCM 암호문**) | 토큰을 발급받을 때 |
| `manual_holding` | 직접 입력한 보유 종목 | 나의 포트폴리오 화면 |
| `symbol_master` | 토스 전체 종목 목록(이름 검색용) | 필요할 때 토스에서 |
| `dart_corp_code` / `sec_cik` | 종목코드를 DART 고유번호로, 티커를 SEC CIK로 바꾸는 표 | 처음 쓸 때 공시처에서 받아 둠 |
| `stored_financials` | 공시 재무(매출, 이익, EPS, BPS 등)를 **주가 없이** 저장한 JSON. 결산일 기준 과거 PER·PBR도 들어 있다. | 매일 06:00 배치가 보유·분석 종목을 받는다. 그 밖의 종목은 처음 볼 때와 하루가 지난 뒤 DART·SEC에서 다시 받고, 실패하면 저장본을 쓴다. |
| `portfolio_snapshot` / `_item` | 장 마감 뒤 하루 한 벌: 합계 한 줄과 종목별 내역 | 평일 16:10 배치(실패하면 18시·20시에 재시도) |
| `reconciliation_result` | 그날 증권사 합계와 앱 합계의 비교(대사) 결과 | 같은 배치 |

스키마는 **Flyway 파일(V1~V10)로만** 바꾼다. 엔티티와 실제 DB 모양이 다르면 앱이 아예 뜨지 않도록 설정해 두었다(`ddl-auto: validate`). 테이블 사이의 전체 관계도(ERD)와 설계 이유는 [3장](#3-데이터베이스--mysqljpaflyway)에서 자세히 본다.

### 1.6 바깥 시스템

이 앱은 혼자서 하는 일이 거의 없다. 잔고와 시세, 재무제표, 기관 보유, AI 분석까지 대부분의 데이터를 바깥 시스템에서 받아 온다. 그래서 바깥 시스템 하나가 막히면 무엇이 빠지는지를 미리 정해 두는 것이 중요하다.

| 시스템 | 무엇에 쓰나 | 인증 방식 | 막히면 |
|---|---|---|---|
| 토스증권 Open API | 보유, 현재가, 일봉 차트 | OAuth(키와 시크릿), **허용 IP 하나만 등록** | 시세와 차트가 빈다. 재무와 기관 칸은 그대로 보인다. |
| 나무증권 API | 보유 | OAuth | 나무증권 보유만 빠진다. |
| DART | 국내 재무, 공시, 배당 | API 키(주소에 붙임) | 국내 재무가 빈다. |
| SEC EDGAR | 미국 재무(XBRL), 13F | User-Agent 필수, 초당 10건 | 미국 재무와 13F 갱신이 멈춘다. |
| OpenFIGI | CUSIP을 티커로 바꾸기 | 키는 선택(없으면 분당 250개) | 티커 없이 회사 이름으로 보이고, 다음 배치가 이어서 채운다. |
| Anthropic(Claude) | AI 기업분석, 스크린샷 읽기, 뉴스 요약 | API 키, **유료** | 분석 실패가 표시되고 나머지는 그대로다. |
| Google News RSS | 종목 뉴스 | 없음 | 뉴스 칸만 빈다. |
| 텔레그램 | 새 13F 알림 | 봇 토큰 | 알림만 가지 않는다. |

"막히면" 칸을 보면 이 앱의 원칙이 보인다. **바깥 하나가 죽어도 화면 전체가 죽지 않게 한다**는 것이다. 이런 설계를 fail-soft라고 부른다. 바깥 호출이 몇 번 있었고 얼마나 실패했는지는 Grafana의 "외부 API" 칸에서 호스트별로 볼 수 있다. 바깥 API를 다루는 장치는 [4장](#4-외부-api-연동)에서 자세히 본다.

### 1.7 캐시·배치·비동기

느린 일을 빠르게 보이게 하는 방법은 크게 세 가지다. 결과를 잠시 들고 있거나(캐시), 사용자가 오기 전에 미리 해 두거나(배치, 예열), 오래 걸리는 일을 뒤로 넘기고 바로 답하는 것(비동기)이다. 이 앱은 세 가지를 모두 쓴다.

| 종류 | 무엇을 | 어디서 | 왜 |
|---|---|---|---|
| 메모리 캐시 6시간 | 공개 기업분석(재무, 문장, 기관 보유) | `StockBriefService` | 방문자가 올 때마다 SEC와 토스를 부르지 않으려고 |
| 메모리 캐시 10분 | 공개 차트 | `PublicChartController` | 토스의 호출 한도(429)를 넘지 않으려고 |
| 메모리 캐시 하루 | 뉴스 요약 | `NewsBriefService` | 유료 호출을 종목당 하루 한 번으로 줄이려고 |
| 메모리 + DB(암호화) | 증권사 토큰 | `TossAuthService`, `NamuhAuthService` | 앱을 다시 띄워도 토큰을 새로 발급받지 않으려고 |
| DB, 하루 한 번 | 배당 공시 조회 | `dividend_fetch` | DART의 하루 2만 건 한도를 지키려고 |
| DB, 영구 | CUSIP → 티커 | `cusip_ticker` | 한 번 찾은 것은 다시 묻지 않으려고 |
| DB, 하루 | 공시 재무(주가를 뺀 부분) | `stored_financials` (`FilingService`) | 분기에 한 번 바뀌는 값을 매번 다시 받지 않으려고. PER·PBR은 읽을 때 지금 주가로 계산한다. |
| 메모리 캐시, 시간 만료 없음 | 13F 집계(같이 산 종목, 보유, 변화) | `QueryCache` | 데이터가 바뀌는 때(배치)를 정확히 알기 때문에 그때 통째로 비운다. 64개까지 들고 LRU로 버린다. |
| 예열 | 위 13F 캐시 | `InstitutionCacheWarmer` | 앱이 뜬 직후나 배치 직후의 첫 방문자가 1~4초를 기다리지 않게 하려고. 비우기(순서 0)가 끝난 뒤 채우기(순서 100)가 돈다. |
| 스케줄, 매일 06:00 | 공시 재무 미리 받기 | `FilingPrefetchService` | 낮에 분석 버튼을 눌렀을 때 공시처를 부르지 않게 하려고 |
| 스케줄, 매일 07:00 | 13F 받기와 티커 변환 | `ThirteenFSyncService` | 공개 자료가 하루 단위로 바뀌기 때문에 |
| 스케줄, 평일 16:10 (18시·20시 재시도) | 장 마감 스냅샷과 대사 | `PortfolioSnapshotService` | 평가금액 이력을 남기고, 앱 합계가 증권사 합계와 맞는지 매일 확인하려고 |
| 이벤트 | 새 13F → 텔레그램 | `FilingAlertService` (`@EventListener`) | 받기와 알림을 떼어 놓아 한쪽이 실패해도 다른 쪽이 돌게 하려고 |
| 비동기, 스레드 하나 | AI 기업분석(2~5분) | `CompanyAnalysisService` | 요청을 몇 분씩 붙잡지 않고 화면이 상태를 다시 묻게 하려고 |
| 서버 cron, 매일 04:00 | DB 백업 | `deploy/backup.sh` | 서버가 망가져도 데이터를 되살리려고 |

표가 길지만 질문은 하나다. **"이 값은 얼마나 자주 바뀌고, 바뀌는 때를 아는가?"** 분기에 한 번 바뀌는 재무는 하루 동안 들고 있어도 되고, 배치가 끝나는 순간에만 바뀌는 13F 집계는 시간 대신 배치 이벤트로 비우면 된다. 캐시를 고를 때마다 이 질문부터 던지면 된다.

### 1.8 보안 경계 — 누가 무엇을 볼 수 있나

이 앱에는 누구나 볼 수 있는 공개 화면과 운영자만 볼 수 있는 내 화면이 한 앱 안에 섞여 있다. 그래서 "어디까지가 공개인가"를 주소 단위로 분명히 나눠 두었다.

<!-- diagram: zones | 주소마다 들어갈 수 있는 사람이 다르다. ③은 인터넷에 아예 열리지 않고 SSH 터널로만 본다. -->

```text
① 공개 (로그인 없음)
   /  ·  /public/**
   /api/public/**  ·  GET /api/institutions/**

② 로그인한 나만
   /portfolio.html
   나머지 /api/**  (돈이 드는 호출 포함)

③ 서버 안 (127.0.0.1) 만
   관리 8081  ·  Prometheus 9090  ·  Grafana 3000   → SSH 터널로만 본다
```

각 경계는 아래 장치들이 지킨다.

| 경계 | 지키는 장치 |
|---|---|
| 공개 ↔ 로그인 | `SecurityConfig`의 주소 규칙이 지키고, 그 규칙은 테스트로 고정되어 있다. 세션 쿠키에는 `HttpOnly`, `SameSite=Strict`, `Secure`를 걸고, 쓰기 요청에는 CSRF 토큰을 요구한다. |
| 공개 화면 남용 | IP당 분당 120번(배당은 15번)까지만 받고, 넘으면 429로 답한다. |
| 공개 화면에 내 정보가 새는 것 | 평단가가 들어간 AI 분석은 공개 주소에서 "없음"으로 답한다. 바깥 API의 오류 문구에는 서버 IP가 들어 있어서 일반 문구로 바꿔 내보낸다. |
| 브라우저 | CSP로 인라인 스크립트를 금지하고, 바깥에서 온 글자는 `esc()`를 거쳐 넣는다. |
| 서버 밖 ↔ 서버 안 | 80번과 443번만 공개하고, 관리 주소와 관측 도구는 127.0.0.1에만 열어 SSH 터널로 본다. |
| 지표에 비밀이 실리는 것 | 바깥 호출 지표의 주소 태그에서 쿼리와 키처럼 보이는 조각을 지운다. |

각 장치의 원리는 [5장](#5-보안--spring-security와-웹-보안)에서 다룬다.

### 1.9 요청이 지나가는 길

이제 실제 요청 네 가지를 처음부터 끝까지 따라가 본다. 앞에서 본 부품들이 어떤 순서로 맞물리는지 보이게 된다.

**① 공개 기업분석 화면에서 `MSFT`를 연다**

가장 흔한 요청이다. 로그인 없이 누구나 보내는 GET 요청이 어떤 필터를 거치고, 캐시가 어디에서 일하는지 보자.

> **직접 해보기** — 브라우저 개발자 도구의 Network 탭을 연 채로 기업분석 화면에서 종목 하나를 눌러 보자. ①의 요청 세 개(stocks, chart, analysis)가 보일 것이다. 같은 종목을 다시 열면 stocks 응답이 훨씬 빨라지는데, 6시간 캐시가 일하고 있기 때문이다.

**지도에서 보면.** 1장에서 요청이 Caddy를 지나 앱으로 들어오는 것까지 봤다. 2장은 그 앱의 안쪽, 요청을 받는 web 층과 업무 규칙을 처리하는 service 층으로 들어간다. 여기서 정한 방식(DI, 설정, 비동기, 배치, 프록시)은 아래의 domain(3장)과 external(4장)이 모두 그대로 따른다.

> **이 장에서 배울 것** — 스프링이 객체를 만들어 꽂아 주는 방식(DI), 설정값을 코드 밖에서 넣는 방법, 오래 걸리는 일을 뒤로 넘기는 방법(비동기), 정해진 시각에 도는 일(배치), 그리고 스프링이 몰래 끼워 넣는 대리 객체(프록시)를 본다.

### 2.1 계층 구조와 의존성 주입(DI)

**무엇인가.** 스프링 애플리케이션은 보통 코드를 역할별 층으로 나눈다. 컨트롤러(`Controller`)가 HTTP 요청을 받고, 서비스(`Service`)가 업무 규칙을 처리하고, 리포지토리(`Repository`)가 DB를, 클라이언트(`Client`)가 바깥 API를 맡는다. 그리고 각 층의 객체는 내가 직접 만들지 않는다. 스프링이 만들어서 생성자로 꽂아 준다. 이것을 의존성 주입(DI)이라고 한다.

**기초부터.** 스프링 없이 자바만 쓴다면 필요한 객체를 직접 만들어야 한다.

```java
// 스프링 없이: 내가 만들고, 내가 고른다
class StockBriefService {
    private final FilingService filing = new FilingService(new DartFinancialService(...), ...);
}
```

이 코드에는 문제가 두 가지 있다. 첫째, `StockBriefService`가 `FilingService`를 만들려면 `FilingService`에게 무엇이 필요한지까지 전부 알아야 한다. `FilingService`가 받는 인자가 하나 늘면 이 코드도 고쳐야 한다. 둘째, 테스트할 때 `FilingService` 자리에 가짜를 끼울 방법이 없다. 테스트를 돌릴 때마다 진짜 DART 서버를 부르게 된다.

DI는 "만드는 일"을 스프링에게 넘기고, 내 클래스는 필요한 것을 **생성자로 받기만** 한다.

```java
@Service                                   // "이 클래스는 스프링이 하나 만들어 들고 있어라(빈)"
class StockBriefService {
    private final FilingService filing;
    StockBriefService(FilingService filing) {  // 스프링이 들고 있던 FilingService 를 꽂아 준다
        this.filing = filing;
    }
}
```

이제 `StockBriefService`는 `FilingService`가 어떻게 만들어지는지 몰라도 된다. 스프링은 앱을 띄울 때 `@Service`가 붙은 클래스를 찾아 하나씩 만들고(이렇게 만든 객체를 빈이라고 한다), 생성자가 요구하는 빈을 찾아 넣어 준다. 실제 생성자는 받는 것이 더 많은데, 여기서는 모양만 줄였다.

테스트에서는 스프링 없이 `new StockBriefService(mock(FilingService.class), ...)`처럼 가짜를 직접 꽂으면 된다. 이 저장소의 테스트 대부분이 이렇게 짜여 있다. `FilingPrefetchServiceTest`를 열어 보면 바로 확인할 수 있다.

**이 프로젝트에서는.** 패키지가 곧 층이다. `web`이 컨트롤러, `service`가 서비스이고, `domain`, `external`, `brokerage`가 그 아래에서 데이터를 가져온다. 모든 의존성은 생성자로 받는다. 필드에 `@Autowired`를 붙여 주입하는 방식은 쓰지 않는다.

인터페이스를 경계로 쓰는 예도 있다. `BrokerageClient`는 "보유 종목을 가져올 수 있는 증권사"를 뜻하는 인터페이스이고, 토스, 나무, 직접 입력이 각각 이것을 구현한다. 스프링은 같은 인터페이스를 구현한 빈들을 `List<BrokerageClient>`로 한꺼번에 넣어 줄 수 있다. 그래서 증권사를 하나 더 붙이려면 새 클래스에 `@Component`만 달면 되고, 합산 코드는 한 줄도 고치지 않는다.

이 인터페이스에는 **주문 메서드가 없다.** 메서드가 없으니 실수로라도 주문을 낼 방법이 없다. 인터페이스 설계로 "할 수 없는 일"을 만든 안전장치다([결정기록 001](결정기록.md#001-주문-api를-만들지-않는다)).

**실무에서는.** 생성자 주입은 사실상 표준이다. 필드를 `final`로 둘 수 있어서 한 번 받은 의존성이 바뀌지 않고, 테스트에서 `new`로 바로 만들 수 있기 때문이다. 인터페이스로 경계를 두면 구현을 바꾸기 쉽고(증권사 추가), 테스트에서 가짜를 끼우기도 쉽다.

**공부할 것.** IoC와 DI의 개념, 빈의 생명주기(언제 만들어지고 언제 사라지는지), `@Component`, `@Service`, `@Repository`의 차이, 순환 의존(A가 B를, B가 A를 필요로 하는 상황)이 왜 문제인지를 공부해 보자.

### 2.2 설정 관리

**무엇인가.** 같은 코드를 내 PC와 서버에서 함께 쓰려면, 환경마다 달라지는 값(DB 주소, API 키, 포트)을 코드 밖으로 빼야 한다. 특히 API 키 같은 비밀값은 코드에 절대 적으면 안 된다. 저장소가 공개되어 있으니 적는 순간 모두에게 보인다.

**이 프로젝트에서는.** 값은 세 단계를 거쳐 코드에 들어온다.

1. 비밀값은 저장소 밖의 `.env` 파일에 적는다. 이 파일은 `.gitignore`에 있어서 커밋되지 않는다.
2. 앱이 뜨기 직전에 `EnvFileLoader`가 `.env`를 읽어 시스템 프로퍼티로 등록한다.
3. `application.yml`의 `${TOSS_CLIENT_ID:}` 같은 자리가 그 값을 읽는다. 서버에서는 `.env` 대신 OS 환경변수로 넣어도 같은 자리로 들어간다.

`application.yml`에는 `${MANAGEMENT_PORT:8081}`처럼 콜론 뒤에 기본값을 둘 수 있다. 다만 우리 로더는 비어 있는 값도 그대로 등록해서, `.env`에 `MANAGEMENT_PORT=`처럼 값 없이 적어 두면 기본값이 무시되는 함정이 있었다([개발일지 전환점 20](개발일지.md)).

관련 있는 설정은 `@ConfigurationProperties`를 붙인 record 하나로 묶어서 받는다. 예를 들어 `AnthropicProperties`에는 Claude 호출에 필요한 키, 모델 이름, 출력 토큰과 웹 검색 횟수의 상한, 타임아웃이 함께 들어 있다. 설정을 여기저기서 하나씩 꺼내 쓰는 것보다 어떤 설정이 있는지 한눈에 보인다.

**실무에서는.** "코드는 하나, 설정은 환경마다"는 12-Factor App이라는 유명한 원칙의 한 항목이다. 비밀값은 저장소에 넣지 않고 환경변수, Vault, 클라우드의 Secret Manager 같은 곳에서 주입한다. `.env` 파일은 `.gitignore`로, 도커 이미지에는 `.dockerignore`로 막아서 어디로도 새지 않게 한다.

**공부할 것.** Spring Profile(`dev`, `prod`처럼 환경별로 설정을 나누는 기능), 설정의 우선순위(환경변수가 yml보다 앞선다), 12-Factor App의 Config 항목을 읽어 보자.

### 2.3 비동기 작업과 폴링

**무엇인가.** HTTP 요청은 보통 몇백 밀리초 안에 답하는 것을 전제로 한다. 그런데 AI 기업분석은 Claude가 웹을 검색하며 글을 쓰느라 2~5분이 걸린다. 그동안 요청을 열어 두면 브라우저, 프록시, 네트워크 중 어디선가 연결이 끊기기 쉽고, 끊기면 사용자는 결과를 받지 못한다. 그래서 "일을 맡기는 요청"과 "결과를 받는 요청"을 나눈다.

**이 프로젝트에서는.** `CompanyAnalysisService.start()`가 이 흐름을 맡는다.

1. `POST /api/analysis/{종목}`이 들어오면 서버는 분석에 필요한 사실(보유 수량, 현재가, 공시 재무)을 모은다.
2. 실제 AI 호출은 **스레드 하나짜리 작업 풀**(`Executors.newSingleThreadExecutor`)에 넘기고, 곧바로 "RUNNING"이라고 답한다.
3. 화면은 3초마다 `GET`으로 상태를 다시 물어본다. 이렇게 주기적으로 묻는 것을 폴링이라고 한다.
4. 작업 스레드가 끝나면 결과를 DB에 저장하고, 다음 폴링에서 화면이 "OK"와 함께 결과를 받는다.

작업 스레드를 하나만 둔 데는 이유가 있다. 분석은 돈이 드는 호출이라 여러 건이 동시에 돌면 비용이 그만큼 늘어난다. 같은 종목이 이미 돌고 있으면 새로 시작하지 않고, "RUNNING"인 채로 15분이 넘도록 끝나지 않으면 서버가 도중에 죽었던 것으로 보고 다시 시작할 수 있게 했다.

**실무에서는.** 오래 걸리는 작업은 "접수 → 처리 → 결과 조회"로 나누는 것이 기본 모양이다. 규모가 크면 접수한 작업을 메시지 큐(Kafka, RabbitMQ, SQS)에 넣고 별도의 워커 서버가 꺼내 처리한다. 폴링 대신 서버가 끝났다고 알려 주는 방식(WebSocket, SSE)을 쓰기도 한다.

**공부할 것.** `ExecutorService`와 `@Async`, 스레드 풀 크기를 정하는 기준, 작업을 두 번 실행해도 안전하게 만드는 방법(멱등성), 메시지 큐의 기본 개념을 공부해 보자.

### 2.4 스케줄 배치

**무엇인가.** 배치는 사람이 누르지 않아도 정해진 때에 한꺼번에 처리하는 일이다. 스프링에서는 메서드에 `@Scheduled(cron = "...", zone = "Asia/Seoul")`을 붙이면 그 시각마다 실행된다. 이 앱에는 배치가 세 개 있고, 각각 배치를 짤 때 생각해야 하는 점을 하나씩 보여 준다.

**① 13F 받기 (매일 07:00) — 멱등하게 짜기.** `ThirteenFSyncService`는 매일 아침 SEC에서 기관들의 새 공시를 받는다. 이미 받은 공시 번호는 건너뛰기 때문에 몇 번을 돌려도 결과가 같다. 이런 성질을 멱등이라고 한다. 멱등하게 짜 두면 배치가 실패했을 때 그냥 다시 돌리면 되고, 앱이 며칠 꺼져 있었어도 다음에 켰을 때 밀린 만큼만 따라잡는다.

새 공시를 받으면 배치는 `ApplicationEvent`를 발행하기만 한다. 텔레그램 알림은 이벤트를 듣는 쪽(`FilingAlertService`)이 따로 보낸다. 이렇게 떼어 두면 텔레그램이 죽어도 공시 받기는 멈추지 않는다. 서로를 직접 부르지 않고 이벤트로만 이어지는 이런 구조를 "느슨한 결합"이라고 한다.

**② 공시 재무 미리 받기 (매일 06:00) — 덮어쓰기 전에 입력부터 확인하기.** `FilingPrefetchService`는 내가 가진 종목과 분석해 둔 종목의 공시 재무를 새벽에 미리 받아 `stored_financials`에 덮어쓴다. 그러면 낮에 분석 버튼을 눌렀을 때 느린 DART와 SEC를 부르지 않고 DB만 읽으면 된다. 사용자가 오기 전에 한가한 시간을 이용해 미리 계산해 둔다는 점에서 캐시 예열과 같은 생각이다. 종목이 키라서 몇 번을 돌려도 종목마다 한 벌만 남는다.

이 배치에서 가장 신경 쓴 부분은 **멀쩡한 데이터를 망가뜨리지 않는 것**이다. 주당 지표(EPS, BPS)를 계산하려면 발행주식수가 필요한데, 주식수는 토스에서 받는다. 토스가 주식수를 주지 않았는데 그대로 재무를 받아 저장하면, 주당 지표가 빈 재무가 어제까지 멀쩡하던 저장본을 덮어쓴다. 그래서 주식수를 못 받은 종목은 아예 건너뛴다. 또 토스 자체가 막혀 있으면 남은 종목도 모두 같은 이유로 실패할 것이므로, 첫 종목에서 바로 멈추고 실패로 기록한다. 손으로 돌릴 때는 `POST /api/financials/prefetch`를 부르고, 결과는 지표 `filing_prefetch_runs_total{outcome}`으로 남는다.

**③ 장 마감 스냅샷과 대사 (평일 16:10) — 다시 만들 수 없는 데이터 다루기.** `PortfolioSnapshotService`는 이 프로젝트에서 가장 "증권사 배치"다운 코드다. 흐름은 다음과 같다.

<!-- diagram: snapshot | 16:10에 돌고, 실패한 날은 18:10·20:10에 다시 시도한다. 성공한 날의 재시도 회차는 첫 단계에서 끝난다. -->

```text
16:10 ─▶ 오늘 것 있나? ── 있음(재시도 회차) ──▶ 건너뜀
            │ 없음

        증권사마다 statement() ── 하나라도 실패 ──▶ 저장 안 함 (빈 날 > 틀린 날)

```

이 배치는 세 가지 판단 위에 서 있다.

먼저, **멱등하다.** 날짜가 키라서 몇 번을 돌려도 그날의 기록은 한 벌뿐이다. 같은 날 다시 돌리면 합계 줄은 고쳐 쓰고(upsert), 종목 줄과 대사 줄은 지우고 새로 넣는다. 이 작업 전체를 한 트랜잭션으로 묶어서, 중간에 실패하면 지우기 전 상태로 돌아간다. 덕분에 재시도와 수동 실행이 서로를 망가뜨리지 않는다.

다음으로, **다시 만들 수 없다는 한계를 인정한다.** 증권사는 "지금" 잔고만 알려 준다. 어제 잔고를 오늘 물어볼 방법이 없으니, 그날 놓친 스냅샷은 영영 만들 수 없다. 그래서 재시도를 나중으로 미루지 않고 그날 시간표(18:10, 20:10)에 넣어 두었다.

마지막으로, **매일 대사를 한다.** 화면에 보이는 합계는 앱이 종목별 금액을 더한 값이다. 그런데 증권사도 같은 응답의 맨 위에 계좌 합계를 알려 준다. 둘을 매일 비교하면, 수량이 0이라 걸러졌거나 모르는 통화라서 앱이 조용히 빠뜨린 종목이 드러난다.

구현하면서 겪은 함정도 두 가지 있다. 하나는 그날 줄을 지우고 바로 같은 키로 다시 넣는 부분이다. JPA의 파생 삭제(`deleteBy...`)는 줄을 하나씩 읽어서 지우기 때문에, 바로 이어서 같은 키를 넣으면 아직 반영되지 않은 삭제와 부딪혀 유니크 키 오류가 날 수 있다. 그래서 JPQL `delete` 한 번(`@Modifying`)으로 즉시 지우게 했다. 다른 하나는 생성자다. 테스트에서 시계를 바꿔 끼우려고 생성자를 둘(운영용, 테스트용) 두었더니, 스프링이 어느 쪽을 써야 할지 몰라 앱이 뜨지 않았다. 단위 테스트는 모두 통과했고, jar를 실제로 띄워 보고서야 알았다. 운영용 생성자에 `@Autowired`를 붙여 스프링에게 알려 주는 것으로 고쳤다.

**실무에서는.** 야간 배치, 정산, 대사는 금융 IT의 전형적인 업무다. 증권사는 자체 원장의 숫자를 예탁원, 거래소, 은행의 숫자와 매일 맞춰 보고, 안 맞는 건(불일치 내역)은 다음 날 아침까지 해소한다. 서버가 여러 대라면 같은 배치가 동시에 두 번 돌지 않게 막는 장치(ShedLock, Quartz 클러스터)가 필요하고, 처리할 양이 많으면 Spring Batch를 쓴다.

**공부할 것.** cron 표현식, 멱등성, Spring Batch의 Job, Step, Chunk 개념, 분산 락을 공부해 보자.

### 2.5 예외 처리와 API 응답

**무엇인가.** 코드 곳곳에서 예외가 날 수 있다. 예외를 컨트롤러마다 따로 처리하면 응답 모양이 제각각이 되고, 실수로 내부 정보를 응답에 실어 보내기 쉽다. 그래서 예외를 응답으로 바꾸는 일을 한 곳에 모은다.

**이 프로젝트에서는.** `GlobalExceptionHandler`(`@RestControllerAdvice`)가 모든 예외를 `{ "error": "사람이 읽을 한국어 문장" }` 한 가지 모양으로 바꾼다. 바깥 API가 실패하면 502를, 요청이 잘못되었으면 400을, 없는 주소면 404를 돌려준다. 토스가 403을 주면 지금 이 컴퓨터의 공인 IP까지 문장에 넣어서, 무엇을 등록해야 하는지 바로 알 수 있게 했다.

예상하지 못한 예외(500)는 **일반 문구만** 내보낸다. 스택 트레이스나 SQL 문장이 응답에 실리면 공격자에게 내부 구조를 알려 주는 지도가 되기 때문이다. 자세한 내용은 로그에만 남긴다. 브라우저가 없는 주소를 열면 HTML로 된 안내 화면을, API가 없는 주소를 부르면 JSON 404를 돌려준다.

**실무에서는.** 팀마다 에러 응답 형식을 표준으로 정해 둔다. 보통 에러 코드, 사람이 읽을 메시지, 추적용 요청 ID를 담는다. 원칙은 "로그에는 자세히, 응답에는 간단히"다.

### 2.6 API 문서 자동화

**무엇인가.** API 주소와 파라미터를 문서에 손으로 적어 두면, 코드가 바뀔 때마다 문서가 늦게 따라가다가 결국 어긋난다. 그래서 문서를 코드에서 자동으로 만든다.

**이 프로젝트에서는.** springdoc 라이브러리가 컨트롤러를 읽어 Swagger UI를 만든다. 앱을 띄우고 `/swagger-ui.html`을 열면 모든 주소와 파라미터, 응답 모양을 보고 직접 호출해 볼 수도 있다. 그래서 다른 문서에는 주소 목록을 적지 않고, 코드로는 표현할 수 없는 것(비용, 숫자의 기준)만 적는다. 운영 서버에서는 공격자에게 지도를 주지 않으려고 `SWAGGER_ENABLED=false`로 끈다.

**실무에서는.** OpenAPI 스펙(Swagger가 만드는 기계용 문서)이 프론트엔드나 외부 협력사와의 계약서 역할을 한다. 스펙에서 클라이언트 코드를 자동으로 만들어 쓰기도 한다.

### 2.7 프록시 — 스프링이 몰래 끼워 넣는 대리 객체

**무엇인가.** 프록시는 진짜 객체를 감싸고 대신 호출을 받는 객체다. 부르는 쪽은 진짜를 부른다고 생각하지만, 실제로는 프록시가 먼저 받아서 앞뒤에 필요한 일을 끼워 넣고 진짜에게 넘긴다. 네트워크에서 말하는 프록시(Caddy, [0.1](#01-웹과-네트워크))와 생각이 같다. 대신 받는 대상이 서버냐 객체냐만 다르다.

**기초부터.** DB에 무언가를 저장하는 메서드가 있다고 해 보자. 여러 줄을 저장하다가 중간에 실패하면 앞에서 저장한 줄까지 되돌려야 한다. 이걸 메서드마다 직접 짜면 이런 코드가 반복된다.

```java
void save(Result r) {
    tx.begin();            // 트랜잭션 열기
    try {
        ...                // 실제로 하고 싶은 일
        tx.commit();       // 성공하면 확정
    } catch (Exception e) {
        tx.rollback();     // 실패하면 되돌리기
        throw e;
    }
}
```

정작 하고 싶은 일은 가운데 한 줄인데, 앞뒤의 반복 코드가 더 길다. 스프링은 이 반복을 대신 해 준다. 메서드에 `@Transactional`만 붙이면, 스프링이 그 객체를 감싼 프록시를 만들고 앞뒤 코드를 프록시에 넣어 둔다.

<!-- diagram: proxy | 밖에서 부르면 프록시가 트랜잭션을 열지만, 같은 클래스 안에서 this로 부르면 프록시를 거치지 않는다. -->

```text
부르는 쪽 ──▶ 프록시 (스프링이 만든 대리 객체)
                │ ① 트랜잭션 열기
                │ ② 진짜 객체의 save() 를 부름 ──▶ 진짜 객체
                │ ③ 예외가 없으면 커밋, 있으면 롤백
                ▼
              부르는 쪽에 결과를 돌려줌
```

`@Transactional`뿐 아니라 `@Cacheable`, `@Async`, Spring Security의 메서드 보안도 모두 이 방식으로 동작한다. 트랜잭션처럼 여러 곳에 공통으로 필요한 일을 업무 코드 밖으로 빼내는 기법을 AOP(관점 지향 프로그래밍)라고 부른다.

**함정 — 같은 클래스 안에서 부르면 동작하지 않는다.** 프록시는 바깥에서 객체를 부를 때만 끼어든다. 같은 클래스 안에서 자기 메서드를 부르면 프록시를 거치지 않는다.

```java
@Service
class AnalysisService {
    void runInBackground() {
        this.save(result);        // ✗ this 는 프록시가 아니라 진짜 → 트랜잭션이 안 열림
    }
    @Transactional
    void save(Result r) { ... }
}
```

`this`는 프록시가 아니라 진짜 객체를 가리키기 때문에, `save()`에 `@Transactional`이 붙어 있어도 트랜잭션이 열리지 않는다. 에러도 나지 않아서 알아채기 어렵다. 이 저장소는 이 함정을 피하려고 **저장만 맡는 빈을 따로** 둔다. `CompanyAnalysisStore`와 `PortfolioSnapshotStore`가 그 예다. 서비스가 이 빈을 주입받아 부르면 항상 바깥에서 부르는 셈이 되어 반드시 프록시를 거친다.

**이 프로젝트의 "끼워 넣기" 세 가지.** 프록시와 비슷하게 흐름 중간에 끼어드는 장치가 세 군데 있다. 생각은 같고 끼어드는 자리만 다르다.

| 장치 | 어디에 끼어드나 | 이 저장소의 예 |
|---|---|---|
| 서블릿 필터 | 들어오는 HTTP 요청의 앞뒤 | `RequestIdFilter`(요청 번호), `PublicRateLimitFilter`(호출 한도), Spring Security |
| 스프링 프록시(AOP) | 빈의 메서드 호출 앞뒤 | `@Transactional`이 붙은 저장 빈 |
| RestClient 인터셉터 | **나가는** HTTP 요청의 앞뒤 | `ResilientHttpInterceptor`(재시도, 서킷 브레이커) |

**실무에서는.** "트랜잭션이 안 먹어요"라는 문제의 가장 흔한 원인이 위의 함정이고, 면접에서도 자주 묻는다. 로그 남기기, 권한 검사, 성능 측정처럼 여러 곳에 공통으로 필요한 일은 업무 코드에 섞지 않고 프록시나 필터로 빼는 것이 실무의 표준이다.

**공부할 것.** JDK 동적 프록시와 CGLIB의 차이, `@Transactional`의 전파(propagation) 옵션과 롤백 규칙(체크 예외는 기본으로 롤백되지 않는다), 필터와 인터셉터와 AOP의 차이를 공부해 보자.

## 3. 데이터베이스 — MySQL·JPA·Flyway

<!-- diagram: map@domain,mysql | 3장은 service 아래의 domain 층과 MySQL을 본다. -->

**지도에서 보면.** 2장의 서비스가 저장하고 읽는 데이터가 어디로 가는지 따라 내려온다. domain 층의 엔티티와 리포지토리가 MySQL의 테이블과 1:1로 이어지고, 그 테이블 모양은 Flyway 파일로만 바뀐다. 여기서 "원본이 여기뿐인 데이터"로 분류한 테이블이 11장 백업의 대상이 된다.

> **이 장에서 배울 것** — 테이블이 무엇을 담고 서로 어떻게 이어지는지(ERD), 키를 어떤 기준으로 골랐는지, 자바 코드에서 DB를 어떻게 다루는지(JPA), 그리고 스키마를 파일로 안전하게 바꾸는 방법(Flyway)을 본다.

DB는 MySQL 8.4 하나이고, 스키마 이름은 `portfolio`다. 테이블은 16개이며, Flyway가 마이그레이션 이력을 적어 두는 `flyway_schema_history` 테이블이 하나 더 있다.

이 장은 세 부분으로 나뉜다. 먼저 무엇이 저장되는지 본다(3.1~3.2). 다음으로 왜 그렇게 설계했는지 본다(3.3~3.6). 마지막으로 코드에서 DB를 어떻게 다루고 바꾸는지 본다(3.7~3.8).

### 3.1 ERD — 테이블 사이의 관계

ERD(Entity Relationship Diagram)는 테이블과 테이블 사이의 관계를 그린 그림이다. 이 노트의 ERD는 다음 표기를 쓴다.

| 표기 | 뜻 |
|---|---|
| `PK` | 기본 키 |
| `UK` | 유니크 키 |
| `IX` | 일반 인덱스 |
| 실선 | 부모가 없으면 자식이 뜻을 잃는 관계(1이 위, N이 아래) |
| 점선 | 같은 값으로 찾아볼 뿐 따로 살아도 되는 관계 |

이 DB에는 FK 제약이 하나도 없다. 관계는 코드가 지킨다(3.4).

실선과 점선의 차이가 중요하다. 실선으로 이어진 테이블은 부모가 없으면 자식이 뜻을 잃는다. 13F 제출이 없는데 그 제출의 보유 줄만 남아 있으면 아무 의미가 없는 것과 같다. 점선으로 이어진 테이블은 같은 값(예: 종목코드)으로 서로를 찾아볼 뿐, 한쪽이 없어도 다른 쪽은 멀쩡히 살아 있을 수 있다.

16개 테이블은 성격에 따라 네 묶음으로 나뉜다.

**① 기관 13F (매일 배치가 채움) — 부모와 자식이 분명한 유일한 묶음**

기관 하나가 분기마다 13F를 한 건씩 내고, 13F 한 건에는 보유 종목이 수백에서 수천 줄 들어 있다. 보유 줄에는 종목이 CUSIP이라는 미국 증권 번호로만 적혀 있어서, 티커로 바꾼 결과를 `cusip_ticker`에 따로 둔다.

<!-- diagram: erd-13f | 기관 → 13F 제출 → 보유 줄은 실선(부모·자식), 보유 줄 → 티커 표는 점선(찾아볼 뿐)이다. -->

```text

│    active          bit      │  꺼 둔 기관도 행은 남긴다
└──────────────┬──────────────┘
               │ 1
               │      cik 로 이어짐
               │ N
┌──────────────┴──────────────┐
│ filing_13f   분기 제출 한 건  │
├─────────────────────────────┤
│ PK accession_no    varchar  │  SEC 접수번호
│ UK (cik, report_period)     │  한 기관·한 분기에 한 건
│    filed_date      date     │
```

`filing_13f`의 유니크 키 `(cik, report_period)`는 "한 기관은 한 분기에 13F를 한 건만 낸다"는 업무 규칙을 DB에 새긴 것이다. `holding_13f`의 유니크 키에 `put_call`까지 들어간 이유는 3.3에서 설명한다. `cusip_ticker`에는 티커를 끝내 못 찾은 CUSIP도 `ticker`를 비운 채 남긴다. 남겨 두지 않으면 다음 배치가 같은 CUSIP을 또 물어보며 호출 한도를 낭비하기 때문이다.

**② 종목 하나를 중심으로 모이는 것들 — 종목코드(`symbol`)가 공통 열쇠**

### 3.2 테이블 한 장 요약

3.1의 그림을 표 하나로 다시 정리했다. 특히 오른쪽 두 칸(누가 채우나, 언제 지우나)을 보면 각 테이블의 생애가 보인다.

| 묶음 | 테이블 | 한 줄에 담기는 것 | 기본 키 | 누가 채우나 | 언제 지우나 |
|---|---|---|---|---|---|
| 13F | `institution` | 기관 하나 | `cik` | 마이그레이션 V2, V6 | 지우지 않고 `active`로 끈다. |
| 13F | `filing_13f` | 기관의 분기 제출 한 건 | `accession_no` | 매일 07:00 배치 | 8분기를 넘으면 지운다. |
| 13F | `holding_13f` | 그 제출의 보유 종목 한 줄 | `id` | 같은 배치 | 제출을 지울 때 같이 지운다. |
| 13F | `cusip_ticker` | CUSIP → 티커 | `cusip` | 같은 배치(OpenFIGI) | 잘못 찾은 것만 지웠다(V7). |
| 분석 | `company_analysis` | 종목당 AI 기업분석 하나(JSON) | `id`, 유니크 `symbol` | "실행", "판단만 새로" 버튼 | 덮어쓴다. |
| 재무 | `stored_financials` | 종목당 공시 재무(JSON, **주가 없이**) | `symbol` | 매일 06:00 배치, 처음 볼 때, 하루가 지난 뒤 | 덮어쓴다. |
| 내 것 | `manual_holding` | 직접 입력한 보유 한 줄 | `id`, 유니크 `(owner_key, symbol)` | 나의 포트폴리오 화면 | 화면에서 삭제한다. |
| 내 것 | `oauth_token` | 증권사 접근 토큰(AES-256-GCM 암호문) | `id`, 유니크 `(provider, owner_key)` | 토큰을 발급받을 때 | 덮어쓴다. |
| 참조 | `symbol_master` | 토스 종목 하나 | `id` | 필요할 때 토스에서 | 다시 받으면 통째로 바꾼다. |
| 참조 | `dart_corp_code` | 국내 종목코드 → DART 고유번호 | `stock_code` | 처음 쓸 때 | 다시 받으면 통째로 바꾼다. |
| 참조 | `sec_cik` | 미국 티커 → SEC CIK | `ticker` | 처음 쓸 때 | 다시 받으면 통째로 바꾼다. |
| 배당 | `dividend_event` | 배당결정 공시 한 건 | `rcept_no` | 배당 화면을 조회할 때(DART) | 지우지 않는다. |
| 배당 | `dividend_fetch` | 종목별 마지막 DART 조회 시각 | `stock_code` | 같은 때 | 덮어쓴다. |
| 이력 | `portfolio_snapshot` | 하루 한 줄 합계 | `snapshot_date` | 평일 16:10 배치 | 지우지 않고, 같은 날은 덮어쓴다. |
| 이력 | `portfolio_snapshot_item` | 그날 종목별 내역 | `id`, 유니크 `(snapshot_date, symbol)` | 같은 배치 | 같은 날 다시 찍으면 지우고 새로 넣는다. |
| 이력 | `reconciliation_result` | 그날 대사 한 줄 | `id`, 유니크 `(snapshot_date, broker, scope)` | 같은 배치 | 같은 날 다시 찍으면 지우고 새로 넣는다. |

이 테이블들을 **"원본이 어디에 있는가"**로 다시 나눠 보면 설계가 왜 이런지 보인다.

왼쪽 테이블들은 원본이 바깥(SEC, DART, 토스)에 있다. 지워도 다음 배치나 조회가 다시 채우므로 캐시처럼 다룬다. 바깥이 실패하면 저장본을 쓰고, 형식이 바뀌어 못 읽으면 버리고 다시 받는다. 오른쪽 테이블들은 원본이 이 DB에만 있다. 내가 직접 입력한 보유, 돈을 주고 만든 AI 분석, 다시는 만들 수 없는 지난 날의 스냅샷이 여기에 있다. 백업이 지켜야 하는 것은 바로 이 오른쪽이다(11.4).

### 3.3 키 설계 — 자연 키와 대리 키

**무엇인가.** 기본 키(PK)를 고르는 방법은 두 가지다. **자연 키**는 업무에 원래 있던 값을 그대로 키로 쓰는 것이다. 종목코드, 공시 접수번호가 그렇다. **대리 키**는 업무와 상관없이 DB가 붙여 주는 일련번호(`AUTO_INCREMENT id`)다.

**이 프로젝트에서는.** 테이블의 성격에 따라 골랐다.

| 고른 것 | 테이블 | 이유 |
|---|---|---|
| 자연 키 | `filing_13f.accession_no`, `dividend_event.rcept_no` | SEC와 DART가 붙인 번호라 바뀌지 않고 유일하다. 같은 공시를 두 번 받아도 같은 줄이 되므로 중복 방지가 저절로 된다. |
| 자연 키 | `stored_financials.symbol`, `dart_corp_code.stock_code`, `cusip_ticker.cusip` | "종목당 한 줄"인 테이블이어서 조회 조건이 곧 키다. |
| 대리 키 + 유니크 키 | `company_analysis (id, UK symbol)`, `manual_holding (id, UK owner_key+symbol)` | JPA가 다루기 쉬운 `id`를 PK로 두고, "종목당 하나", "사람·종목당 하나" 같은 업무 규칙은 유니크 키로 DB가 지키게 했다. |
| 복합 유니크 키 | `holding_13f (accession_no, cusip, put_call)` | 같은 제출, 같은 종목이라도 주식 줄과 콜옵션 줄, 풋옵션 줄이 따로 있다. 셋을 묶어야 한 줄이 정해진다. |

**실무에서는.** 증권 시스템에도 계좌번호, 주문번호 같은 자연 키가 많다. 다만 자연 키가 바뀔 수 있다면(종목코드 변경, 회원 ID 변경) 대리 키를 PK로 두고 자연 키에는 유니크 키를 거는 편이 안전하다.

여기서 하나 더 기억할 점이 있다. **유니크 키는 애플리케이션이 실수해도 DB가 막아 주는 마지막 방어선**이다. 코드에서 "있으면 고치고 없으면 넣는다"를 꼼꼼히 짜도, 같은 순간에 요청 두 개가 들어오면 둘 다 "없다"를 보고 각자 넣을 수 있다. 이때 유니크 키가 있으면 둘째 요청이 실패하고, 없으면 중복된 줄이 조용히 생긴다.

### 3.4 FK 제약을 걸지 않은 이유

**무엇인가.** FK(외래 키) 제약은 "자식 줄은 반드시 존재하는 부모를 가리켜야 한다"는 규칙을 DB가 강제하는 것이다. 부모가 없는 자식 줄을 넣으려 하거나 자식이 남아 있는 부모를 지우려 하면 DB가 거부한다.

**이 프로젝트에는 FK가 하나도 없다.** 테이블 사이에 관계는 있지만(3.1의 실선), 그 관계를 지키는 것은 DB가 아니라 코드다. 일부러 그렇게 정한 이유는 세 가지다.

첫째, **13F는 배치 한 곳에서만 쓴다.** `ThirteenFSyncService`가 지울 때 자식(`holding_13f`)을 먼저 지우고 부모(`filing_13f`)를 나중에 지운다. 쓰는 곳이 한 곳뿐이라 관계가 어긋날 길이 좁다.

둘째, **`holding_13f.cusip`이 가리키는 `cusip_ticker` 줄은 비어 있는 것이 정상이다.** 보유 줄을 먼저 저장하고, 티커는 OpenFIGI에 물어서 나중에 채운다. OpenFIGI는 분당 호출 수가 제한되어 있어서 하루에 다 못 채우기도 한다. 여기에 FK를 걸면 티커를 아직 못 찾은 종목은 보유 줄조차 저장할 수 없게 된다.

셋째, **점선으로 이어진 테이블은 서로 몰라도 된다.** AI 분석은 있는데 공시 재무가 없거나, 그 반대여도 정상이다.

**대가.** 코드가 실수로 부모 없는 자식 줄(고아 행)을 만들어도 DB가 막아 주지 않는다. 그래서 관계를 건드리는 코드는 배치 한 곳에 모아 두었다.

**실무에서는.** 의견이 갈리는 주제다. 계좌, 주문, 체결처럼 **돈이 걸린 원장 테이블에는 FK를 거는 편**이 많고, 대용량 로그나 배치로 적재하는 테이블에는 쓰기 성능과 적재 순서 때문에 빼는 편이 많다. 면접에서는 "걸었다/안 걸었다"보다 "왜 그렇게 정했는지"를 설명할 수 있는 것이 중요하다.

### 3.5 JSON을 통째로 넣은 열 — `analysis_json`, `financials_json`

**무엇인가.** 데이터를 여러 테이블과 열로 쪼개지 않고, JSON 문서 하나를 `LONGTEXT` 열 하나에 통째로 넣는 방식이다.

**이 프로젝트에서는.** 두 열이 이렇게 저장된다. `company_analysis.analysis_json`에는 판정, 일곱 개 섹션, 지표, 출처가 들어 있는 AI 분석 본문이 들어가며, 한 건에 10~30KB다. `stored_financials.financials_json`에는 연간, 올해 누적, 최근 4분기 재무와 과거 PER·PBR이 들어간다.

쪼개지 않은 이유는 **항상 통째로 읽고 통째로 쓰기 때문**이다. 분석 섹션 하나만 조회하거나, "PER이 10배 아래인 종목"을 SQL로 찾을 일이 없다. 통째로 저장하면 모양이 바뀌어도(섹션이 하나 늘어도) 마이그레이션이 필요 없고, 자바 record(`CompanyAnalysisView`, `CompanyFinancials`)를 Jackson이 그대로 읽고 쓰면 된다.

다만 이 방식을 쓸 때 두 가지 원칙을 지켰다.

첫째, **조건으로 거르는 데 쓰는 값은 JSON 밖의 열로 꺼낸다.** `status`, `analyzed_at`, `researched_at`, `includes_position`, `has_history`가 그렇다. 특히 `includes_position`(분석에 평단가가 들어갔는가)은 공개 화면에 내보낼지를 가르는 기준이다. JSON을 열어 보지 않고 열 하나로 판단할 수 있어야 실수가 없다.

둘째, **매일 바뀌는 값은 넣지 않는다.** 공시 재무는 분기에 한 번 바뀌지만, PER과 PBR은 주가를 따라 매일 바뀐다. 그래서 재무는 주가 없이 저장하고, 읽을 때 `withPrice()`로 지금 주가를 넣어 계산한다.

**실무에서는.** MySQL의 `JSON` 타입(형식 검증과 부분 조회 가능)이나 PostgreSQL의 `jsonb`(인덱스 가능)를 쓰는 경우가 많다. 이 프로젝트는 부분 조회가 없어서 `LONGTEXT`로 충분했다. 이 방식을 남용하면 "관계형 DB 안에 숨은 NoSQL"이 되어 정합성을 잃기 쉬우니, 통째로 읽고 쓰는 문서에만 쓴다.

### 3.6 상태판을 겸하는 테이블 — `company_analysis`

AI 분석은 몇 분이 걸려서 별도 스레드에서 돈다고 했다(2.3). 그러면 "지금 분석이 도는 중인가, 끝났는가, 실패했는가"를 어딘가에 적어 두어야 화면이 물어볼 수 있다. 작업 상태만 담는 테이블을 따로 두는 방법도 있지만, 이 프로젝트는 분석 결과 테이블이 상태판을 겸하게 했다.

<!-- diagram: analysis-states | 마지막 성공(analysis_json)과 마지막 시도(status)를 따로 두어, 다시 분석하다 실패해도 이전 분석이 남는다. -->

```text
           "실행" 클릭                          클로드 응답
 NONE ──────────────────▶ RUNNING ──────────────────────────▶ OK
(행 없음)                    │                                  │
                            │ 실패                   "판단만 새로" (조사 7일 안)
                            ▼                                  │
                          ERROR ◀───── 실패 ───── RUNNING ◀─────┘
              (analysis_json 은 그대로 남는다)
```

이 테이블에는 세 가지 설계가 들어 있다.

첫째, **마지막 성공과 마지막 시도를 다른 열에 둔다.** `analysis_json`과 `analyzed_at`은 마지막으로 **성공한** 분석이고, `status`와 `last_error`는 마지막 **시도**의 결과다. 그래서 다시 분석하다 실패해도 멀쩡하던 이전 분석이 사라지지 않는다. 화면은 이전 분석을 보여 주면서 "마지막 시도는 실패했다"고 알릴 수 있다.

둘째, **시각을 세 가지로 나눠 둔다.** `researched_at`은 웹 조사를 한 시각(V9에서 추가), `analyzed_at`은 판정을 내린 시각, `updated_at`은 마지막으로 시도한 시각이다. "판단만 새로"는 웹 조사 없이 판정만 다시 쓰므로 `analyzed_at`만 바뀐다. 화면은 이 둘을 나눠 "판단 갱신 ○일 · 조사 ○일"처럼 보여 준다. 조사 시각을 따로 두지 않으면 일주일 전 조사로 내린 판정이 오늘 것처럼 보이게 된다.

셋째, **죽은 작업을 알아본다.** 분석 도중 서버가 죽으면 상태는 `RUNNING`인 채로 남는다. 그래서 `RUNNING`인데 `updated_at`이 15분 넘게 지났으면 죽은 작업으로 보고 다시 시작할 수 있게 했다.

**실무에서는.** 같은 문제를 작업 테이블과 상태 열(`READY`, `RUNNING`, `DONE`, `FAILED`)로 풀거나, 메시지 큐(Kafka, RabbitMQ)로 푼다. 증권사의 일괄 처리(정산, 배치)도 "상태 열을 두고, 실패하면 다시 처리할 수 있게"가 기본 모양이다.

### 3.7 JPA 엔티티와 리포지토리

**무엇인가.** JPA는 자바 객체와 DB 테이블을 이어 주는 표준이다. 테이블 한 줄을 자바 객체(엔티티) 하나로 다루고, SQL을 직접 쓰지 않아도 저장하고 조회할 수 있게 해 준다.

**이 프로젝트에서는.** `domain/` 패키지에 테이블마다 엔티티(`@Entity`)가 하나씩 있고, 조회는 `JpaRepository`를 상속한 인터페이스(리포지토리)로 한다. 리포지토리는 **쿼리 메서드**를 지원한다. 메서드 이름만 규칙대로 지으면 JPA가 SQL을 만들어 준다. 예를 들어 `findByAccessionNoAndCusipIn(String, Collection<String>)`이라고 선언하면 `WHERE accession_no = ? AND cusip IN (...)`이 된다.

이 프로젝트는 JPA의 **연관관계 매핑(`@ManyToOne` 등)을 쓰지 않았다.** FK를 걸지 않은 것과 같은 이유다. 필요한 데이터는 키 값으로 따로 조회한다. 덕분에 JPA를 쓸 때 흔히 겪는 지연 로딩 예외나 N+1 문제(목록을 읽은 뒤 줄마다 한 번씩 더 조회해서 쿼리가 폭증하는 문제)가 생길 자리가 없다.

트랜잭션도 신경 썼다. 읽기만 하는 서비스에는 `@Transactional(readOnly = true)`를 붙여 읽기 전용으로 연다(`InstitutionPortfolioService`). 백그라운드 분석 스레드에는 요청 스레드의 트랜잭션이 따라가지 않기 때문에, 저장만 맡는 별도 빈(`CompanyAnalysisStore`)에 `@Transactional`을 둔다. 이렇게 하면 같은 클래스 안에서 자기 메서드를 부를 때 트랜잭션이 안 열리는 함정(2.7)도 함께 피한다.

성능을 고친 사례도 하나 있다. 공개 기업분석에서 종목 하나를 보여 주려고, 처음에는 기관마다 보유 줄 수천 개를 전부 읽은 뒤 자바에서 그 종목만 골라냈다. 지금은 그 종목의 CUSIP만 `IN` 조건으로 읽는다(`movesFor`). `idx_holding_13f_cusip` 인덱스가 이 조회를 받쳐 준다.

**실무에서는.** JPA는 생산성이 높지만, N+1 문제, 지연 로딩 예외, 필요 이상으로 많이 읽는 조회를 늘 조심해야 한다. 복잡한 조회는 QueryDSL, JPQL, 네이티브 SQL, MyBatis를 섞어 쓴다. 금융권에서는 SQL을 직접 관리하는 MyBatis의 비중이 높은 편이다.

**공부할 것.** 영속성 컨텍스트, 1차 캐시, 변경 감지(dirty checking), N+1 문제와 fetch join, 트랜잭션의 전파와 격리 수준, 인덱스와 실행 계획(`EXPLAIN`)을 공부해 보자.

> **직접 해보기** — `EXPLAIN SELECT * FROM holding_13f WHERE cusip = '594918104';`를 실행해서 `key` 칸에 `idx_holding_13f_cusip`이 나오는지 확인해 보자. 조건을 인덱스가 없는 열(`issuer_name`)로 바꾸면 `type`이 `ALL`(전체 스캔)로 바뀐다.

### 3.8 스키마 마이그레이션 — Flyway

**무엇인가.** 테이블을 만들거나 열을 더하는 일을 사람이 DB에 접속해 직접 하면, 내 PC와 서버의 DB 모양이 조금씩 달라진다. 누가 언제 무엇을 바꿨는지도 남지 않는다. 마이그레이션은 스키마 변경을 순서가 있는 SQL 파일로 남기고, 도구가 그 파일을 차례로 실행하게 하는 방식이다.

**이 프로젝트에서는.** `src/main/resources/db/migration/`에 `V1__init.sql`부터 `V10__portfolio_snapshot.sql`까지 있다. 앱이 뜰 때 Flyway가 아직 적용하지 않은 파일만 번호 순서대로 실행하고, 실행한 기록을 `flyway_schema_history`에 남긴다.

Hibernate는 `ddl-auto: validate`로 설정했다. 테이블을 **만들지 않고 검사만** 한다는 뜻이다. 엔티티와 실제 DB 모양이 다르면 앱이 아예 뜨지 않는다. 그래서 엔티티를 고칠 때는 반드시 다음 번호의 V 파일을 같이 만들어야 한다.

**이미 적용한 V 파일은 절대 고치지 않는다.** Flyway는 파일마다 체크섬(내용의 지문)을 기록해 두는데, 내용이 바뀌면 체크섬이 달라져 앱이 뜨지 않는다. 고칠 것이 있으면 새 V 파일을 만든다.

파일마다 배울 점이 조금씩 다르다.

| 버전 | 한 일 | 배울 점 |
|---|---|---|
| V1 | 처음 테이블 6개 | Flyway를 나중에 붙였기 때문에, 이미 테이블이 있던 DB는 `baseline`으로 "적용됨" 표시만 했다. |
| V2 | 13F 테이블 4개와 기관 기초 데이터 | 스키마와 기준 데이터를 한 파일에 같이 넣을 수 있다. |
| V3 | 기관 설명 한 줄 수정 | 이미 적용한 V2를 고치지 않고 새 파일로 고쳤다. |
| V4 | 배당 테이블 2개 | |
| V5 | `includes_position` 열 추가, 기존 줄은 `1`(비공개) | 열을 더할 때 **안전한 쪽을 기본값**으로 둔다. 기존 분석을 실수로 공개하지 않으려는 것이다. |
| V6 | 기관 10곳 교체 | 줄을 지우지 않고 `active = 0`으로 껐다. |
| V7 | 잘못 찾은 티커 정리 | 데이터 정리도 마이그레이션 파일로 남긴다. |
| V8 | `stored_financials` | |
| V9 | `researched_at` 추가, 기존 줄은 `analyzed_at` 값으로 채움 | 열 추가와 **기존 값 채우기를 한 파일에서** 한다. |
| V10 | 스냅샷과 대사 테이블 3개 | 날짜를 키로 한 멱등 배치용 테이블이다. |

**실무에서는.** 운영 DB를 사람이 직접 `ALTER`하지 않고, 검토를 거친 마이그레이션 파일로만 바꾼다(Flyway, Liquibase). 그리고 되돌릴 일을 생각해서 변경을 **expand → contract** 두 단계로 나눈다. 먼저 열을 더하는 배포(옛 코드도 그대로 동작)를 하고, 새 코드를 배포한 뒤, 다음 배포에서 옛 열을 지운다.

이 프로젝트도 "스키마는 더하기만 한다"는 규칙을 지킨다. 배포가 실패해 이미지가 앞 버전으로 되돌아가면 옛 코드가 새 스키마를 만나게 되는데, 열을 더하기만 했다면 옛 코드는 새 열을 무시하고 그대로 동작한다. 반대로 열을 지웠다면 옛 코드가 그 열을 찾다가 멈춘다. 이미지는 한 줄로 되돌릴 수 있지만 DB는 되돌릴 수 없다는 점을 늘 기억해야 한다.

**공부할 것.** 마이그레이션 도구의 원리, 무중단 스키마 변경, 큰 테이블을 `ALTER`할 때 생기는 잠금 문제(online DDL)를 공부해 보자.

## 4. 외부 API 연동

<!-- diagram: map@external,extapi | 4장은 service 옆의 external 층과, 그 너머의 바깥 API를 본다. -->

**지도에서 보면.** 3장이 앱이 직접 가진 데이터라면, 4장은 앱이 남에게서 받아 오는 데이터다. service가 external 층의 클라이언트를 부르고, 클라이언트가 토스·DART·SEC·Claude 같은 바깥 API로 나간다. 이 경계를 넘는 순간 상대가 느리거나 죽을 수 있으므로, 이 장의 장치들은 모두 그 경계 위에 놓인다.

> **이 장에서 배울 것** — 바깥 API가 느리거나 죽어도 우리 앱이 같이 넘어지지 않게 하는 장치(타임아웃, 재시도, 서킷 브레이커, 부분 실패 격리, 캐시)를 요청이 나가서 돌아오는 순서대로 본다.
>
> **먼저 알아둘 말** — [OAuth 토큰](#04-바깥-연동과-안정성) · [타임아웃](#04-바깥-연동과-안정성) · [재시도·백오프](#04-바깥-연동과-안정성) · [서킷 브레이커](#04-바깥-연동과-안정성) · [fail-soft](#04-바깥-연동과-안정성) · [호출 한도](#04-바깥-연동과-안정성)

이 앱은 바깥 시스템을 여럿 부른다. 잔고와 시세는 토스증권과 나무증권에서, 재무제표는 DART(한국)와 SEC EDGAR(미국)에서, 기관 보유는 SEC 13F와 OpenFIGI에서 받고, AI 분석은 Anthropic의 Claude에 맡긴다. 알림은 텔레그램으로 보낸다.

바깥을 부르는 코드는 우리 코드만 부르는 코드와 전제가 다르다. 상대는 언제든 느려지거나, 막히거나, 응답 모양을 바꿀 수 있다. 실제로 토스는 허용 IP가 바뀔 때마다 403을 돌려주고, SEC는 초당 10건을 넘으면 요청을 막는다. 그래서 이 장은 "바깥이 실패한다"를 전제로 두고, 요청이 나가서 돌아오는 순서대로 장치를 하나씩 본다. 순서는 다음과 같다. 누구인지 밝히고(4.1), 너무 자주 부르지 않고(4.2), 답이 늦으면 포기하고(4.3), 실패하면 다시 해 보고(4.4), 계속 실패하면 잠시 부르지 않고(4.5), 그래도 안 되면 그 부분만 비운 채 화면을 보여 준다(4.6). 마지막으로 받은 응답을 안전하게 읽는 법(4.7)과 돈이 드는 호출을 통제하는 법(4.8)을 본다.

바깥을 부르는 HTTP 클라이언트는 스프링 6의 `RestClient`다. 바깥 시스템마다 기본 주소, 헤더, 타임아웃이 달라서 빈을 따로 만든다(`TossRestClientConfig`, `DartRestClientConfig`, `PublicDataRestClientConfig` 등). Claude만은 RestClient 대신 Anthropic의 자바 SDK로 부른다.

### 4.1 누구인지 밝히기 — 토큰

증권사 API는 매 요청마다 키와 시크릿을 보내지 않는다. 키로 한 번 로그인해서 **유효기간이 있는 토큰**을 받고, 그 뒤의 요청은 토큰으로 한다. 토큰은 하루 정도 유효하다.

문제는 토큰을 얼마나 자주 받느냐다. 토큰을 메모리에만 들고 있으면 앱을 다시 띄울 때마다 새로 받아야 하고, 개발 중에 앱을 자주 재시작하면 증권사의 발급 횟수 한도에 걸린다. 그래서 토큰을 **메모리와 DB 두 곳**에 둔다.

<!-- diagram: token | 메모리 → DB → 증권사 순서로 찾고, 새로 받으면 양쪽에 저장한다. 401을 받으면 양쪽에서 지운다. -->

```text
메모리 → 없으면 MySQL(복호화해서) → 없으면 증권사에 발급 요청 → 양쪽에 저장(MySQL 에는 암호화해서)
401 을 받으면 양쪽에서 지움 → 다음 호출에서 새로 발급
```

먼저 메모리를 보고, 없으면 DB를 보고, 그래도 없으면 증권사에 새로 받는다. 증권사가 401(토큰이 만료되었거나 무효함)을 주면 양쪽에서 지우고 다음 호출에서 다시 받는다. 앱을 다시 띄운 직후에 401이 한 번 나올 수 있는 이유가 이것이다. DB에 남아 있던 토큰이 그사이 만료된 것이고, 한 번 더 부르면 새로 받는다.

DB에 넣는 토큰은 평문이 아니라 **AES-256-GCM으로 암호화한 값**이다(`external/auth/TokenCipher`). 토큰 하나면 하루 동안 계좌를 볼 수 있으니, DB 덤프가 새어 나가도 토큰을 쓸 수 없게 하려는 것이다. 암호화 키는 DB가 아니라 환경변수(`TOKEN_ENCRYPTION_KEY`)에만 둔다. 자세한 원리는 5.4에서 본다.

### 4.2 너무 자주 부르지 않기 — 상대의 호출 한도

바깥 API는 대부분 호출 횟수를 제한한다. 한도를 넘기면 429를 받거나, 심하면 한동안 차단된다. 그래서 상대의 규칙을 코드로 지킨다.

SEC는 초당 10건까지만 받고, 요청마다 `User-Agent` 헤더에 연락처를 적으라고 요구한다. 연락처가 없으면 403을 준다. 이 앱은 설정의 `SEC_USER_AGENT`를 모든 SEC 요청에 붙인다. OpenFIGI는 키가 없으면 한 번에 10개씩, 분당 25번까지만 받는다. 13F 배치는 이 속도에 맞춰 CUSIP을 묻고, 한도에 다섯 번 연달아 걸리면 그날은 접고 다음 날 이어서 묻는다. DART는 하루 2만 건이 한도라서, 배당 공시는 종목마다 하루 한 번만 조회한다(`dividend_fetch`).

반대로 우리 공개 API도 남이 너무 자주 부르지 못하게 막는다. 이 이야기는 5.4에서 다룬다.

### 4.3 답이 늦으면 포기하기 — 타임아웃

**기초부터.** 바깥 API를 부르는 동안 요청을 처리하던 스레드는 답을 기다리며 멈춰 있다. 상대가 영영 답하지 않으면 스레드도 영영 묶인다. 톰캣의 스레드는 수가 정해져 있으니, 이런 요청이 쌓이면 결국 스레드가 바닥나고 앱 전체가 아무 요청도 받지 못하게 된다. 바깥 하나의 장애가 우리 앱 전체의 장애로 번지는 것이다.

타임아웃은 "이만큼 기다려도 답이 없으면 포기한다"는 시간이다. 두 종류가 있다. **연결 타임아웃**은 상대와 연결이 맺어질 때까지 기다리는 시간이고, **응답 타임아웃**은 연결된 뒤 답이 올 때까지 기다리는 시간이다.

**이 프로젝트에서는.** 모든 RestClient에 연결 5초, 응답 30초를 걸었다(`HttpClientResilienceConfig`). 이 일을 찾은 과정이 기억할 만하다. 원래는 재시도를 붙이려고 이 코드를 열었는데, 스프링 부트 3.3의 RestClient에는 **기본 타임아웃이 아예 없다**는 것을 그때 알았다. 재시도보다 타임아웃이 먼저였다. 기다림이 끝나지 않는 요청은 재시도할 기회조차 오지 않기 때문이다.

### 4.4 실패하면 다시 해 보기 — 재시도

네트워크가 잠깐 끊기거나 상대 서버가 순간적으로 과부하에 걸리면 요청이 실패한다. 이런 실패는 조금 뒤에 다시 보내면 성공하는 경우가 많다. 그래서 실패한 요청을 다시 보낸다. 다만 아무 요청이나 다시 보내면 안 된다. 이 앱의 규칙은 다음과 같다.

- **GET만 다시 보낸다.** GET은 읽기만 하므로 두 번 보내도 결과가 같다. POST는 서버의 무언가를 바꾸는 요청이라, 첫 요청이 사실은 처리되었는데 응답만 늦게 온 것이라면 다시 보냈을 때 두 번 처리될 수 있다.
- **네트워크 오류와 5xx만 다시 보낸다.** 5xx는 상대 서버 쪽 문제라 기다리면 나아질 수 있다. 4xx는 요청 자체가 잘못된 것이라 다시 보내도 결과가 같다. 429(너무 자주 부름)는 다시 보내면 상황을 더 나쁘게 만든다.
- **최대 3번까지, 기다리는 시간을 늘려 가며 보낸다.** 0.5초 뒤, 그다음은 1초 뒤에 보내고, 그 시간에 무작위 값(지터)을 조금 섞는다. 실패한 클라이언트들이 모두 정확히 같은 순간에 다시 몰려들면 막 회복하던 서버가 다시 쓰러지기 때문이다.

이 규칙은 `ResilientHttpInterceptor` 한 곳에 있다. 인터셉터는 나가는 모든 요청에 끼어드는 코드라서(2.7), 바깥 시스템마다 재시도 코드를 따로 짤 필요가 없다. 재시도가 일어나면 지표 `http_client_retries`가 올라간다.

### 4.5 계속 실패하면 잠시 부르지 않기 — 서킷 브레이커

**기초부터.** 상대 서버가 완전히 죽었다고 해 보자. 요청마다 타임아웃 30초를 다 기다리고, 재시도까지 세 번 하면, 화면 하나를 그리는 데 1분 넘게 걸린다. 그 사이 우리 스레드는 계속 묶이고, 죽은 서버에는 쓸모없는 요청이 계속 쏟아진다.

서킷 브레이커는 집의 누전 차단기처럼 동작한다. 실패가 일정 비율을 넘으면 회로를 **열어서**, 한동안은 상대를 아예 부르지 않고 바로 실패로 처리한다. 시간이 지나면 **반열림** 상태가 되어 몇 번만 시험 삼아 보내 보고, 성공하면 **닫아서** 정상으로 돌아간다.

<!-- diagram: breaker | 실패가 몰리면 30초 동안 부르지 않고, 시험 삼아 몇 번 보내 본 뒤 정상으로 돌아간다. -->

```text
닫힘(정상) ── 실패율이 기준을 넘음 ──▶ 열림(부르지 않고 바로 실패)
   ▲                                      │ 30초 뒤

                                           │ 시험 요청이 실패
                                           └──────▶ 다시 열림
```

**이 프로젝트에서는.** Resilience4j 라이브러리로 상대 호스트마다 서킷 브레이커를 하나씩 둔다. 최근 20번 중 절반이 실패하면 30초 동안 열린다. 토스가 죽었다고 SEC 호출까지 막히면 안 되니 호스트별로 나눴다.

여기서 하나 신경 쓴 점이 있다. **4xx는 실패로 세지 않는다.** 토스의 403(허용 IP 문제)까지 실패로 세면 회로가 열려 버리고, 그 뒤로는 토스를 아예 부르지 않으니 "허용 IP에 이 주소를 등록하세요"라는 안내 문구도 사라진다. 사용자가 고칠 수 있는 문제의 안내가 가려지지 않게 한 것이다. 회로가 열리면 지표 `resilience4j_circuitbreaker_state`가 바뀌고 `CircuitBreakerOpen` 알림이 간다.

### 4.6 그래도 안 되면 그 부분만 비우기 — fail-soft

타임아웃, 재시도, 서킷 브레이커를 다 거쳐도 실패할 때가 있다. 그때 화면 전체를 에러로 만들지 않고, **실패한 부분만 비운 채** 나머지를 보여 준다. 이것을 fail-soft라고 한다.

공개 기업분석(`StockBriefService.build()`)이 좋은 예다. 이 화면은 SEC 재무, 토스 현재가, DB의 13F 보유를 모아서 만든다. 토스가 막히면 현재가가 없으니 PER과 PBR만 비우고, 재무와 기관 칸은 그대로 보여 준다. 나의 포트폴리오도 마찬가지다. 토스 잔고 조회가 실패해도 나무증권 잔고는 그대로 보인다.

다만 비워서는 안 되는 것도 있다. 환율을 못 받으면 원화 환산을 아예 포기하고 에러를 낸다. 환율 자리에 1을 넣고 계속 계산하면 미국 주식 금액이 1,380배 작게 나오는데, 틀린 숫자는 빈칸보다 나쁘다([결정기록 005](결정기록.md#005-환율을-못-구하면-예외를-던진다)). "무엇은 비워도 되고 무엇은 멈춰야 하는가"를 정하는 것이 fail-soft 설계의 핵심이다.

자주 바뀌지 않는 데이터는 캐시로 바깥 호출 자체를 줄인다. 공개 기업분석은 6시간, 공개 차트는 10분 동안 메모리에 들고 있다(1.7).

### 4.7 받은 응답을 안전하게 읽기

바깥 응답은 우리가 만든 것이 아니라서 생각보다 거칠다. 이 프로젝트에서 겪은 두 가지를 보자.

첫째, **큰 응답은 한 번에 메모리에 올리지 않는다.** 13F 보유표 XML은 보유 종목이 수천 개인 큰 기관이면 파일이 매우 크다. 이것을 통째로 읽어 DOM 트리를 만들면 메모리가 크게 튄다. 그래서 StAX라는 스트리밍 방식으로 한 줄씩 읽으며 필요한 값만 꺼낸다(`InfoTableParser`).

둘째, **문서가 스스로 밝힌 인코딩을 믿지 않는다.** DART 공시 본문은 머리에 `charset=euc-kr`이라고 적혀 있는데, 실제 내용은 UTF-8인 경우가 있다. 적힌 대로 EUC-KR로 읽으면 한글이 깨진다. 그래서 먼저 UTF-8로 엄격하게 읽어 보고, 맞지 않을 때만 EUC-KR로 읽는다(`DartApiClient.decode()`). 칸 사이에 줄바꿈 없는 공백(NBSP)이 섞여 있어서 자바의 `\s`로 못 잡는 함정도 있었는데, 읽기 전에 보통 공백으로 바꿔서 풀었다.

### 4.8 돈이 드는 호출 통제하기

Claude 호출은 한 번에 수백에서 천몇백 원이 든다. 그래서 다른 바깥 호출과 다르게 다룬다. 분석은 **사람이 버튼을 눌렀을 때만** 실행하고, 결과를 DB에 저장해서 다시 볼 때는 돈이 들지 않게 한다([결정기록 006](결정기록.md#006-분석은-버튼을-눌러야-실행된다)). 같은 지시문과 스키마가 매번 다시 과금되지 않도록 프롬프트 캐싱을 켜 두었고, 이미 가진 숫자(재무, 보유)는 앱이 계산해서 넣어 모델이 다시 검색하지 않게 했다. 호출 수와 토큰은 `ClaudeMetrics`가 지표로 남긴다.

**실무에서는.** 대외 연동(다른 기관, 결제사, 거래소)은 장애의 가장 큰 원인 중 하나다. 그래서 타임아웃, 지수 백오프를 쓰는 재시도, 서킷 브레이커, 같은 요청이 두 번 처리되지 않게 하는 멱등 키, 민감 정보를 가린 요청·응답 로그, 그리고 상대 시스템의 점검 시간 대응까지 꼭 챙긴다.

**공부할 것.** HTTP 상태 코드의 의미(401과 403과 429의 차이), 타임아웃의 종류, 재시도와 멱등성의 관계(왜 GET만 다시 보내는가), 지수 백오프와 지터, 서킷 브레이커의 세 상태, OAuth 2.0의 흐름, 캐시 무효화 전략을 공부해 보자.

> **직접 해보기** — `ResilientHttpInterceptorTest`를 열어 "5xx면 다시 보내고 4xx면 다시 보내지 않는다"가 어떻게 고정되어 있는지 읽어 보자. 그다음 서킷 브레이커가 열림 → 반열림 → 닫힘으로 돌아오는 경우를 테스트로 하나 더 써 보자. 30초를 실제로 기다리지 않도록 설정값을 줄이는 것이 요령이다.

## 5. 보안 — Spring Security와 웹 보안

<!-- diagram: map@browser,caddy,web | 5장은 브라우저에서 Caddy를 지나 web 층의 필터에 이르는 입구를 본다. -->

**지도에서 보면.** 2~4장은 요청이 앱 안에 들어온 뒤의 이야기였다. 5장은 다시 입구로 돌아가, 누가 들어올 수 있고 무엇을 할 수 있는지를 본다. 문을 지키는 장치는 세 곳에 나뉘어 있다. 브라우저에는 쿠키와 CSP가, Caddy에는 HTTPS와 차단 규칙이, web 층에는 Spring Security 필터가 있다.

> **이 장에서 배울 것** — 공개 화면과 내 화면이 한 앱에 섞여 있을 때 누가 무엇을 볼 수 있게 할지 정하는 법(인증과 인가), 그리고 브라우저를 노리는 공격(CSRF, XSS)을 막는 법을 본다.
>
> **먼저 알아둘 말** — [인증·인가](#06-보안) · [쿠키·세션](#01-웹과-네트워크) · [CSRF](#06-보안) · [XSS](#06-보안) · [CSP](#06-보안) · [AES-GCM](#06-보안)

이 프로젝트는 누구나 보는 공개 화면과 운영자만 보는 내 화면이 한 앱 안에 섞여 있다. 그래서 보안을 공부하기에 좋은 재료가 많다. 주소마다 규칙이 다르고, 공개 쪽으로 내 정보가 새지 않게 막아야 하고, 로그인 쿠키를 노리는 공격도 막아야 한다. 규칙은 모두 `config/SecurityConfig.java`에 있고, 그 규칙이 맞는지는 `SecurityConfigTest`가 고정한다.

### 5.1 인증과 인가

**무엇인가.** 인증은 "당신이 누구인가"를 확인하는 일이고, 인가는 "당신이 이것을 해도 되는가"를 판단하는 일이다. 로그인이 인증이고, 로그인한 사람만 잔고 화면을 볼 수 있게 하는 것이 인가다.

**이 프로젝트에서는.** 계정은 하나뿐이다. 환경변수 `OWNER_USERNAME`과 `OWNER_PASSWORD`로 운영자 한 명만 정하고, 회원 테이블은 없다. 여러 사람이 각자 증권사 계좌를 연결하는 서비스가 아니기 때문이다([결정기록 004](결정기록.md#004-증권사-로그인을-포기하고-스크린샷으로-우회한다)).

로그인은 폼 로그인과 세션 쿠키로 한다. 로그인 화면은 정적 HTML(`/public/login.html`)이고, 처리는 스프링 시큐리티의 `/login`이 맡는다. 로그인에 성공하면 서버가 세션을 만들고 그 번호를 쿠키로 내려준다. 이 쿠키에는 세 가지 속성을 건다. `HttpOnly`는 자바스크립트가 쿠키를 읽지 못하게 해서, 화면에 악성 스크립트가 끼어들어도 쿠키를 훔쳐 가지 못하게 한다. `SameSite=Strict`는 다른 사이트에서 시작된 요청에는 쿠키를 붙이지 않게 한다. `Secure`는 HTTPS에서만 쿠키를 보내게 하며, 운영 서버에서 켠다. 세션은 12시간 동안 유지된다.

인가는 주소 단위로 정한다. `/`, `/public/**`, `/api/public/**`, `GET /api/institutions/**`는 누구나 볼 수 있고, 나머지는 로그인이 필요하다. 로그인하지 않은 채 API를 부르면 401을 JSON으로 돌려주고, 화면을 열면 로그인 페이지로 보낸다. API에 로그인 페이지 HTML을 돌려주면 화면 코드가 그것을 JSON으로 읽으려다 엉뚱한 에러를 내기 때문에 둘을 나눴다.

헬스체크와 지표 같은 관리 주소는 아예 **다른 포트(8081)** 로 떼어 내고, 서버 안에서만 열었다. 같은 포트에 두고 주소 규칙으로 막는 것보다, 문 자체를 바깥에 내지 않는 편이 실수할 여지가 적다.

### 5.2 CSRF

**기초부터.** 브라우저는 요청이 어느 사이트에서 시작되었든, **목적지 사이트의 쿠키를 자동으로 붙인다.** 그래서 이런 일이 생길 수 있다.

<!-- diagram: csrf | 브라우저는 쿠키를 자동으로 붙이지만, 헤더는 우리 화면만 만들 수 있다. 그래서 헤더가 없는 요청은 403이다. -->

```text
① 나는 우리 앱에 로그인해 있다 (브라우저에 세션 쿠키)
② 다른 탭에서 수상한 사이트를 연다
③ 그 사이트의 숨은 폼이 우리 앱으로 POST /api/analysis/MSFT 를 보낸다
④ 브라우저가 우리 앱 쿠키를 자동으로 붙인다 → 서버는 "나" 의 요청으로 안다 → 돈이 나간다
```

수상한 사이트는 내 쿠키를 읽을 수도 없고 볼 수도 없다. 그런데도 브라우저가 쿠키를 알아서 붙여 주기 때문에 공격이 성립한다. 이것이 CSRF(사이트 간 요청 위조)다.

막는 방법의 핵심은 "쿠키만으로는 부족하고, **우리 화면만 알 수 있는 값**을 하나 더 내라"는 것이다.

**이 프로젝트에서는.** 스프링 시큐리티의 `CookieCsrfTokenRepository`가 `XSRF-TOKEN`이라는 쿠키에 무작위 토큰을 내려준다. 우리 화면의 자바스크립트는 POST, PUT, DELETE를 보낼 때마다 이 쿠키 값을 읽어 `X-XSRF-TOKEN` 헤더에 다시 담아 보낸다(`portfolio.js`의 `apiFetch`, `stock.js`의 `runAi`). 서버는 쿠키의 값과 헤더의 값이 같을 때만 요청을 받는다.

수상한 사이트는 이 헤더를 만들 수 없다. 브라우저가 다른 사이트의 쿠키를 자바스크립트로 읽지 못하게 막기 때문이다. 그래서 쿠키는 자동으로 붙어도 헤더가 없어 403으로 거절된다. 앞에서 본 `SameSite=Strict` 쿠키도 같은 공격을 한 번 더 막는다.

화면 코드에서 `fetch`를 직접 쓰면 이 헤더가 빠져서 403이 난다. 그래서 쓰기 요청은 반드시 `apiFetch`를 거치게 했다.

### 5.3 브라우저 보안 헤더 — CSP

**무엇인가.** XSS는 남이 넣은 글자에 숨어 있던 스크립트가 내 화면에서 실행되는 공격이다. 예를 들어 회사 이름 칸에 `<script>...</script>`가 들어 있는데 그것을 그대로 화면에 넣으면, 그 스크립트가 내 로그인 상태로 실행된다.

방어는 두 겹이다. 첫째는 **이스케이프**다. 바깥에서 온 글자(회사 이름, 뉴스 제목, AI가 쓴 글)는 화면에 넣기 전에 항상 `esc()`를 거쳐 `<`를 `&lt;`로 바꾼다. 그러면 스크립트가 아니라 글자로만 보인다.

둘째는 **CSP**(Content-Security-Policy)다. 응답 헤더로 "스크립트는 우리 서버와 jsdelivr에서 온 파일만 실행하라"고 브라우저에 지시한다. 그러면 어떤 이유로 이스케이프가 뚫려서 HTML 안에 스크립트가 끼어들어도, 브라우저가 그 스크립트를 실행하지 않는다.

**이 프로젝트에서는.** CSP 때문에 HTML 안에 직접 쓴 스크립트(`<script>...</script>`)와 `onclick=` 같은 속성이 모두 막힌다. 그래서 화면 코드는 전부 `.js` 파일로 분리했다. 처음에는 불편하지만, 이 규칙 덕분에 XSS가 뚫리더라도 피해가 거기서 멈춘다. 그 밖에 `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options: DENY`(다른 사이트가 우리 화면을 틀 안에 넣지 못하게 함)도 함께 보낸다.

### 5.4 그 밖의 방어

위의 세 가지 외에도 위협마다 막는 장치가 있다.

| 위협 | 방어 | 파일 |
|---|---|---|
| 공개 API를 마구 불러 서버를 괴롭히거나 데이터를 긁어 가는 것 | IP당 분당 120번(배당 캘린더는 15번)까지만 받는다. 1분 단위 고정 창으로 세고, 넘으면 429와 함께 `Retry-After`로 몇 초 뒤에 오라고 알린다. | `RateLimiter`, `PublicRateLimitFilter` |
| DB 덤프가 새어 나가 증권사 토큰을 쓰는 것 | 토큰을 AES-256-GCM으로 암호화해 저장한다. 매번 새 IV를 쓰고, GCM 태그로 위조를 잡아내고, 암호문 앞에 형식 버전(`enc:v1:`)을 붙인다. 증권사와 계정을 암호문에 묶어서, 다른 줄로 옮겨 붙이면 풀리지 않는다. | `TokenCipher` |
| 공개 화면으로 내 평단가가 새는 것 | 평단가가 들어간 분석은 공개 주소에서 내보내지 않고, 그런 분석이 **있다는 사실조차** 숨긴다. | `CompanyAnalysisService.findPublic` |
| 이상한 주소로 캐시를 오염시키는 것 | 공개 주소는 티커 모양(정규식)에 맞는 값만 받아 캐시 키로 쓴다. | `StockBriefController` |
| 공격자에게 내부 지도를 주는 것 | 운영에서 Swagger를 끄고, 500 응답에는 내부 정보를 싣지 않는다. | `application.yml`, `GlobalExceptionHandler` |
| 위험한 설정으로 배포하는 것 | 배포 스크립트가 `.env`에 로그인 비밀번호, 암호화 키 같은 필수 보안값이 있는지 검사하고, 빠졌으면 배포를 멈춘다. | `deploy/deploy.sh` |

**실무에서는.** 금융권은 보안 심의와 취약점 점검을 정기적으로 받는다. 점검표는 보통 OWASP Top 10을 기준으로 하고, 위의 항목들이 거기에 그대로 나온다.

**공부할 것.** OWASP Top 10, 세션 방식과 JWT 방식의 차이, CSRF·XSS·SQL Injection의 원리, CSP, AES의 운영 모드(CBC와 GCM의 차이), 비밀번호 해시(bcrypt)를 공부해 보자.

> **직접 해보기** — 로그인하지 않은 채 `curl -i localhost:8080/api/portfolio/unified`를 보내 401이 오는지 확인해 보자. 이어서 `curl -i -X POST localhost:8080/api/analysis/MSFT`를 CSRF 헤더 없이 보내 403이 오는지도 확인해 보자. 내 PC에서는 비밀번호를 넣고 앱을 띄워야 로그인이 켜진다.

## 6. 프론트엔드 — 빌드 없는 HTML/CSS/JS

<!-- diagram: map@browser | 6장은 지도 맨 왼쪽의 브라우저, 곧 화면 코드를 본다. -->

**지도에서 보면.** 5장에서 브라우저가 지키는 규칙(CSP, CSRF 헤더)을 봤다. 6장은 그 규칙 아래에서 화면 코드가 어떻게 짜여 있는지 본다. 화면은 web 층이 내보내는 정적 파일이고, fetch로 같은 web 층의 API를 부른다.

> **이 장에서 배울 것** — 프레임워크 없이 HTML, CSS, JS로 화면을 짜는 방법과, 키보드나 화면 낭독기로도 쓸 수 있게 만드는 방법(접근성)을 본다.
>
> **먼저 알아둘 말** — [정적 파일](#01-웹과-네트워크) · [JSON](#01-웹과-네트워크) · [상태 코드](#01-웹과-네트워크)

**왜 프레임워크가 없나.** 이 프로젝트의 화면은 React나 Vue 없이 순수한 HTML, CSS, JS로 만들었다. 빌드 단계(npm, 번들러)가 없어서 배포가 단순하고, 프레임워크가 감춰 주는 브라우저의 기본기(DOM, 이벤트, fetch)를 그대로 보면서 공부할 수 있다. 화면 파일은 `src/main/resources/static/`에 있고, jar 안에 들어가 스프링이 그대로 내보낸다.

### 6.1 화면 코드를 짜는 방법

화면 코드에서 쓴 기법을 하나씩 보자.

**서버 호출.** 화면은 `fetch`로 서버를 부르고 JSON을 받는다. 자바의 RestClient가 하는 일을 브라우저에서 `fetch`가 한다고 보면 된다. 읽기 요청은 `getJson`이라는 작은 함수로, 쓰기 요청은 CSRF 헤더를 붙여 주는 `apiFetch`로 보낸다(`public/site.js`, `portfolio.js`). `apiFetch`는 401을 받으면 로그인 페이지로 보내는 일도 한다.

**공용 코드.** AI 분석 결과를 그리는 코드는 나의 포트폴리오와 공개 기업분석이 함께 쓴다. 처음에는 두 화면에 비슷한 코드가 따로 있었는데, 한쪽만 고치고 다른 쪽을 잊는 일이 반복되어 `analysis-view.js` 한 파일로 모았다. 캔들차트도 같은 이유로 `chart-view.js` 하나다.

**이벤트 위임.** 화면에 티커 버튼이 수백 개 있을 때, 버튼마다 클릭 핸들러를 다는 대신 `document`에 핸들러 하나만 달고 `closest("[data-stock]")`로 어느 버튼이 눌렸는지 찾는다(`public/stock.js`). 나중에 새로 그려진 버튼도 따로 핸들러를 달 필요가 없다.

**상태를 주소에 남기기.** 종목 창을 열면 주소에 `#stock=MSFT`가, 기업분석 페이지에는 `?t=MSFT`가 남는다. 그래서 새로고침해도 같은 화면이 뜨고, 주소를 복사해 남에게 보내면 같은 종목이 열린다. `history.pushState`로 주소를 바꾸고, 뒤로 가기는 `popstate` 이벤트로 처리한다.

**사이드바 메뉴.** 메뉴 항목은 `public/nav.js` 맨 위의 `MENU` 배열 한 곳에만 있다. HTML 파일에는 메뉴를 쓰지 않는다. 새 화면을 만들면 이 배열에 한 줄만 넣으면 모든 화면의 사이드바에 생긴다.

### 6.2 디자인 토큰과 반응형

**디자인 토큰.** 색, 간격, 글꼴 크기는 CSS 변수로 `public/tokens.css` 한 곳에 모았다. 화면의 CSS는 숫자를 직접 쓰지 않고 이 변수만 쓴다. 그래서 바탕색 하나를 바꾸면 모든 화면이 같이 바뀐다. 색에는 규칙이 하나 있다. **빨강과 파랑은 항상 주가의 오르내림만 뜻한다.** 버튼이나 선택 표시에 색을 쓰면 사용자가 그것을 등락으로 오해하기 때문에, 강조는 검정으로만 한다([결정기록 008](결정기록.md#008-색은-빨강과-파랑뿐이고-등락만-뜻한다)).

**캔버스 차트와 토큰.** 차트는 캔버스에 그리는데, 캔버스는 CSS 변수를 스스로 읽지 못한다. 그래서 그리기 직전에 `getComputedStyle`로 변수 값을 읽어 넘긴다(`cssVar()`). 색을 차트 코드 안에 직접 적어 두면 토큰을 바꿀 때 차트만 옛 색으로 남는다.

**반응형.** 좁은 화면 대응은 CSS `@media`로만 한다. 화면 폭이 바뀔 때 자바스크립트로 화면을 다시 그리면, 열려 있던 창이 닫히거나 입력하던 값이 날아가기 때문이다.

### 6.3 접근성(a11y)

접근성은 마우스를 쓰지 못하거나 화면을 보지 못하는 사람도 화면을 쓸 수 있게 하는 일이다. 실무에서 점점 필수가 되고 있고, 공공과 금융 분야에는 법적인 요구도 있다.

이 프로젝트는 **axe-core**라는 도구로 자동 검사를 하고, 위반 0개를 기준으로 삼는다. 사람 눈으로는 글자와 바탕의 대비 4.37:1과 4.5:1을 구분하지 못하지만, 기준선은 4.5:1이라서 도구로 재야 한다.

그 밖에 지킨 규칙은 다음과 같다. 클릭되는 것은 **키보드로도 쓸 수 있어야** 한다. 표의 티커는 `<button>`이라 Tab으로 가서 Enter로 열 수 있다. `div`에 클릭 핸들러만 달면 키보드로는 쓸 수 없다. 창(드로어)을 열면 닫기 버튼으로 초점을 옮기고, Esc로 닫으면 창을 연 곳으로 초점을 돌려준다. 닫힌 창은 `inert`로 막는다. `aria-hidden`은 화면 낭독기에게만 숨길 뿐 Tab 이동은 막지 못한다. 가로로 스크롤되는 영역에는 `tabindex="0"`을 붙여 키보드로도 스크롤할 수 있게 했다.

**공부할 것.** DOM API, 이벤트 버블링, `fetch`와 Promise·async/await, CSS 변수와 Grid·Flexbox, WCAG 2.x의 기본(대비, 키보드, 화면 낭독기)을 공부해 보자. 그다음에 React를 배우면 "프레임워크가 무엇을 대신해 주는지"가 분명하게 보인다.

## 7. 테스트

<!-- diagram: map@code,ci | 7장은 지도 아래쪽 줄의 시작, 코드와 CI의 테스트를 본다. -->

**지도에서 보면.** 여기서부터 지도의 아래쪽 줄로 내려온다. 위쪽 줄이 "서버에서 무엇이 도는가"였다면, 아래쪽 줄은 "코드가 어떻게 서버까지 가는가"다. 그 첫 관문이 테스트다. PR을 올리면 CI가 테스트를 돌리고, 통과해야만 다음 칸(빌드와 이미지)으로 간다.

> **이 장에서 배울 것** — 바깥 API와 DB 없이도 도는 테스트를 짜는 법, 규칙과 보안까지 테스트로 고정하는 법, 그리고 테스트가 줄어들면 PR을 막는 장치(커버리지 최소선)를 본다.
>
> **먼저 알아둘 말** — [단위·통합 테스트](#09-테스트) · [목](#09-테스트) · [픽스처](#09-테스트) · [커버리지·품질 게이트](#09-테스트)

**이 프로젝트에서는.** JUnit 5, AssertJ, Mockito로 테스트 228개를 짰다. 가장 중요한 원칙은 **바깥 API와 DB 없이 도는 테스트만 둔다**는 것이다. CI(GitHub Actions)에는 증권사 키도, DART 키도, MySQL도 없다. 그래도 테스트가 그대로 돌아야 PR마다 자동으로 검사할 수 있다. 그래서 바깥 응답이 필요한 테스트는 실제 응답을 파일로 저장해 두고(픽스처, `src/test/resources/dart/...`) 그 파일을 읽어 검사한다. 서비스끼리 의존하는 부분은 Mockito의 가짜 객체(목)를 꽂는다(2.1).

테스트로 고정하는 대상은 계산만이 아니다. **규칙**도 테스트로 고정한다. `StockNotesTest`는 마이크로소프트의 실제 재무 숫자를 넣고 "성장이 빨라지고 있다"는 문장이 나오는지 확인하며, "매수"나 "적정가" 같은 낱말이 공개 문장에 절대 나오지 않는지까지 검사한다. **보안 규칙**도 테스트로 고정한다. `SecurityConfigTest`는 어느 주소가 공개이고 어느 주소가 로그인이 필요한지를, `CompanyAnalysisPublicTest`는 평단가가 들어간 분석이 공개 주소로 새지 않는지를 확인한다. 누군가 실수로 규칙을 바꾸면 테스트가 먼저 깨진다.

테스트 이름은 한글 문장으로 쓴다. 예를 들어 `평단가가_들어간_분석은_공개하지_않고_있다는_것도_숨긴다()`처럼 쓰면, 테스트가 실패했을 때 무엇이 깨졌는지 이름만 보고 알 수 있다.

화면은 자바 테스트로 검사하기 어려워서 `puppeteer-core`로 실제 크롬을 띄워 클릭하고, 스크린샷을 찍고, axe 접근성 검사를 돌린다.

**커버리지 최소선.** 커버리지는 JaCoCo로 재고, CI 실행 화면에 패키지별 표로 남긴다. 그런데 숫자를 보여 주기만 해서는 아무도 지키지 않았다. 그래서 CI가 `jacoco:check`로 최소선을 검사하고, 못 미치면 PR을 막게 했다. 이때 최소선을 **어디에** 거는지가 중요하다. 계산 코드가 모인 패키지(공시 재무 계산, 분석, 기업분석 문장 등)에는 높은 선을 걸고, 전체에는 낮은 선(38%)만 걸었다. 바깥 API 클라이언트는 키가 있어야 의미 있게 테스트할 수 있어서 일부러 테스트하지 않는데, 전체 숫자를 높이라고 하면 그런 곳에 의미 없는 테스트만 늘어나기 때문이다.

**배운 것.** 커버리지 숫자를 처음 보고 우선순위가 바뀌었다. 공시 계산은 잘 덮여 있었는데, 정작 핵심인 증권사 합산 계산이 4%였다. 또 테스트로는 잡히지 않고 **눈으로 봐야만 잡히는 버그**도 있었다. 트리맵의 비중이 틀리게 그려진 버그는 axe 검사로는 위반 0이었다.

**실무에서는.** 단위 테스트는 빠르니 많이, DB까지 포함한 통합 테스트(Testcontainers)는 그보다 적게, 화면부터 끝까지 도는 E2E 테스트는 가장 적게 둔다. 이 모양을 "테스트 피라미드"라고 부른다. 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 쓰면 같은 버그가 다시 생기지 않는다.

**공부할 것.** JUnit 5, AssertJ, Mockito(mock, stub, spy의 차이), `@SpringBootTest`와 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`)의 차이, Testcontainers, 테스트 더블의 종류를 공부해 보자.

> **직접 해보기** — `@DataJpaTest`와 Testcontainers(MySQL)로 `Holding13FRepository.findByAccessionNoAndCusipIn`을 실제 DB에서 검증하는 테스트를 만들어 보자. 다만 이렇게 하면 CI에 도커가 필요해진다. 지금의 "바깥 없이 도는 테스트" 원칙과 무엇을 맞바꾸는지도 생각해 보자.

## 8. 빌드와 컨테이너 — Maven·Docker

<!-- diagram: map@ci,image | 8장은 CI 안에서 jar와 도커 이미지를 만드는 칸을 본다. -->

**지도에서 보면.** 7장의 테스트를 통과한 코드는 실행 파일(jar)로 묶이고, 다시 도커 이미지로 굳어 저장소(ghcr.io)에 올라간다. 이 이미지가 10장에서 서버에 올라가는 바로 그 꾸러미다.

> **이 장에서 배울 것** — 코드를 실행 파일(jar)로 만들고, 다시 어디서나 똑같이 뜨는 꾸러미(도커 이미지)로 만드는 과정을 본다.
>
> **먼저 알아둘 말** — [jar](#07-빌드배포인프라) · [Maven](#07-빌드배포인프라) · [이미지·컨테이너](#07-빌드배포인프라) · [볼륨](#07-빌드배포인프라) · [Compose·profile](#07-빌드배포인프라)

### 8.1 Maven

Maven은 의존성(라이브러리)을 받고, 컴파일하고, 테스트를 돌리고, 실행 파일로 묶는 도구다. 설정은 `pom.xml`에 있다. 저장소에는 Maven 자체 대신 `./mvnw`(Maven Wrapper)라는 스크립트가 있는데, 이것을 쓰면 누구의 PC에서든 같은 버전의 Maven이 받아져 실행된다. "내 PC에서는 되는데"를 줄이는 장치다.

`./mvnw package`를 실행하면 `target/portfolio-0.0.1-SNAPSHOT.jar`가 만들어진다. 이 jar에는 필요한 라이브러리와 화면 파일까지 모두 들어 있어서(fat jar), `java -jar` 한 줄로 앱이 뜬다.

**겪은 함정.** 이 저장소의 경로에는 한글(`주식`)이 들어 있다. 그 때문에 `mvnw spring-boot:run`으로 실행하면 클래스 경로가 깨져서 앱이 뜨지 않는다. 그래서 내 PC에서는 항상 jar를 만들어 실행한다. 커버리지 도구 JaCoCo도 같은 이유로 내 PC에서는 제대로 돌지 않아서, 리눅스인 CI에서만 잰다.

### 8.2 Dockerfile — 멀티 스테이지

**기초부터.** jar를 서버에서 실행하려면 서버에 맞는 버전의 자바가 깔려 있어야 하고, 시간대 같은 설정도 맞아야 한다. 서버를 새로 만들 때마다 이걸 손으로 맞추면 언젠가 어긋난다. 도커 이미지는 "자바와 설정과 jar"를 한 꾸러미로 굳혀서, 어느 서버에서 띄우든 똑같이 동작하게 한다.

**이 프로젝트에서는.** `Dockerfile`을 열어 보면 단계가 둘로 나뉘어 있다. 이것을 멀티 스테이지 빌드라고 한다.

1. **빌드 단계**: JDK가 든 이미지에서 jar를 만든다. 이때 `pom.xml`만 먼저 복사해서 의존성을 받고, 그다음에 소스를 복사해 컴파일한다. 도커는 단계마다 결과를 레이어로 저장해 두고 입력이 같으면 다시 쓰는데(레이어 캐시), 의존성 단계를 앞에 떼어 두면 소스만 바뀌었을 때 오래 걸리는 의존성 받기를 건너뛸 수 있다.
2. **실행 단계**: 자바 실행 환경(JRE)만 든 가벼운 이미지에 완성된 jar 하나만 복사한다. 빌드 도구와 소스 코드는 실행 이미지에 들어가지 않는다. 이미지 크기가 몇 배 작아지고, 운영 서버에 불필요한 도구가 올라가지 않는다.

실행 단계에서는 루트가 아닌 일반 사용자로 앱을 실행한다. 앱이 뚫리더라도 컨테이너 안에서 할 수 있는 일을 최소로 줄이려는 것이다. 시간대는 `Asia/Seoul`, 자바 힙은 `-Xmx512m`으로 정했다.

윈도우에서 만든 `mvnw` 파일은 줄 끝이 CRLF여서 리눅스 컨테이너에서 "bad interpreter" 오류를 내며 멈춘 적이 있다. 빌드 단계에서 `sed`로 줄 끝을 고치고, `.gitattributes`로 `*.sh` 파일은 항상 LF로 저장하게 해서 해결했다.

### 8.3 Docker Compose

컨테이너가 하나라면 `docker run`으로 충분하지만, 앱과 DB와 프록시를 함께 띄우려면 순서와 네트워크를 맞춰야 한다. Docker Compose는 이것을 YAML 파일 하나로 적어 두고 `docker compose up` 한 줄로 띄우게 해 준다.

이 저장소에는 compose 파일이 둘 있다. 개발용 `docker-compose.yml`은 앱과 MySQL을 띄운다. `depends_on`의 `condition: service_healthy`를 써서, MySQL이 접속을 받을 준비가 된 뒤에 앱을 띄운다. 그냥 MySQL을 먼저 띄우기만 하면 DB가 아직 준비 중일 때 앱이 접속을 시도하다 실패한다.

운영용 `deploy/compose.yml`은 앱, MySQL, Caddy를 띄운다. 운영용답게 몇 가지를 더 지킨다. 앱 포트를 바깥에 열지 않고, 로그 파일 크기와 컨테이너 메모리에 한도를 두고, 비밀번호에 기본값을 두지 않는다. `${VAR:?메시지}` 문법을 쓰면 값이 비어 있을 때 compose가 메시지를 내며 멈춘다. 비밀번호를 빠뜨린 채 배포되는 일을 막는 장치다.

**profile.** Prometheus, Grafana, Alertmanager에는 `profiles: [monitoring]`을 붙였다. 이 서비스들은 `COMPOSE_PROFILES=monitoring`일 때만 뜬다. 메모리가 작은 서버에서 선택 기능을 끄는 스위치다. 여기에도 함정이 있었다. compose는 **꺼진 profile 서비스의 `${VAR:?}`까지 검사**한다. 그래서 모니터링용 값에 필수 검사를 걸어 두었더니, 모니터링을 끈 서버에서는 앱 배포까지 막혔다([결정기록 014](결정기록.md#014-관측은-서버-안에서만-보고-ssh-터널로-연다)).

**`.env`의 함정.** compose가 읽는 `.env` 파일에 `KEY=   # 설명`처럼 값 없이 같은 줄에 설명을 적으면, compose는 `# 설명`을 값으로 읽는다. 셸에서는 `#` 뒤가 주석이지만 compose의 규칙은 다르다. 그래서 설명은 항상 윗줄에 쓴다.

**실무에서는.** 컨테이너 이미지가 배포의 단위다. 규모가 커지면 Kubernetes가 Compose의 역할(여러 컨테이너 띄우기, 죽으면 다시 띄우기, 네트워크 잇기)을 여러 서버에 걸쳐 한다.

**공부할 것.** 이미지와 컨테이너의 차이, 레이어 캐시, 볼륨, 도커 네트워크, 컨테이너 헬스체크, 이미지 크기 줄이기를 공부하고, 그다음 Kubernetes의 기본(Pod, Deployment, Service)으로 넘어가 보자.

> **직접 해보기** — `docker compose up -d --build`로 앱과 DB를 띄운 뒤 `docker compose ps`로 상태를, `docker compose logs -f app`으로 로그를 보자. `docker exec -it <mysql 컨테이너> mysql -u...`로 DB 안에도 들어가 보자.

## 9. CI/CD — GitHub Actions

<!-- diagram: map@code,ci,image,deploy | 9장은 아래쪽 줄 전체, 코드에서 배포까지의 자동화를 본다. -->

**지도에서 보면.** 7장과 8장에서 본 칸들을 GitHub Actions가 어떻게 하나의 흐름으로 잇는지 본다. 브랜치와 PR에서 시작해 CI, 이미지, 배포 스크립트까지 사람이 손대지 않고 이어진다.

> **이 장에서 배울 것** — 코드를 합치기 전에 자동으로 검사하고(CI), 합치면 자동으로 서버에 올리는(CD) 흐름을 본다.
>
> **먼저 알아둘 말** — [CI·CD](#07-빌드배포인프라) · [워크플로·잡·러너](#07-빌드배포인프라) · [PR·스쿼시 병합](#07-빌드배포인프라) · [시크릿](#06-보안) · [최소 권한](#06-보안)

### 9.1 브랜치 전략과 PR

`main` 브랜치에는 직접 밀어 넣을 수 없다. GitHub의 브랜치 보호 규칙이 막고 있다. 모든 변경은 **브랜치를 만들고 → PR을 올리고 → CI가 통과하면 → 스쿼시 병합**하는 순서를 밟는다. 혼자 하는 프로젝트라 승인자는 없지만, CI가 통과하지 않으면 관리자라도 합칠 수 없다.

스쿼시 병합은 PR 안의 여러 커밋을 하나로 눌러 `main`에 올리는 방식이다. 그래서 `main`의 이력은 "PR 하나 = 커밋 하나"로 깔끔하고, 문제가 생겼을 때 어느 PR이 원인인지 찾기 쉽다.

### 9.2 CI — `.github/workflows/ci.yml`

CI 워크플로는 PR을 올리거나 `main`에 합칠 때마다 돈다. 단계별로 무엇을 하는지, 실무에서는 어떤 의미인지 정리하면 다음과 같다.

| 단계 | 하는 일 | 실무에서 의미하는 것 |
|---|---|---|
| 트리거 | `main`에 푸시할 때와 PR을 올릴 때 돈다. | |
| `concurrency` | 같은 브랜치에 연달아 푸시하면 앞의 실행을 취소한다. | 낡은 실행에 러너 시간을 쓰지 않는다. |
| `permissions` | 기본은 읽기 권한만 주고, 이미지를 올리는 잡에만 `packages: write`를 준다. | **최소 권한 원칙**이다. 워크플로가 탈취되어도 할 수 있는 일이 적다. |
| Java 설정 | `actions/setup-java`로 자바를 깔고 Maven 의존성을 캐시한다. | 매번 의존성을 새로 받지 않아 빌드가 빨라진다. |
| 테스트 | `./mvnw -B test`를 돌린다. | 비밀값이 하나도 없이 돈다(7장). |
| 커버리지 최소선 | `./mvnw jacoco:check`로 최소선을 검사한다(규칙은 `pom.xml`). | 숫자를 보여 주기만 하면 아무도 지키지 않는다. 떨어지면 막아야 지켜진다. |
| 산출물 | 테스트 리포트와 커버리지 리포트를 7일 동안 보관한다. | 실패했을 때 원인을 나중에 찾아볼 수 있다. |
| 이미지 | `main`이면 `ghcr.io/...:sha-xxxxxxx`와 `:main` 태그로 이미지를 올린다. PR이면 만들어 보기만 하고 올리지 않는다. | 커밋 해시로 태그를 달면 되돌릴 버전을 정확히 집을 수 있다. |
| 배포 설정 검사 | 가짜 값을 넣고 `docker compose config`(모니터링 켬과 끔 둘 다), `promtool check config`를 돌리고, 대시보드 JSON을 `jq`로 검사한다. | 설정 파일도 코드처럼 합치기 전에 검사한다. 합친 뒤 서버에서 처음 터지면 이미 운영 반영이 시작된 뒤다. |

### 9.3 CD — `.github/workflows/deploy.yml`

배포 워크플로는 CI가 `main`에서 **성공했을 때만** 이어서 돈다(`workflow_run`). CI가 실패한 코드는 서버에 올라가지 않는다. 특정 버전을 손으로 배포하는 길(`workflow_dispatch`)도 열어 두었는데, 이전 태그를 넣으면 그대로 되돌리기가 된다.

배포는 중간에 끊으면 서버가 어중간한 상태로 남기 때문에, `concurrency`의 `cancel-in-progress`를 `false`로 두어 하나씩 차례로 돌게 했다.

서버 접속에 쓰는 SSH 키와 서버의 호스트 키는 GitHub Secrets에 넣는다. 호스트 키를 고정하고 `StrictHostKeyChecking yes`로 접속하면, 누군가 중간에서 가짜 서버로 바꿔치기하는 공격(중간자 공격)을 막을 수 있다. 이미지 저장소에 로그인할 때는 **그 작업 동안만 유효한 토큰**을 쓴다. 서버에 오래 살아 있는 토큰을 남기지 않기 위해서다. 서버가 아직 없어서 Secrets가 비어 있으면 배포 단계를 건너뛰고 성공으로 끝난다.

**실무에서는.** Jenkins, GitLab CI, GitHub Actions, ArgoCD(GitOps) 등 도구는 달라도 흐름은 같다. 테스트하고, 빌드하고, 결과물(이미지)을 저장하고, 배포하고, 검증하고, 실패하면 되돌린다. 금융권은 여기에 운영 반영 전 **승인 단계**(변경 관리)가 붙는다. GitHub의 `environment: production`에 승인자를 거는 것이 그 연습이 된다.

**공부할 것.** YAML 문법, Actions의 job·step·runner, Secrets, 아티팩트와 캐시, 배포 전략(Rolling, Blue-Green, Canary), GitOps를 공부해 보자.

## 10. 인프라와 배포 — 서버·Caddy·배포 스크립트

**지도에서 보면.** 9장의 흐름이 끝나는 곳이 서버다. deploy.sh가 새 이미지로 앱을 바꿔 끼우고, 그동안 앞단의 Caddy가 요청을 붙잡아 준다. 위쪽 줄과 아래쪽 줄이 만나는 지점이다.

> **이 장에서 배울 것** — 빈 서버를 준비하고, 앞단 프록시로 HTTPS를 붙이고, 새 버전을 올렸다가 문제가 있으면 되돌리는 과정을 본다.
>
> **먼저 알아둘 말** — [리버스 프록시](#01-웹과-네트워크) · [TLS 종료](#01-웹과-네트워크) · [방화벽](#07-빌드배포인프라) · [헬스체크](#07-빌드배포인프라) · [롤백](#07-빌드배포인프라) · [블루그린](#07-빌드배포인프라) · [SSH 터널](#07-빌드배포인프라)

서버 관련 파일은 모두 `deploy/`에 있고, 실제 절차는 [운영 7장](운영.md#7-배포)에 있다. 이 장은 각 파일이 왜 그렇게 생겼는지를 본다.

### 10.1 서버 준비 — `deploy/server-setup.sh`

새 서버에서 한 번 실행하는 스크립트다. 하는 일과 그 이유는 다음과 같다.

| 하는 일 | 왜 |
|---|---|
| 도커를 설치하고 사용자를 docker 그룹에 넣는다. | 매번 `sudo` 없이 도커를 쓰기 위해서다. |
| **iptables에서 80번과 443번을 연다.** | 오라클 클라우드의 우분투 이미지는 클라우드 콘솔에서 포트를 열어도 OS 방화벽이 한 번 더 막는다. "연결 시간 초과"의 흔한 원인이다. |
| 스왑을 2GB 잡는다. | 작은 서버에서 MySQL과 JVM의 메모리 사용이 겹치면 메모리가 바닥나(OOM) 컨테이너가 강제로 죽는다. |
| 시간대를 한국으로 맞춘다. | 로그 시각과 배치 시각을 한국 시간으로 맞춘다. |
| cron에 백업을 등록한다. | 매일 04:00에 DB를 덤프한다(11.4). |

**도커 포트는 호스트 방화벽을 우회한다.** 이것은 꼭 알아 둘 함정이다. compose에 `"3000:3000"`처럼 포트를 열면, 도커는 iptables의 nat 표(PREROUTING)에 규칙을 넣어 들어온 패킷의 목적지를 컨테이너 주소로 바꾼다. 목적지가 바뀐 패킷은 호스트로 들어오는 INPUT 경로가 아니라 FORWARD 경로를 탄다. 그래서 ufw로 3000번을 막아 두었어도 실제로는 열려 있다. 이 때문에 서버 안에서만 볼 포트(8081, 9090, 3000)는 `"127.0.0.1:3000:3000"`처럼 **루프백 주소에만** 묶는다. 제대로 묶였는지는 서버에서 `ss -ltn`을 실행해 `127.0.0.1:3000`으로 나오는지 보면 된다.

**공부할 것.** 리눅스 기본 명령, systemd, 방화벽(iptables, ufw)과 클라우드 보안 그룹의 차이, iptables의 표(filter, nat)와 체인(PREROUTING, INPUT, FORWARD), SSH 키 인증과 포트 포워딩(`ssh -L`), cron을 공부해 보자.

### 10.2 리버스 프록시와 HTTPS — Caddy

**기초부터.** 앱을 인터넷에 바로 내놓지 않고 앞에 문지기를 하나 둔다. 이 문지기가 [리버스 프록시](#01-웹과-네트워크)다.

<!-- diagram: rproxy | 앱은 HTTPS와 인증서를 모르고, Caddy가 앞에서 문지기를 한다. -->

```text
바깥 ──HTTPS 443──▶ Caddy ──HTTP 8080──▶ 앱 (바깥에 포트를 열지 않음)
                    │
                    ├ 암호 풀기(TLS 종료) · 인증서 자동 갱신
                    ├ /actuator 같은 위험한 주소 차단
                    ├ 진짜 사용자 IP 를 X-Forwarded-For 로 적어 넘김
                    └ 앱이 재시작하는 동안 요청을 붙잡았다가 넘김
```

이렇게 하면 앱은 HTTPS와 인증서를 몰라도 되고, 앱을 바꿔 끼우는 동안에도 바깥에서는 서버가 계속 살아 있는 것처럼 보인다.

**이 프로젝트에서는.** `deploy/Caddyfile`은 몇 줄뿐이다. 도메인 이름만 적으면 Caddy가 Let's Encrypt에서 인증서를 자동으로 받고 갱신한다(ACME 규약). `reverse_proxy app:8080` 한 줄이 바깥 요청을 앱으로 넘긴다. 앱 컨테이너는 바깥에 포트를 열지 않는다.

Caddy는 요청을 넘길 때 `X-Forwarded-For`(원래 사용자 IP)와 `X-Forwarded-Proto`(원래 HTTPS였는지)를 붙인다. 스프링은 `forward-headers-strategy: framework` 설정으로 이 헤더를 믿고 읽는다. 그래야 호출 한도를 진짜 사용자 IP로 세고, 쿠키의 `Secure` 속성과 HSTS를 HTTPS 기준으로 정할 수 있다.

`lb_try_duration 30s` 설정은 앱이 재시작하는 동안 502를 바로 돌려주지 않고 최대 30초까지 요청을 붙잡아 두었다가 앱이 뜨면 넘긴다. 리허설에서 배포할 때마다 13초 동안 나던 502가 이 설정 하나로 0이 되었다. `/actuator` 주소는 Caddy에서 막는다.

**실무에서는.** Nginx가 가장 흔하고, 클라우드에서는 L7 로드밸런서(AWS ALB 등)가 이 역할을 한다. TLS 종료, 경로별 라우팅, 압축, 요청 제한을 앞단에서 처리한다.

### 10.3 배포와 롤백 — `deploy/deploy.sh`

배포 워크플로가 서버에 SSH로 접속해 실행하는 스크립트다. 순서는 다음과 같다.

```
1. 띄우기 전 검사: .env 에 로그인 비밀번호·암호화 키·Secure 쿠키·Swagger 끄기가 있나 → 없으면 중단
2. 새 이미지 pull
3. stock-portfolio:current 를 새 태그로 옮기고 앱 컨테이너만 다시 만들기 (DB·Caddy 는 그대로)
4. 헬스체크(/actuator/health/readiness)가 UP 될 때까지 대기
   - 벽시계 기준 제한 시간, 컨테이너가 계속 죽으면 세 번 만에 실패 판정
5. 성공 → 지금/바로 앞 태그를 파일에 기록, 오래된 이미지 정리(둘은 남김)
   실패 → 앱 로그 출력, 바로 앞 태그로 자동 되돌림, 종료 코드 1 (워크플로 빨간불)
```

첫 단계부터 보자. 스크립트는 띄우기 전에 `.env`에 필수 보안값이 있는지 검사하고, 하나라도 빠졌으면 배포를 멈춘다. 지켜야 할 설정을 사람의 기억에 맡기지 않고 스크립트가 검사하게 한 것이다.

새 이미지를 받은 뒤에는 앱 컨테이너만 바꿔 끼운다. DB와 Caddy는 그대로 둔다. 그다음 헬스체크 주소가 "UP"이 될 때까지 기다린다. readiness는 DB 연결까지 확인하기 때문에, DB에 붙지 못하는 버전은 여기서 걸러진다. 정해진 시간 안에 UP이 되지 않거나 컨테이너가 계속 죽으면 실패로 판정하고, 앱 로그를 남긴 뒤 바로 앞 버전으로 자동으로 되돌린다. 그리고 종료 코드 1을 내서 GitHub의 배포 워크플로를 빨간불로 만든다.

내 PC에서 실제 이미지로 리허설을 했다. 일부러 깨진 이미지도 올려서 자동 되돌림까지 확인했다. 결과는 [운영 7장](운영.md#7-배포)에 있다.

**배운 것.** 세 가지가 남았다. 첫째, 헬스체크를 기다린 시간을 "잠든 시간"의 합으로 세면 실제로는 1.5배 넘게 기다린다. curl이 응답을 기다린 시간이 빠지기 때문이다. 그래서 셸의 `SECONDS` 변수로 실제 경과 시간(벽시계)을 잰다. 둘째, **DB는 되돌아가지 않는다.** 이미지는 한 줄로 되돌릴 수 있지만 마이그레이션은 그렇지 않다. 그래서 스키마는 더하기만 한다(3.8). 셋째, 지켜야 할 설정은 사람이 아니라 스크립트가 검사해야 한다.

**실무에서는.** 지금 방식은 "한 대를 바꿔 끼우고, 앞단이 그동안 버텨 주는" 방식이다. 진짜 무중단 배포는 새 버전을 옆에 띄운 뒤 트래픽을 한 번에 넘기는 블루그린 방식이나, 여러 대를 하나씩 바꾸는 롤링 방식으로 한다. 블루그린은 앱을 두 벌 띄워야 해서 메모리가 두 배 들기 때문에, 무료 서버에서는 보류했다.

**공부할 것.** 셸 스크립트(`set -euo pipefail`, 종료 코드), 헬스체크의 liveness와 readiness 차이, 배포 전략 비교, 롤백 시나리오 설계를 공부해 보자.

> **직접 해보기** — [운영 7장](운영.md#7-배포)의 리허설을 그대로 따라 해 보자. 핵심은 로컬 레지스트리(`registry:2`)에 일부러 뜨자마자 죽는 이미지를 올리고, `./deploy.sh`가 그것을 되돌리는 모습을 눈으로 확인하는 것이다.

## 11. 운영 — 헬스체크·지표·로그·백업

<!-- diagram: map@monitoring,mysql | 11장은 서버가 뜬 뒤 운영을 위한 Prometheus와, 백업 대상인 MySQL을 본다. -->

**지도에서 보면.** 10장까지는 서버에 올리는 이야기였다. 11장은 올린 뒤의 이야기다. Prometheus가 앱의 지표를 긁어 가고, 문제가 생기면 텔레그램으로 알린다. 로그는 앱 안에서 요청 번호를 달고 남고, MySQL은 매일 백업된다.

> **이 장에서 배울 것** — 앱이 지금 괜찮은지(헬스체크, 지표), 무슨 일이 있었는지(로그), 망가지면 되살릴 수 있는지(백업)를 알아보는 방법을 본다.
>
> **먼저 알아둘 말** — [관측](#08-관측과-운영) · [지표·태그](#08-관측과-운영) · [Prometheus·pull](#08-관측과-운영) · [MDC](#08-관측과-운영) · [구조화 로그](#08-관측과-운영) · [알림 피로](#08-관측과-운영) · [런북](#08-관측과-운영)

서비스를 띄운 뒤에는 "지금 잘 돌고 있나", "아까 무슨 일이 있었나", "망가지면 되살릴 수 있나"라는 질문에 답할 수 있어야 한다. 이 장은 그 세 질문에 답하는 장치를 차례로 본다. 헬스체크와 지표는 첫째 질문에, 로그는 둘째 질문에, 백업은 셋째 질문에 답한다.

### 11.1 헬스체크

**무엇인가.** 헬스체크는 "지금 괜찮은가"를 묻는 주소다. 배포 스크립트나 로드밸런서가 이 주소를 주기적으로 불러 보고, 답이 이상하면 그 서버로 요청을 보내지 않거나 배포를 되돌린다.

**이 프로젝트에서는.** 스프링 부트 Actuator가 두 가지 헬스체크를 제공한다. `/actuator/health/liveness`는 "프로세스가 살아 있는가"를, `/actuator/health/readiness`는 "DB 연결까지 포함해 요청을 받을 준비가 되었는가"를 답한다. 이 주소들은 **관리 포트 8081**로 따로 떼어 서버 안(127.0.0.1)에서만 열었다. 배포 스크립트는 readiness가 UP이 되는지를 보고 배포의 성공과 실패를 정한다(10.3).

**왜 둘로 나누나.** liveness에 DB 검사를 넣으면 사고가 난다. DB가 잠깐 죽었을 때 liveness가 실패하고, 쿠버네티스 같은 도구는 "프로세스가 죽었다"고 보고 앱을 재시작한다. 그런데 문제는 앱이 아니라 DB라서 재시작해도 다시 실패하고, 앱은 끝없이 재시작을 반복한다. 그래서 "살아 있는가"와 "일할 준비가 되었는가"를 나눈다.

**실무에서는.** Kubernetes의 livenessProbe와 readinessProbe, 클라우드 로드밸런서의 헬스체크가 이런 주소를 본다.

### 11.2 지표

**무엇인가.** 지표(metric)는 시간에 따라 재는 숫자다. 초당 요청 수, 응답 시간, 메모리 사용량, 바깥 API 실패 수 같은 것이 지표다. 로그가 "무슨 일이 있었나"를 한 줄씩 적는다면, 지표는 "얼마나 자주, 얼마나 빨리"를 숫자로 보여 준다.

**지표를 내보내는 쪽 — 앱.** 스프링 부트는 Micrometer라는 라이브러리로 지표를 재고, `/actuator/prometheus` 주소에서 글자로 내보낸다. JVM 메모리, GC, HTTP 응답 시간, DB 커넥션 풀 같은 기본 지표는 저절로 나온다.

**바깥 API 호출 지표.** 바깥 API를 몇 번 불렀고 얼마나 실패했는지를 보는 지표(`http_client_requests_seconds`)는 조금 신경 써야 나온다. 스프링이 관측 기능을 미리 연결해 둔 `RestClient.Builder`를 **주입받아서** 만든 클라이언트에서만 이 지표가 나온다. `RestClient.builder()`로 직접 만들면 그 연결을 건너뛴다. 이 프로젝트도 처음에는 직접 만들어서 지표가 하나도 없었다.

이 지표에는 보안 문제도 있다. 지표의 태그에 요청 주소가 그대로 실리는데, 바깥 API 키를 주소의 쿼리에 붙이는 코드가 하나라도 생기면 키가 Prometheus에 고스란히 남는다. 그래서 `SafeClientRequestObservationConvention`이 주소에서 쿼리와 호스트를 버리고, 키처럼 보이는 조각은 `none`으로 바꾼다. "지표에 무엇이 실리는가"도 보안 검토 대상이다.

**앱이 직접 만든 지표.** 업무 결과도 지표로 내보낸다. Claude 호출 수와 토큰(`claude_requests`, `claude_tokens`), 재시도 횟수(`http_client_retries`), 서킷 브레이커 상태(`resilience4j_circuitbreaker_state`), 장 마감 배치 결과(`portfolio_snapshot_runs_total{outcome}`, `portfolio_reconciliation_mismatches`), 공시 재무 배치 결과(`filing_prefetch_runs_total{outcome}`)가 있다. 배치나 업무 결과까지 지표로 내보내면, 장애와 똑같은 알림 경로를 탈 수 있다.

**지표를 모으는 쪽 — Prometheus.** Prometheus는 **당겨 가는(pull)** 방식이다. 앱이 어딘가로 지표를 보내는 것이 아니라, Prometheus가 `deploy/monitoring/prometheus.yml`에 적힌 `app:8081/actuator/prometheus`를 15초마다 긁어 가서 시계열 DB에 쌓는다. 이 방식에는 좋은 점이 있다. 긁기에 실패하면 `up` 지표가 0이 되므로, "앱이 죽었다"는 사실 자체가 지표가 된다. 리허설에서는 앱을 멈추고 약 12초 만에 0이 되었다. 앱은 Prometheus가 있는지조차 몰라도 된다.

**지표를 보는 쪽 — Grafana.** Grafana는 Prometheus의 지표를 그래프로 보여 준다. 데이터소스(`provisioning/datasources/prometheus.yml`)와 대시보드(`dashboards/stock-portfolio.json`)를 파일로 두고 Grafana가 뜰 때 읽게 했다. 이것을 프로비저닝이라고 한다. 화면에서 손으로 만든 대시보드는 서버를 새로 깔면 사라지지만, 파일로 두면 서버를 새로 깔아도 같은 화면이 뜨고, 바꾼 내용이 PR로 남는다. 그래서 화면에서 저장하는 기능은 막아 두었고, 고칠 때는 JSON을 내보내 파일을 바꾼다.

Prometheus와 Grafana는 서버의 127.0.0.1에만 열려 있다. 그래서 **SSH 터널로 본다.** `ssh -L 3000:127.0.0.1:3000 ubuntu@서버`를 실행하면 내 PC의 3000번 포트가 서버 안의 3000번 포트로 이어지고, 내 PC에서 `localhost:3000`을 열면 Grafana가 보인다. 인터넷에 로그인 화면을 하나 더 내놓지 않는 방법이다([운영 7장 지표 보기](운영.md#지표-보기)).

**알림.** 알림 규칙은 파일과 테스트로 관리한다. 지금 규칙은 11개다. `deploy/monitoring/alerts.yml`에 "언제 울릴지"를 PromQL로 쓰고, `alerts.test.yml`에 가짜 시계열을 넣어 "이 시각에는 울려야 한다", "이 시각에는 울리면 안 된다"를 적는다. CI가 `promtool test rules`로 이것을 돌린다. 알림도 코드처럼 리뷰하고 테스트하는 것이다.

알림을 설계할 때는 **사람이 지금 무언가를 해야 하는 것만** 알린다는 원칙을 지켰다. `for: 2m`처럼 상태가 일정 시간 이어질 때만 울리게 해서, 한 번 튄 값으로는 울리지 않게 했다. 앱을 다시 띄운 직후 한 번 나오는 정상적인 실패(토스 401)도 뺐다. 알림이 잦으면 결국 아무도 보지 않게 되는데, 이것을 "알림 피로"라고 한다.

알림을 보내는 텔레그램 봇 토큰은 환경변수에서 컨테이너 안의 파일(`bot_token_file`)로만 넘긴다. 설정 파일, 명령줄(`ps`로 남에게 보인다), 로그 어디에도 남지 않게 하려는 것이다.

**실무에서는.** 증권사의 관제도 같은 구조다. 지표를 모으는 수집기, 시계열 저장소, 대시보드, 알림이 나뉘어 있고, 관제 화면은 내부망에서만 연다. 클라우드에서는 CloudWatch나 Datadog이 이 역할을 한다.

**공부할 것.** RED 지표(Rate, Errors, Duration), USE 지표(Utilization, Saturation, Errors), PromQL의 기본, 알림 기준값을 정하는 법을 공부해 보자.

> **직접 해보기** — SSH 터널을 연 뒤 Prometheus 화면에서 `up{job="stock-portfolio"}`를 쳐 보자. 그 상태로 앱 컨테이너를 멈췄다가 다시 켜면서, 값이 0이 되었다가 1로 돌아오기까지 걸리는 시간을 재 보자.

### 11.3 로그

**무엇인가.** 로그는 "그때 무슨 일이 있었나"를 남기는 기록이다. 운영에서 중요한 것은 로그가 많으냐가 아니라 **찾을 수 있느냐**다. 동시에 들어온 요청 수십 개의 로그 줄이 뒤섞이면, 오류 한 줄을 보고도 그것이 어느 요청에서 나온 것인지 알 수 없다.

**이 프로젝트에서는.** 요청마다 번호를 붙이고, 그 번호를 모든 로그 줄에 찍는다.

<!-- diagram: reqid | 요청 번호가 모든 로그 줄과 응답 헤더에 붙고, 작업 스레드로 넘어갈 때도 복사된다. 배치는 새 번호를 만든다. -->

```text
브라우저 ──▶ Caddy ── X-Request-Id: 0f8fad5b-… (요청마다 UUID) ──▶ 앱
                                                                   │
              RequestIdFilter: 번호를 MDC(스레드별 로그 문맥)에 넣음   │
              ├─ 이 요청이 남기는 모든 줄에 requestId 가 자동으로 붙음  │
              ├─ 응답 헤더 X-Request-Id 로 돌려줌 (화면 오류 → 번호로 검색)
              └─ 끝나면 access 한 줄: GET /api/... 200 87ms
                                                                   │
              AI 분석은 백그라운드 스레드로 넘어감 ── LogContext.carry ─┘ 번호를 복사해 감
              13F 배치는 요청이 없음 ── LogContext.job("batch-13f") ── 새 번호
```

Caddy가 요청마다 UUID를 만들어 `X-Request-Id` 헤더에 담아 넘긴다. 앱의 `RequestIdFilter`가 이 번호를 MDC에 넣는다. MDC는 스레드마다 따로 붙는 로그 꼬리표 저장소인데, 여기 넣은 값은 그 스레드가 찍는 모든 로그 줄에 자동으로 붙는다. 같은 번호를 응답 헤더로도 돌려주기 때문에, 화면에서 오류가 났을 때 그 번호로 서버 로그를 바로 찾을 수 있다. 요청이 끝나면 메서드, 주소, 상태 코드, 걸린 시간을 담은 접근 로그 한 줄을 남긴다.

여기서 조심할 점이 있다. **MDC는 스레드마다 따로라서, 일을 다른 스레드로 넘기면 번호가 사라진다.** AI 분석은 요청 스레드에서 작업 스레드로 넘어가므로, 넘길 때 `LogContext.carry`로 번호를 복사해 가고 일이 끝나면 치운다. 톰캣은 스레드를 재사용하기 때문에, 치우지 않으면 다음 요청이 앞 요청의 번호를 물려받는다. 배치처럼 애초에 요청이 없는 일은 `LogContext.job("batch-…")`으로 새 번호를 만든다.

바깥에서 들어온 번호는 모양(영숫자와 하이픈 8~64자)이 맞을 때만 받는다. 번호에 줄바꿈을 섞어 보내면 가짜 로그 줄을 끼워 넣을 수 있기 때문이다. 이것을 로그 인젝션이라고 한다.

**로그의 모양.** 로그는 두 가지 모양으로 찍는다(`logback-spring.xml`). 내 PC에서는 사람이 읽기 좋은 줄글로, 서버에서는 `LOG_FORMAT=json`으로 **한 줄에 JSON 하나**씩 찍는다. JSON이면 `jq 'select(.requestId=="…")'`로 한 요청의 줄만, `select(.level=="ERROR")`로 오류만 뽑을 수 있다. 보는 명령은 [운영 - 로그 보기](운영.md#로그-보기)에 있다. 컨테이너 로그는 `json-file` 드라이버에 크기 한도(20MB 파일 5개)를 걸어, 로그가 디스크를 가득 채워 서버가 멈추는 사고를 막는다.

**겪은 함정.** 처음에는 두 가지 모양 중 하나의 출력기(appender)만 연결했다. 그랬더니 logback이 "쓰지 않는 appender가 있다"는 경고와 함께 내부 상태를 수십 줄의 줄글로 쏟아내서, JSON 로그 맨 앞을 더럽혔다. 단위 테스트는 모두 통과했고, jar를 띄워 보고서야 알았다. 둘 다 연결하고 필터(`LogFormatFilter`)로 하나만 통과시켜 풀었다. SQL 출력(`show-sql`)과 시작 배너도 로거를 거치지 않는 줄글이라 서버에서는 끈다.

**실무에서는.** 로그를 서버마다 두지 않고 한곳으로 모은다(ELK, Loki, CloudWatch). 서비스가 여럿이면 같은 번호를 다음 서비스로 헤더에 담아 넘겨서 전체 흐름을 잇는다. 이것을 분산 추적이라고 하며, OpenTelemetry나 Micrometer Tracing의 trace ID가 이 번호의 발전된 형태다. 증권사에서는 주문과 체결 한 건을 처음부터 끝까지 따라가는 **거래 추적**이 감사 대응의 기본이다. 개인정보와 토큰은 로그에 남기기 전에 가린다.

**공부할 것.** MDC, 구조화 로그, 로그 레벨 정책(무엇을 INFO, WARN, ERROR로 남길지), 분산 추적(trace와 span), 로그 인젝션을 공부해 보자.

> **직접 해보기** — 앱을 `LOG_FORMAT=json`으로 띄우고 `curl -H "X-Request-Id: test-12345678" localhost:8080/api/public/analysis/MSFT -i`를 보내 보자. 응답 헤더와 서버 로그에서 같은 번호를 찾을 수 있을 것이다.

### 11.4 백업과 복구

DB 백업은 `deploy/backup.sh`가 매일 04:00에 한다. 이 스크립트에는 몇 가지 장치가 들어 있다.

`mysqldump --single-transaction`으로 덤프를 뜬다. 이 옵션을 쓰면 테이블을 잠그지 않고 한 시점의 모습을 그대로 뜰 수 있어서(InnoDB 엔진의 기능), 백업하는 동안 앱을 멈출 필요가 없다. 덤프가 끝나면 파일 끝에 `Dump completed`가 있는지 확인한다. 디스크가 차거나 연결이 끊겨 중간에 멈춘 파일을 성공한 백업으로 착각하지 않으려는 것이다. 백업은 14일 동안 보관하고, 파일 권한은 `chmod 600`으로 주인만 읽게 한다. 서버가 통째로 날아가면 서버 안의 백업도 같이 날아가므로, 선택적으로 rclone으로 서버 밖에도 복사한다. 증권사 토큰의 암호화 키는 백업과 **따로** 보관한다. 둘을 같이 두면 백업이 새어 나갔을 때 토큰까지 풀린다.

무엇을 지켜야 하는지는 3.2에서 본 "원본이 여기뿐인 테이블"이다. 바깥에서 다시 받을 수 있는 테이블은 잃어도 다시 채워지지만, 직접 입력한 보유와 돈을 주고 만든 분석과 지난 날의 스냅샷은 백업 말고는 되살릴 길이 없다.

**실무에서는.** "백업은 복구해 봐야 백업이다"라는 말이 있다. 백업 파일이 있어도 실제로 되살려 본 적이 없으면 정말 되살아나는지 알 수 없다. 그래서 정기적으로 복구 훈련을 하고, RPO(데이터를 얼마나 잃어도 되는가)와 RTO(얼마 만에 되살려야 하는가)를 정해 둔다.

> **직접 해보기** — 백업 파일을 빈 MySQL 컨테이너에 복구해 보자([운영 7장 백업과 되살리기](운영.md#백업과-되살리기)). 그리고 앱을 그 DB에 붙여 화면이 그대로 나오는지 확인해 보자.

## 12. 협업과 문서

<!-- diagram: map@code | 12장은 코드와 함께 저장소에 있는 문서와 PR을 본다. -->

**지도에서 보면.** 지도의 시작점인 "브랜치 · PR" 칸에는 코드만 있는 것이 아니다. 왜 그렇게 했는지 남기는 결정기록, 운영 매뉴얼, 회고, 그리고 이 노트까지 같은 저장소에서 PR로 함께 바뀐다.

> **이 장에서 배울 것** — 문서를 수명별로 나눠 두는 방법과, 각 문서가 실무의 무엇에 해당하는지를 본다.

이 저장소의 마크다운 문서는 여덟 개뿐이다. 문서마다 "언제 바뀌는가"가 다르게 나눠져 있다. 지금 구조를 적는 문서는 구조가 바뀔 때마다 고치고, 과거의 결정을 적는 문서는 고치지 않고 덧붙이기만 한다. 이렇게 수명으로 나눠 두면 새 내용을 어디에 써야 할지 헷갈리지 않는다.

| 문서 | 실무에서 해당하는 것 |
|---|---|
| [결정기록](결정기록.md) | **ADR**(Architecture Decision Record)이다. "그때 왜 그렇게 정했나"를 적는다. 쓴 기록은 고치지 않고, 결정이 바뀌면 새 기록을 덧붙인다. |
| [아키텍처](아키텍처.md) | 시스템 설계서다. 현재형으로 쓰고, 구조가 바뀌면 고친다. |
| [운영](운영.md) | 운영 매뉴얼이자 런북이다. |
| [로드맵](로드맵.md) | 백로그다. 끝난 일은 지운다. |
| [개발일지](개발일지.md) | 회고(retrospective)다. 덧붙이기만 한다. |
| `CLAUDE.md` | 팀의 코딩 규칙이자 새로 온 사람을 위한 안내서다. |
| 커밋과 PR 설명 | 변경 이력이다. "무엇을 바꿨나"보다 "왜 바꿨나"를 쓴다. |
| `.claude/skills/tech-note/` | 문서 자동화다. 이 노트를 코드에 맞게 고치는 절차와 스크립트가 있다. `facts.js`는 테이블 수와 테스트 수를 코드에서 뽑고, `linkcheck.js`는 링크를 검사하고, `build-html.js`는 목차와 용어 풍선이 붙은 HTML 판을 만들면서 글자 그림을 `html/diagrams.js`의 명세로 그린 그림으로 바꾼다. 실무에서 말하는 "문서도 코드처럼 검사한다(docs-as-code)"에 해당한다. |

**주석의 원칙.** 코드가 무엇을 하는지는 코드가 스스로 말한다. 그래서 주석에는 **왜 그렇게 했는지**를 쓴다. 예를 들어 `// 13F 에 나오는 미국 티커만. BRK.B·BF-B 같은 점·하이픈 포함`처럼, 코드만 봐서는 알 수 없는 이유를 적는다.

**같은 내용을 두 곳에 쓰지 않는다.** 같은 내용이 두 문서에 있으면 한쪽만 고쳐지고 결국 어긋난다. 그래서 다른 문서에 있는 내용은 링크로 건다. 화면 코드에서 AI 분석 렌더러를 한 파일로 모은 것도 같은 이유다(6.1).

## 14. 면접에서 받을 만한 질문

> **이 장에서 배울 것** — 면접에서 이 프로젝트를 설명할 때 나올 법한 질문과, 답할 때 가리킬 곳을 모았다.

답은 외우기보다 "무엇을 했고, 왜 그렇게 했고, 대가는 무엇이었나"의 순서로 말할 수 있으면 된다. 괄호 안의 절을 다시 읽어 보면 그 근거가 있다.

1. **배포 중에 장애가 나면 어떻게 되나요?** 헬스체크가 실패하면 `deploy.sh`가 바로 앞 버전으로 자동으로 되돌린다. 리허설로 직접 확인했다. 다만 DB 마이그레이션은 되돌릴 수 없어서 스키마는 더하기만 하고, 지울 때는 expand/contract로 나눈다(3.8, 10.3).
2. **무중단 배포인가요?** 완전한 무중단은 아니다. 앱을 바꿔 끼우는 동안 앞단 Caddy가 요청을 붙잡아 두어서 실패 응답은 0이다. 블루그린은 메모리가 두 배 들어서 무료 서버에서는 보류했다(10.2, 10.3).
3. **비밀값은 어떻게 관리하나요?** `.env`는 서버에만 두고, 배포 키는 GitHub Secrets에 둔다. 증권사 토큰은 DB에 AES-GCM으로 암호화하고 키는 DB 밖에 둔다. 이미지 저장소 토큰은 작업 동안만 유효하다(5.4, 9.3).
4. **CSRF는 왜 필요하고 어떻게 막았나요?** 브라우저가 다른 사이트에서 시작된 요청에도 쿠키를 자동으로 붙이기 때문이다. `XSRF-TOKEN` 쿠키 값을 헤더로 다시 보내게 했고, `SameSite=Strict`로 한 번 더 막았다(5.2).
5. **인라인 스크립트를 왜 금지했나요?** CSP로 우리 파일만 실행하게 해서, XSS가 뚫려도 주입된 스크립트가 실행되지 않게 하려고 했다(5.3).
6. **외부 API가 느리거나 죽으면 어떻게 되나요?** 연결 5초·응답 30초 타임아웃, GET만 5xx와 네트워크 오류에 재시도, 호스트별 서킷 브레이커, 실패한 부분만 비우는 fail-soft, 캐시를 차례로 둔다. 회로가 열리면 `CircuitBreakerOpen` 알림이 온다(4장).
7. **테스트가 외부 API를 부르지 않는 이유는요?** CI에 비밀값이 없어도 돌아야 하고, 바깥 상태와 상관없이 항상 같은 결과가 나와야 하기 때문이다(7장).
8. **공개 화면으로 개인정보가 새지 않게 한 방법은요?** 분석을 저장할 때 평단가가 들어갔는지 열(`includes_position`)로 표시하고, 공개 주소는 그런 분석이 있다는 사실조차 숨긴다. 이 규칙을 테스트로 고정했다(3.5, 7장).
9. **JPA에서 성능 문제를 겪은 적이 있나요?** 종목 하나를 보려고 기관마다 보유 줄 전체를 읽던 것을, 그 종목의 CUSIP만 `IN` 조건으로 읽게 바꿨다(3.7).
10. **FK를 왜 걸지 않았나요? JSON 열은 왜 썼나요?** 13F를 쓰는 곳이 배치 하나뿐이고, 티커는 나중에 채워서 비어 있는 것이 정상이기 때문이다. JSON 열은 통째로 읽고 쓰는 문서에만 쓰고, 거르는 데 쓰는 값은 열로 꺼냈다([3.4](#34-fk-제약을-걸지-않은-이유), [3.5](#35-json을-통째로-넣은-열--analysis_json-financials_json)).
11. **AI(LLM)를 쓸 때 숫자는 어떻게 믿나요?** 숫자는 앱이 계산해서 사실로 넣고, LLM에게는 조사만 맡긴다([결정기록 003](결정기록.md#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다)). 공개 화면의 문장은 LLM이 아니라 규칙(`StockNotes`)이 만든다.
12. **배치가 두 번 돌거나 실패하면요?** 날짜가 키라서 한 트랜잭션에서 합계를 고쳐 쓰고 그날 줄을 지우고 새로 넣는다. 과거는 다시 만들 수 없으니 그날 18시와 20시에 재시도하고, 증권사 하나라도 실패하면 저장하지 않는다([15.4](#154-장-마감-스냅샷과-대사--멱등-배치)).
13. **숫자가 맞는지 어떻게 아나요?** 매일 대사를 한다. 앱이 더한 합계와 증권사가 같은 응답에 준 계좌 합계를 비교해 0.1%를 넘으면 알림이 온다(2.4).
14. **장애가 나면 로그를 어떻게 찾나요?** 요청마다 번호를 붙인다(Caddy의 UUID → MDC → 응답 헤더). 백그라운드 스레드에도 번호를 복사해 가고, 서버 로그는 JSON이라 jq로 번호와 레벨을 거른다([15.1](#151-요청-id와-json-로그--한-요청을-끝까지-따라가기)).
15. **커버리지 기준은 몇 %인가요?** 전체는 38%로 낮게 두고, 계산 코드 패키지에만 따로 높은 선을 걸었다. 바깥 API 클라이언트를 억지로 테스트하는 일을 피하려는 것이다([15.3](#153-커버리지-최소선--숫자를-보여주기만-하면-아무도-안-본다)).
16. **`@Transactional`이 동작하지 않는 경우를 아나요?** 스프링은 프록시로 트랜잭션을 거는데, 같은 클래스 안에서 `this.메서드()`로 부르면 프록시를 거치지 않는다. 그래서 저장만 맡는 빈(`CompanyAnalysisStore`)을 따로 두었다([2.7](#27-프록시--스프링이-몰래-끼워-넣는-대리-객체)).
17. **배치가 바깥 장애 때 멀쩡한 데이터를 망치지 않게 한 방법은요?** 덮어쓰기 전에 입력(발행주식수)부터 확인하고, 받지 못한 종목은 건너뛴다. 토스가 통째로 막히면 첫 종목에서 멈춘다(`FilingPrefetchService`, [2.4](#24-스케줄-배치)).

### 15.1 요청 ID와 JSON 로그 — 한 요청을 끝까지 따라가기

**문제.** 동시에 들어온 요청의 로그 줄이 섞여서, 오류 한 줄을 봐도 어느 요청에서 나온 것인지 알 수 없었다. AI 분석은 몇 분 뒤에 다른 스레드에서 실패를 남기기 때문에, 그 실패를 처음 요청과 이을 방법도 없었다. 로그가 줄글이라 grep 말고는 찾을 도구도 없었다.

**해결.** Caddy가 요청마다 UUID를 붙이고, `RequestIdFilter`가 그 번호를 MDC에 넣고 응답 헤더로도 돌려준다. 백그라운드 스레드로 넘어갈 때는 `LogContext.carry`로 번호를 복사해 가고, 배치는 `LogContext.job("batch-…")`으로 새 번호를 만든다. 서버에서는 `LOG_FORMAT=json`으로 한 줄에 JSON 하나씩 찍는다.

**코드.** `config/RequestIdFilter.java`, `common/LogContext.java`, `config/LogFormatFilter.java`, `logback-spring.xml`, `deploy/Caddyfile`에 있다.

**실무.** 분산 추적의 가장 작은 형태(trace ID)다. 증권사의 거래 추적과 감사 로그가 같은 생각이다. Loki나 ELK 같은 수집기는 JSON 필드로 로그를 거른다.

**겪은 함정.** 세 가지였다. 첫째, 출력기를 하나만 연결했더니 logback이 경고와 함께 내부 상태를 줄글로 쏟아냈다. 둘 다 연결하고 필터로 하나만 통과시켜 풀었다. 둘째, SQL 출력과 시작 배너는 로거를 거치지 않는 줄글이라 서버에서 껐다. 셋째, 바깥에서 보낸 번호에 줄바꿈을 넣으면 가짜 로그 줄을 만들 수 있어서(로그 인젝션) 모양을 검사하게 했다. 자세한 설명은 [11.3 로그](#113-로그)에, 보는 명령은 [운영 - 로그 보기](운영.md#로그-보기)에 있다.

### 15.2 캐시 예열 — 첫 방문자도 캐시에서

**문제.** 13F 조회 결과는 캐시에 들고 있다가, 배치가 데이터를 바꾸면 통째로 비운다. 그런데 비운 직후의 첫 방문자는 "같이 산 종목" 계산(1~4초)을 혼자 기다려야 했다. 배포로 앱이 다시 떠도 마찬가지였다.

**해결.** `InstitutionCacheWarmer`가 앱이 뜬 직후(`ApplicationReadyEvent`)와 배치가 끝난 직후(`ThirteenFDataChangedEvent`)에, 첫 화면과 기관 상세에서 쓰는 조회 22건을 뒤에서 미리 계산해 둔다. 이때 순서가 중요하다. 캐시를 비우는 쪽보다 채우는 쪽이 먼저 돌면 옛 값을 채운 꼴이 된다. 그래서 비우기(`@Order(0)`)가 채우기(`@Order(100)`)보다 먼저 돌게 순서를 고정하고, 테스트로 확인했다.

**결과.** "같이 산 종목"의 첫 요청이 1.35초에서 0.02초가 되었다(내 PC 기준).

**실무.** 캐시 워밍이라고 부른다. 배포 직후 트래픽을 조금씩 늘려 넘기는 것(슬로 스타트)과 목적이 같다.

**겪은 함정.** 예열을 붙인 뒤에도 앱이 뜬 후 맨 첫 요청은 0.6초가 걸렸다. 서블릿 초기화 때문이라고 짐작하고 설정을 넣었는데, 로그를 보니 초기화는 2ms였다. 짐작이 틀렸으니 설정을 되돌렸다. 캐시는 제대로 일하고 있었고(SQL이 나가지 않았다), 0.6초는 JSON 직렬화 같은 첫 실행 비용이었다. **짐작으로 고치지 말고, 재 보고 고쳐야 한다**는 교훈이 남았다.

### 15.3 커버리지 최소선 — 숫자를 보여주기만 하면 아무도 안 본다

**문제.** 커버리지를 CI 화면에 표로 띄우기만 했다. 숫자가 떨어져도 아무 일이 일어나지 않으니 아무도 지키지 않았다.

**해결.** CI가 테스트를 돈 뒤 `./mvnw jacoco:check`로 최소선을 검사하게 했다. 전체에는 38%를 걸고, 계산 코드 패키지에는 따로 높은 선을 걸었다(`external.filing` 75%, `service.analysis`·`service.stock`·`external.edgar` 60%, `external.dart` 45%). 선은 지금 수치보다 몇 %p 아래에 두었고, 내리지 않고 올리기만 한다.

**코드.** `pom.xml`의 jacoco `<rules>`와 `.github/workflows/ci.yml`의 "커버리지 최소선" 단계에 있다.

**실무.** SonarQube 같은 도구의 품질 게이트와 같다. 여기서 중요한 것은 숫자보다 **어디에** 거느냐다. 키가 필요한 바깥 API 클라이언트까지 높이라고 하면 의미 없는 테스트만 늘어난다.

**겪은 함정.** 두 가지였다. 첫째, 검사를 빌드 단계에 묶었더니 내 PC에서 빌드가 멈췄다. 한글 경로 때문에 JaCoCo가 내 PC에서 제대로 돌지 않기 때문이다. 그래서 CI에서만 따로 부르게 했다. 둘째, 실행 데이터가 없으면 `jacoco:check`는 "건너뜀"만 찍고 **통과**로 끝난다. `-q` 옵션으로 조용히 돌리면 그 메시지조차 보이지 않는다. 그래서 "All coverage checks have been met"라는 문구가 없으면 실패로 처리하게 했다.

### 15.4 장 마감 스냅샷과 대사 — 멱등 배치

**문제.** 화면은 지금 잔고만 보여 줘서 이력이 없었다. 또 화면의 합계는 앱이 더한 값인데, 그 숫자가 증권사의 숫자와 맞는지 한 번도 확인한 적이 없었다.

**해결.** 평일 16:10에 `PortfolioSnapshotService`가 돌고, 실패하면 18:10과 20:10에 다시 시도한다(그날 성공했으면 건너뛴다). 증권사 클라이언트가 `statement()`로 보유와 **같은 응답에 들어 있는 계좌 합계**를 함께 돌려주면, `Reconciler`가 둘을 0.1%(최소 1원 또는 1센트) 기준으로 비교한다. `PortfolioSnapshotStore`가 한 트랜잭션에서 합계 줄을 고쳐 쓰고 그날의 종목 줄과 대사 줄을 지우고 새로 넣는다.

**코드.** `service/snapshot/`, `brokerage/BrokerageStatement.java`, `V10__portfolio_snapshot.sql`, 그리고 `alerts.yml`의 `ReconciliationMismatch`와 `SnapshotFailing` 규칙에 있다.

**실무.** 증권사의 일일 배치와 원장 대사가 바로 이것이다. 자체 원장의 숫자를 예탁원, 거래소, 은행의 숫자와 매일 맞추고, 어긋난 것은 다음 날 아침까지 해소한다.

**설계 판단.** 다섯 가지를 지켰다. 날짜가 키라서 몇 번을 돌려도 한 벌만 남는다(**멱등**). 과거는 다시 만들 수 없으니 그날 안에 재시도한다(**재처리 한계 인정**). 증권사 하나라도 실패하면 저장하지 않는다(**빈 날이 틀린 날보다 낫다**). 앱은 지표만 내보내고 알림은 Alertmanager가 보낸다(**알림 경로는 하나**). 로그에는 금액을 남기지 않는다.

**겪은 함정.** 생성자를 둘(운영용, 테스트용 시계) 두었더니 스프링이 어느 쪽을 써야 할지 몰라 앱이 뜨지 않았다. 단위 테스트는 모두 통과했고, jar를 띄워서야 잡혔다. 운영용 생성자에 `@Autowired`를 붙여 해결했다. 그날 줄을 지우고 바로 같은 키로 넣는 부분은 파생 삭제 대신 JPQL `delete` 한 번(`@Modifying`)으로 즉시 반영되게 했다.

ERD는 [3.1의 ④](#31-erd--테이블-사이의-관계)에, 운영 절차는 [운영 - 장 마감 스냅샷과 대사](운영.md#장-마감-스냅샷과-대사)에, 결정 배경은 [결정기록 020](결정기록.md#020-장-마감-스냅샷은-하루-한-번-대사는-증권사-합계와)에 있다.

### 15.5 평가금액 추이 화면

**해결.** 나의 포트폴리오에서 증권사 칩 아래에 평가금액(검정 실선)과 매입금액(회색 점선) 두 선을 그리고, 최근 대사 결과를 한 줄로 보여 준다. 이 차트는 표가 다 그려진 뒤에 따로 불러온다. 이력 조회가 느려도 표가 늦게 뜨지 않게 하려는 것이다.

**코드.** `portfolio.js`의 `loadHistory`, `renderHistory`와 `portfolio.html`의 `.history`에 있다.

**규칙.** 선에는 색을 입히지 않았다. 빨강과 파랑은 등락 전용이기 때문이다. 첫날 대비 변화율 숫자에만 등락 색을 쓰고, 대사가 어긋났을 때는 색 대신 굵은 글씨로 알린다. 캔버스는 CSS 변수를 읽지 못해서 그릴 때 변수 값을 읽어 넘긴다(6.2).

**확인.** 실제 DB에 가짜 줄을 넣지 않고, 브라우저에서 데모 값으로 `renderHistory`를 직접 불러 그려 보며 확인했다.

### 이날 얻은 원칙 세 가지

1. **띄워 봐야 보이는 것이 있다.** 로그 모양이 깨진 것, 빈을 못 만들어 앱이 멈춘 것, 첫 요청이 느린 것은 셋 다 단위 테스트로는 보이지 않았다. jar를 실제로 띄워 보고서야 보였다.
2. **"통과"가 정말 검사했다는 뜻인지 확인한다.** 아무것도 검사하지 않고 건너뛰면서 성공으로 끝나는 도구가 있다(`jacoco:check`).
3. **틀린 숫자보다 빈칸이 낫다.** 일부만 성공한 스냅샷을 남기지 않는 것과, 모르는 로그 형식을 줄글로 흘려보내는 것은 같은 생각에서 나왔다. 확실하지 않으면 남기지 않는다.
