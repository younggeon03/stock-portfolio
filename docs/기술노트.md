# 기술노트 — 이 프로젝트로 배우는 실무 기술

이 문서는 주니어 개발자가 이 저장소를 교재 삼아 백엔드, 데이터베이스, 프론트엔드, 배포, 운영을 공부할 수 있도록 정리한 노트다. 주식이나 공시 같은 도메인 이야기는 꼭 필요한 만큼만 하고, 대신 "어떤 기술을 왜 골랐는지", "그 기술이 실무에서는 무엇에 해당하는지", "다음에 무엇을 공부하면 되는지"에 집중한다.

이 저장소는 혼자 만든 작은 서비스지만, 실무 서비스가 갖춰야 하는 것을 대부분 갖고 있다. 로그인 영역과 공개 영역의 분리, 바깥 API가 죽어도 버티는 장치, 매일 도는 배치와 숫자 맞춰 보기(대사), 자동 테스트와 자동 배포, 지표와 알림까지 있다. 그래서 코드 한 줄 한 줄보다 "왜 이렇게 짰는가"를 따라가면 실무의 기본 뼈대를 한 바퀴 돌아볼 수 있다.

지금 구조의 정답은 [아키텍처](아키텍처.md)에, 그렇게 정한 이유는 [결정기록](결정기록.md)에 있다. 이 노트는 그 두 문서를 공부하기 좋은 순서로 다시 엮은 것이다. 파일 경로는 모두 저장소 루트를 기준으로 적었다. 코드 주석에도 "왜"가 적혀 있으니, 노트를 읽으면서 해당 파일을 같이 열어 보면 훨씬 빨리 익힐 수 있다.

### 이 문서를 읽는 법

이 노트는 자바 문법과 예외, 컬렉션 정도는 이미 아는 사람을 위해 썼다. 반대로 스프링, 데이터베이스, 네트워크, 운영에서 쓰는 실무 용어(프록시, 멱등, 서킷 브레이커 같은 말)는 처음 본다고 가정했다. 그런 용어는 0장에 모아 두었고, 본문에서 처음 나올 때도 한 번 더 풀어 쓴다.

각 장은 같은 모양으로 시작하고 끝난다. 아래 표시를 알아 두면 읽기가 편하다.

| 표시 | 뜻 |
|---|---|
| **이 장에서 배울 것** | 장 첫머리의 요약이다. 시간이 없을 때는 이것만 읽고 넘어가도 큰 그림은 잡힌다. |
| **먼저 알아둘 말** | 그 장에 나오는 실무 용어다. 누르면 [0장 용어집](#0-먼저-알아둘-말--용어집)의 해당 갈래로 간다. |
| **함정**, **겪은 함정** | 이 프로젝트를 만들면서 실제로 저지른 실수다. 같은 실수를 반복하지 않으려고 남겼다. |
| **직접 해보기** | 손으로 해 볼 과제다. 읽기만 하는 것보다 하나라도 직접 해 보는 편이 훨씬 오래 남는다. |
| 선으로 그린 상자 그림 | 흐름도다. 위에서 아래로 읽는다. 편집기에서 선이 어긋나 보이면 고정폭 글꼴(D2Coding, 나눔고딕코딩)로 바꿔 보자. |
| `이런 글자` | 저장소 안의 파일, 클래스, 명령이다. IntelliJ에서 `Shift`를 두 번 누르고 이름을 치면 바로 열 수 있다. |

각 절은 대체로 **무엇인가 → 이 프로젝트에서는 → 실무에서는 → 공부할 것** 순서로 쓴다. 처음 보는 개념이면 그 앞에 **기초부터**를 두어, 그 기술이 없으면 무엇이 불편한지부터 보여 준다.

## 0. 먼저 알아둘 말 — 용어집

> **이 장에서 배울 것** — 뒤에서 계속 나오는 실무 용어를 갈래별로 모았다. 처음부터 다 외울 필요는 없다. 본문을 읽다가 모르는 말이 나오면 이곳으로 돌아와 찾으면 된다. 각 용어 옆에는 그 개념이 이 저장소의 어디에 있는지 적어 두었으니, 코드를 같이 열어 보면 뜻이 훨씬 빨리 잡힌다.

표는 세 칸이다. 첫 칸은 용어, 둘째 칸은 뜻과 짧은 비유, 셋째 칸은 이 저장소에서 그 개념을 볼 수 있는 곳이다.

### 0.1 웹과 네트워크

브라우저와 서버, 서버와 서버가 주고받는 방식에 관한 말이다. 1장과 10장을 읽기 전에 훑어 두면 좋다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **HTTP 메서드** | 요청의 종류다. `GET`은 읽기만 하겠다는 약속이어서 여러 번 보내도 결과가 같아야 한다. `POST`, `PUT`, `DELETE`는 서버의 무언가를 바꾼다. | 공개 화면은 GET만 부른다. 무언가를 바꾸는 요청에는 CSRF 토큰을 붙인다(5.2). |
| **상태 코드** | 응답 맨 앞에 붙는 세 자리 숫자다. 2xx는 성공, 4xx는 요청한 쪽의 문제, 5xx는 서버 쪽의 문제를 뜻한다. 자주 보는 것으로는 401(누군지 모름, 로그인 필요), 403(누군지는 알지만 허락하지 않음), 404(없음), 429(너무 자주 부름), 502(내 서버가 뒤의 서버에게서 잘못된 답을 받음)가 있다. | 토스가 403을 주면 대부분 허용 IP 문제다. 공개 API를 너무 자주 부르면 429를, 바깥 API가 실패하면 502를 돌려준다(`GlobalExceptionHandler`). |
| **헤더** | 요청과 응답에 붙는 `이름: 값` 형태의 꼬리표다. 택배 상자에 붙은 송장을 떠올리면 된다. | `X-Request-Id`(요청 번호), `X-XSRF-TOKEN`(CSRF 토큰), `Retry-After`(429일 때 몇 초 뒤에 다시 오라는 안내)를 쓴다. |
| **포트** | 한 컴퓨터 안에서 프로그램을 구분하는 번호다. IP가 건물 주소라면 포트는 호수다. | 앱은 8080, 관리 주소는 8081, MySQL은 3306, HTTPS는 443을 쓴다. |
| **루프백 (127.0.0.1, localhost)** | 자기 자신만 부를 수 있는 주소다. 이 주소에만 열어 둔 포트는 바깥에서 들어올 수 없다. 집 안에서만 통하는 인터폰과 같다. | 관리 포트, Prometheus, Grafana를 이 주소에만 연다. |
| **공인 IP, 허용 IP** | 공인 IP는 인터넷에서 보이는 내 주소다. 허용 IP는 상대 서비스가 "이 주소에서 온 요청만 받겠다"고 등록해 둔 목록이다. | 토스는 허용 IP를 하나만 받는다. 학교 망은 IP가 자주 바뀌어서 고정 IP 서버가 필요하다. |
| **프록시 (proxy)** | 누군가를 대신해 요청을 주고받는 중간자다. 누구를 대신하느냐에 따라 아래 두 가지로 나뉜다. | 아래 두 줄과, 스프링 안의 프록시(0.2)를 보자. |
| **포워드 프록시** | 클라이언트 쪽의 대리인이다. 회사 망에서 바깥으로 나갈 때 거치는 관문이 대표적이며, 바깥 서버에는 프록시의 주소만 보인다. | 지금은 쓰지 않는다. 로드맵에 있는 "토스 요청만 SSH 터널(SOCKS)로 보내기"가 이 방식이다. |
| **리버스 프록시** | 서버 쪽의 대리인이다. 바깥에서 온 요청을 먼저 받아 안쪽 서버로 넘긴다. 그 과정에서 HTTPS를 풀고, 위험한 주소를 막고, 서버가 재시작하는 동안 요청을 붙잡아 둔다. 건물 1층의 안내 데스크와 비슷하다. | Caddy가 이 역할을 한다(10.2). |
| **로드밸런서** | 여러 대의 서버에 요청을 나눠 주는 리버스 프록시다. 은행 창구에 손님을 배정하는 번호표 기계를 떠올리면 된다. | 앱이 한 대뿐이라 아직 없다. |
| **TLS, HTTPS, TLS 종료** | TLS는 통신을 암호화하는 규약이고, HTTPS는 TLS 위에서 주고받는 HTTP다. TLS 종료는 앞단 프록시가 암호를 풀고 안쪽 서버에는 평문 HTTP로 넘기는 방식을 말한다. | Caddy가 443 포트에서 암호를 풀고 앱의 8080 포트로 넘긴다. |
| **인증서, Let's Encrypt, ACME** | 인증서는 이 도메인이 진짜라는 증명서다. Let's Encrypt는 인증서를 무료로 발급하는 기관이고, ACME는 발급과 갱신을 자동으로 처리하는 규약이다. | Caddy가 인증서를 알아서 받고 갱신한다. |
| **X-Forwarded-For** | 프록시를 거치면 앱에는 프록시의 IP만 보인다. 그래서 프록시가 원래 사용자의 IP를 이 헤더에 적어서 넘긴다. | 공개 API의 호출 한도를 진짜 사용자 IP 기준으로 셀 수 있는 이유다(`forward-headers-strategy` 설정). |
| **쿠키, 세션** | 쿠키는 브라우저가 저장해 두었다가 요청마다 자동으로 보내는 값이다. 세션은 서버가 기억하는 로그인 상태이고, 쿠키에는 그 세션을 찾는 번호표만 들어 있다. 놀이공원 손목밴드와 비슷하다. | 로그인 쿠키에 `HttpOnly`와 `SameSite=Strict`를 걸었다(5.1). |
| **정적 파일** | 서버가 계산 없이 그대로 내보내는 파일이다. HTML, CSS, JS, 이미지가 여기에 속한다. | `src/main/resources/static/`에 있다. jar 안에 들어가므로 CSS만 고쳐도 다시 빌드해야 한다. |
| **JSON, 직렬화** | JSON은 `{"이름": 값}` 모양의 글자 형식이다. 직렬화는 자바 객체를 JSON 글자로, 또는 그 반대로 바꾸는 일이다. | 스프링이 Jackson 라이브러리로 record를 JSON으로 바꿔 응답한다. |

### 0.2 스프링과 서버 안쪽

스프링이 객체를 만들고 이어 주는 방식, 그리고 서버 안에서 일이 도는 방식에 관한 말이다. 2장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **빈 (Bean)** | 스프링이 만들어서 들고 있는 객체다. 보통 앱 전체에서 하나만 만들어 함께 쓴다. | `@Service`, `@Component`, `@RestController`가 붙은 클래스가 빈이 된다. |
| **IoC, DI (의존성 주입)** | 필요한 객체를 내가 `new`로 만들지 않고 생성자로 받기만 하는 방식이다. 무엇을 꽂아 줄지는 스프링이 정한다. 객체를 만드는 주도권이 내 코드에서 스프링으로 넘어갔다고 해서 "제어의 역전(IoC)"이라고 부른다. | 모든 서비스가 생성자로 의존성을 받는다(2.1). |
| **계층 (레이어)** | 역할별로 나눈 코드의 층이다. 컨트롤러가 주소를 받고, 서비스가 규칙을 처리하고, 리포지토리가 DB를, 클라이언트가 바깥 API를 맡는다. | 패키지가 곧 층이다. `web` → `service` → `domain`, `external` 순서로 내려간다. |
| **DTO, 엔티티, record** | DTO는 주고받는 데이터의 모양을 정한 객체다. 엔티티는 테이블의 한 줄과 1:1로 대응하는 객체다. record는 값만 담는 짧은 자바 클래스 문법이다. | `external/toss/dto/`에 DTO가, `domain/`에 엔티티가 있고, 응답 대부분이 record다. |
| **필터 (Filter)** | 모든 요청이 컨트롤러에 닿기 전과 후에 끼어드는 코드다. 건물 입구의 검색대처럼 누구든 거쳐 간다. | `RequestIdFilter`, `PublicRateLimitFilter`, 그리고 Spring Security의 필터 묶음이 있다. |
| **인터셉터** | 정해진 흐름에 끼어드는 코드다. 이 저장소에서는 바깥으로 나가는 HTTP 요청에 끼어드는 것을 말한다. | `ResilientHttpInterceptor`가 타임아웃, 재시도, 서킷 브레이커를 맡는다. |
| **스프링 프록시, AOP** | `@Transactional` 같은 애노테이션이 붙으면 스프링은 원래 객체를 감싸는 대리 객체를 만들고, 메서드 앞뒤에 필요한 일을 끼워 넣는다. 같은 클래스 안에서 `this.메서드()`로 부르면 대리 객체를 거치지 않으므로 애노테이션이 동작하지 않는다. | 그래서 저장만 맡는 빈을 따로 두었다. `CompanyAnalysisStore`, `PortfolioSnapshotStore`가 그 예다(2.7). |
| **트랜잭션** | 여러 DB 작업을 "전부 성공하거나 전부 취소되는" 하나의 묶음으로 처리하는 것이다. 계좌 이체에서 출금과 입금이 같이 되거나 같이 안 되어야 하는 것과 같다. | 장 마감 스냅샷을 저장할 때 한 트랜잭션으로 묶는다(`PortfolioSnapshotStore`). |
| **스레드, 스레드 풀** | 스레드는 동시에 도는 실행 흐름이다. 스레드 풀은 스레드를 미리 만들어 두고 돌려 쓰는 묶음이다. | 톰캣이 요청마다 스레드를 하나씩 내준다. AI 분석, 13F 받기, 캐시 예열은 각자 스레드 하나짜리 `ExecutorService`에서 돈다. |
| **비동기, 폴링** | 비동기는 오래 걸리는 일을 다른 곳에 맡겨 두고 바로 답하는 방식이다. 폴링은 일이 끝났는지 주기적으로 다시 물어보는 방식이다. | AI 분석은 바로 `RUNNING`으로 답하고, 화면이 3초마다 상태를 다시 묻는다(2.3). |
| **이벤트, 느슨한 결합** | "이 일이 일어났다"고 알리기만 하고, 그 소식을 누가 듣는지는 모르게 짜는 방식이다. 한쪽이 고장 나도 다른 쪽은 계속 돌아간다. | 새 13F가 들어오면 `NewFilingEvent`를 내고, 텔레그램 알림은 그 이벤트를 듣고 따로 보낸다. |
| **스케줄러, cron 표현식** | 스케줄러는 정해진 시각에 코드를 실행하는 장치이고, cron 표현식은 그 시각을 적는 형식이다. 스프링은 `초 분 시 일 월 요일` 순서로 쓴다. | `0 0 6 * * *`는 매일 06:00, `0 10 16,18,20 * * MON-FRI`는 평일 16시·18시·20시 10분이다. |
| **설정, 환경변수, `.env`** | 코드 밖에서 넣어 주는 값이다. API 키 같은 비밀값은 코드에 쓰지 않고 실행 환경이 넣어 준다. | `application.yml`의 `${TOSS_CLIENT_ID:}` 같은 자리로 들어온다(2.2). |

### 0.3 데이터베이스

테이블과 키, 그리고 자바에서 DB를 다루는 도구에 관한 말이다. 3장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **스키마, 테이블, 행, 열** | 스키마는 DB 안의 이름공간이고, 테이블은 표, 행은 표의 한 줄, 열은 표의 한 칸이다. | 스키마 이름은 `portfolio`이고 테이블은 16개다(3장). |
| **PK (기본 키)** | 한 줄을 하나로 집어낼 수 있게 해 주는 값이다. 중복되거나 비어 있을 수 없다. | `filing_13f.accession_no`, `stored_financials.symbol`이 PK다. |
| **유니크 키** | 중복을 DB가 직접 막아 주는 열 또는 열의 묶음이다. 코드가 실수해도 DB가 막아 주는 마지막 방어선이다. | `(owner_key, symbol)`, `(snapshot_date, symbol)`에 걸려 있다. |
| **인덱스** | 빨리 찾으려고 따로 만들어 두는 정렬된 목록이다. 책 뒤의 찾아보기와 같다. | `idx_holding_13f_cusip`이 종목별 13F 조회를 받쳐 준다. |
| **FK (외래 키)** | "자식 줄은 반드시 존재하는 부모를 가리켜야 한다"는 규칙을 DB가 강제하는 제약이다. | 이 저장소에는 일부러 하나도 걸지 않았다(3.4). |
| **자연 키, 대리 키** | 자연 키는 업무에 원래 있던 값(종목코드, 공시 번호)이고, 대리 키는 DB가 붙여 주는 일련번호(`id`)다. | 3.3에서 어떤 테이블에 무엇을 골랐는지 설명한다. |
| **ORM, JPA, Hibernate** | ORM은 자바 객체와 테이블을 이어 주는 기술이다. JPA는 그 자바 표준이고, Hibernate는 그 표준을 구현한 라이브러리다. | 엔티티와 `JpaRepository`로 DB를 다룬다(3.7). |
| **쿼리 메서드** | 메서드 이름만 규칙에 맞게 지으면 SQL을 만들어 주는 JPA 기능이다. | `findBySymbolIn(...)`이 `WHERE symbol IN (...)`이 된다. |
| **N+1 문제** | 목록을 한 번 읽은 뒤 줄마다 한 번씩 더 조회하느라 쿼리가 N+1번 나가는 성능 문제다. | 연관관계 매핑을 쓰지 않아서 이 문제가 생길 자리가 없다(3.7). |
| **마이그레이션, Flyway, 체크섬** | 마이그레이션은 스키마 변경을 순서가 있는 SQL 파일로 남기는 방식이고, Flyway는 그 파일을 실행해 주는 도구다. 체크섬은 파일 내용이 바뀌었는지 확인하는 지문이다. | `V1__init.sql`부터 차례로 있다. 이미 적용한 파일을 고치면 체크섬이 달라져 앱이 뜨지 않는다(3.8). |
| **upsert** | 같은 키의 줄이 있으면 고치고(update), 없으면 새로 넣는(insert) 동작이다. | 스냅샷 합계 줄과 `stored_financials`가 이렇게 저장된다. |
| **덤프, 백업** | DB 내용을 SQL 파일로 떠 두는 것이다. | `deploy/backup.sh`가 매일 04:00에 뜬다(11.4). |

### 0.4 바깥 연동과 안정성

다른 회사의 API를 부를 때 쓰는 말, 그리고 상대가 느리거나 죽었을 때 버티는 장치에 관한 말이다. 4장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **API, API 키** | API는 프로그램끼리 서로 부르는 창구다. API 키는 누가 부르는지 증명하는 비밀값이다. | 토스, 나무, DART, SEC, Claude를 API로 부른다. |
| **OAuth 토큰 (액세스 토큰)** | 키로 한 번 로그인해서 받는, 유효기간이 있는 출입증이다. 그 뒤의 요청은 키 대신 이 출입증으로 한다. | 토큰을 메모리와 DB(암호화) 두 곳에 들고 있다(4장). |
| **타임아웃** | "이만큼 기다려도 답이 없으면 포기한다"는 시간이다. 연결 타임아웃은 상대와 연결될 때까지, 응답 타임아웃은 연결된 뒤 답이 올 때까지를 잰다. | 연결 5초, 응답 30초다. 이 값이 없으면 스레드가 영원히 묶일 수 있다(4장). |
| **재시도, 지수 백오프, 지터** | 재시도는 실패한 요청을 다시 보내는 것이다. 지수 백오프는 다시 보내기 전 기다리는 시간을 점점 늘리는 방식이고, 지터는 그 시간에 무작위 값을 섞어 모두가 같은 순간에 몰리지 않게 하는 것이다. | GET 요청이 네트워크 오류나 5xx로 실패했을 때만 최대 3번까지 다시 보낸다(4장). |
| **서킷 브레이커** | 실패가 몰리면 한동안 아예 부르지 않고 바로 실패로 처리하는 장치다. 집의 누전 차단기와 같다. 정상인 **닫힘**, 차단 중인 **열림**, 시험 삼아 몇 번만 보내 보는 **반열림**의 세 상태가 있다. | 상대 호스트마다 하나씩 두며, 최근 20번 중 절반이 실패하면 30초 동안 차단한다(4장). |
| **fail-soft (부분 실패 격리)** | 한 부분이 실패해도 전체는 계속 동작하도록 짜는 방식이다. | 토스가 막혀도 재무와 기관 칸은 그대로 보인다(4장). |
| **호출 한도 (rate limit)** | 정해진 시간 동안 부를 수 있는 횟수의 제한이다. 넘으면 보통 429를 받는다. | SEC는 초당 10건으로 제한한다. 우리도 공개 API에 IP당 분당 120번의 한도를 걸었다. |
| **캐시, TTL, 무효화** | 캐시는 계산이나 조회 결과를 잠시 들고 있는 것이다. TTL은 들고 있을 시간이고, 무효화는 낡은 결과를 버리는 것이다. | 공개 기업분석은 6시간 들고 있고, 13F 집계는 배치가 끝나면 통째로 버린다(1.7). |
| **캐시 예열 (warm-up)** | 사용자가 오기 전에 캐시를 미리 채워 두는 것이다. | `InstitutionCacheWarmer`와 공시 재무 야간 배치가 이 일을 한다. |
| **LRU** | 캐시가 꽉 차면 가장 오래 쓰지 않은 것부터 버리는 규칙이다. | `QueryCache`가 64개까지 들고 이 규칙으로 버린다. |

### 0.5 배치와 숫자 맞추기

사람이 누르지 않아도 정해진 때에 도는 일, 그리고 숫자가 맞는지 확인하는 일에 관한 말이다. 2.4와 15장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **배치 (batch)** | 사람이 누르지 않아도 정해진 때에 한꺼번에 처리하는 일이다. | 매일 06:00 공시 재무, 매일 07:00 13F, 평일 16:10 스냅샷이 돈다(2.4). |
| **멱등 (idempotent)** | 몇 번을 해도 한 번 한 것과 결과가 같은 성질이다. 엘리베이터 버튼은 열 번을 눌러도 엘리베이터가 한 번만 온다. 멱등하게 짜 두면 실패 후 다시 돌리거나 실수로 두 번 돌려도 안전하다. | 이미 받은 공시 번호는 건너뛰고, 스냅샷은 날짜를 키로 저장한다. |
| **원장 (ledger)** | 돈이나 수량의 공식 기록이다. | 이 앱에서는 증권사의 응답이 원장이고, 앱은 그 숫자를 더할 뿐이다. |
| **스냅샷** | 어느 순간의 모습을 그대로 찍어 둔 기록이다. | `portfolio_snapshot`에 하루 한 벌씩 남긴다. |
| **대사 (reconciliation)** | 서로 다른 두 시스템의 숫자가 맞는지 맞춰 보는 일이다. 가계부와 통장 잔고를 맞춰 보는 것과 같다. | 앱이 더한 합계와 증권사가 알려 준 합계를 매일 비교한다(15.4). |
| **재처리** | 실패한 배치를 다시 돌리는 것이다. 배치가 멱등해야 안전하게 재처리할 수 있다. | 18:10과 20:10에 다시 시도하고, `POST /api/portfolio/snapshots`로 손으로도 돌릴 수 있다. |

### 0.6 보안

누가 무엇을 할 수 있는지 정하고, 브라우저를 노리는 공격을 막는 일에 관한 말이다. 5장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **인증, 인가** | 인증은 "당신이 누구인가"를 확인하는 일(로그인)이고, 인가는 "당신이 이것을 해도 되는가"를 판단하는 일(권한)이다. | 폼 로그인으로 인증하고, `SecurityConfig`의 주소별 규칙으로 인가한다. |
| **CSRF** | 다른 사이트가 내 브라우저에 남아 있는 로그인 쿠키를 이용해 몰래 요청을 보내는 공격이다. | `XSRF-TOKEN` 쿠키와 헤더로 막는다(5.2). |
| **XSS, 이스케이프** | XSS는 남이 넣은 글자에 숨어 있던 스크립트가 내 화면에서 실행되는 공격이다. 이스케이프는 `<` 같은 문자를 `&lt;`로 바꿔서 글자로만 보이게 하는 처리다. | 바깥에서 온 글자는 모두 `esc()`를 거쳐 화면에 넣는다. |
| **CSP** | "스크립트는 이 출처에서 온 것만 실행하라"고 브라우저에 지시하는 응답 헤더다. | 인라인 스크립트를 아예 금지했다(5.3). |
| **대칭키 암호, AES-GCM, IV** | 대칭키 암호는 같은 키로 잠그고 여는 암호다. AES-GCM은 암호문이 위조되었는지까지 잡아내는 방식이고, IV는 매번 바꿔 넣는 무작위 시작값이다. | 증권사 토큰을 DB에 넣을 때 암호화한다(`TokenCipher`). |
| **시크릿** | 비밀번호나 키 같은 비밀값이다. 저장소, 로그, 화면 어디에도 남기면 안 된다. | 서버의 `.env`와 GitHub Secrets에만 둔다. |
| **최소 권한 원칙** | 꼭 필요한 권한만 주는 원칙이다. | CI는 기본으로 읽기 권한만 갖고, 이미지를 올리는 단계에만 쓰기 권한을 준다. |

### 0.7 빌드·배포·인프라

코드를 실행 파일로 만들고, 서버에 올리고, 서버를 운영하는 일에 관한 말이다. 8장부터 10장까지 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **jar (fat jar)** | jar는 자바 프로그램을 묶은 파일이다. fat jar는 필요한 라이브러리까지 모두 넣어서 `java -jar` 한 줄로 실행되게 만든 jar다. | `target/portfolio-0.0.1-SNAPSHOT.jar`가 만들어진다. |
| **Maven, 래퍼** | Maven은 의존성 받기, 컴파일, 테스트, 패키징을 맡는 도구다. 래퍼는 누구나 같은 버전의 Maven을 쓰게 해 주는 스크립트다. | `pom.xml`에 설정이 있고, `./mvnw`로 실행한다. |
| **이미지, 컨테이너** | 이미지는 실행에 필요한 모든 것을 통째로 굳혀 둔 꾸러미이고, 컨테이너는 그 이미지를 실제로 띄운 것이다. 붕어빵 틀과 붕어빵의 관계와 같다. | `Dockerfile`이 이미지를 만든다(8장). |
| **레지스트리, 태그** | 레지스트리는 이미지를 보관하는 저장소이고, 태그는 이미지에 붙이는 버전 이름표다. | `ghcr.io/.../stock-portfolio:sha-xxxxxxx` 형태로 올라간다. |
| **볼륨** | 컨테이너를 지워도 사라지지 않는 저장 공간이다. | MySQL 데이터가 `mysql-data` 볼륨에 있다. |
| **Docker Compose, profile** | Compose는 여러 컨테이너를 파일 하나로 함께 띄우는 도구다. profile은 그중 골라서 켜는 묶음이다. | `deploy/compose.yml`이 있고, 모니터링은 `monitoring` profile로 켠다. |
| **CI, CD** | CI(지속적 통합)는 코드를 합치기 전에 자동으로 테스트하고 빌드하는 것이다. CD(지속적 배포)는 합친 뒤 자동으로 서버에 반영하는 것이다. | `.github/workflows/ci.yml`과 `deploy.yml`에 있다(9장). |
| **워크플로, 잡, 러너** | 워크플로는 GitHub Actions에서 자동화를 묶은 단위이고, 잡은 그 안의 작업 하나, 러너는 작업을 실제로 실행하는 컴퓨터다. | "테스트와 패키징" 같은 잡이 있다. |
| **PR, 브랜치 보호, 스쿼시 병합** | PR은 내 브랜치를 합쳐 달라는 요청이고, 브랜치 보호는 `main`에 아무나 바로 밀어 넣지 못하게 막는 규칙이다. 스쿼시 병합은 PR의 여러 커밋을 하나로 눌러 합치는 방식이다. | 9.1에서 설명한다. |
| **헬스체크, liveness, readiness** | 헬스체크는 서버가 괜찮은지 물어보는 주소다. liveness는 프로세스가 살아 있는지를, readiness는 요청을 받을 준비(DB 연결 포함)가 되었는지를 본다. | `:8081/actuator/health/...`에 있다(11.1). |
| **롤백** | 문제가 생겼을 때 앞 버전으로 되돌리는 것이다. | 헬스체크가 실패하면 `deploy.sh`가 자동으로 되돌린다. |
| **무중단 배포, 블루그린, 롤링** | 무중단 배포는 배포하는 동안에도 요청을 놓치지 않는 것이다. 블루그린은 새 버전을 옆에 띄운 뒤 한 번에 전환하는 방식이고, 롤링은 여러 대를 하나씩 바꾸는 방식이다. | 지금은 Caddy가 재시작 동안 요청을 붙잡아 주는 방식을 쓴다(10.3). |
| **SSH, SSH 터널** | SSH는 서버에 암호화된 통로로 접속하는 방법이다. SSH 터널은 내 PC의 포트를 서버 안의 포트에 이어 주는 통로다. | Grafana를 `ssh -L 3000:...`으로 연다. |
| **방화벽, iptables** | 방화벽은 들어오고 나가는 연결을 거르는 규칙이고, iptables는 리눅스에서 그 규칙을 다루는 도구다. | 서버는 80번과 443번 포트만 연다(10.1). |
| **스왑, OOM** | 스왑은 메모리가 모자랄 때 디스크를 메모리처럼 쓰는 공간이다. OOM(Out Of Memory)은 메모리가 바닥나 프로세스가 강제로 죽는 상황이다. | 서버에 스왑 2GB를 잡아 둔다. |

### 0.8 관측과 운영

서비스가 지금 괜찮은지, 무슨 일이 있었는지 알아보는 일에 관한 말이다. 11장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **관측 (observability)** | 밖에서 시스템의 속사정을 알아보는 능력이다. 보통 로그, 지표, 추적의 세 가지로 나눈다. | 11장 전체가 이 이야기다. |
| **로그 레벨** | 로그의 중요도다. `DEBUG`, `INFO`, `WARN`, `ERROR` 순서로 중요해진다. | 실패했지만 계속 진행할 수 있는 일은 WARN으로 남긴다. |
| **구조화 로그** | 줄글 대신 JSON처럼 필드가 나뉜 로그다. 도구로 거르고 모으기 쉽다. | 서버에서는 `LOG_FORMAT=json`으로 이 형식을 쓴다. |
| **MDC** | 스레드마다 따로 붙는 로그 꼬리표 저장소다. 여기 넣은 값은 그 스레드가 찍는 모든 로그 줄에 자동으로 붙는다. | 요청 번호를 넣어 모든 줄에 찍는다(11.3). |
| **요청 ID, trace ID** | 요청 ID는 요청 하나에 붙인 번호다. trace ID는 그 번호를 여러 서버에 걸쳐 이어 붙인 것이다. | `X-Request-Id` 헤더로 주고받는다. |
| **지표, 카운터, 게이지, 태그** | 지표(metric)는 시간에 따라 재는 숫자다. 카운터는 늘어나기만 하는 수, 게이지는 오르내리는 현재 값이고, 태그는 같은 지표를 갈라 보는 이름표다. | `filing_prefetch_runs_total{outcome="failure"}`에서 `outcome`이 태그다. |
| **Actuator, Micrometer** | Actuator는 스프링이 제공하는 운영용 주소 모음이고, Micrometer는 지표를 재는 라이브러리다. | `/actuator/prometheus`에서 지표를 내보낸다. |
| **Prometheus, pull, PromQL** | Prometheus는 지표를 모아 시간순으로 쌓는 DB다. 앱이 지표를 보내는 것이 아니라 Prometheus가 주기적으로 긁어 간다(pull)는 점이 중요하다. PromQL은 그 데이터를 조회하는 언어다. | 15초마다 앱에서 긁어 간다(11.2). |
| **Grafana, 대시보드** | 지표를 그래프로 보여 주는 화면이다. | 대시보드 하나를 파일로 관리한다. |
| **알림, Alertmanager, 알림 피로** | 알림은 규칙에 맞는 상황이 생기면 사람에게 알리는 것이고, Alertmanager는 알림을 묶어서 보내는 도구다. 알림 피로는 알림이 너무 잦아서 결국 아무도 보지 않게 되는 현상이다. | 텔레그램으로 보내며, 규칙은 11개다. |
| **런북 (runbook)** | "이 증상이 보이면 이렇게 한다"를 적어 둔 대응 매뉴얼이다. | [운영 - 장애 대응](운영.md#장애-대응)이 런북이다. |
| **부하 테스트** | 가짜 사용자를 많이 보내서 서버가 버티는지 재는 테스트다. | k6로 하며 스크립트는 `loadtest/`에 있다. |
| **p95** | 응답 시간을 빠른 순으로 줄 세웠을 때 95% 지점의 값이다. 평균보다 "느린 편의 사용자가 실제로 겪는 시간"을 잘 보여 준다. | 첫 화면의 p95를 8.8초에서 0.1초로 줄였다. |

### 0.9 테스트

코드가 맞게 동작하는지 자동으로 확인하는 일에 관한 말이다. 7장을 읽을 때 필요하다.

| 용어 | 뜻 (비유) | 이 저장소에서 |
|---|---|---|
| **단위, 통합, E2E 테스트** | 단위 테스트는 클래스 하나만, 통합 테스트는 DB를 포함한 여러 부품을 함께, E2E 테스트는 사용자처럼 화면부터 끝까지 검사한다. | 대부분 단위 테스트이고, 화면은 puppeteer로 확인한다. |
| **목 (mock), 스텁** | 목과 스텁은 진짜 대신 꽂아 쓰는 가짜 객체다. 스텁은 정해 둔 답만 돌려주고, 목은 거기에 더해 "실제로 불렸는지"까지 검사할 수 있다. | Mockito의 `mock()`, `when(...).thenReturn(...)`, `verify(...)`를 쓴다. |
| **픽스처** | 테스트에 쓰려고 저장해 둔 입력 데이터다. | `src/test/resources/dart/`에 실제 응답을 파일로 저장해 두었다. |
| **커버리지, 품질 게이트** | 커버리지는 테스트가 코드의 몇 퍼센트를 실행했는지를 나타낸다. 품질 게이트는 기준에 못 미치면 합치지 못하게 막는 관문이다. | JaCoCo로 재고 `jacoco:check`로 막는다(15.3). |

>
> **먼저 알아둘 말** — [포트](#01-웹과-네트워크) · [루프백](#01-웹과-네트워크) · [리버스 프록시](#01-웹과-네트워크) · [컨테이너](#07-빌드배포인프라) · [배치](#05-배치와-숫자-맞추기) · [캐시](#04-바깥-연동과-안정성)

이 장은 지금 이 프로젝트가 실제로 어떤 모양인지를 위에서 아래로 훑는다. 처음에는 세부를 다 이해하지 않아도 괜찮다. "이런 부품들이 있고, 요청이 이런 순서로 지나간다"는 지도만 머리에 넣어 두면, 뒤의 장을 읽을 때 지금 어디를 보고 있는지 길을 잃지 않는다.

그림은 모두 글자로 그렸다. 그래서 GitHub뿐 아니라 IntelliJ나 VS Code에서 열어도 그대로 보인다.

### 1.1 한눈에

아래는 서버 한 대에서 `docker compose`로 띄운 전체 모습이다. 맨 위의 브라우저에서 출발해 아래로 내려가며 읽으면 된다.

```text
[서버 한 대 · docker compose]

브라우저 (HTML/CSS/JS)
  │  HTTPS 443        ← 바깥에 열린 포트는 80·443 뿐
  ▼
Caddy                 HTTPS 종료 · 인증서 자동 갱신 · 재시작 중 요청 붙잡기
  │  HTTP 8080        (서버 안 네트워크)
  ▼
Spring Boot 앱        jar 하나 = 프로세스 하나 (화면도 같이 내보냄)
  ├─ JDBC 3306 ──▶ MySQL 8.4 (도커 볼륨, 바깥 포트 없음)
  └─ HTTPS ──────▶ 바깥 API (토스 · 나무 · DART · SEC · OpenFIGI · Claude · 뉴스)

Prometheus ── 15초마다 긁음 ──▶ 앱 관리 포트 8081 (/actuator/prometheus)
  │  규칙이 맞으면
  ▼
Alertmanager ──▶ 텔레그램

Grafana ── Prometheus 를 읽음 ◀── SSH 터널 ── 운영자 PC

※ 8081 · 9090(Prometheus) · 3000(Grafana) · 9093(Alertmanager) 은 서버 자신(127.0.0.1)에만 열린다
```

브라우저가 보낸 요청은 먼저 Caddy에 닿는다. Caddy는 [리버스 프록시](#01-웹과-네트워크)로서 HTTPS 암호를 풀고, 요청을 서버 안쪽 네트워크를 통해 스프링부트 앱으로 넘긴다. 앱은 필요하면 MySQL을 읽고 쓰거나 바깥 API를 부른 뒤 JSON으로 답한다. 화면 파일(HTML, CSS, JS)도 같은 앱이 내보낸다.

그림의 아래쪽 절반은 운영을 위한 부품이다. Prometheus가 15초마다 앱의 관리 포트에서 지표를 긁어 가고, 규칙에 맞는 상황이 생기면 Alertmanager가 텔레그램으로 알린다. Grafana는 그 지표를 그래프로 보여 주는 화면이다.

이 그림에서 꼭 기억할 점은 두 가지다.

첫째, **바깥에 열린 포트는 80번과 443번뿐이다.** 앱(8080)과 DB(3306)는 컨테이너끼리만 통하는 네트워크에 있고, 관리 포트(8081), Prometheus(9090), Grafana(3000)는 서버 자신을 뜻하는 127.0.0.1에만 열려 있다. 바깥에서 들어올 수 있는 문을 하나로 줄여 두면 그 문 하나만 잘 지키면 된다.

둘째, **앱은 프로세스 하나다.** 화면을 내보내는 서버와 API 서버를 나누지 않았고, 기능별로 여러 서비스로 쪼개는 마이크로서비스 구조도 쓰지 않았다. 혼자 운영하는 규모에서는 나눌 때 드는 비용(서비스 사이의 통신, 배포 순서, 장애 추적)이 얻는 이익보다 크기 때문이다.

### 1.2 실행 단위 — 무엇이 어디서 도나

1.1의 그림에서 상자 하나하나가 컨테이너다. 표로 정리하면 다음과 같다.

| 이름 | 이미지 / 실행 | 포트 | 바깥 공개 | 메모리 | 하는 일 |
|---|---|---|---|---|---|
| caddy | `caddy:2.8` | 80·443 | **예** | - | HTTPS를 풀고 인증서를 자동으로 갱신한다. 앱이 재시작하는 동안 요청을 붙잡아 두고, `/actuator`를 막고, 요청마다 `X-Request-Id`를 붙인다. |
| app | `ghcr.io/.../stock-portfolio:sha-xxxxxxx` (JRE 21) | 8080, 관리 8081 | 아니오 (8081은 127.0.0.1) | 한도 900MB, 힙 512MB | 화면, API, 배치(공시 재무 06:00, 13F 07:00, 스냅샷 평일 16:10), 바깥 API 연동을 모두 맡는다. 로그는 JSON으로 남긴다(`LOG_FORMAT=json`). |
| mysql | `mysql:8.4` | 3306 | 아니오 | - | 데이터를 저장한다. 데이터는 `mysql-data` 볼륨에 있다. |
| prometheus | `prom/prometheus:v3.5.5` (선택) | 9090 | 아니오 (127.0.0.1) | 한도 256MB | 지표를 모아 15일 동안 보관한다. |
| grafana | `grafana/grafana:12.1.10` (선택) | 3000 | 아니오 (127.0.0.1) | 한도 256MB | 지표를 대시보드로 보여 준다. |
| alertmanager | `prom/alertmanager:v0.30.0` (선택) | 9093 | 아니오 (127.0.0.1) | 한도 64MB | 경보를 묶어서 텔레그램으로 보낸다. |

"(선택)"이라고 적힌 세 개는 compose의 `monitoring` profile에 속한다. profile은 골라서 켤 수 있는 묶음이어서, 메모리가 1GB밖에 없는 작은 서버라면 이 셋을 끄고 앱과 DB만 돌릴 수 있다.

내 PC에서 개발할 때는 이 중 app만 `java -jar`로 띄우고, MySQL은 PC에 설치된 것을 쓴다. 서버와 똑같은 구성을 PC에서 확인하고 싶다면 `deploy/` 폴더로 리허설을 하면 된다([운영 7장](운영.md#7-배포)).

### 1.3 앱 안쪽 — 패키지 지도

이번에는 1.1 그림의 "Spring Boot 앱" 상자 안으로 들어가 본다. 앱의 코드는 역할에 따라 패키지로 나뉘어 있다.

```text
web          컨트롤러 · 예외 처리 (주소를 받아 JSON 으로 답함)
  │
  ▼
service      업무 규칙 (합산 · 비교 · 문장 규칙)
  ├──▶ brokerage   증권사 보유 (토스 · 나무 · 직접 입력) ──▶ external 를 씀
  ├──▶ external    바깥 API 클라이언트 ──▶ domain 을 씀
  └──▶ domain      JPA 엔티티 · 리포지토리 (아무것도 모름)

config       보안 · 호출 한도 · 관측 · 스케줄 (모든 층에 가로로 걸침)

※ 의존은 위에서 아래로만. web 은 external 을 직접 부르지 않는다
```

요청은 위에서 아래로 흐른다. `web`이 주소를 받아 `service`에 넘기면, `service`가 업무 규칙을 처리하면서 필요한 데이터를 `brokerage`, `external`, `domain`에서 가져온다. `config`는 이 흐름 전체에 가로로 걸쳐 있는 설정이다. 보안 규칙이나 호출 한도처럼 어느 한 층에 속하지 않는 것들이 여기에 있다.

| 패키지 | 하는 일 | 대표 클래스 |
|---|---|---|
| `web` | 주소를 받아 JSON으로 답한다. 업무 규칙은 두지 않는다. | `StockBriefController`, `InstitutionController`, `CompanyAnalysisController`, `GlobalExceptionHandler` |
| `service` | 합산, 비교, 문장 규칙 같은 업무 규칙을 처리한다. | `UnifiedPortfolioService`(증권사 합산), `InstitutionPortfolioService`(13F 비교), `StockNotes`(공개 기업분석 문장), `CompanyAnalysisService`(AI 분석 흐름) |
| `brokerage` | 증권사마다 다른 보유 조회 방식을 하나의 모양으로 맞춘다. **주문 메서드는 없다.** | `BrokerageClient`(인터페이스), `TossBrokerageClient`, `NamuhBrokerageClient`, `ManualBrokerageClient` |
| `external` | 바깥 시스템마다 하위 패키지를 하나씩 둔다. | `toss/`, `namuh/`, `dart/`, `edgar/`, `thirteenf/`, `anthropic/`, `news/`, `telegram/`, `auth/`(토큰 암호화) |
| `domain` | 테이블과 1:1로 대응하는 엔티티와 조회 메서드를 둔다. | `Filing13F`, `Holding13F`, `CompanyAnalysis`, `OAuthToken` 등 |
| `config` | 여러 층에 가로로 걸치는 설정을 둔다. | `SecurityConfig`, `PublicRateLimitFilter`, `SafeClientRequestObservationConvention`, `SchedulingConfig` |

여기서 지키는 규칙은 하나다. **의존은 위에서 아래로만 간다.** `domain`은 다른 패키지를 전혀 모르고, `web`은 `external`을 직접 부르지 않는다. 이렇게 해 두면 바깥 API의 사정이 화면 코드까지 새어 나오지 않는다. 예를 들어 토스의 응답 모양이 바뀌어도 `external/toss` 안에서만 고치면 되고, 컨트롤러는 손댈 필요가 없다.

### 1.4 화면 지도

화면은 `src/main/resources/static/`에 빌드 과정 없이 들어 있다. 모든 화면의 왼쪽에는 같은 사이드바(`public/nav.js`)가 붙는다. 화면마다 누가 볼 수 있는지, 주로 어떤 API를 부르는지를 정리하면 다음과 같다.

| 화면 | 파일 | 누가 보나 | 주로 부르는 API |
|---|---|---|---|
| 기관 포트폴리오(첫 화면) | `index.html` + `public/home.js` | 누구나 | `/api/institutions`, `/consensus` |
| 기관 상세 | `public/institution.html` + `.js` | 누구나 | `/api/institutions/{cik}/holdings`, `/changes` |
| 내 포트폴리오와 비교 | `public/overlap.html` + `.js` | 누구나 | `/api/institutions/overlap` |
| 배당 캘린더 | `public/dividends.html` + `.js` | 누구나 | `/api/public/dividends` |
| 기업분석 (페이지와 창) | `public/company.html`, `public/stock.js` | 누구나 (AI 실행은 운영자만) | `/api/public/stocks/{티커}`, `/chart`, `/analysis` |
| 나의 포트폴리오 | `portfolio.html` + `.js` + `.css` | **로그인한 운영자** | `/api/portfolio/unified`, `/api/portfolio/snapshots`(평가금액 추이와 대사), `/api/analysis`(+`/reassess`), `/api/toss/chart`, `/api/news` |
| 로그인, 404 | `public/login.html`, `public/404.html` | 누구나 | `/login` |

여러 화면이 함께 쓰는 파일도 있다. `tokens.css`에는 색, 간격, 글꼴 같은 디자인 값이 모여 있고, `site.css`와 `site.js`는 공개 화면의 공통 코드다. `analysis-view.js`와 `analysis.css`는 AI 분석 결과를 그리는 코드이고, `chart-view.js`는 캔들차트를 그린다. 마지막 두 묶음은 나의 포트폴리오와 공개 기업분석이 **같은 파일**을 쓴다. 같은 화면 조각을 두 곳에 복사해 두면 한쪽만 고치고 다른 쪽을 잊기 쉬워서, 처음부터 한 파일로 모았다.

### 1.5 데이터 — 테이블 16개

DB에는 테이블이 16개 있다. 그중 관계가 가장 분명한 것은 기관 13F 묶음이다. 기관 하나가 분기마다 13F를 내고, 13F 한 건에는 보유 종목이 여러 줄 들어 있다.

```text
institution        기관
  │  1 : N         분기마다 13F 를 낸다
  ▼
filing_13f         13F 제출 한 건 (분기 · 제출일 · 합계)
  │  1 : N         보유 줄
  ▼
holding_13f        종목 하나 (CUSIP · 주식 수 · 금액)
  │  N : 1         CUSIP 으로 찾음
  ▼
cusip_ticker       CUSIP → 티커 (못 찾은 것도 남김)
```

전체 테이블과, 각 테이블을 누가 채우는지는 다음과 같다.

| 테이블 | 담는 것 | 누가 채우나 |
|---|---|---|
| `institution` | 따라가는 기관 10곳(꺼 둔 곳 포함) | 마이그레이션(V2, V6) |
| `filing_13f` | 기관이 분기마다 낸 13F 한 건 | 매일 07:00 배치(SEC) |
| `holding_13f` | 그 제출의 보유 줄(종목, 주식 수, 금액) | 같은 배치 |
| `cusip_ticker` | CUSIP을 티커로 바꾼 결과(못 찾은 것도 남김) | 같은 배치(OpenFIGI) |
| `company_analysis` | AI 기업분석 결과(JSON), 평단가가 들어갔는지 여부, 조사와 판정 시각 | "실행"이나 "판단만 새로"를 눌렀을 때 |
| `dividend_event` / `dividend_fetch` | 배당결정 공시 / 종목별 마지막 조회일(하루 한 번 제한용) | 배당 화면을 조회할 때(DART) |
| `oauth_token` | 증권사 토큰(**AES-256-GCM 암호문**) | 토큰을 발급받을 때 |
| `manual_holding` | 직접 입력한 보유 종목 | 나의 포트폴리오 화면 |
| `symbol_master` | 토스 전체 종목 목록(이름 검색용) | 필요할 때 토스에서 |
| `dart_corp_code` / `sec_cik` | 종목코드를 DART 고유번호로, 티커를 SEC CIK로 바꾸는 표 | 처음 쓸 때 공시처에서 받아 둠 |
| `stored_financials` | 공시 재무(매출, 이익, EPS, BPS 등)를 **주가 없이** 저장한 JSON. 결산일 기준 과거 PER·PBR도 들어 있다. | 매일 06:00 배치가 보유·분석 종목을 받는다. 그 밖의 종목은 처음 볼 때와 하루가 지난 뒤 DART·SEC에서 다시 받고, 실패하면 저장본을 쓴다. |
| `portfolio_snapshot` / `_item` | 장 마감 뒤 하루 한 벌: 합계 한 줄과 종목별 내역 | 평일 16:10 배치(실패하면 18시·20시에 재시도) |
| `reconciliation_result` | 그날 증권사 합계와 앱 합계의 비교(대사) 결과 | 같은 배치 |

스키마는 **Flyway 파일(V1~V10)로만** 바꾼다. 엔티티와 실제 DB 모양이 다르면 앱이 아예 뜨지 않도록 설정해 두었다(`ddl-auto: validate`). 테이블 사이의 전체 관계도(ERD)와 설계 이유는 [3장](#3-데이터베이스--mysqljpaflyway)에서 자세히 본다.

### 1.6 바깥 시스템

이 앱은 혼자서 하는 일이 거의 없다. 잔고와 시세, 재무제표, 기관 보유, AI 분석까지 대부분의 데이터를 바깥 시스템에서 받아 온다. 그래서 바깥 시스템 하나가 막히면 무엇이 빠지는지를 미리 정해 두는 것이 중요하다.

| 시스템 | 무엇에 쓰나 | 인증 방식 | 막히면 |
|---|---|---|---|
| 토스증권 Open API | 보유, 현재가, 일봉 차트 | OAuth(키와 시크릿), **허용 IP 하나만 등록** | 시세와 차트가 빈다. 재무와 기관 칸은 그대로 보인다. |
| 나무증권 API | 보유 | OAuth | 나무증권 보유만 빠진다. |
| DART | 국내 재무, 공시, 배당 | API 키(주소에 붙임) | 국내 재무가 빈다. |
| SEC EDGAR | 미국 재무(XBRL), 13F | User-Agent 필수, 초당 10건 | 미국 재무와 13F 갱신이 멈춘다. |
| OpenFIGI | CUSIP을 티커로 바꾸기 | 키는 선택(없으면 분당 250개) | 티커 없이 회사 이름으로 보이고, 다음 배치가 이어서 채운다. |
| Anthropic(Claude) | AI 기업분석, 스크린샷 읽기, 뉴스 요약 | API 키, **유료** | 분석 실패가 표시되고 나머지는 그대로다. |
| Google News RSS | 종목 뉴스 | 없음 | 뉴스 칸만 빈다. |
| 텔레그램 | 새 13F 알림 | 봇 토큰 | 알림만 가지 않는다. |

"막히면" 칸을 보면 이 앱의 원칙이 보인다. **바깥 하나가 죽어도 화면 전체가 죽지 않게 한다**는 것이다. 이런 설계를 fail-soft라고 부른다. 바깥 호출이 몇 번 있었고 얼마나 실패했는지는 Grafana의 "외부 API" 칸에서 호스트별로 볼 수 있다. 바깥 API를 다루는 장치는 [4장](#4-외부-api-연동)에서 자세히 본다.

### 1.7 캐시·배치·비동기

느린 일을 빠르게 보이게 하는 방법은 크게 세 가지다. 결과를 잠시 들고 있거나(캐시), 사용자가 오기 전에 미리 해 두거나(배치, 예열), 오래 걸리는 일을 뒤로 넘기고 바로 답하는 것(비동기)이다. 이 앱은 세 가지를 모두 쓴다.

| 종류 | 무엇을 | 어디서 | 왜 |
|---|---|---|---|
| 메모리 캐시 6시간 | 공개 기업분석(재무, 문장, 기관 보유) | `StockBriefService` | 방문자가 올 때마다 SEC와 토스를 부르지 않으려고 |
| 메모리 캐시 10분 | 공개 차트 | `PublicChartController` | 토스의 호출 한도(429)를 넘지 않으려고 |
| 메모리 캐시 하루 | 뉴스 요약 | `NewsBriefService` | 유료 호출을 종목당 하루 한 번으로 줄이려고 |
| 메모리 + DB(암호화) | 증권사 토큰 | `TossAuthService`, `NamuhAuthService` | 앱을 다시 띄워도 토큰을 새로 발급받지 않으려고 |
| DB, 하루 한 번 | 배당 공시 조회 | `dividend_fetch` | DART의 하루 2만 건 한도를 지키려고 |
| DB, 영구 | CUSIP → 티커 | `cusip_ticker` | 한 번 찾은 것은 다시 묻지 않으려고 |
| DB, 하루 | 공시 재무(주가를 뺀 부분) | `stored_financials` (`FilingService`) | 분기에 한 번 바뀌는 값을 매번 다시 받지 않으려고. PER·PBR은 읽을 때 지금 주가로 계산한다. |
| 메모리 캐시, 시간 만료 없음 | 13F 집계(같이 산 종목, 보유, 변화) | `QueryCache` | 데이터가 바뀌는 때(배치)를 정확히 알기 때문에 그때 통째로 비운다. 64개까지 들고 LRU로 버린다. |
| 예열 | 위 13F 캐시 | `InstitutionCacheWarmer` | 앱이 뜬 직후나 배치 직후의 첫 방문자가 1~4초를 기다리지 않게 하려고. 비우기(순서 0)가 끝난 뒤 채우기(순서 100)가 돈다. |
| 스케줄, 매일 06:00 | 공시 재무 미리 받기 | `FilingPrefetchService` | 낮에 분석 버튼을 눌렀을 때 공시처를 부르지 않게 하려고 |
| 스케줄, 매일 07:00 | 13F 받기와 티커 변환 | `ThirteenFSyncService` | 공개 자료가 하루 단위로 바뀌기 때문에 |
| 스케줄, 평일 16:10 (18시·20시 재시도) | 장 마감 스냅샷과 대사 | `PortfolioSnapshotService` | 평가금액 이력을 남기고, 앱 합계가 증권사 합계와 맞는지 매일 확인하려고 |
| 이벤트 | 새 13F → 텔레그램 | `FilingAlertService` (`@EventListener`) | 받기와 알림을 떼어 놓아 한쪽이 실패해도 다른 쪽이 돌게 하려고 |
| 비동기, 스레드 하나 | AI 기업분석(2~5분) | `CompanyAnalysisService` | 요청을 몇 분씩 붙잡지 않고 화면이 상태를 다시 묻게 하려고 |
| 서버 cron, 매일 04:00 | DB 백업 | `deploy/backup.sh` | 서버가 망가져도 데이터를 되살리려고 |

표가 길지만 질문은 하나다. **"이 값은 얼마나 자주 바뀌고, 바뀌는 때를 아는가?"** 분기에 한 번 바뀌는 재무는 하루 동안 들고 있어도 되고, 배치가 끝나는 순간에만 바뀌는 13F 집계는 시간 대신 배치 이벤트로 비우면 된다. 캐시를 고를 때마다 이 질문부터 던지면 된다.

### 1.8 보안 경계 — 누가 무엇을 볼 수 있나

이 앱에는 누구나 볼 수 있는 공개 화면과 운영자만 볼 수 있는 내 화면이 한 앱 안에 섞여 있다. 그래서 "어디까지가 공개인가"를 주소 단위로 분명히 나눠 두었다.

```text
① 공개 (로그인 없음)
   /  ·  /public/**
   /api/public/**  ·  GET /api/institutions/**

② 로그인한 나만
   /portfolio.html
   나머지 /api/**  (돈이 드는 호출 포함)

③ 서버 안 (127.0.0.1) 만
   관리 8081  ·  Prometheus 9090  ·  Grafana 3000   → SSH 터널로만 본다
```

각 경계는 아래 장치들이 지킨다.

| 경계 | 지키는 장치 |
|---|---|
| 공개 ↔ 로그인 | `SecurityConfig`의 주소 규칙이 지키고, 그 규칙은 테스트로 고정되어 있다. 세션 쿠키에는 `HttpOnly`, `SameSite=Strict`, `Secure`를 걸고, 쓰기 요청에는 CSRF 토큰을 요구한다. |
| 공개 화면 남용 | IP당 분당 120번(배당은 15번)까지만 받고, 넘으면 429로 답한다. |
| 공개 화면에 내 정보가 새는 것 | 평단가가 들어간 AI 분석은 공개 주소에서 "없음"으로 답한다. 바깥 API의 오류 문구에는 서버 IP가 들어 있어서 일반 문구로 바꿔 내보낸다. |
| 브라우저 | CSP로 인라인 스크립트를 금지하고, 바깥에서 온 글자는 `esc()`를 거쳐 넣는다. |
| 서버 밖 ↔ 서버 안 | 80번과 443번만 공개하고, 관리 주소와 관측 도구는 127.0.0.1에만 열어 SSH 터널로 본다. |
| 지표에 비밀이 실리는 것 | 바깥 호출 지표의 주소 태그에서 쿼리와 키처럼 보이는 조각을 지운다. |

각 장치의 원리는 [5장](#5-보안--spring-security와-웹-보안)에서 다룬다.

### 1.9 요청이 지나가는 길

이제 실제 요청 네 가지를 처음부터 끝까지 따라가 본다. 앞에서 본 부품들이 어떤 순서로 맞물리는지 보이게 된다.

**① 공개 기업분석 화면에서 `MSFT`를 연다**

가장 흔한 요청이다. 로그인 없이 누구나 보내는 GET 요청이 어떤 필터를 거치고, 캐시가 어디에서 일하는지 보자.

```text
브라우저 (stock.js)
  │  ① GET /api/public/stocks/MSFT  (HTTPS)
  ▼
Caddy
  │  ② HTTP 로 넘김 + X-Forwarded-For (사용자 IP) + X-Request-Id (요청 번호)
  ▼
RequestIdFilter  번호를 로그 문맥(MDC)에 → 이 요청의 모든 로그 줄에 붙음, 응답 헤더로도 돌려줌
  ▼
필터 (보안 규칙 · IP 당 분당 120번)
  │  ③ 공개 주소, 한도 안 → 통과
  ▼
StockBriefService
  ├─ 6시간 캐시에 있으면 → 바로 응답
  └─ 없으면
       ├─ ④ SEC 에서 10-K 재무, 토스에서 현재가
       ├─ ⑤ MySQL 에서 기관 10곳의 이 종목 13F
       ├─ ⑥ StockNotes 가 정해진 규칙으로 문장
       └─ ⑦ JSON 으로 응답

브라우저는 이어서 /api/public/chart · /api/public/analysis 로 차트 칸과 AI 칸을 채운다
```

요청은 Caddy를 지나며 사용자 IP와 요청 번호를 달고 앱에 들어온다. 앱의 필터가 요청 번호를 로그 문맥에 넣고, 공개 주소인지와 호출 한도 안인지를 확인한 뒤 서비스로 넘긴다. 서비스는 6시간 캐시를 먼저 보고, 없을 때만 SEC, 토스, MySQL을 차례로 불러 답을 만든다. 화면은 이 답으로 첫 칸을 그린 뒤 차트와 AI 칸을 따로 불러 채운다. 느린 칸 때문에 화면 전체가 늦게 뜨지 않게 하려는 것이다.

**② 나의 포트폴리오에서 AI 기업분석을 누른다** (돈이 드는 호출, 2~5분)

이번에는 몇 분씩 걸리는 일을 어떻게 다루는지 본다.

```text
브라우저
  │  ① POST /api/analysis/MSFT  (로그인 + CSRF 토큰)
  ▼
CompanyAnalysisService

```

HTTP 요청 하나를 5분 동안 열어 두면 중간에 끊기기 쉽다. 그래서 서버는 숫자로 된 사실(보유 수량, 현재가, 공시 재무)만 먼저 모은 뒤, 실제 AI 호출은 작업 스레드에 넘기고 바로 "RUNNING"이라고 답한다. 화면은 몇 초마다 상태를 다시 물어보다가 "OK"가 오면 결과를 그린다. 이 방식은 [2.3](#23-비동기-작업과-폴링)에서 자세히 본다.

### 1.10 코드에서 운영까지

마지막으로, 코드를 고친 뒤 그 변경이 실제 서버에 반영되기까지의 길이다.

```text
브랜치 · 커밋
  ▼
PR
  ▼
CI            테스트 · 이미지 빌드 · 배포 설정 검사
  ▼           (모두 통과해야만)
main 에 스쿼시 병합
  ▼
이미지 → ghcr.io (태그 sha-xxxxxxx)
  ▼
배포 워크플로 → SSH → deploy.sh
  ▼
헬스체크 (readiness 가 UP 인가?)
  ├─ 예     → 새 버전으로 운영
  └─ 아니오 → 바로 앞 버전으로 자동 되돌림
```

`main` 브랜치에는 직접 밀어 넣을 수 없다. 브랜치에서 작업한 뒤 PR을 올리면 CI가 테스트, 이미지 빌드, 배포 설정 검사를 자동으로 돌리고, 셋이 모두 통과해야 합칠 수 있다. 합치는 순간 이미지가 만들어져 저장소(ghcr.io)에 올라가고, 배포 워크플로가 서버에 접속해 새 이미지로 바꿔 끼운다. 새 버전이 헬스체크를 통과하지 못하면 바로 앞 버전으로 자동으로 되돌아간다. 자세한 내용은 [9장 CI/CD](#9-cicd--github-actions)와 [10장 배포](#10-인프라와-배포--서버caddy배포-스크립트)에 있다.

**실무 연결.** 대부분의 회사 백엔드가 이 장의 모양과 같다. 앞단의 프록시(Nginx, Caddy, 클라우드의 L7 로드밸런서)가 요청을 받고, 뒤의 애플리케이션 서버가 처리하고, DB가 저장한다. 규모가 커지면 앱이 여러 대가 되고 그 사이에 로드밸런서, 공용 캐시(Redis), 메시지 큐가 들어가지만 기본 뼈대는 같다. 이 프로젝트의 메모리 캐시는 앱이 두 대가 되는 순간 Redis 같은 공용 캐시로 옮겨야 한다. 앱마다 캐시 내용이 달라지기 때문이다. 이것이 "다음 규모"로 갈 때의 첫 숙제다.

> **직접 해보기** — 브라우저 개발자 도구의 Network 탭을 연 채로 기업분석 화면에서 종목 하나를 눌러 보자. ①의 요청 세 개(stocks, chart, analysis)가 보일 것이다. 같은 종목을 다시 열면 stocks 응답이 훨씬 빨라지는데, 6시간 캐시가 일하고 있기 때문이다.

## 2. 백엔드 — Spring Boot

> **이 장에서 배울 것** — 스프링이 객체를 만들어 꽂아 주는 방식(DI), 설정을 밖에서 넣는 법, 오래 걸리는 일을 뒤로 넘기는 법(비동기), 정해진 시각에 도는 일(배치), 그리고 스프링이 몰래 끼워 넣는 대리 객체(프록시)를 봅니다.
>
> **먼저 알아둘 말** — [빈](#02-스프링과-서버-안쪽) · [DI](#02-스프링과-서버-안쪽) · [스프링 프록시](#02-스프링과-서버-안쪽) · [트랜잭션](#02-스프링과-서버-안쪽) · [비동기·폴링](#02-스프링과-서버-안쪽) · [cron](#02-스프링과-서버-안쪽) · [멱등](#05-배치와-숫자-맞추기) · [대사](#05-배치와-숫자-맞추기)

### 2.1 계층 구조와 의존성 주입(DI)

**무엇.** 코드를 역할별 층으로 나눕니다. `Controller`(HTTP) → `Service`(규칙) → `Repository`(DB) / `Client`(바깥 API). 스프링이 객체를 만들어 생성자로 꽂아 줍니다(DI).

**기초부터.** 자바만 쓸 때는 필요한 객체를 직접 만듭니다.

```java
// 스프링 없이: 내가 만들고, 내가 고른다
class StockBriefService {
    private final FilingService filing = new FilingService(new DartFinancialService(...), ...);
}
```

이러면 `FilingService` 가 무엇을 필요로 하는지 `StockBriefService` 가 전부 알아야 하고, 테스트에서 가짜로 바꿔 끼울 수도 없습니다. DI 는 "만들기" 를 스프링에게 넘기고 **생성자로 받기만** 합니다.

```java
@Service                                   // "이 클래스는 스프링이 하나 만들어 들고 있어라(빈)"
class StockBriefService {
    private final FilingService filing;
    StockBriefService(FilingService filing) {  // 스프링이 들고 있던 FilingService 를 꽂아 준다
        this.filing = filing;
    }
}
```

(실제 생성자는 받는 것이 더 많습니다. 모양만 줄였습니다.) 테스트에서는 스프링 없이 `new StockBriefService(mock(FilingService.class), ...)` 로 가짜를 꽂습니다. 이 저장소의 테스트 대부분이 이렇게 짜여 있습니다(예: `FilingPrefetchServiceTest`).

**이 프로젝트에서는.**
- 패키지가 곧 층입니다: `web` → `service` → `domain`·`external`·`brokerage`
- 모든 의존성을 **생성자 주입**으로 받습니다(`@Autowired` 필드 주입 없음). 예: `StockBriefService` 생성자
- `BrokerageClient` 인터페이스에 **주문 메서드가 없습니다.** 인터페이스 설계로 "할 수 없는 일" 을 만든 안전장치입니다 → [결정기록 001](결정기록.md#001-주문-api를-만들지-않는다)

**실무에서는.** 생성자 주입은 사실상 표준입니다(불변 필드, 테스트에서 `new` 로 만들기 쉬움). 인터페이스로 경계를 두면 구현을 바꾸거나(증권사 추가) 테스트에서 가짜를 꽂기 쉽습니다.

**공부할 것.** IoC/DI 개념, 빈 생명주기, `@Component`/`@Service`/`@Repository` 차이, 순환 의존이 왜 문제인가.

### 2.2 설정 관리

**이 프로젝트에서는.**
- 비밀값은 `.env` 파일 → `EnvFileLoader` 가 시스템 프로퍼티로 등록 → `application.yml` 의 `${TOSS_CLIENT_ID}` 가 읽음
- `application.yml` 의 `${MANAGEMENT_PORT:8081}` 처럼 **기본값**을 둡니다. 단, 우리 로더는 빈 값도 넣어서 기본값이 안 먹는 함정이 있었습니다([개발일지 전환점 20](개발일지.md))
- 묶음 설정은 `@ConfigurationProperties` 레코드로 받습니다(예: `AnthropicProperties`)

**실무에서는.** "코드는 하나, 설정은 환경마다" (12-Factor App). 비밀값은 저장소에 절대 넣지 않고 환경변수·Vault·클라우드 Secret Manager 로 주입합니다. `.env` 는 `.gitignore`, 이미지에는 `.dockerignore` 로 막습니다.

**공부할 것.** Spring Profile(`dev`/`prod`), 설정 우선순위(환경변수 > yml), 12-Factor App 의 Config 항목.

### 2.3 비동기 작업과 폴링

**이 프로젝트에서는.** AI 기업분석은 2~5분 걸립니다. HTTP 요청을 그동안 붙잡으면 끊기기 쉬워서:
1. `POST /api/analysis/{종목}` 은 작업을 **단일 스레드 풀**(`Executors.newSingleThreadExecutor`)에 넘기고 바로 `RUNNING` 을 응답
2. 화면이 몇 초마다 `GET` 으로 상태를 다시 물음(폴링)
3. 같은 종목이 이미 돌고 있으면 중복 실행하지 않고, 15분 넘게 안 끝나면 죽은 것으로 보고 다시 시작
→ `CompanyAnalysisService.start()`

**실무에서는.** 오래 걸리는 작업 = "접수 → 처리 → 결과 조회" 패턴. 규모가 크면 메시지 큐(Kafka·RabbitMQ·SQS)와 워커로 나눕니다. 폴링 대신 WebSocket·SSE 로 밀어 주기도 합니다.

**공부할 것.** `ExecutorService`, `@Async`, 스레드 풀 크기, 작업 멱등성, 메시지 큐 기본.

### 2.4 스케줄 배치

**이 프로젝트에서는.** `ThirteenFSyncService` 가 매일 07:00(한국 시간) SEC 에서 새 공시를 받습니다. `@Scheduled(cron = "...", zone = "Asia/Seoul")`.
- **멱등**하게 짰습니다. 이미 받은 공시는 건너뛰므로 몇 번 돌려도 결과가 같습니다
- 새 공시를 받으면 `ApplicationEvent` 를 발행하고, 알림(텔레그램)은 이벤트를 받아서 따로 처리합니다(느슨한 결합)

**공시 재무 야간 배치**(`FilingPrefetchService`) — 매일 06:00. 보유·분석해 둔 종목의 공시 재무를 미리 받아 `stored_financials` 를 덮어씁니다(종목이 키라 몇 번 돌아도 한 벌).
- **"미리 계산" 은 캐시 예열과 같은 생각**입니다. 요청이 올 때 느린 바깥(DART·SEC)을 부르지 않게 한가한 시간에 당겨 둡니다
- **덮어쓰기 전에 입력부터 확인**: 발행주식수를 못 받으면 주당 지표가 빈 재무가 만들어져 멀쩡한 저장본을 망칩니다. 그래서 그 종목은 건너뛰고, 토스 자체가 실패하면 남은 종목도 같은 이유로 실패하니 첫 종목에서 멈춥니다
- 수동 실행 `POST /api/financials/prefetch`, 지표 `filing_prefetch_runs_total{outcome}`

**장 마감 스냅샷과 대사**(`PortfolioSnapshotService`) — 이 프로젝트에서 가장 "증권사 배치" 다운 코드입니다.

```text
16:10 ─▶ 오늘 것 있나? ── 있음(재시도 회차) ──▶ 건너뜀
            │ 없음
            ▼
        증권사마다 statement() ── 하나라도 실패 ──▶ 저장 안 함 (빈 날 > 틀린 날)
            │ 보유 + 증권사가 밝힌 합계
            ▼
        대사: |앱 합계 − 증권사 합계| ≤ max(0.1%, 1원)?
            ▼
        한 트랜잭션: 합계 upsert → 그날 종목·대사 줄 delete → insert   (멱등)
            ▼
        지표 → Prometheus 규칙 → 텔레그램
18:10, 20:10 ─▶ 같은 흐름 (그날 성공했으면 첫 단계에서 끝)
```

- **멱등**: 날짜가 키라서 몇 번 돌려도 그날 한 벌. 재시도와 수동 실행이 서로를 망가뜨리지 않습니다
- **재처리 한계를 인정**: 과거 날짜는 다시 만들 수 없습니다(증권사는 지금 잔고만 줌). 그래서 재시도를 그날 시간표에 넣었습니다
- **대사**: 화면 합계는 앱이 더한 값입니다. 증권사도 같은 응답 맨 위에 계좌 합계를 줍니다. 둘을 매일 맞춰 보면 "앱이 조용히 빠뜨린 종목" 이 드러납니다. 지운 줄의 `delete` 를 JPQL 한 번(`@Modifying`)으로 즉시 보내는 이유는, 파생 삭제는 한 줄씩 읽고 지워서 바로 이어 같은 키를 넣으면 유니크 키에 걸릴 수 있기 때문입니다
- 겪은 함정: 생성자를 둘(운영용, 테스트용 시계) 두었더니 스프링이 어느 쪽을 쓸지 몰라 기동이 멈췄습니다. 단위 테스트는 통과했고 jar 를 띄워서야 잡혔습니다 → `@Autowired` 로 밝힘

**실무에서는.** 야간 배치·정산·대사(서로 다른 시스템의 숫자가 맞는지 맞춰 보기)가 전형적입니다. 증권사에서는 자체 원장과 예탁원·거래소·은행 숫자를 매일 맞추고, 안 맞는 건(불일치 내역)을 다음 날 아침까지 해소합니다. 서버가 여러 대면 같은 배치가 동시에 도는 걸 막아야 합니다(ShedLock, Quartz 클러스터). 큰 배치는 Spring Batch 를 씁니다.

**공부할 것.** cron 표현식, 멱등성, Spring Batch(Job/Step/Chunk), 분산 락.

### 2.5 예외 처리와 API 응답

**이 프로젝트에서는.** `GlobalExceptionHandler`(`@RestControllerAdvice`)가 예외를 한 곳에서 응답으로 바꿉니다.
- 500 은 **일반 메시지만** 내보냅니다(스택 트레이스·SQL 이 새면 공격자에게 지도가 됨)
- 브라우저가 없는 주소를 열면 HTML 404, API 는 JSON 404

**실무에서는.** 에러 응답 형식을 팀 표준으로 맞춥니다(코드·메시지·추적 ID). 로그에는 자세히, 응답에는 간단히.

### 2.6 API 문서 자동화

**이 프로젝트에서는.** springdoc 이 컨트롤러를 읽어 Swagger UI 를 만듭니다(`/swagger-ui.html`). 문서에 주소 목록을 손으로 쓰지 않습니다. 운영에서는 `SWAGGER_ENABLED=false` 로 끕니다.

**실무에서는.** OpenAPI 스펙으로 프론트·외부 협력사와 계약합니다. 스펙에서 클라이언트 코드를 생성하기도 합니다.

### 2.7 프록시 — 스프링이 몰래 끼워 넣는 대리 객체

**무엇.** 프록시는 "진짜를 감싸고 대신 받는 객체" 입니다. 부르는 쪽은 진짜를 부른다고 생각하지만, 실제로는 프록시가 먼저 받아 앞뒤에 일을 끼워 넣고 진짜에게 넘깁니다. 네트워크의 프록시(Caddy, [0.1](#01-웹과-네트워크))와 생각이 같습니다. 대상이 서버냐 객체냐만 다릅니다.

```text
부르는 쪽 ──▶ 프록시 (스프링이 만든 대리 객체)
                │ ① 트랜잭션 열기
                │ ② 진짜 객체의 save() 를 부름 ──▶ 진짜 객체
                │ ③ 예외가 없으면 커밋, 있으면 롤백
                ▼
              부르는 쪽에 결과를 돌려줌
```

`@Transactional`, `@Cacheable`, `@Async`, Spring Security 의 메서드 보안이 전부 이 방식입니다. 이걸 **AOP**(관심사 분리: 트랜잭션 같은 공통 일을 업무 코드 밖으로 빼기)라고 부릅니다.

**함정 — 같은 클래스 안에서 부르면 안 듣는다.**

```java
@Service
class AnalysisService {
    void runInBackground() {
        this.save(result);        // ✗ this 는 프록시가 아니라 진짜 → 트랜잭션이 안 열림
    }
    @Transactional
    void save(Result r) { ... }
}
```

밖에서 들어올 때만 프록시를 거치기 때문입니다. 이 저장소는 그래서 **저장만 맡는 빈을 따로** 둡니다: `CompanyAnalysisStore`, `PortfolioSnapshotStore`. 서비스가 그 빈을 주입받아 부르면 반드시 프록시를 거칩니다.

**이 프로젝트의 "끼워 넣기" 셋.** 생각은 같고 끼어드는 자리가 다릅니다.

| 무엇 | 어디에 끼어드나 | 이 저장소 |
|---|---|---|
| 서블릿 필터 | 들어오는 HTTP 요청 전후 | `RequestIdFilter`(요청 번호), `PublicRateLimitFilter`(호출 한도), Spring Security |
| 스프링 프록시(AOP) | 빈의 메서드 호출 전후 | `@Transactional` 이 붙은 저장 빈 |
| RestClient 인터셉터 | **나가는** HTTP 요청 전후 | `ResilientHttpInterceptor`(재시도·서킷 브레이커) |

**실무에서는.** "트랜잭션이 안 먹어요" 의 가장 흔한 원인이 위 함정입니다. 면접 단골이기도 합니다. 로그·권한 검사·성능 측정 같은 공통 일을 업무 코드에 섞지 않고 프록시·필터로 빼는 게 실무 표준입니다.

**공부할 것.** JDK 동적 프록시 vs CGLIB, `@Transactional` 의 전파(propagation)와 롤백 규칙(체크 예외는 기본으로 롤백 안 됨), 필터 vs 인터셉터 vs AOP 차이.


### 3.3 키 설계 — 자연 키와 대리 키

**무엇.** 기본 키를 고르는 두 방법입니다. **자연 키**는 업무에 원래 있는 값(종목코드, 공시번호), **대리 키**는 DB 가 붙이는 일련번호(`AUTO_INCREMENT id`)입니다.

**이 프로젝트에서는.**

| 고른 것 | 테이블 | 이유 |
|---|---|---|
| 자연 키 | `filing_13f.accession_no`, `dividend_event.rcept_no` | 바깥(SEC·DART)이 준 번호라 안 바뀌고 유일하다. 같은 공시를 두 번 받아도 같은 행이 된다(중복 방지가 공짜) |
| 자연 키 | `stored_financials.symbol`, `dart_corp_code.stock_code`, `cusip_ticker.cusip` | "종목당 한 줄" 이라 조회 조건이 곧 키다 |
| 대리 키 + 유니크 | `company_analysis (id, UK symbol)`, `manual_holding (id, UK owner_key+symbol)` | JPA 가 다루기 쉬운 `id` 를 두고, 업무 규칙("종목당 하나", "사람·종목당 하나")은 유니크 키로 DB 가 지킨다 |
| 복합 유니크 | `holding_13f (accession_no, cusip, put_call)` | 같은 제출·같은 종목이라도 콜옵션·풋옵션 줄이 따로 있다. 셋을 묶어야 한 줄이 정해진다 |

**실무에서는.** 증권 시스템도 계좌번호·주문번호 같은 자연 키가 많습니다. 다만 자연 키가 바뀔 수 있으면(종목코드 변경, 회원 ID 변경) 대리 키를 PK 로 두고 자연 키는 유니크로 둡니다. **유니크 키는 "애플리케이션이 실수해도 DB 가 막는" 마지막 방어선**입니다. 코드에서 "있으면 수정, 없으면 추가" 를 해도 동시에 두 요청이 오면 둘 다 "없음" 을 볼 수 있습니다.

### 3.4 FK 제약을 걸지 않은 이유

**무엇.** FK(외래 키) 제약은 "자식 행은 존재하는 부모를 가리켜야 한다" 를 DB 가 강제하는 것입니다.

**이 프로젝트에는 하나도 없습니다.** 관계는 있지만(3.1 의 실선) 지키는 건 코드입니다.

- **13F 는 배치 한 곳에서만 쓴다.** `ThirteenFSyncService` 가 자식(`holding_13f`)을 먼저 지우고 부모(`filing_13f`)를 지웁니다. 쓰는 곳이 하나라 어긋날 길이 좁습니다
- **`holding_13f.cusip → cusip_ticker` 는 비어 있는 게 정상이다.** 보유 줄을 먼저 저장하고 티커는 OpenFIGI 로 나중에 찾습니다(분당 호출 제한). FK 를 걸면 티커를 못 찾은 종목은 보유 줄도 저장할 수 없습니다
- **점선 관계는 서로 몰라도 된다.** AI 분석은 있는데 공시 재무가 없거나, 그 반대여도 정상입니다

**대가.** 잘못된 코드가 고아 행(부모 없는 자식)을 만들어도 DB 가 막아주지 않습니다.

**실무에서는.** 의견이 갈립니다. 계좌·주문·체결처럼 **돈이 걸린 원장은 FK 를 거는 편**이 많고, 대용량 로그·배치 적재 테이블은 쓰기 성능과 적재 순서 때문에 빼는 편이 많습니다. 면접에서는 "왜 걸었나/안 걸었나" 를 말할 수 있는 게 중요합니다.

### 3.5 JSON 을 통째로 넣은 열 — `analysis_json`, `financials_json`

**무엇.** 표로 쪼개지 않고 문서 하나를 `LONGTEXT` 열에 넣는 방식입니다.

**이 프로젝트에서는.**
- `company_analysis.analysis_json`: 판정 + 7개 섹션 + 지표 + 출처. 한 건에 10~30KB
- `stored_financials.financials_json`: 연간·올해 누적·최근 4분기 재무와 과거 배수

쪼개지 않은 이유는 **항상 통째로 읽고 통째로 쓰기 때문**입니다. 섹션 하나만 조회하거나 "PER 10배 아래인 종목" 을 SQL 로 찾을 일이 없습니다. 모양이 바뀌어도(섹션 추가) 마이그레이션이 필요 없고, 자바 record(`CompanyAnalysisView`, `CompanyFinancials`)를 Jackson 이 그대로 읽고 씁니다.

**지킨 원칙 둘.**
1. **거르는 데 쓰는 값은 JSON 밖의 열로 꺼낸다.** `status`, `analyzed_at`, `researched_at`, `includes_position`, `has_history` 가 그렇습니다. 특히 `includes_position`(평단가가 들어갔나)은 공개 화면이 거르는 기준이라 JSON 을 열어 보지 않고 열 하나로 판단합니다
2. **매일 바뀌는 값은 넣지 않는다.** 공시 재무는 분기에 한 번 바뀌지만 PER·PBR 은 주가 따라 매일 바뀝니다. 그래서 주가 없이 저장하고 읽을 때 `withPrice()` 로 계산합니다

**실무에서는.** MySQL 의 `JSON` 타입(형식 검증·부분 조회)이나 PostgreSQL 의 `jsonb`(인덱스 가능)를 씁니다. 이 프로젝트는 부분 조회가 없어 `LONGTEXT` 로 충분했습니다. 남용하면 "DB 안의 NoSQL" 이 되어 정합성을 잃으니 **통째로 읽고 쓰는 문서**에만 씁니다.

### 3.6 상태판을 겸하는 테이블 — `company_analysis`

AI 분석은 몇 분 걸려서 별도 스레드에서 돕니다. 작업 큐 테이블을 따로 두지 않고 이 테이블이 상태판을 겸합니다.

```text
           "실행" 클릭                          클로드 응답
 NONE ──────────────────▶ RUNNING ──────────────────────────▶ OK
(행 없음)                    │                                  │
                            │ 실패                   "판단만 새로" (조사 7일 안)
                            ▼                                  │
                          ERROR ◀───── 실패 ───── RUNNING ◀─────┘
              (analysis_json 은 그대로 남는다)
```

- **성공 결과와 마지막 시도를 다른 열에 둔다.** `analysis_json`·`analyzed_at` 은 마지막 **성공**, `status`·`last_error` 는 마지막 **시도**입니다. 재분석이 실패해도 멀쩡한 분석을 잃지 않습니다
- **시각을 셋 둔다.** `researched_at`(웹 조사, V9), `analyzed_at`(판정), `updated_at`(마지막 시도). "판단만 새로" 는 판정 시각만 바꾸므로 화면이 "판단 갱신 · 조사" 를 따로 보여줍니다
- **죽은 작업을 알아본다.** `RUNNING` 인데 `updated_at` 이 15분을 넘었으면 서버가 죽었던 것으로 보고 다시 시작을 허용합니다

**실무에서는.** 같은 문제를 작업 테이블 + 상태 열(`READY/RUNNING/DONE/FAILED`)이나 메시지 큐(Kafka·RabbitMQ)로 풉니다. 증권사의 일괄 처리(정산·배치)도 "상태 열 + 재처리 가능" 이 기본 모양입니다.

### 3.7 JPA 엔티티와 리포지토리

**이 프로젝트에서는.**
- 엔티티: `domain/*.java` (`@Entity`), 테이블마다 하나. 리포지토리: `JpaRepository` 상속 인터페이스
- **연관관계 매핑(`@ManyToOne` 등)을 쓰지 않았습니다.** FK 를 안 건 것과 같은 이유이고, 덕분에 지연 로딩 예외와 N+1 이 생길 자리가 없습니다. 필요한 건 키 값으로 따로 조회합니다
- **쿼리 메서드**: 이름만으로 SQL 이 만들어집니다. 예: `findByAccessionNoAndCusipIn(String, Collection<String>)` → `WHERE accession_no = ? AND cusip IN (...)`
- 서비스에 `@Transactional(readOnly = true)` 를 붙여 읽기 전용 트랜잭션으로 엽니다(`InstitutionPortfolioService`)
- **스레드와 트랜잭션**: 백그라운드 분석 스레드에는 요청의 트랜잭션이 따라가지 않습니다. 그래서 저장만 맡는 별도 빈(`CompanyAnalysisStore`)에 `@Transactional` 을 둡니다. 같은 클래스 안에서 자기 메서드를 부르면 프록시를 안 거쳐 `@Transactional` 이 안 듣는 함정도 이걸로 피합니다
- 성능 예: 종목 하나를 보려고 기관마다 수천 줄을 다 읽던 것을, 그 종목 CUSIP 만 `IN` 으로 읽게 바꿨습니다(`movesFor`). `idx_holding_13f_cusip` 인덱스가 이 조회를 받칩니다

**실무에서는.** JPA 는 생산성이 높지만 **N+1 문제**, 지연 로딩 예외, 불필요한 전체 조회를 조심해야 합니다. 복잡한 조회는 QueryDSL·JPQL·네이티브 SQL·MyBatis 를 섞어 씁니다(금융권은 MyBatis 비중이 높습니다).

**공부할 것.** 영속성 컨텍스트, 1차 캐시, 변경 감지(dirty checking), N+1 과 fetch join, 트랜잭션 전파와 격리 수준, 인덱스와 실행 계획(`EXPLAIN`).

> **직접 해보기** — `EXPLAIN SELECT * FROM holding_13f WHERE cusip = '594918104';` 를 돌려 `key` 칸에 `idx_holding_13f_cusip` 이 나오는지 보세요. 인덱스가 없는 열(`issuer_name`)로 바꾸면 `type: ALL`(전체 스캔)이 나옵니다.

### 3.8 스키마 마이그레이션 — Flyway

**이 프로젝트에서는.**
- `src/main/resources/db/migration/V1__init.sql` ~ `V10__portfolio_snapshot.sql`. 앱이 뜰 때 적용 안 된 파일만 순서대로 실행
- Hibernate 는 `ddl-auto: validate` — 테이블을 **만들지 않고 검사만** 합니다. 엔티티와 DB 가 다르면 기동이 멈춥니다
- **이미 적용된 V 파일은 절대 고치지 않습니다.** 체크섬이 달라져 기동이 멈춥니다. 고칠 게 있으면 새 V 파일을 만듭니다

| 버전 | 한 일 | 배울 점 |
|---|---|---|
| V1 | 처음 테이블 6개 | Flyway 를 늦게 붙여 기존 DB 는 `baseline` 으로 "적용됨" 표시만 |
| V2 | 13F 테이블 4개 + 기관 시드 | 스키마와 기준 데이터를 같이 넣기 |
| V3 | 기관 설명 한 줄 수정 | 적용된 V2 를 고치지 않고 새 파일로 |
| V4 | 배당 테이블 2개 | |
| V5 | `includes_position` 열 추가, 기존 행은 `1`(비공개) | **안전한 쪽 기본값**으로 열 추가 |
| V6 | 기관 10곳 교체 | 지우지 않고 `active = 0` |
| V7 | 잘못 찾은 티커 정리 | 데이터 정리도 마이그레이션으로 |
| V8 | `stored_financials` | |
| V9 | `researched_at` 추가, 기존 행은 `analyzed_at` 으로 채움 | 열 추가와 **값 채우기를 한 파일에서** |
| V10 | 스냅샷·대사 테이블 3개 | 날짜를 키로 한 멱등 배치 테이블 |

**실무에서는.** 운영 DB 를 사람이 직접 `ALTER` 하지 않고, 검토된 마이그레이션 파일로만 바꿉니다(Flyway·Liquibase). 롤백을 생각해 **expand → contract** 로 나눕니다: ① 열 추가(옛 코드도 동작) → ② 새 코드 배포 → ③ 다음 배포에서 옛 열 제거. 이 프로젝트도 "스키마는 더하기만" 을 지킵니다. 자동 배포가 실패해 옛 이미지로 롤백되면 옛 코드가 새 스키마를 만나기 때문입니다.

**공부할 것.** 마이그레이션 도구, 무중단 스키마 변경, 대용량 테이블 `ALTER` 의 잠금 문제(online DDL).

| 주제 | 이 프로젝트의 방법 | 파일 |
|---|---|---|
| HTTP 클라이언트 | 스프링 6 `RestClient`. 바깥 시스템마다 빈을 따로(타임아웃·기본 헤더가 달라서) | `PublicDataRestClientConfig` |

| 호출 한도 지키기 | SEC 는 초당 10건 제한·User-Agent 필수. 받는 쪽 규칙을 코드로 지킨다 | `external/thirteenf` |
| 실패 대응 (fail-soft) | 토스가 막혀도 재무·기관 칸은 보여준다. 부가 정보 실패가 화면 전체를 죽이지 않게 | `StockBriefService.build()` |
| 타임아웃 | 연결 5초·응답 30초. 스프링 부트 3.3 기본값은 **타임아웃이 없다** — 상대가 답을 안 주면 스레드가 끝없이 묶인다 | `HttpClientResilienceConfig` |
| 재시도 | GET 만, 네트워크 오류·5xx 만, 최대 3번(0.5초→1초 + 흔들기). 4xx·429 는 다시 보내도 같거나 더 나빠서 안 함. POST 는 두 번 실행될 수 있어 안 함 | `ResilientHttpInterceptor` |

| 캐시 | 자주 안 바뀌는 데이터는 메모리 캐시(6시간 TTL, 크기 상한) | `StockBriefService` |
| 파싱 | 큰 XML 은 StAX(스트리밍)로. 한 번에 메모리에 올리지 않는다 | `InfoTableParser` |
| 문자 인코딩 | "EUC-KR 이라고 적혀 있지만 실제로는 UTF-8" 인 문서 → 엄격한 UTF-8 해독 후 실패 시 EUC-KR | `DartApiClient.decode()` |
| 비용 통제 | 돈이 드는 호출(Claude)은 사람이 누를 때만. 프롬프트 캐싱으로 반복 비용 절감 | `CompanyAnalysisService` |

**실무에서는.** 대외 연동(타 기관·PG·거래소)이 장애의 큰 원인입니다. 꼭 챙기는 것: **타임아웃**, **재시도(+지수 백오프)**, **서킷 브레이커**(Resilience4j), **멱등 키**, 요청·응답 로그(민감 정보 마스킹), 상대 시스템 점검 시간 대응.

**공부할 것.** HTTP 상태 코드 의미(401 vs 403 vs 429), 타임아웃 종류(connect/read), 재시도와 멱등성(왜 GET 만?), 지수 백오프와 지터, 서킷 브레이커의 세 상태(닫힘·열림·반열림), OAuth 2.0 흐름, 캐시 무효화 전략.

> **직접 해보기** — `ResilientHttpInterceptorTest` 를 열어 "5xx 면 다시 보내고 4xx 면 안 보낸다" 가 어떻게 고정돼 있는지 읽어 보세요. 그다음 서킷 브레이커가 **열림 → 반열림 → 닫힘** 으로 돌아오는 경우를 테스트로 하나 더 써 보세요(시간을 기다리지 않게 설정값을 줄이는 게 요령입니다).

## 5. 보안 — Spring Security와 웹 보안

> **이 장에서 배울 것** — 공개 화면과 내 화면이 한 앱에 섞여 있을 때 누가 무엇을 볼 수 있게 할지, 브라우저를 노리는 공격(CSRF·XSS)을 어떻게 막는지 봅니다.
>
> **먼저 알아둘 말** — [인증·인가](#06-보안) · [쿠키·세션](#01-웹과-네트워크) · [CSRF](#06-보안) · [XSS](#06-보안) · [CSP](#06-보안) · [AES-GCM](#06-보안)

이 프로젝트는 **공개 화면**(누구나)과 **내 화면**(로그인)이 한 앱에 섞여 있어서 보안 공부 거리가 많습니다. 규칙은 `config/SecurityConfig.java` 와 그 테스트에 고정돼 있습니다.

### 5.1 인증과 인가

- **폼 로그인 + 세션 쿠키.** 로그인 화면은 정적 HTML(`/public/login.html`), 처리는 `/login`
- 세션 쿠키: `HttpOnly`(JS 가 못 읽음), `SameSite=Strict`, 운영에서는 `Secure`(HTTPS 에서만), 12시간
- **주소마다 규칙**: `/`, `/public/**`, `/api/public/**`, `GET /api/institutions/**` 는 공개. 나머지는 로그인. API 는 로그인 안 했으면 401(JSON), 화면은 로그인 페이지로
- 관리 주소(헬스체크·지표)는 **다른 포트(8081)** 로 떼어 서버 안에서만 엽니다

### 5.2 CSRF

**기초부터.** 브라우저는 어느 사이트에서 시작된 요청이든 **목적지 사이트의 쿠키를 자동으로 붙입니다.** 그래서 이런 일이 생길 수 있습니다.

```text
① 나는 우리 앱에 로그인해 있다 (브라우저에 세션 쿠키)
② 다른 탭에서 수상한 사이트를 연다
③ 그 사이트의 숨은 폼이 우리 앱으로 POST /api/analysis/MSFT 를 보낸다
④ 브라우저가 우리 앱 쿠키를 자동으로 붙인다 → 서버는 "나" 의 요청으로 안다 → 돈이 나간다
```

막는 법은 "쿠키만으로는 안 되고, **우리 화면만 알 수 있는 값**을 하나 더 내라" 입니다.

- 쿠키 기반 인증은 "다른 사이트가 내 브라우저로 요청을 보내는" 공격(CSRF)에 약합니다
- `CookieCsrfTokenRepository` 가 `XSRF-TOKEN` 쿠키를 내려주고, 화면 JS 가 POST·PUT·DELETE 때 그 값을 `X-XSRF-TOKEN` 헤더로 다시 보냅니다(`portfolio.js` 의 `apiFetch`, `stock.js` 의 `runAi`)
- 다른 사이트는 우리 쿠키를 읽을 수 없으니 헤더를 못 만듭니다

### 5.3 브라우저 보안 헤더 — CSP

- `Content-Security-Policy` 로 "스크립트는 우리 서버와 jsdelivr 에서만" 을 강제합니다
- 그래서 **인라인 스크립트(`<script>...</script>`, `onclick=`)를 전부 금지**했습니다. 화면 코드는 모두 `.js` 파일입니다. XSS 가 뚫려도 주입된 스크립트가 실행되지 않습니다
- 바깥 글자(회사 이름 등)는 항상 `esc()` 로 HTML 이스케이프 후 넣습니다

### 5.4 그 밖의 방어

| 위협 | 방어 | 파일 |
|---|---|---|
| 공개 API 남용·크롤링 | IP 당 분당 120번(고정 창 방식), 넘으면 429 + `Retry-After` | `RateLimiter`, `PublicRateLimitFilter` |
| DB 덤프 유출 | 증권사 토큰을 AES-256-GCM 으로 암호화. 매번 새 IV, 위조 감지(GCM 태그), 형식에 버전(`enc:v1:`) | `TokenCipher` |
| 개인 정보 노출 | 공개 주소는 "평단가가 들어간 분석" 을 내보내지 않고, **있다는 사실도** 숨김 | `CompanyAnalysisService.findPublic` |
| 캐시 오염 | 공개 주소는 티커 모양(정규식)만 받아 캐시 키로 씀 | `StockBriefController` |
| 공격 지도 | 운영에서 Swagger 끄기, 500 응답에 내부 정보 없음 | `application.yml`, `GlobalExceptionHandler` |
| 위험 설정으로 배포 | 배포 스크립트가 `.env` 의 필수 보안값을 검사하고 빠지면 배포 중단 | `deploy/deploy.sh` |

**실무에서는.** 금융권은 보안 심의·취약점 점검(OWASP Top 10 기준)을 정기적으로 받습니다. 위 항목들이 점검표에 그대로 나옵니다.

**공부할 것.** OWASP Top 10, 세션 vs JWT, CSRF·XSS·SQL Injection 원리, CSP, 대칭키 암호(AES 모드: CBC vs GCM), 비밀번호 해시(bcrypt).

> **직접 해보기** — 로그인하지 않은 상태로 `curl -i localhost:8080/api/portfolio/unified` 를 보내 401 을 확인하고, `curl -i -X POST localhost:8080/api/analysis/MSFT` 를 CSRF 헤더 없이 보내 403 을 확인하세요.

## 6. 프론트엔드 — 빌드 없는 HTML/CSS/JS

> **이 장에서 배울 것** — 프레임워크 없이 HTML·CSS·JS 로 화면을 짜는 법과, 키보드·화면 낭독기로도 쓸 수 있게 만드는 법(접근성)을 봅니다.
>
> **먼저 알아둘 말** — [정적 파일](#01-웹과-네트워크) · [JSON](#01-웹과-네트워크) · [상태 코드](#01-웹과-네트워크)

**왜 프레임워크가 없나.** React·Vue 없이 순수 HTML/CSS/JS 로 만들었습니다. 빌드 단계가 없어 배포가 단순하고, 브라우저 기본기(DOM·이벤트·fetch)를 그대로 공부할 수 있습니다. 화면은 `src/main/resources/static/` 에 있고 jar 안에 들어가 스프링이 그대로 내보냅니다.

| 주제 | 이 프로젝트의 방법 | 파일 |
|---|---|---|
| 서버 호출 | `fetch` + JSON. GET 은 `getJson`, 쓰기 요청은 CSRF 헤더를 붙이는 `apiFetch` | `public/site.js`, `portfolio.js` |
| 공용 코드 | 두 화면이 쓰는 분석 렌더러를 한 파일로(`analysis-view.js`). 복사하면 반드시 어긋난다 | `public/analysis-view.js` |
| 이벤트 위임 | 버튼마다 핸들러를 달지 않고 `document` 에 하나만: `closest("[data-stock]")` | `public/stock.js` |
| 상태를 주소에 | `#stock=MSFT`, `?t=MSFT`. 새로고침·링크 공유에도 같은 화면. `history.pushState`/`popstate` | `public/stock.js` |
| 디자인 토큰 | 색·간격·글꼴을 CSS 변수 한 곳에. 화면은 변수만 쓴다 | `public/tokens.css` |
| 반응형 | 좁은 화면 대응은 CSS `@media` 로만. JS 로 DOM 을 다시 그리면 입력 중인 값이 날아간다 | `public/site.css` |
| 사이드바 메뉴 | 메뉴 항목을 `MENU` 배열 한 곳에. 새 기능은 한 줄 추가 | `public/nav.js` |
| 차트 | 캔버스 차트는 CSS 변수를 못 읽어서 `getComputedStyle` 로 읽어 넘긴다 | `portfolio.js` `cssVar()` |

### 6.1 접근성(a11y)

실무에서 점점 필수가 되는 영역입니다(공공·금융은 법적 요구가 있습니다).

- **axe-core** 로 자동 검사, 기준은 위반 0. 사람 눈으로는 대비 4.37:1 과 4.5:1 을 구분 못 합니다
- 클릭되는 건 **키보드로도**: 표의 티커는 `<button>` 이라 Tab·Enter 가 됩니다. `div` 에 클릭만 달면 키보드로 못 씁니다
- 창(드로어)을 열면 닫기 버튼에 초점, Esc 로 닫으면 연 곳으로 초점 복귀
- 닫힌 창은 `inert` 로 막습니다(`aria-hidden` 은 Tab 을 못 막음)
- 가로로 스크롤되는 영역은 `tabindex="0"` 으로 키보드 스크롤 가능하게

**공부할 것.** DOM API, 이벤트 버블링, `fetch` 와 Promise/async-await, CSS 변수·Grid·Flexbox, WCAG 2.x 기본(대비·키보드·스크린리더), 그다음에 React 를 배우면 "프레임워크가 무엇을 대신해 주는지" 가 보입니다.

## 7. 테스트

> **이 장에서 배울 것** — 바깥 API·DB 없이도 도는 테스트를 짜는 법과, 테스트가 줄면 PR 을 막는 장치(커버리지 최소선)를 봅니다.
>
> **먼저 알아둘 말** — [단위·통합 테스트](#09-테스트) · [목](#09-테스트) · [픽스처](#09-테스트) · [커버리지·품질 게이트](#09-테스트)

**이 프로젝트에서는.** JUnit 5 + AssertJ + Mockito, 테스트 228개.

- **바깥 API·DB 없이 도는 테스트만** 둡니다. 키가 없는 CI 에서도 그대로 돌아야 하기 때문입니다. 바깥 응답은 파일로 저장해 픽스처로 씁니다(`src/test/resources/dart/...`)
- **규칙을 테스트로 고정**합니다. 예: `StockNotesTest` 는 마이크로소프트 실제 숫자로 "성장이 빨라지고 있습니다" 문장을 고정하고, "매수/적정가" 같은 낱말이 나오지 않는 것까지 검사합니다
- **보안 규칙도 테스트로**: `SecurityConfigTest`(어느 주소가 공개인가), `CompanyAnalysisPublicTest`(평단가가 든 분석이 공개되지 않는가)

- 커버리지는 JaCoCo 로 재고 CI 요약에 표로 남깁니다. **계산 코드 패키지에만 최소선**을 걸어(`jacoco:check`) 테스트를 지우거나 테스트 없이 큰 코드를 넣으면 PR 이 막힙니다. 전체 숫자에는 낮은 선(38%)만 둡니다. 키가 필요한 바깥 API 클라이언트를 일부러 테스트하지 않아서, 전체를 올리라고 하면 의미 없는 테스트가 늘어납니다

**배운 것.** 커버리지 숫자를 보고 우선순위가 바뀌었습니다. 공시 계산은 잘 덮였는데 정작 핵심인 합산 계산이 4% 였습니다. 그리고 **눈으로 봐야만 잡히는 버그**가 있습니다(트리맵 비중 오류는 axe 위반 0 이었음).

**실무에서는.** 단위 테스트(빠름, 많이) → 통합 테스트(DB 포함, Testcontainers) → E2E(적게). "테스트 피라미드". 버그를 고칠 때 그 버그를 재현하는 테스트를 먼저 쓰면 다시 안 생깁니다.

**공부할 것.** JUnit 5, AssertJ, Mockito(mock vs stub vs spy), `@SpringBootTest` vs 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`), Testcontainers, 테스트 더블.

> **직접 해보기** — `@DataJpaTest` + Testcontainers(MySQL)로 `Holding13FRepository.findByAccessionNoAndCusipIn` 을 실제 DB 에서 검증하는 테스트를 만들어 보세요. 단, CI 에 도커가 필요해집니다(지금 원칙과의 트레이드오프를 생각해 보세요).

## 8. 빌드와 컨테이너 — Maven·Docker

> **이 장에서 배울 것** — 코드를 실행 파일(jar)로, 다시 어디서나 똑같이 뜨는 꾸러미(도커 이미지)로 만드는 과정을 봅니다.
>
> **먼저 알아둘 말** — [jar](#07-빌드배포인프라) · [Maven](#07-빌드배포인프라) · [이미지·컨테이너](#07-빌드배포인프라) · [볼륨](#07-빌드배포인프라) · [Compose·profile](#07-빌드배포인프라)

### 8.1 Maven

- `pom.xml` 에 의존성과 플러그인. `./mvnw`(Maven Wrapper)로 누구나 같은 Maven 버전을 씁니다
- `./mvnw package` → `target/portfolio-0.0.1-SNAPSHOT.jar` (실행 가능한 fat jar)
- 함정: 경로에 한글이 있으면 `spring-boot:run` 이 깨져서 jar 로 실행합니다. JaCoCo 도 같은 이유로 리눅스(CI)에서만 잽니다

### 8.2 Dockerfile — 멀티 스테이지

`Dockerfile` 을 열어 보세요.

1. **빌드 단계**: JDK 이미지에서 `pom.xml` 만 먼저 복사해 의존성을 받음 → **레이어 캐시**(소스만 바뀌면 의존성 단계를 건너뜀) → 소스 복사 → jar 생성
2. **실행 단계**: JRE 이미지에 jar 하나만. 이미지가 몇 배 작아지고 빌드 도구·소스가 운영 서버에 올라가지 않음
3. **비루트 사용자**로 실행(뚫려도 컨테이너 안 권한 최소화), 시간대 `Asia/Seoul`, 힙 `-Xmx512m`
4. 윈도우 CRLF 때문에 `mvnw` 가 "bad interpreter" 로 멈추던 것을 `sed` 로 고침. `.gitattributes` 로 `*.sh` 는 항상 LF

### 8.3 Docker Compose

- 개발용 `docker-compose.yml`: 앱 + MySQL. `depends_on: condition: service_healthy` 로 DB 가 접속을 받을 준비가 된 뒤 앱을 띄움
- 운영용 `deploy/compose.yml`: 앱 + MySQL + Caddy. 앱 포트를 바깥에 열지 않음, 로그 크기 제한, 메모리 제한, 비밀번호 기본값 없음(`${VAR:?메시지}`)
- **profile**: `profiles: [monitoring]` 이 붙은 서비스(prometheus·grafana)는 `COMPOSE_PROFILES=monitoring` 일 때만 뜹니다. 작은 서버에서 선택 기능을 끄는 스위치입니다. 함정: compose 는 **꺼진 profile 서비스의 `${VAR:?}` 도 해석**해서, 거기에 필수값 검사를 걸면 관측을 끈 서버의 앱 배포까지 막힙니다 → [결정기록 014](결정기록.md#014-관측은-서버-안에서만-보고-ssh-터널로-연다)
- **`.env` 함정**: `KEY=   # 설명` 처럼 값 없이 같은 줄에 설명을 남기면 compose 는 `# 설명` 을 값으로 읽습니다. 셸과 규칙이 다릅니다

**실무에서는.** 컨테이너 이미지가 배포 단위입니다. 규모가 크면 Kubernetes 가 Compose 의 역할(여러 컨테이너 띄우기·재시작·네트워크)을 클러스터 단위로 합니다.

**공부할 것.** 이미지 vs 컨테이너, 레이어 캐시, 볼륨, 네트워크, 헬스체크, 이미지 크기 줄이기, 그다음 Kubernetes 기본(Pod·Deployment·Service).

> **직접 해보기** — `docker compose up -d --build` 로 띄운 뒤 `docker compose ps`, `docker compose logs -f app`, `docker exec -it <mysql> mysql -u...` 로 안을 들여다보세요.

## 9. CI/CD — GitHub Actions

> **이 장에서 배울 것** — 코드를 합치기 전에 자동으로 검사하고(CI), 합치면 자동으로 서버에 올리는(CD) 흐름을 봅니다.
>
> **먼저 알아둘 말** — [CI·CD](#07-빌드배포인프라) · [워크플로·잡·러너](#07-빌드배포인프라) · [PR·스쿼시 병합](#07-빌드배포인프라) · [시크릿](#06-보안) · [최소 권한](#06-보안)

### 9.1 브랜치 전략과 PR

- `main` 에 직접 푸시 금지(브랜치 보호 규칙). **브랜치 → PR → CI 통과 → 스쿼시 병합**
- 스쿼시 병합이라 `main` 이력은 "PR 하나 = 커밋 하나" 로 깔끔합니다

### 9.2 CI — `.github/workflows/ci.yml`

| 단계 | 무엇 | 실무 포인트 |
|---|---|---|
| 트리거 | `push`(main), `pull_request` | |
| `concurrency` | 같은 브랜치에 연달아 푸시하면 앞 실행 취소 | 러너 시간 절약 |
| `permissions` | 기본 읽기만, 이미지 올리는 작업에만 `packages: write` | **최소 권한 원칙** |
| Java 설정 | `actions/setup-java` + Maven 캐시 | 빌드 시간 단축 |
| 테스트 | `./mvnw -B test` | 비밀값 없이 돈다 |
| 커버리지 최소선 | `./mvnw jacoco:check` (규칙은 `pom.xml`) | 숫자를 보여주기만 하면 아무도 안 본다. 떨어지면 막아야 지켜진다 |
| 산출물 | 테스트 리포트·커버리지 보관 7일 | 실패 원인 추적 |
| 이미지 | `main` 이면 `ghcr.io/...:sha-xxxxxxx` 와 `:main` 으로 올림. PR 은 만들어 보기만 | 커밋 해시 태그 = 되돌릴 버전을 정확히 집음 |
| 배포 설정 검사 | 더미 값으로 `docker compose config`(관측 켬·끔), `promtool check config`, 대시보드 JSON·uid 를 `jq` 로 | 설정 파일도 코드처럼 합치기 전에 검사. 합친 뒤 서버에서 처음 터지면 이미 운영 반영이 시작된 뒤 |

### 9.3 CD — `.github/workflows/deploy.yml`

- `workflow_run`: CI 가 `main` 에서 **성공했을 때만** 배포 워크플로가 이어서 돕니다
- `workflow_dispatch`: 손으로 특정 태그를 배포(= 되돌리기)
- `concurrency: cancel-in-progress: false`: 배포는 중간에 끊지 않고 차례로
- SSH 키·호스트 키는 **GitHub Secrets**. `known_hosts` 를 고정해 중간자 공격 방지(`StrictHostKeyChecking yes`)
- 이미지 저장소 로그인은 **그 작업 동안만 유효한 토큰**으로. 서버에 오래 사는 토큰을 두지 않음
- 서버가 아직 없으면(Secrets 없음) 건너뛰고 초록불

**실무에서는.** Jenkins·GitLab CI·GitHub Actions·ArgoCD(GitOps) 등 도구는 달라도 흐름은 같습니다: 테스트 → 빌드 → 아티팩트(이미지) 저장 → 배포 → 검증 → 실패 시 롤백. 금융권은 운영 반영 전에 **승인 단계**(변경 관리)가 붙습니다. GitHub 의 `environment: production` 에 승인자를 거는 것이 그 연습입니다.

**공부할 것.** YAML 문법, Actions 의 job/step/runner, Secrets, 아티팩트, 캐시, 배포 전략(Rolling·Blue-Green·Canary), GitOps.

## 10. 인프라와 배포 — 서버·Caddy·배포 스크립트

> **이 장에서 배울 것** — 빈 서버를 준비하고, 앞단 프록시로 HTTPS 를 붙이고, 새 버전을 올렸다가 문제가 있으면 되돌리는 과정을 봅니다.
>
> **먼저 알아둘 말** — [리버스 프록시](#01-웹과-네트워크) · [TLS 종료](#01-웹과-네트워크) · [방화벽](#07-빌드배포인프라) · [헬스체크](#07-빌드배포인프라) · [롤백](#07-빌드배포인프라) · [블루그린](#07-빌드배포인프라) · [SSH 터널](#07-빌드배포인프라)

파일은 전부 `deploy/` 에 있고 절차는 [운영 7장](운영.md#7-배포)입니다.

### 10.1 서버 준비 — `deploy/server-setup.sh`

| 하는 일 | 왜 |
|---|---|
| 도커 설치, 사용자를 docker 그룹에 | |
| **iptables 80·443 열기** | 오라클 우분투 이미지는 클라우드 콘솔에서 열어도 OS 방화벽이 또 막는다. "연결 시간 초과" 의 흔한 원인 |
| 스왑 2GB | 작은 서버에서 MySQL + JVM 이 겹치면 OOM 으로 컨테이너가 죽는다 |
| 시간대 한국 | 로그·배치 시각 |
| cron 에 백업 등록 | 매일 04:00 |

**도커 포트 공개는 호스트 방화벽을 우회합니다.** compose 에 `"3000:3000"` 처럼 쓰면 도커가 iptables 의 nat 표(PREROUTING)에 DOCKER 체인을 걸어 들어온 패킷의 목적지를 컨테이너 주소로 바꿉니다. 바뀐 패킷은 호스트로 들어오는 INPUT 이 아니라 FORWARD 경로를 타서, ufw 로 3000 을 막아 둬도 열려 있습니다. 그래서 서버 안에서만 볼 포트(8081·9090·3000)는 `"127.0.0.1:3000:3000"` 으로 **루프백에만** 묶습니다. 확인은 서버에서 `ss -ltn` 으로 `127.0.0.1:3000` 인지 봅니다.

**공부할 것.** 리눅스 기본 명령, systemd, 방화벽(iptables/ufw)과 클라우드 보안 그룹의 차이, iptables 의 표(filter·nat)와 체인(PREROUTING·INPUT·FORWARD), SSH 키 인증과 포트 포워딩(`ssh -L`), cron.

### 10.2 리버스 프록시와 HTTPS — Caddy

**기초부터.** 앱을 인터넷에 바로 내놓지 않고 앞에 문지기를 하나 둡니다. 이 문지기가 [리버스 프록시](#01-웹과-네트워크)입니다.

```text
바깥 ──HTTPS 443──▶ Caddy ──HTTP 8080──▶ 앱 (바깥에 포트를 열지 않음)
                    │
                    ├ 암호 풀기(TLS 종료) · 인증서 자동 갱신
                    ├ /actuator 같은 위험한 주소 차단
                    ├ 진짜 사용자 IP 를 X-Forwarded-For 로 적어 넘김
                    └ 앱이 재시작하는 동안 요청을 붙잡았다가 넘김
```

앱은 HTTPS·인증서를 몰라도 되고, 앱을 바꿔 끼우는 동안에도 바깥에서는 서버가 계속 살아 있는 것처럼 보입니다.

`deploy/Caddyfile` 은 몇 줄뿐입니다.
- 도메인만 적으면 **Let's Encrypt 인증서를 자동 발급·갱신**(ACME 프로토콜)
- `reverse_proxy app:8080` — 바깥 요청을 앱으로. 앱은 바깥에 포트를 열지 않음
- `X-Forwarded-For`·`X-Forwarded-Proto` 를 붙임 → 스프링(`forward-headers-strategy: framework`)이 진짜 사용자 IP(호출 한도)와 https 여부(쿠키 `Secure`·HSTS)를 앎
- `lb_try_duration 30s` — 앱이 재시작하는 동안 502 를 주지 않고 요청을 잡아뒀다 넘김. 리허설에서 배포마다 13초 나던 502 가 0 이 됨
- `/actuator` 차단

**실무에서는.** Nginx 가 가장 흔하고, 클라우드에서는 L7 로드밸런서(AWS ALB 등)가 이 역할을 합니다. TLS 종료, 경로 라우팅, 압축, 요청 제한을 앞단에서 처리합니다.

### 10.3 배포와 롤백 — `deploy/deploy.sh`

```
1. 띄우기 전 검사: .env 에 로그인 비밀번호·암호화 키·Secure 쿠키·Swagger 끄기가 있나 → 없으면 중단
2. 새 이미지 pull
3. stock-portfolio:current 를 새 태그로 옮기고 앱 컨테이너만 다시 만들기 (DB·Caddy 는 그대로)
4. 헬스체크(/actuator/health/readiness)가 UP 될 때까지 대기
   - 벽시계 기준 제한 시간, 컨테이너가 계속 죽으면 세 번 만에 실패 판정
5. 성공 → 지금/바로 앞 태그를 파일에 기록, 오래된 이미지 정리(둘은 남김)
   실패 → 앱 로그 출력, 바로 앞 태그로 자동 되돌림, 종료 코드 1 (워크플로 빨간불)
```

리허설 결과(내 PC 에서 실제 이미지로, 일부러 깨진 이미지까지): [운영 7장](운영.md#7-배포).

**배운 것.**
- 헬스체크 대기를 "잠든 시간" 으로 세면 실제로는 1.5배 넘게 기다린다(curl 이 기다린 시간이 빠짐) → `SECONDS` 로 벽시계 측정
- **DB 는 되돌아가지 않는다.** 이미지는 한 줄로 되돌리지만 마이그레이션은 아니다 → 스키마는 더하기만
- 지켜야 할 설정은 사람이 아니라 스크립트가 검사한다

**실무에서는.** 지금 방식은 "한 대를 바꿔 끼우기 + 앞단이 잠깐 버텨 주기" 입니다. 진짜 무중단은 Blue-Green(새 버전을 옆에 띄우고 트래픽 전환)이나 Rolling(여러 대를 하나씩)으로 합니다. 메모리가 두 배 들어서 무료 서버에서는 보류했습니다.

**공부할 것.** 셸 스크립트(`set -euo pipefail`, 종료 코드), 헬스체크 liveness vs readiness, 배포 전략 비교, 롤백 시나리오 설계.

> **직접 해보기** — [운영 7장](운영.md#7-배포)의 리허설을 그대로 따라 해 보세요. 로컬 레지스트리(`registry:2`)에 일부러 뜨자마자 죽는 이미지를 올리고 `./deploy.sh` 가 되돌리는 걸 눈으로 확인하는 것이 핵심입니다.

## 11. 운영 — 헬스체크·지표·로그·백업

> **이 장에서 배울 것** — 앱이 지금 괜찮은지(헬스체크·지표), 무슨 일이 있었는지(로그), 망가지면 되살릴 수 있는지(백업)를 봅니다.
>
> **먼저 알아둘 말** — [관측](#08-관측과-운영) · [지표·태그](#08-관측과-운영) · [Prometheus·pull](#08-관측과-운영) · [MDC](#08-관측과-운영) · [구조화 로그](#08-관측과-운영) · [알림 피로](#08-관측과-운영) · [런북](#08-관측과-운영)

### 11.1 헬스체크

- Spring Boot Actuator: `/actuator/health/liveness`(프로세스가 살아 있나), `/actuator/health/readiness`(DB 까지 연결돼 요청을 받을 준비가 됐나)
- **관리 포트 8081** 로 분리하고 서버 안(`127.0.0.1`)에서만 엽니다
- 배포 스크립트가 readiness 를 보고 성공/롤백을 정합니다

**실무에서는.** Kubernetes 의 livenessProbe/readinessProbe, 로드밸런서 헬스체크가 같은 주소를 봅니다. liveness 에 DB 를 넣으면 DB 장애 때 앱이 계속 재시작되는 사고가 납니다(그래서 둘을 나눔).

### 11.2 지표

- 앱: Micrometer + `/actuator/prometheus` 가 지표를 글자로 내놓습니다(JVM 메모리·GC·HTTP 응답 시간·DB 풀 등)
- **바깥 API 호출 지표**(`http_client_requests_seconds`)는 스프링이 관측을 연결해 둔 `RestClient.Builder` 를 **주입받아** 만든 클라이언트에서만 나옵니다. `RestClient.builder()` 로 직접 만들면 이 연결을 건너뜁니다(이 프로젝트가 처음에 그랬습니다). 또 지표 태그에 주소가 그대로 실리므로, 키를 쿼리에 이어 붙이는 코드가 생기면 키가 Prometheus 에 남습니다. 그래서 `SafeClientRequestObservationConvention` 이 쿼리·호스트를 버리고 키처럼 보이는 조각을 `none` 으로 바꿉니다. "지표에 무엇이 실리나" 도 보안 검토 대상입니다
- **Prometheus 는 당겨 갑니다(pull).** 앱이 어딘가로 보내는 게 아니라 Prometheus 가 `deploy/monitoring/prometheus.yml` 에 적힌 `app:8081/actuator/prometheus` 를 15초마다 긁어 시계열 DB 에 쌓습니다. 긁기에 실패하면 `up` 지표가 0 이 되어 "앱이 죽었다" 자체가 지표가 됩니다(리허설: 멈춘 지 약 12초 만에 0). 앱은 Prometheus 의 존재를 몰라도 됩니다
- **Grafana 는 프로비저닝으로 띄웁니다.** 데이터소스(`provisioning/datasources/prometheus.yml`, uid `prometheus`)와 대시보드(`dashboards/stock-portfolio.json`)를 파일로 두고 기동 때 읽게 했습니다. 화면에서 손으로 만들지 않으니 서버를 새로 깔아도 같은 화면이 뜨고, 변경이 PR 로 남습니다. 화면 저장은 막아 두었습니다(고친 뒤 JSON 을 내보내 파일을 바꿈)
- **SSH 터널로 봅니다.** 두 포트는 서버의 127.0.0.1 에만 열려 있어서 `ssh -L 3000:127.0.0.1:3000 ubuntu@서버` 로 내 PC 의 3000 을 서버의 127.0.0.1:3000 에 잇고 `localhost:3000` 을 엽니다. 인터넷에 로그인 화면을 하나 더 만들지 않는 방법입니다 → [운영 7장 지표 보기](운영.md#지표-보기)
- **앱이 직접 만든 지표**도 있습니다: `claude_requests`·`claude_tokens`(Claude 호출), `http_client_retries`(재시도), `resilience4j_circuitbreaker_state`(서킷 브레이커), `portfolio_snapshot_runs_total{outcome}`·`portfolio_reconciliation_mismatches`(장 마감 배치). 배치나 비즈니스 결과도 지표로 내보내면 같은 알림 경로를 탑니다
- **알림은 규칙 파일 + 테스트**입니다(지금 11개). `deploy/monitoring/alerts.yml` 에 "언제 울릴지" 를 PromQL 로 쓰고, `alerts.test.yml` 에 가짜 시계열을 넣어 "이 시각에 울려야 한다/안 울려야 한다" 를 적습니다. CI 가 `promtool test rules` 로 돌립니다. 알림도 코드처럼 리뷰·테스트합니다
- 알림 설계 원칙: **사람이 지금 무언가를 해야 하는 것만** 알립니다. `for: 2m` 처럼 지속 시간을 둬 한 번 튄 값으로 울리지 않게 하고, 재시작 직후 한 번 나오는 정상 실패(토스 401)는 뺍니다. 잦은 알림은 결국 무시됩니다(알림 피로)
- 비밀값을 컨테이너에 넘기는 법: Alertmanager 봇 토큰은 환경변수 → 컨테이너 안 파일(`bot_token_file`)로만 갑니다. 설정 파일·명령줄(`ps` 에 보임)·로그에 남지 않습니다

**실무에서는.** 증권사 관제도 같은 구조입니다. 수집기·시계열 저장소·대시보드·알림이 나뉘어 있고, 관제 화면은 내부망에서만 엽니다. 클라우드면 CloudWatch·Datadog 이 이 역할을 합니다.

> **직접 해보기** — 터널을 열고 Prometheus 화면에서 `up{job="stock-portfolio"}` 를 쳐 본 뒤, 앱 컨테이너를 멈췄다 켜면서 값이 0 → 1 로 바뀌는 데 걸리는 시간을 재 보세요.

**공부할 것.** RED 지표(Rate·Errors·Duration), USE 지표, Prometheus 쿼리(PromQL) 기본, 알림 임계값 설계.

### 11.3 로그

**무엇.** 로그는 "그때 무슨 일이 있었나" 를 남기는 기록입니다. 운영에서 중요한 건 **찾을 수 있느냐**입니다. 동시에 들어온 요청 수십 개의 줄이 뒤섞이면, 오류 한 줄을 보고도 그게 어느 요청이었는지 모릅니다.

**이 프로젝트에서는.**

```text
브라우저 ──▶ Caddy ── X-Request-Id: 0f8fad5b-… (요청마다 UUID) ──▶ 앱
                                                                   │
              RequestIdFilter: 번호를 MDC(스레드별 로그 문맥)에 넣음   │
              ├─ 이 요청이 남기는 모든 줄에 requestId 가 자동으로 붙음  │
              ├─ 응답 헤더 X-Request-Id 로 돌려줌 (화면 오류 → 번호로 검색)
              └─ 끝나면 access 한 줄: GET /api/... 200 87ms
                                                                   │
              AI 분석은 백그라운드 스레드로 넘어감 ── LogContext.carry ─┘ 번호를 복사해 감
              13F 배치는 요청이 없음 ── LogContext.job("batch-13f") ── 새 번호
```

- **두 가지 모양**(`logback-spring.xml`): 내 PC 는 사람이 읽는 줄글, 서버는 `LOG_FORMAT=json` 으로 **한 줄에 JSON 하나**(logstash 인코더). JSON 이면 `jq 'select(.requestId=="…")'` 로 한 요청의 줄만, `select(.level=="ERROR")` 로 오류만 뽑습니다. 보는 명령은 [운영 - 로그 보기](운영.md#로그-보기)
- **MDC 는 스레드마다 따로**라서 일을 다른 스레드로 넘기면 번호가 사라집니다. 넘길 때 복사해 가고, 끝나면 치웁니다. 톰캣은 스레드를 재사용하므로 안 치우면 다음 요청이 앞 번호를 물려받습니다
- 바깥에서 온 번호는 모양(영숫자·하이픈 8~64자)이 맞을 때만 받습니다. 줄바꿈을 넣어 가짜 로그 줄을 끼우는 공격(로그 인젝션)을 막습니다
- 컨테이너 로그는 `json-file` 드라이버에 크기 제한(20MB × 5개). 로그가 디스크를 채워 서버가 멈추는 사고 방지
- 겪은 함정: appender 하나만 연결했더니 logback 이 "안 쓰는 appender" 경고와 함께 내부 상태 수십 줄을 줄글로 쏟아내 JSON 로그 앞을 더럽혔습니다. 둘 다 연결하고 필터(`LogFormatFilter`)로 하나만 통과시켜 풀었습니다. SQL 출력(`show-sql`)·시작 배너도 로거를 안 거치는 줄글이라 서버에서 끕니다

**실무에서는.** 로그를 중앙으로 모읍니다(ELK·Loki·CloudWatch). 서비스가 여럿이면 같은 번호를 다음 서비스로 헤더로 넘겨 전체 흐름을 잇습니다(분산 추적. OpenTelemetry·Micrometer Tracing 의 trace ID 가 이 번호의 발전형). 증권사에서는 주문·체결 한 건을 끝까지 따라가는 **거래 추적**이 감사 대응의 기본입니다. 개인정보·토큰은 마스킹합니다.

**공부할 것.** MDC, 구조화 로그, 로그 레벨 정책(무엇을 INFO/WARN/ERROR 로), 분산 추적(trace·span), 로그 인젝션.

> **직접 해보기** — 앱을 `LOG_FORMAT=json` 으로 띄우고 `curl -H "X-Request-Id: test-12345678" localhost:8080/api/public/analysis/MSFT -i` 를 보낸 뒤, 응답 헤더와 로그에서 같은 번호를 찾아 보세요.

## 14. 면접에서 받을 만한 질문

> **이 장에서 배울 것** — 면접에서 이 프로젝트를 설명할 때 나올 질문과, 답할 때 가리킬 곳입니다.

이 프로젝트를 이야기할 때 나올 법한 질문과, 답할 때 가리킬 곳입니다.

1. **배포 중 장애가 나면 어떻게 되나요?** → 헬스체크 실패 시 자동 롤백(`deploy.sh`), 리허설 결과. DB 마이그레이션은 되돌리지 않으므로 expand/contract
2. **무중단 배포인가요?** → 완전한 무중단은 아님. 앞단이 재시작 동안 요청을 붙잡아 실패 응답 0. Blue-Green 과의 트레이드오프(메모리)
3. **비밀값은 어떻게 관리하나요?** → `.env` 는 서버에만, 배포 키는 GitHub Secrets, 토큰은 DB 에 AES-GCM 암호화, 작업 동안만 유효한 레지스트리 토큰
4. **CSRF 를 어떻게 막았나요? 왜 필요하죠?** → 쿠키 세션 + `XSRF-TOKEN` 쿠키/헤더 이중 제출, `SameSite=Strict`
5. **인라인 스크립트를 왜 금지했나요?** → CSP 로 XSS 영향 차단
6. **외부 API 가 느리거나 죽으면?** → 타임아웃(연결 5초·응답 30초), GET 만 5xx·네트워크 오류에 재시도, 호스트별 서킷 브레이커(`ResilientHttpInterceptor`), fail-soft(부분 응답), 캐시. 열리면 `CircuitBreakerOpen` 알림
7. **테스트가 외부 API 를 안 부르는 이유는?** → CI 에 비밀값이 없어도 돌아야 함, 결정적(deterministic) 테스트
8. **개인정보가 공개 화면에 새지 않게 한 방법은?** → 저장 시 `includes_position` 표시, 공개 주소는 필터 + "있다는 사실도" 숨김, 테스트로 고정
9. **JPA 에서 성능 문제를 겪은 적은?** → 종목 하나 조회에 기관별 전체 보유를 읽던 것을 `IN` 조건 쿼리로 바꾼 사례
9-1. **FK 를 왜 안 걸었나요? JSON 열은 왜 썼나요?** → [3.4](#34-fk-제약을-걸지-않은-이유)·[3.5](#35-json-을-통째로-넣은-열--analysis_json-financials_json). 쓰는 곳이 배치 하나, 티커는 나중에 채움, 통째로 읽고 쓰는 문서만 JSON 이고 거르는 값은 열로 꺼냄
10. **AI(LLM)를 쓸 때 숫자 신뢰성은?** → 숫자는 앱이 계산해 사실로 넣고 LLM 은 조사만([결정기록 003](결정기록.md#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다)), 공개 문장은 규칙 기반(`StockNotes`)
11. **배치가 두 번 돌면? 실패하면?** → 날짜가 키라 한 트랜잭션에서 upsert + 지우고 새로(멱등). 과거는 다시 못 만드니 그날 18·20시 재시도, 증권사 하나라도 실패하면 저장 안 함 ([15.4](#154-장-마감-스냅샷과-대사--멱등-배치))
12. **숫자가 맞는지 어떻게 아나요?** → 매일 대사: 앱이 더한 합계 vs 증권사가 같은 응답에 준 계좌 합계, 0.1% 넘으면 알림
13. **장애가 나면 로그를 어떻게 찾나요?** → 요청마다 번호(Caddy UUID → MDC → 응답 헤더), 백그라운드 스레드에도 복사, 서버는 JSON 로그라 jq 로 번호·레벨 필터 ([15.1](#151-요청-id-와-json-로그--한-요청을-끝까지-따라가기))
14. **커버리지 기준은 몇 %인가요?** → 전체는 낮게(38%), 계산 코드 패키지만 따로 높게. 바깥 API 클라이언트를 억지로 테스트하지 않으려고 ([15.3](#153-커버리지-최소선--숫자를-보여주기만-하면-아무도-안-본다))
15. **`@Transactional` 이 안 먹는 경우를 아나요?** → 스프링은 프록시로 트랜잭션을 거는데, 같은 클래스 안에서 `this.메서드()` 로 부르면 프록시를 안 거친다. 그래서 저장만 맡는 빈(`CompanyAnalysisStore`)을 따로 뒀다 ([2.7](#27-프록시--스프링이-몰래-끼워-넣는-대리-객체))
16. **배치가 바깥 장애 때 멀쩡한 데이터를 망치지 않게 한 방법은?** → 덮어쓰기 전에 입력(발행주식수)부터 확인하고, 못 받으면 그 종목은 건너뜀. 토스가 통째로 막히면 첫 종목에서 멈춤(`FilingPrefetchService`, [2.4](#24-스케줄-배치))

| 문제 | 동시에 들어온 요청의 로그 줄이 섞여, 오류 한 줄이 어느 요청 것인지 모름. AI 분석은 몇 분 뒤 다른 스레드에서 실패를 남겨 시작 요청과 이을 수 없음. 줄글 로그는 grep 으로만 찾음 |
| 해결 | Caddy 가 요청마다 UUID → `RequestIdFilter` 가 MDC 에 넣고 응답 헤더로 돌려줌 → `LogContext.carry` 로 백그라운드 스레드에 복사, 배치는 `LogContext.job("batch-…")` 로 새 번호. 서버는 `LOG_FORMAT=json` 으로 한 줄에 JSON 하나 |
| 코드 | `config/RequestIdFilter.java`, `common/LogContext.java`, `config/LogFormatFilter.java`, `logback-spring.xml`, `deploy/Caddyfile` |
| 실무 | 분산 추적의 가장 작은 형태(trace ID). 증권사의 거래 추적·감사 로그. Loki·ELK 같은 수집기는 JSON 필드로 거른다 |
| 함정 | ① appender 를 하나만 연결했더니 logback 이 경고와 함께 내부 상태를 줄글로 쏟아냄 → 둘 다 연결하고 필터로 하나만 통과 ② `show-sql`·시작 배너는 로거를 안 거치는 줄글 → 서버에서 끔 ③ 바깥이 보낸 번호에 줄바꿈을 넣으면 가짜 로그 줄을 만들 수 있음(로그 인젝션) → 모양 검사 |

### 15.2 캐시 예열 — 첫 방문자도 캐시에서

| | |
|---|---|
| 문제 | 13F 조회 캐시는 배치가 데이터를 바꾸면 통째로 비움. 그 뒤 첫 방문자가 "같이 산 종목" 계산(1~4초)을 혼자 기다림. 배포로 앱이 다시 떠도 마찬가지 |
| 해결 | `InstitutionCacheWarmer` 가 앱 기동(`ApplicationReadyEvent`)과 배치 끝(`ThirteenFDataChangedEvent`)에 첫 화면·기관 상세 조회 22건을 뒤에서 계산. 비우기(`@Order(0)`)가 채우기(`@Order(100)`)보다 먼저 돌게 순서를 고정하고 테스트로 확인 |
| 결과 | "같이 산 종목" 첫 요청 1.35초 → 0.02초 (내 PC) |
| 실무 | 캐시 워밍. 배포 직후 트래픽을 조금씩 넘기는 것(슬로 스타트)과 같은 목적 |
| 함정 | 예열 뒤에도 기동 후 맨 첫 요청이 0.6초. 서블릿 초기화 탓이라 짐작해 설정을 넣었는데 로그를 보니 초기화는 2ms 였음 → 되돌림. 캐시는 맞았고(SQL 없음) JSON 직렬화 등 첫 실행 비용. **짐작으로 고치지 말고 재고 고친다** |

### 15.3 커버리지 최소선 — 숫자를 보여주기만 하면 아무도 안 본다

| | |
|---|---|
| 문제 | 커버리지를 CI 화면에 표로만 띄움. 떨어져도 아무 일이 없어서 지켜지지 않음 |
| 해결 | CI 가 테스트 뒤 `./mvnw jacoco:check`. 전체 38% + 계산 코드 패키지만 따로(`external.filing` 75, `service.analysis`·`service.stock`·`external.edgar` 60, `external.dart` 45). 지금 수치보다 몇 %p 아래, 내리지 않고 올리기만 |
| 코드 | `pom.xml` 의 jacoco `<rules>`, `.github/workflows/ci.yml` 의 "커버리지 최소선" |
| 실무 | 품질 게이트(SonarQube 등). 숫자보다 "어디에" 거느냐가 중요 — 키가 필요한 바깥 API 클라이언트까지 올리라고 하면 의미 없는 테스트만 는다 |
| 함정 | ① 빌드 단계에 묶으면 내 PC(한글 경로라 JaCoCo 에이전트가 깨짐)에서 빌드가 멈춤 → CI 에서만 따로 부름 ② 실행 데이터가 없으면 `jacoco:check` 는 "건너뜀" 만 찍고 **통과**. `-q` 로 돌리면 그것도 안 보임 → "All coverage checks have been met" 문구가 없으면 실패하게 |

### 15.4 장 마감 스냅샷과 대사 — 멱등 배치

| | |
|---|---|
| 문제 | 화면은 지금 잔고만 보여 이력이 없음. 화면 합계는 앱이 더한 값인데 증권사 숫자와 맞는지 확인한 적이 없음 |
| 해결 | 평일 16:10 `PortfolioSnapshotService`, 실패 시 18:10·20:10 재시도(그날 성공했으면 건너뜀). 증권사 클라이언트가 `statement()` 로 보유와 **같은 응답의 계좌 합계**를 함께 돌려주고, `Reconciler` 가 0.1%(최소 1원·1센트)로 비교. `PortfolioSnapshotStore` 가 한 트랜잭션에서 합계 upsert + 그날 줄 지우고 새로 |
| 코드 | `service/snapshot/`, `brokerage/BrokerageStatement.java`, `V10__portfolio_snapshot.sql`, `alerts.yml` 의 `ReconciliationMismatch`·`SnapshotFailing` |
| 실무 | 증권사의 일일 배치·원장 대사. 자체 원장과 예탁원·거래소·은행 숫자를 매일 맞추고 불일치를 다음 날 아침까지 해소 |
| 설계 판단 | **멱등**(날짜가 키, 몇 번 돌려도 한 벌) · **재처리 한계 인정**(과거는 다시 못 만듦 → 그날 안에 재시도) · **빈 날 > 틀린 날**(증권사 하나라도 실패하면 저장 안 함) · **알림 경로 하나**(앱은 지표만, 알림은 Alertmanager) · **로그에 금액 없음** |
| 함정 | 생성자를 둘(운영용·테스트용 시계) 두었더니 스프링이 어느 쪽을 쓸지 몰라 기동이 멈춤. 단위 테스트는 전부 통과했고 jar 를 띄워서야 잡힘 → `@Autowired` 로 밝힘. 지우고 바로 같은 키를 넣을 때는 파생 삭제 대신 JPQL `delete` 한 번(`@Modifying`)으로 즉시 반영 |

ERD 는 [3.1 ④](#31-erd--테이블-사이의-관계), 운영 절차는 [운영 - 장 마감 스냅샷과 대사](운영.md#장-마감-스냅샷과-대사), 결정 배경은 [결정기록 020](결정기록.md#020-장-마감-스냅샷은-하루-한-번-대사는-증권사-합계와).

### 이날 얻은 원칙 세 가지

1. **띄워 봐야 보이는 게 있다.** 로그 모양, 빈 생성 실패, 첫 요청 지연 — 셋 다 단위 테스트로는 안 보였다
2. **"통과" 가 진짜 검사했다는 뜻인지 확인한다.** 건너뛰고도 성공을 내는 도구가 있다(`jacoco:check`)
3. **틀린 숫자보다 빈칸이 낫다.** 부분 실패한 스냅샷을 남기지 않는 것, 모르는 로그 형식을 줄글로 떨어뜨리는 것 모두 같은 생각이다
