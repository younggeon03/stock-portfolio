**어떤 순서로 만들었고, 어디서 방향이 바뀌었는지**만 적습니다. 덧붙이기만 하고 고치지 않습니다.

## 전환점 1 — 문서 요약을 믿었다가 틀렸다 (1단계)

보유종목 주소를 찾으려고 API 문서를 요약해서 읽었더니 `/api/v1/asset` 이라고 나왔습니다. 없는 주소였습니다. `openapi.json` 원본을 받아 직접 파싱하니 진짜 경로는 `/api/v1/holdings` 였습니다.

**그 뒤로는 항상 스펙 파일을 직접 받아 확인했습니다.** 이 습관이 나중에 "토스 로그인이 가능한가"를 판단할 때 결정적이었습니다. 요약을 읽었으면 "OAuth 를 지원한다"로 끝났을 겁니다.

## 전환점 2 — 만들어놓고 지웠다 (4단계)

목표 비중을 넣으면 "몇 주 사고팔아라"를 계산해주는 기능을 만들었습니다. 그리고 지웠습니다.

목표 비중은 결국 내가 정한 숫자입니다. 그게 맞는지는 아무도 모릅니다. 기계적인 나눗셈에 "제안"이라는 이름을 붙인 것뿐이었습니다.

| | 예전 | 지금 |
|---|---|---|
| 근거 | 내가 입력한 목표 비중 | 기업분석에서 나온 관점과 리스크 |
| 출력 | "SOXL 3주 매도" | "자산의 81%가 3배 레버리지에 몰려 있다" |

파일 여섯 개를 지웠습니다. 화면도 이때 성격이 바뀌었습니다.

## 전환점 3 — 이 앱의 존재 이유를 발견했다 (5단계)

나무증권을 붙이고 합쳐보니 이랬습니다.

| 보는 방식 | SOXL 비중 |
|---|---|
| 토스 앱에서만 | 2.98% |
| 나무 앱에서만 | 81.51% |
| **합치면** | **81.47%** |

토스 화면만 보고 "3%네, 더 사도 되겠다"고 판단할 뻔했습니다. 이때부터 "비중을 드러내는 것"이 이 앱의 목적이 됐습니다. 10단계에서 비중 막대를 화면 맨 위 전체 폭으로 올린 것도 여기서 나왔습니다.

나무 API 가 준 함정 셋(charset 403, `rsp_cd=00166`, `acct_type=01`)은 [문제해결](운영.md#장애-대응)에 있습니다.

## 전환점 4 — 산수를 모델에게 맡기지 않기로 했다 (6단계)

증권사 어느 쪽도 재무 데이터를 주지 않아서 외부 LLM 을 쓰기로 했습니다. 문제는 **어디까지 맡기느냐**였습니다.

수량과 평단가를 주고 "수익률을 계산해서 분석해줘"라고 하면 편합니다. 그런데 LLM 은 산수를 그럴듯하게 틀립니다. 분석 글 한복판에 "현재 12.4% 손실 중"이라고 적혀 있으면 맞는지 확인하려고 사람이 직접 계산해야 합니다. 그럴 거면 맡길 이유가 없습니다.

이 프로젝트에서 가장 오래 고민한 부분이라 [결정기록 003](결정기록.md#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다)에 따로 정리했습니다.

### 돈 안 쓰고 화면을 검증하는 법을 여기서 배웠다

크레딧이 없어서 분석을 못 돌리는데 화면은 만들어야 했습니다. 손으로 만든 분석 데이터를 MySQL 에 직접 넣었습니다. 7개 섹션, 지표 표, 출처 각주, 리스크 카드가 다 제대로 그려지는 걸 0원으로 확인했습니다.

같은 방식이 9단계에서 `POST /api/import/screenshot/sample` 로 이어졌습니다.

## 전환점 5 — 남의 계좌는 볼 수 없다는 걸 확인했다 (8단계)

배포했을 때 다른 사람도 자기 계좌를 보게 하고 싶었습니다. 스펙을 세 가지 방법으로 확인한 결과 **불가능합니다.**

포기가 아니라 방향 전환이었습니다. 시세 API 는 계좌 헤더가 필요 없다는 사실(5단계에서 나온 부산물)을 이용하면, 남이 종목만 알려줘도 가격은 우리가 채울 수 있습니다. 그게 9단계 스크린샷 등록이 됐습니다.

근거는 [결정기록 004](결정기록.md#004-증권사-로그인을-포기하고-스크린샷으로-우회한다)에 전부 적어 뒀습니다.

## 전환점 6 — 조용히 틀린 숫자가 제일 위험하다 (9단계)

환율 조회가 실패하면 1 을 돌려주게 해놨더니 $136 짜리가 **136원**으로 표시됐습니다. 1,380배 틀린 값이 비중 계산까지 오염시켰는데 **에러는 안 났습니다.**

"모른다"를 그럴듯한 기본값으로 때우면 안 된다는 걸 여기서 배웠습니다. 같은 원칙이 10단계 이동평균선에도 적용됐습니다. 기간이 안 찬 앞부분을 0 으로 채우면 선이 바닥에서 솟구칩니다. 그래프가 거짓말을 하는 겁니다.

[결정기록 005](결정기록.md#005-환율을-못-구하면-예외를-던진다)에 있습니다.

## 전환점 7 — 필요한 데이터는 이미 있었다 (10단계)

캔들차트를 그리려고 일봉 API 를 다시 보려던 참에, `TossCandle` 에 시가·고가·저가·거래량이 **이미 다 들어 있는 걸** 발견했습니다. 서버가 종가만 남기고 버리고 있었습니다.

새로 받아올 게 없었습니다. 버리던 걸 안 버리면 됐습니다.

화면도 이때 다시 만들었습니다. 스크롤이 너무 길어서 고치려고 보니 진짜 문제는 색이었습니다. 파란 버튼, 초록 배지, 빨간 수익률이 한 화면에 섞여서 색이 의미를 잃고 있었습니다. [결정기록 008](결정기록.md#008-색은-빨강과-파랑뿐이고-등락만-뜻한다)에 있습니다.

## 전환점 8 — 안 띄워보고 만든 화면은 반쯤 고장나 있었다 (12단계)

10단계 화면을 **한 번도 브라우저에 안 띄워보고** 문서까지 다 썼습니다. 토스 IP 가 막혀 시세가 없었기 때문입니다. IP 를 등록하고 크롬으로 직접 클릭해보니 버그가 둘 나왔습니다.

**드로어를 열면 표를 못 눌렀습니다.** 배경을 어둡게 하는 막이 화면 전체를 덮고 있어서, 다른 종목을 누르면 종목이 바뀌는 게 아니라 드로어가 닫혔습니다. `document.elementFromPoint()` 로 표 한가운데를 찍으니 `drawerBackdrop` 이 나왔습니다. 종목을 옮겨가며 비교하는 게 드로어를 만든 이유인데 그게 막혀 있었습니다.

**고치고 나니 드로어가 하필 숫자를 가렸습니다.** 오른쪽 620px 이 평가금액·수익률·비중 자리였습니다. 보이는 건 수량과 현재가뿐이었습니다. 본문을 왼쪽으로 밀고, 갈아탈 때는 네 열을 숨기게 했습니다.

**교훈은 하나입니다.** 화면은 띄워보기 전까지 만든 게 아닙니다. 지금은 `puppeteer-core` 로 클릭까지 자동화해서 확인합니다.

### 문서가 코드의 오류를 잡았다

선택된 줄 배경이 연한 파랑(`#eef3ff`)이었습니다. [결정기록 008](결정기록.md#008-색은-빨강과-파랑뿐이고-등락만-뜻한다)에 "파랑은 내렸다는 뜻"이라고 적어놓고 정작 화면에서 어기고 있었습니다.

**규칙을 글로 적어두지 않았으면 그냥 넘어갔을 겁니다.** 결정기록을 따로 두는 이유를 여기서 처음 실감했습니다.

## 전환점 9 — 문서를 수명으로 나눴다 (11·13단계)

문서가 두 개였는데 둘 다 창고가 됐습니다. `todo.md` 가 563줄이었고 그 안에 남은 할 일, 회고, 주소 목록, 조사 결과가 섞여 있었습니다. 루트에 `README.md` 가 없어서 깃허브에서 리포를 열면 파일 목록만 보였습니다.

**주제가 아니라 "언제 바뀌나"로 나눴습니다.**

| 무엇 | 언제 바뀌나 | 어디로 |
|---|---|---|
| 남은 일 | 하면 사라짐 | `TODO.md` |
| 왜 이렇게 만들었나 | 거의 안 바뀜 | `docs/아키텍처.md` |
| 되돌리기 어려운 판단 | 안 바뀜 | `docs/결정기록.md` |
| 끝난 일의 회고 | 안 바뀜 | 이 문서 |
| 증상과 해결 | 새 함정 만나면 추가 | `docs/문제해결.md` |

13단계에서 하나를 더 옮겼습니다. **손으로 쓴 API 문서는 반드시 어긋납니다.** 컨트롤러를 그대로 옮겨 적은 문서라 코드를 고칠 때마다 같이 고쳐야 하는데, 그게 될 리가 없습니다. springdoc 을 붙여 주소 목록은 코드에서 자동 생성하고, `docs/API.md` 에는 **코드만 봐서는 알 수 없는 것**만 남겼습니다. 비용, 헤더의 의미, 없는 기능, 숫자를 믿어도 되는 이유입니다.

이때 `CLAUDE.md` 도 만들었습니다. 문서는 전부 사람용이었는데 정작 코드를 치는 건 대부분 클로드였고, 클로드는 세션마다 기억이 없어서 빌드 명령과 제약을 매번 다시 알아내고 있었습니다.

## 전환점 10 — 후킹이 약하다는 걸 인정했다 (15단계)

"두 증권사를 합치면 진짜 비중이 보인다" 가 지금까지의 후킹이었습니다. 약했습니다.

- 계좌가 둘 이상이어야 의미가 있는데 대부분은 한 곳만 씁니다
- 한 번 보면 끝입니다. 84.9% 를 발견한 다음 날 다시 열 이유가 없습니다
- 진단이지 행동이 아닙니다. "81% 네" 다음에 뭘 해야 하는지 안 알려줍니다

그래서 분석 맨 위에 **판정**을 올렸습니다. 지금까지 "매수·매도를 단정하지 않는다" 를 지켜왔는데 그걸 뒤집는 판단이라 [결정기록 009](결정기록.md#009-판정을-내린다-단-내-계좌를-전제로)에 따로 남겼습니다.

**핵심은 종목 판정이 아니라 보유 상태 판정이라는 점입니다.** 같은 SOXL 이라도 자산의 85% 를 넣은 사람과 안 들고 있는 사람에게 다른 답이 나갑니다. 증권가 컨센서스는 누가 얼마나 들고 있는지 몰라 모두에게 같은 답을 줍니다. 이 앱은 평단가와 비중을 압니다. [003](결정기록.md#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다)에서 정한 구조가 여기서 값을 했습니다.

읽는 순서도 결론부터로 바꿨습니다. 판정 → 한 줄 요약 → 현재가 vs 내 평단가 → 감당 중인 위험 → 회사 조사. 재무제표부터 읽게 하면 안 됩니다.

### 구현했는데 안 보였던 것

분기·연도 전환을 만들고 화면에서 확인하려는데 버튼이 안 나왔습니다. 코드는 맞았습니다. **저장된 지표가 전부 시점값이었습니다.** 옛 형식은 값 하나에 기준일 하나뿐이라, 거기서 옮겨온 데이터에는 기간 값이 아예 없었습니다. 전환할 게 없으니 버튼도 안 그려졌습니다.

기능이 없는 것과 데이터가 없는 것은 다릅니다. 화면만 보고 "구현 안 됐네" 라고 판단하면 엉뚱한 데를 고치게 됩니다.

## 전환점 11 — 사람 눈으로 못 보는 걸 기계가 봤다 (16단계)

가상 유저 서비스를 쓸까 하다가 접었습니다. "이거 쓰시겠어요" 에 대한 LLM 의 답은 그럴듯하게 들릴 뿐 수요의 증거가 아닙니다. 대신 기계가 확인할 수 있는 것만 쟀습니다. `axe-core` 로 접근성을, 스크립트로 키보드 이동과 터치 대상 크기를 쟀습니다.

진짜 문제가 나왔습니다.

**닫힌 드로어에 Tab 이 들어갔습니다.** 페이지에서 Tab 을 처음 누르면 초점이 안 보이는 드로어 안으로 떨어졌습니다. `aria-hidden` 은 "읽어주지 마라" 일 뿐이라 초점은 그대로 들어갑니다. `inert` 로 바꿔 둘 다 막았습니다.

**대비가 35곳에서 모자랐습니다.** 흐린 글자가 흰 바탕에서 2.6:1 이었습니다. 기준은 4.5:1 입니다. **4.37 과 4.5 는 사람이 구분할 수 없습니다.** 눈으로 아무리 봐도 못 잡을 문제였습니다.

그 밖에 크기 조절 손잡이의 필수 ARIA 속성 누락, 랜드마크 없음, 모바일 터치 대상 23~24px, 10.5px 글자를 고쳤습니다. 네 조합(밝은/어두운 × 목록/드로어 + 모바일)에서 위반 0 이 됐습니다.

**교훈은 도구를 고르는 기준입니다.** 기준이 구체적이고 검증 가능하면 자동화가 값을 하고, 취향과 수요를 묻는 일은 사람이 해야 합니다.

## 전환점 12 — 같은 글을 아홉 번 보내고 있었다 (17단계)

비용을 물어보고 나서야 어디로 새는지 봤습니다. 분석 한 번에 $1.7~2.5, 그중 70% 가 입력 토큰이었습니다. 분석이 어려워서가 아니었습니다. 웹검색이 길어지면 턴이 끊겨 이어서 부르는데, 그때마다 지시문·스키마·이미 찾은 검색 결과가 **통째로 다시** 나가고 있었습니다.

프롬프트 캐싱을 걸었습니다. 지시문과 제출 스키마(합쳐 1만 토큰)에 1시간 표시, 검색 결과가 쌓이는 뒷부분에 자동 표시. 캐시에서 읽으면 값이 10분의 1입니다.

두 가지를 배웠습니다.

**캐시는 접두사 일치입니다.** 앞에서부터 글자가 똑같은 구간까지만 듣습니다. 조립 순서가 `tools → system → messages` 라서 system 에 표시 하나를 붙이면 도구까지 같이 잡힙니다. 반대로 지시문 앞에 날짜 한 줄만 끼워도 그 뒤가 전부 무효가 됩니다.

**캐싱이 죽어도 에러가 안 납니다.** 요청은 그대로 성공하고 요금만 올라갑니다. 처음 만들 때 잘 되던 게 나중에 프롬프트 조립을 고치면서 조용히 깨지는 게 전형적인 모양입니다. 그래서 `usage` 의 캐시 값을 로그에 박아 놓고, 0이면 죽은 것이라고 [CLAUDE.md](../CLAUDE.md) 에 적어 뒀습니다. 유일한 증거가 그 숫자뿐입니다.

기록에 남기는 토큰 수도 바꿨습니다. 캐싱을 켜면 `inputTokens` 가 "캐시에 없던 나머지" 만 남아서, 그대로 저장하면 캐싱 전후를 비교할 수 없습니다. 셋을 더한 전체 크기를 저장합니다.

남은 절감 수단은 전부 무언가를 내주는 거래라 [TODO](로드맵.md) 에 "무엇을 내주는지" 와 함께 적어뒀습니다. 분석 본체를 싼 모델로 내리는 건 하지 않기로 했습니다. 이 앱의 존재 이유가 판정의 정확성인데, 싸게 만들려고 판정을 못 믿게 되면 기능을 지우는 게 낫습니다.

### 잘린 선의 정체

"이평선이 잘려 있다" 는 말을 듣고 데이터부터 봤습니다. 멀쩡했습니다. 120일선은 200봉 중 81개 값이 정상으로 들어 있었습니다.

**화면이 문제였습니다.** 200봉을 전부 펼치면 120일선은 121번째 봉부터 생기니 화면 한가운데에서 뚝 시작합니다. 데이터로는 맞고 그림으로는 잘린 선입니다. 계산은 200봉으로 하고 처음 보이는 구간만 마지막 80봉(= 200 - 120)으로 잡으니 네 선이 모두 끝에서 끝까지 이어졌습니다.

같이 나온 것 하나 더. 차트가 어두운 화면에서 혼자 하얗게 떠 있었습니다. **캔버스는 CSS 변수를 스스로 못 따라갑니다.** 색을 코드에 직접 적어둔 대가였습니다.

### 글자를 키웠는데도 안 읽힌 이유

본문을 15px 로 키우고 대비를 12:1 까지 올렸는데도 "눈에 안 들어온다" 는 말이 나왔습니다. 크기도 대비도 아니었습니다. **덩어리였습니다.** 문단이 전부 같은 크기·같은 색이면 어디부터 읽을지 눈이 못 잡고 통째로 건너뜁니다.

두 개만 세웠습니다. 각 문단의 첫 문장(대개 결론)과 단위가 붙은 숫자. 제목은 본문과 두 단계를 벌렸습니다(19px). 단위 없는 숫자는 건드리지 않습니다 — 연도나 순번까지 진해지면 다시 노이즈가 됩니다.

처음 만든 정규식이 "122.25 달러로" 를 놓쳤습니다. 단위 뒤에 한글이 오면 제외하게 짰는데, 한국어는 단위 뒤에 조사가 붙습니다. 정작 흔한 경우가 전부 빠졌습니다.

### 낭비를 먼저 막는다 (17단계 마무리)

크레딧을 기다리는 동안 할 수 있는 걸 셋 했습니다. 셋 다 "더 좋게" 가 아니라 "덜 새게" 입니다.

**뉴스 요약의 출력 한도가 900이었습니다.** 이 모델은 사고가 기본으로 켜져 있고 노력 기본값이 높음이라, 사고가 한도를 다 먹으면 정작 답이 안 나옵니다. **잘린 호출도 요금은 그대로 나갑니다.** 한도를 올리는 것보다 이 호출만 노력을 낮추는 쪽을 골랐습니다. 헤드라인 10개를 세 줄로 줄이는 데 긴 사고가 필요 없고, 출력은 입력의 5배 값이라 노력을 낮추면 값이 직접 내려갑니다. 한도에 걸리면 로그에 경고가 찍히게 해 뒀습니다. 조용히 잘리는 게 제일 나쁩니다.

**스크린샷은 이미지가 지시문보다 컸습니다.** 이미지 토큰은 `⌈가로/28⌉ × ⌈세로/28⌉` 이라 휴대폰 캡처 1170×2532 가 그 자체로 3,822토큰입니다. 지시문과 스키마를 합친 2,077보다 큽니다. 긴 변을 2,000으로 맞춰 2,376까지 내렸습니다.

여기서 두 가지를 정했습니다. **줄이기가 실패하면 원본을 그대로 보냅니다** — 값을 아끼려다 등록 기능을 죽이면 안 됩니다. 그리고 **JPEG 로 다시 압축하지 않습니다.** 증권사 화면은 글자가 전부라 작은 숫자 획에 번짐이 생기면 그대로 오독이 됩니다. 어차피 토큰 값은 용량이 아니라 크기로 매겨지니 PNG 로 내보내 손해 볼 게 없습니다.

한계선은 코드가 아니라 설정(`screenshot-max-edge`)으로 뺐습니다. **"얼마나 줄여야 숫자를 안 틀리는가" 는 진짜 캡처로만 알 수 있습니다.** 모르는 값을 코드에 박으면 나중에 다시 빌드해야 합니다.

**미사용 테이블은 하나인 줄 알았는데 둘이었습니다.** `target_weight` 만 적어뒀는데 `target_allocation` 도 같이 남아 있었습니다. 지우기 전에 내용을 찍어보고 지웠습니다. 되돌릴 수 없는 작업은 기록이 남아야 합니다.

### 숫자를 다시 쟀더니 내가 틀렸다

비용을 물어보길래 다시 계산하다가, 지난번에 말한 고정 프롬프트 1만 토큰이 틀렸다는 걸 알았습니다. **파일 바이트 크기를 글자 수로 읽었습니다.** 한글은 UTF-8 에서 한 글자가 3바이트입니다. 실제로 재보니 7,500토큰이었습니다.

`wc -c` 는 바이트를 셉니다. 영어 프로젝트에서는 둘이 같아서 평생 틀릴 일이 없는 습관인데, 한글 문서에서는 3배로 틀립니다.

그 김에 토큰 세기 API 로 실측하려 했더니 그것도 크레딧을 요구했습니다. 그래서 실제 프롬프트를 파일로 뽑아 한글과 ASCII 를 나눠 세고 비율을 달리 곱했습니다. 추정이라는 걸 TODO 에 같이 적어뒀습니다. **추정을 실측인 것처럼 적으면 다음에 또 이 실수를 합니다.**

## 전환점 13 — 비중 얘기만 하고 있었다 (18단계)

크레딧이 없어서 앱의 유료 경로 대신 CLI 에서 직접 7종목을 조사해 DB 에 넣었다. 형식만 같으면 화면은 그대로 뜬다.

그 결과를 보고 사용자가 말했다. **"비중대로 사고 팔라는 의견이 너무 중요시 되는 것 같다. 결국은 이 기업이 평단가 대비 오르냐 내리냐가 제일 중요하다."**

맞는 지적이었다. 판정 일곱 개 중 여섯 개가 비중 얘기로 끝나고 있었다. 프롬프트에 "비중이 판정을 뒤집는다" 라고 써둔 게 원인이었다.

그 문장은 [결정기록 009](결정기록.md#009-판정을-내린다-단-내-계좌를-전제로) 에서 나왔다. "증권가 컨센서스와 다르려면 이 사람의 비중을 알아야 한다" 는 생각이었고, 그건 여전히 맞다. **틀린 건 순서였다.**

비중은 답이 아니라 크기 조절이다. 답은 가격이다. 그래서 순서를 바꿨다. 1순위 현재가가 적정가 대비 어디인가, 2순위 평단가까지 갈 수 있나, 3순위 비중.

### 적정가를 안 내놓고 있었다

같은 지적의 연장선에서 더 큰 문제가 드러났다. 밸류에이션 섹션이 PER·PBR 을 나열만 하고 "그래서 비싼가 싼가" 를 안 쓰고 있었다.

숫자를 늘어놓는 건 분석이 아니다. 그래서 프롬프트에 적정가 계산을 강제했다. 주당 이익을 구하고, **그 회사가 과거에 받아온 PER 범위**를 적용하고, 하나의 숫자가 아니라 범위로 적게 했다. 업종 평균이 아니라 그 회사의 과거 범위를 쓰게 한 건 회사마다 받는 배수가 다르기 때문이다.

이렇게 하니 답이 선명해졌다. LG전자 평단가는 2028년 컨센서스 이익으로 계산해도 PER 31배다. **회사가 계획대로 3년을 성장해도 평단가에 못 미친다.** "기다리면 회복된다" 가 성립하지 않는다는 걸 숫자로 보일 수 있었다.

레버리지 상품은 적정가 계산 자체가 성립하지 않는다. 감쇠 때문에 지수 레벨이 가격으로 옮겨지지 않아서다. 그래서 SOXL 에는 적정가 대신 **적정 비중**을 계산하게 했다. 하루 변동성 9.39% 에 계좌를 하루 1% 까지만 흔들리게 하려면 비중이 10.6% 여야 한다는 식이다. 모르겠다고 끝내지 않고 답을 바꿔서 내놓는 쪽을 골랐다.

### 글이 안 읽혔던 이유

"글이 잘 안 읽힌다" 는 말을 듣고 문장 길이를 실제로 쟀다. 평균 36자, 가장 긴 문장 104자, 60자 넘는 문장이 11% 였다.

한 문장에 숫자를 셋씩 넣고 있었다. "2024년 말 BPS 가 116,100원이므로 현재가 202,500원 기준 PBR 은 약 1.74배다" 같은 식이다. 읽는 사람이 세 숫자를 동시에 들고 있어야 한다.

끊었더니 평균 24자, 최장 54자, 60자 초과 0% 가 됐다. **측정할 수 있는 건 측정하고 고치는 게 빠르다.**

### 두 번의 데이터 사고

**하나.** 브로드컴 10주 매수를 직접 입력으로 넣었더니 25주가 됐다. 나무증권이 이미 15주로 올라와 있었다. 증권사 API 가 자동으로 가져오는 종목에 손으로 또 넣으면 중복된다. 합계가 맞는지 보고 알았다.

**둘.** JSON 을 텍스트 치환으로 고치다가 파이썬 소스의 `\n` 이 실제 개행으로 들어가 파일이 깨졌다. **JSON 은 파싱해서 고치고 다시 써야 한다.** 텍스트 치환은 이렇게 깨진다.

### 재무를 웹에서 긁고 있었다

분석을 쓰다 보니 더 근본적인 문제가 보였다. 매출·영업이익·부채비율·ROE 를 웹페이지에서 긁어 쓰고 있었다.

[결정기록 003](결정기록.md#003-숫자는-앱이-계산하고-조사만-llm에게-맡긴다) 이 "숫자는 앱이, 조사는 LLM이" 인데 재무제표는 공시된 확정 숫자다. **원칙을 이미 어기고 있었다.**

실제로 사고가 날 뻔했다. 삼성중공업 조사에서 목표주가가 15,000원부터 90,000원까지 여섯 배 엇갈렸고, 어떤 자료는 주가를 48,050원이라고 했는데 앱 조회값은 20,500원이었다. 눈치채서 뺐지만 못 봤으면 그대로 들어갔다.

DART OpenAPI 로 가져오면 공시 원본이고 무료다. 부채비율·ROE·PER·PBR 은 앱이 직접 계산하면 된다. 재무는 DART, 주가는 이미 토스에서 받고 있다. [TODO](로드맵.md) 에 사양까지 확인해 적어뒀다.

## 전환점 14 — 재무를 공시에서 가져온다 (19단계)

DART 키가 나와서 붙였다. 국내 개별 기업은 이제 재무를 웹에서 긁지 않는다.

### 무엇을 넣었나

가장 최근 사업보고서 한 건에 세 해가 같이 들어 있다. 거기에 올해 가장 최근 분기·반기 보고서를 하나 더 부른다. 종목당 2~5번이고 0원이다.

부채비율·영업이익률·ROE·EPS·BPS·PER·PBR 은 앱이 나눈다. 공시 원문 주소(`rcpNo`)를 프롬프트에 같이 넣어서 클로드가 그걸 출처로 쓰게 했다. 검색 가이드에서는 "사업보고서 재무제표" 검색어를 빼고 전망·의견만 찾으라고 바꿨다.

### 반기보고서는 칸이 두 개다

반기보고서 손익에는 `thstrm_amount` 와 `thstrm_add_amount` 가 있다. 앞의 것은 **그 분기 3개월**, 뒤의 것이 **연초부터 누적**이다. 앞의 것을 쓰면 상반기 이익이 반토막 난다. 테스트에 이 경우를 박아뒀다.

PER 은 연간 이익이 아니라 최근 4분기로 잰다. 작년 연간 + 올해 누적 − 작년 같은 기간 누적이다. 삼성전자는 2025년 순이익이 45조인데 최근 4분기는 150조다. 연간으로 재면 PER 이 세 배 넘게 틀린다. 반도체 사이클이 이렇게 빨리 돌 때 연간 숫자는 이미 과거다.

### 모르는 채로 둔 것

- **순이익이 지배주주 몫이 아니다.** 요약 API 가 그걸 안 준다. 프롬프트에 그렇다고 적어두고 TODO 로 남겼다
- **과거 PER 범위는 여전히 웹이다.** 과거 연말 주가가 없어서다
- **미국 종목은 그대로다.** SEC EDGAR 는 다음

### 스크립트로 자바를 고치면 안 된다

프롬프트 조립 코드를 파이썬 문자열 치환으로 고쳤더니 자바 문자열 안의 `\n` 이 진짜 줄바꿈으로 들어가 컴파일이 깨졌다. 고치려고 돌린 두 번째 치환도 같은 이유로 안 들었다. 결국 편집기로 한 줄씩 고쳤다. 전환점 13 의 JSON 사고와 같은 종류다. **이스케이프가 두 겹이 되는 곳에서는 치환하지 않는다.**

### 확인한 것과 못 한 것

앱을 띄워 보유 국내 6종목(현대차·대한전선·삼성전자·LG전자·삼성중공업·두산로보틱스)을 실제 DART 로 불렀다. 전부 2025 사업보고서 + 2026 반기보고서, 연결 기준으로 나왔다. 고유번호 매핑은 상장사 3,993건이 들어갔다.

**PER·PBR 은 확인 못 했다.** 토스가 403 이었다(학교 망 IP 가 바뀌어 미등록). 주식수와 현재가가 토스에서 오기 때문에 그 둘만 비었다. 재무는 토스와 상관없이 나오게 해둔 게 여기서 맞았다.

## 전환점 15 — 미국 종목도 공시에서 (20단계)

DART 에 이어 SEC EDGAR 를 붙였다. 브로드컴 재무도 이제 웹에서 긁지 않는다.

### 모델부터 옮겼다

`DartFinancials` 를 `CompanyFinancials` 로 바꾸고 통화를 넣었다. 비율 계산도 거기로 모았다. DART 와 EDGAR 는 원재료 숫자만 꺼내고 나누기는 한 곳에서 한다. 증권사 어댑터를 `BrokerageClient` 하나로 묶은 것과 같은 생각이다. 부르는 쪽은 `FilingService` 하나만 알고, 한국인지 미국인지는 거기서 가른다.

미리보기 주소도 `/api/dart` 에서 `/api/financials` 로 바꿨다. 공시처 이름이 주소에 박혀 있으면 공시처가 늘 때마다 주소가 늘어난다.

### EDGAR 는 보고서가 아니라 사실 목록이다

DART 는 "2025 사업보고서" 를 달라고 하면 표를 준다. EDGAR 는 회사가 낸 모든 숫자를 태그별로 쏟아준다. 한 태그 안에 10-K 와 10-Q 가, 3개월치와 누적과 1년치가, 같은 기간을 다음 해에 비교 칸으로 다시 실은 것까지 섞여 있다. 그래서 시작일·종료일로 직접 골라야 한다. 1년치는 350~380일, 올해 누적은 결산 다음 날 시작하는 것 중 가장 늦게 끝나는 것.

### 태그가 중간에 바뀐다

처음 받아보고 놀랐다. 브로드컴 순이익 `NetIncomeLoss` 가 FY2024 에서 끊겼다. 그 뒤로는 `ProfitLoss` 로 낸다. 자본도 `StockholdersEquity` 가 2019년에 끊기고 비지배지분 포함 태그로 넘어갔다.

우선순위 목록만 두고 첫 번째 것을 쓰면 FY2025 순이익이 통째로 빈다. 그래서 **후보 중 가장 최근 기간까지 있는 태그**를 고르게 했다. 이 경우를 테스트 이름으로 박았다.

### 기댓값을 같은 코드로 만들지 않았다

테스트 데이터는 실제 브로드컴 응답(150KB)에서 쓰는 태그만 남긴 것이다. 기댓값은 자바가 아니라 파이썬으로 원본 JSON 을 따로 계산해 구했다. 같은 로직으로 기댓값을 만들면 로직이 틀려도 테스트가 통과한다.

최근 4분기 순이익 382.7억 달러, EPS 8.02달러, 현재가 363.5달러 기준 PER 45.3배. FY2025 연간 순이익(231억 달러)으로 재면 PER 이 75배가 나온다. 성장 속도가 빠른 회사일수록 연간 숫자는 낡는다. DART 에서 삼성전자로 본 것과 같다.

### 확인한 것과 못 한 것

테스트 61개 통과. **앱을 띄워 실제 EDGAR 를 부르는 확인은 못 했다.** 띄워둔 앱이 시스템 메모리 부족으로 내려갔다. 응답 형태는 직접 받아서 봤고 그 응답으로 테스트했으니 파싱은 맞다. 남은 건 `SEC_USER_AGENT` 를 넣고 주소 하나 부르는 것이다.

SEC 는 연락처가 담긴 User-Agent 를 요구한다. 흔한 문자열로 부르면 `data.sec.gov` 는 통과하지만 매핑 파일이 있는 `www.sec.gov` 는 403 이다. 사용자 이메일을 대신 넣지 않고 `.env` 에 직접 넣도록 남겼다.

## 전환점 16 — 주식수를 보통주만 쓰고 있었다 (21단계)

PER 을 처음 채워보니 현대차가 7.89배였다. 순이익에는 우선주 몫까지 들어 있는데 토스가 주는 발행주식수는 보통주뿐이었다. 우선주 몫까지 보통주 한 주에 얹혀 EPS 가 부풀어 있었다.

DART 주식 총수 현황(`stockTotqySttus`) 으로 바꿨다. **보통주+우선주, 자기주식 제외.** 재무와 같은 보고서에서 받아 기준일도 맞췄다. 무엇으로 나눴는지는 프롬프트에 같이 적는다. 이 기준 하나로 PER 이 20% 넘게 움직이니 모델도 알아야 한다.

| 종목 | 전 (보통주) | 후 (보통주+우선주−자기주식) | PER 전 → 후 |
|---|---:|---:|---:|
| 현대차 | 203M | 261.8M | 7.89 → 10.15 |
| 삼성전자 | 5,846M | 6,566.6M | 11.11 → 12.48 |
| LG전자 | 163M | 179.3M | 22.59 → 24.87 |
| 삼성중공업 | 880M | 854.1M | 32.36 → 31.41 |

삼성중공업은 반대로 PER 이 내려갔다. 우선주가 거의 없고 자기주식이 빠졌기 때문이다. **방향이 종목마다 다르다는 게 "대충 보통주로 나눠도 비슷하다" 가 틀린 이유다.**

현대차의 남은 차이는 비지배지분이다. 요약 API 가 지배주주 순이익을 안 줘서 아직 못 고쳤다.

### 지배주주 순이익

주가는 지배기업 주식의 값인데 EPS 를 연결 순이익으로 재고 있었다. 자회사 소수주주 몫까지 보통주에 얹힌 셈이다. 요약 API 에는 지배주주 몫이 없어서 전체 재무제표를 보고서당 한 번 더 부른다. 300줄 가까이 오는데 필요한 건 둘뿐이라 **한글 계정명이 아니라 IFRS 계정 ID** 로 고른다. 계정명은 회사마다 "지배기업소유주지분", "지배기업의 소유주" 로 다르다.

자본변동표에도 같은 ID 가 칸마다 다른 뜻으로 여러 번 나온다. 재무상태표·손익계산서만 보게 했고, 테스트에 자본변동표의 0 을 일부러 넣어 거르는지 확인했다.

순이익 열과 부채비율은 연결 그대로다. 부채비율은 관례상 자본총계로 나누고, 회사가 갚아야 할 빚은 소수주주 몫과 상관없다. 바뀐 건 주당 지표와 ROE 뿐이다.

현대차 최근 4분기 EPS 가 35,156원에서 31,114원이 됐다. 우선주를 넣은 게 첫째, 이게 둘째다. PER 7.89 → 10.15 → 11.47.

### 과거 배수

적정가는 "그 회사가 과거에 받아온 PER 범위" 에 기대는데, 그 범위를 웹에서 찾고 있었다. 출처마다 연결/별도, 지배/연결 순이익, 결산일/연평균 주가가 달라 같은 해 PER 이 두세 배 벌어진다. 이익은 이미 공시에서 오니 주가만 있으면 됐다.

토스 일봉은 한 번에 200봉이지만 `nextBefore` 로 넘길 수 있었다. DTO 주석에 "페이지를 넘길 일은 없다" 고 적혀 있었는데 이번에 넘기게 됐다. 주석도 고쳤다.

가장 걱정한 건 **액면분할**이다. 브로드컴은 2024년 7월에 10분할했다. 과거 주가가 분할 전 값이면 FY2023 PER 이 10배로 튄다. 실제로 받아보니 FY2023 결산일 종가가 $83.84 로 분할이 반영돼 있었다. 확인 안 하고 넘어갔으면 틀렸는지도 몰랐을 것이다.

결산일도 12월로 가정하지 않았다. 브로드컴은 11월 초, 3월 결산 한국 회사도 있다. DART 는 재무상태표 기준일("2025.12.31 현재")에서 읽는다.

| | 결산일 종가 | PER | PBR |
|---|---:|---:|---:|
| 현대차 2023 | 203,500원 | 4.45 | 0.58 |
| 현대차 2024 | 212,000원 | 4.43 | 0.51 |
| 현대차 2025 | 297,000원 | 8.23 | 0.67 |

현대차는 3년 내내 PER 4~8배를 받던 회사인데 지금 11배다. 이런 걸 숫자로 보여주려고 만든 기능이다.

## 전환점 19 — 만드는 사람에서 운영하는 사람으로 (24단계)

목표를 다시 잡았다. 증권사 IT 에 가고 싶고, 그러려면 기능을 늘리는 것보다 **배포하고 운영하고 장애를 겪어보는 경험**이 필요하다. 계획은 [로드맵](로드맵.md)에 다섯 단계로 적었다.

멀티 스테이지 Dockerfile, 앱 + MySQL compose, GitHub Actions(테스트 → 이미지 빌드)를 붙였다. CI 에 비밀값이 하나도 없다. 테스트가 처음부터 바깥 API 와 DB 를 안 부르게 짜여 있어서다. 공시 테스트도 실제 응답을 파일로 떠서 쓴다(전환점 15).

`docker compose up` 으로 띄운 컨테이너에서 `/api/financials/005930` 이 200 이고 PER 까지 나왔다. 컨테이너 안에서 DART·토스·MySQL 이 다 붙는다는 뜻이다.
